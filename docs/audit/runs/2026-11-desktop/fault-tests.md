# Fault tests

Real downloader against a local server that injects faults, on Windows, at commit `a139e6a9d`, with two mutation jobs running beside it. Every finished file was compared by SHA-256 with the original, generated from the offset so a byte in the wrong place or from another version shows. Each run was held to one rule (`safe_end` in the patches): exit status 0 only with the exact file, otherwise nothing at the final name.

No failure was near a time limit: no wait reached `PATIENCE`, and neither finding depends on timing. F-2 is counted in waits, not measured in seconds.

## Findings

### F-1 [P2] An unreadable or missing resume file makes the CLI save under another name and strands the old files

- Where: `crates/engine/src/target.rs`, `plan_in_folder` and `saved_state`
- Category: wrong implementation
- Failure: a download into a folder (the CLI) is killed, and its `f.bin.wcstate` is then damaged or gone. Running the same command does not start over at `f.bin`. It saves a correct file as `f (1).bin` and leaves the old `f.bin.wcpart` (and `f.bin.wcstate`, if damaged) there for good, at the file's full length. No later run touches them.
- Evidence: `saved_state` documents "the download starts over and replaces it", but it returns `None`, and `plan_in_folder` then takes `Plan::FreeName`. Output with a torn resume file: `Saved 128.00 MiB to ...\downloads\f (1).bin; files: ["f (1).bin", "f.bin.wcpart", "f.bin.wcstate"]`, `f (1).bin` has the right checksum, and `f.bin.wcpart holds 134217728 bytes`. A resume file of a format this version does not read goes the same way (`LoadError::Version`, `LoadError::TooLarge`). A kill alone did not produce it here: every kill left a readable resume file, which is saved with a sync and a rename, so the trigger is damage from outside or a downgrade. `Manager` is not affected: with a settled path, `plan_exact` starts over in place (`killed_with_a_torn_resume_file_the_download_starts_over_at_its_path` passes).
- Reproduction: `git apply docs/audit/runs/2026-11-desktop/proofs/FT-kill.patch`, then `cargo test -p wirecatch-cli --test fault_kill -- --nocapture a_resume_file_torn_in_half a_part_file_with_no_resume_file`. Fails with `left: ["f (1).bin", "f.bin.wcpart", "f.bin.wcstate"]`, `right: ["f.bin"]`.
- Confidence: certain

### F-2 [P2] A valid short partial answer is waited out as a failed connection

- Where: `crates/engine/src/worker.rs`, `stream` and `run_assignment`
- Category: inefficiency
- Failure: a server that caps each answer sends a `206` with matching `Content-Range` and `Content-Length`, shorter than the range asked for, which HTTP allows. The engine treats its clean end as `Error::PrematureEof` and pauses for the first backoff (500 ms plus jitter) before asking for the rest. The file is right, but 16 MiB from a server capping answers at 256 KiB took 65 requests, 57 waits and 5.17 s, against about 55 ms for the same size from a server without a cap, on the same machine under the same load.
- Evidence: stderr holds `connection failed, retrying error=connection closed early at byte ... of a part ending at ... retry_in=...` for answers that ended where their own headers said. `stream` only knows `request_end`, what it asked for, so an end short of that is `Ended::Eof` whatever the answer's `Content-Range` said. The cost grows with the file: at a cap of 1 MiB, one connection can get at most about 2 MiB/s. The `max_request_bytes` option avoids it, but only when set in advance for that server. The test counts waits, not time.
- Reproduction: `git apply docs/audit/runs/2026-11-desktop/proofs/FT-sizes.patch`, then `cargo test -p wirecatch-cli --test fault_sizes -- --nocapture a_clean_short_answer`. Fails with `65 requests, 57 waits, 5.171062s` and `left: 57`, `right: 0`.
- Confidence: certain

## Leads, not findings

- Without validators, a same-size change cannot be seen by any client, so bytes of two versions can be joined. D34.2 records that a validator left out proves nothing. Not tested.
- A `Last-Modified` with no `Date` header is not a validator under D34.2, so a run across a change exits 0 with mixed bytes. A correct `Date` makes the run refuse (`only_a_last_modified_and_the_bytes_change_in_a_parallel_download`).
- After a kill, up to the last second of data is fetched again (`checkpoint_interval`), and the list's row can trail the resume file by up to 2 s (`SAVE_PROGRESS_EVERY`) until the engine reads it. Both are by design and both recover.
- For the reviewers of the engine: part files are sparse on Windows (`storage::reserve`), so a full disk arrives as a failed write mid-download, not at the start, which makes the untested fault the likelier path. A kill keeps the system's write cache, so these tests say nothing about a power cut.

## Not tested

- Full disk (no dedicated volume).
- Power cuts, and anything else that loses the system's write cache.
- Linux. All runs were on Windows, and a kill there is `TerminateProcess`.
- Kills and size faults over HTTP/2, HTTP/3 and FTP: the fault server speaks only HTTP/1.1.
- Files over 4 GiB through `Manager`: only through the CLI, as the targets say.
