# Contract 21: engine-ftp

How FTP and FTPS downloads and the engine's own SOCKS5 client really behave. All of it is crate-private, reached through `transport`.

## Which link means what

- `ftp://`: plain, port 21. `ftpes://`: `AUTH TLS`, port 21. `ftps://`: implicit TLS, port 990; port 21 means `AUTH TLS`. Never falls back to less: a refused `AUTH TLS`, `PBSZ 0` or `PROT P` (other than 4xx) is `Error::FtpTlsUnavailable`, before any credential or file byte in the clear.
- `Target::new` refuses a folder path, `\r`, `\n` or `\0` in path, user or password, and a path that is not UTF-8 (`Error::InvalidUrl`, without the password). It strips `;type=` from the path it sends, but `display_url` and so `final_url` keep it (chunk 21-2). Path is relative to the login folder; `%2F` makes it absolute.
- No user name: `anonymous` / `anonymous@`. A user name without a password sends an empty password.
- `ftps` and `ftpes` hosts are opaque to `url`: `host_str()` is not normalised or decoded. Only `Target::new` decodes them, so `Target` is the one place that knows the real host.

## Connections

- `probe` runs under `with_retries` and tries each resolved address. The address that answered is pinned in `Server.addr`: every later control and data connection goes there. With `socks5h://` it is the name instead, resolved again by the proxy each time.
- A `PASV` address is ignored; only the port is used. There are no redirects, so credentials go only to that server.
- Each worker keeps a logged-in control connection between ranges. With TLS, one session cache per control connection, so data connections resume that control connection's session. A new control connection gets a new cache.
- `EPSV` is tried once per download; a 5xx or an unreadable 229 switches every connection to `PASV`.
- Each range: `check_same_file`, passive port, connect data, `REST` when `from > 0`, `RETR`, TLS on data after the 1xx.
- The FTP path applies no `PrivateNetwork` rule: no guard, no address filter (chunk 21-1).

## What the probe reports

`total` is `SIZE`, else the size in the `150` reply. `ranged` is `REST 0` answered 350 and a known total. `validators.last_modified` is the `MDTM` text. `etag` is always `None`. The first transfer is already running from byte 0; `file_name` and `content_type` are `None`.

## Changed files

`check_same_file` compares `SIZE` and `MDTM` over the control connection when a worker logs in and before every range, and returns `Error::RemoteChanged` on a difference. A value the server stops giving is not a change. A file replaced during a range is not seen until the next range.

## Ends of a transfer

- `Transfer::next` returns `Ok(None)` only after the data connection ended and a 2xx final reply came. A TLS close without `close_notify` counts as an end, and the final reply decides. 4xx or 5xx final replies become `Error::FtpReply`.
- FTP sends to the end of the file whatever the range: the worker stops at the range's end and `finish` drops the data connection.
- `finish` keeps the control connection only if a final reply was read, or one arrives within `min(stall, 5 s)` and is not 1xx. A cancelled token returns at once and closes it. A broken or half-read reply is never reused.
- `Transfer::next` has no time limit of its own on the data read: `receive` applies the stall timeout. Control commands and replies are limited by `Control.stall`, connecting and TLS handshakes by `connect_timeout`.

## Errors and retries

- 4xx `FtpReply` is retryable, 5xx is not. For workers, 421, 425 and 530 count as refusals (`Refusals::StepBack`), retried and stepped back from, even though 530 alone is not retryable.
- 530 on the first connection is `FtpLoginRefused`, not retried. On later connections it is `FtpReply`.
- An unexpected code is `Error::Network` with `InvalidData`, retryable.
- Reply limits: 4096 bytes a line, 256 lines, 512 characters kept for messages.
- `command`'s `shown` argument is what is logged: `USER <hidden>`, `PASS <hidden>`, and `SIZE`, `MDTM` and `RETR` without the path. Reply text is logged at debug and put in errors as the server sent it.

## SOCKS5 (`socks.rs`)

- `Socks5::from_url` takes `socks5://` (names resolved here) and `socks5h://` (names sent to the proxy), port 1080 by default; anything else is `None`. `Debug` hides the login.
- `connect` has no time limit: the caller's. `SocksFailure::Proxy` keeps the system's error, so `is_refused_by_system` can see a proxy that is not running. `Refused` is relayed by the proxy and has no OS code, so it is retried as an ordinary failure. `LoginRefused` becomes `Error::ProxyLoginRefused`, not retried.
- Used only by FTP, through `Proxies::ftp_route`: a proxy that is not SOCKS5 is `Error::FtpProxyUnsupported`, unless `ftp_direct` is set or the exceptions name the host.
