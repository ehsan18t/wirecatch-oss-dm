# Contract 28: failure-messages

How the two steps from an error to what a person or a protocol client reads really behave.

## `wirecatch-messages`

Pure functions, no state and no I/O. Depends on the engine, protocol and sites crates for types.

- `describe(error, folder, worked) -> UserError`: one arm per engine error except `TooLarge` and `TargetTaken`, which take the catch-all ("The download failed ({error}). Try again.", `Retry`). Run paths never reach it with `TargetTaken`: `run.rs` handles that first when no stop was asked for, and the other callers use the default `Replace`.
- `describe_run(error, folder, worked, chosen_by, through_proxy)`: `describe` with three overrides: `PrivateNetwork` by who chose the link; a connect failure and a certificate failure name the proxy when one is given, with `ChangeQueue`.
- `private_network(chosen_by)`: `Website` offers `RefreshLink`; `Person` and `LocalPage` offer no fix.
- `disk(io_error, folder)` and the `Io` arm share `disk_failure`, which decides by `io::ErrorKind` and raw OS code alone, in this order: full disk or quota, `FreeDiskSpace`; denied or read-only, `ChooseFolder`; not found, not a directory, already exists or bad name, `ChooseFolder`; anything else, `Retry` with the OS text. The action and path of `EngineError::Io` appear only in that last case.
- `invalid_link(reason)` ignores `reason` and equals `describe(InvalidUrl)`.
- `storage_failed`, `stopped_unexpectedly`, `CAPTURE_TO_OWN_NETWORK`: fixed words.

Guarantees and limits:

- Every message ends with a full stop and has no em dash, as far as the house-style tests cover; a `TargetRejected` reason goes through as given, so its wording is the resolver's.
- `TargetRejected` always gives `RefreshLink`, whatever the reason. The manager's resolver (`settle.rs`) also returns folder and name errors as reasons, not only "another file than the browser saw".
- Message words assume a download row with buttons. A caller that keeps only `.message` (add-on install, app update, capture refusal through `row.error`) carries that advice along.
- `FixAction` is the only machine-readable result. Nothing may be decided from `message`.
- FTP reply text is server-controlled but capped by the engine (`MAX_TEXT` 512 in `ftp/control.rs`). Passwords are not in `FtpLoginRefused` or `FtpReply`.
- No function knows whether a download can resume.

## `wirecatch_core::CoreError`

- `Display` is the person's text; `to_protocol()` gives `ProtocolError { code, message: to_string() }`.
- Codes: not-found variants and `UnknownAddon` to `NotFound`; `InvalidUrl`, `NotStarted`, `LimitReached`, `WrongState`, `UpdateCheckFailed`, `AddonRequired` to their own codes; `Invalid`, `DefaultQueue`, `Path`, `Profile` to `InvalidRequest`; `Store`, `File`, `FilesSplit`, `AddonFilesLeft`, `AddonNotRemoved`, `Closed`, `Internal` to `Internal`.
- `InvalidUrl` echoes the trimmed input whole, and its words list the FTP schemes even from `parse_web_url`, which refuses them.
- `NotStarted(text)` wraps the text as "Wirecatch could not take over this download. {text} The browser keeps it.", so the text must be whole sentences.
- `From<SettingsError>` maps case by case; it adds no text.
- `blocking(runtime, work)` runs on the blocking pool; a join failure becomes `Internal`.

## `crates/core/tests/manager/ftp.rs`

Proves through `Manager` and the scripted FTP server: refused named and anonymous logins (no password in the text), a missing file, `ftpes` with no encryption sends no `USER`, and a failed capture returns `NotStarted` with the reason. It does not check that the capture's row is gone.
