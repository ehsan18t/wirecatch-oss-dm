# Contract 06: bridge-and-frames

## `wirecatch_protocol::frame`

- A frame is a 4-byte little-endian length, then that many body bytes. `MAX_FRAME_LEN` is 1 MiB, inclusive.
- `body_len` refuses an oversized header before anything is allocated. A read allocates the announced body (at most 1 MiB) before its bytes arrive.
- `read*` return `Ok(None)` only when the stream ends before a frame's first byte. A stream that ends inside a header or body is an `Io` error (`UnexpectedEof`).
- `TooLarge` from a read leaves the stream unsynchronised: the body was not consumed, so the caller must end the connection or skip it itself (`raw_frame::read_blocking`, `server::FrameReader`).
- `encode` and `write*` refuse a body over the limit. The caller decides what that means: the server's `send` turns it into an `io::Error` that ends the connection.
- The async reads are not cancel-safe, and their docs do not say so: a read dropped mid-frame loses bytes. `server::FrameReader` is the cancel-safe reader. Callers outside this chunk (`shell::bridge`, `shell::launch`) were not reviewed here.

## `wirecatch_protocol::wire` and `version`

- `Envelope::read`, `RequestHead::read` and `HelloHead::read` never fail on bad input: each returns `None`. All three reject a body with a duplicate field of the ones they read.
- `CallMethod` reads an unknown method as `Unknown`; a non-string method is `None` from `RequestHead::read`.
- `HelloHead::read` is `None` when `params` is missing or `start_app` is not a boolean; the bridge takes `None` as "may start".
- `Hello::versions` errors with `Empty` when newest is older than oldest; a missing `max_protocol_version` means one version.
- `VersionRange::agree` gives the newest shared version, or says which side is behind.
- `Message::as_of(version)` drops events newer than `version` and maps newer error codes to their older equivalent. It leaves replies untouched. Every message an app writes must pass through it.
- `since` is an exhaustive match for each of calls, events and codes. The `KNOWN` lists are hand-kept, and the generated TypeScript types catch an omission.
- `UNKNOWN_REQUEST_ID` is 0. The bridge treats a request with id 0 like any other.

## Bridge executable (`crates/bridge`)

- Serves only `chrome-extension://<the one id>/` (with any further `--` flags), or exactly two arguments where the second is the Firefox add-on id. The manifest path is not checked. Refusal exits with failure before touching stdin or the app (D22, defense in depth).
- Stdout carries frames only. Logs go to stderr and the release log folder.
- Connects once, on the first frame, and never reconnects within one process. The first frame's `start_app` picks `Start`; a first frame that is not a readable hello allows starting.
- While connecting it holds at most 32 frames, then stops reading stdin, so it does not notice a closed stdin until the attempt ends.
- Budget is `BRIDGE_START_BUDGET_MS` (5 s) in total, launch included. `NotRunning`, `NoEndpointKey` and `WrongOwner` are retried after a launch, and the key is read again at each attempt. With `Start::Never` those give `app_not_running` with no launch. Every other error gives `app_unavailable` with no launch and no retry, `BadEndpointKey` included.
- After a failed first connection it answers every request with that same error until stdin closes. It does not exit by itself, so the extension must close the port.
- While connected it relays bytes unchanged. Each request with a usable id is tracked; a request reusing an id still waiting is answered `invalid_request` and not sent. Requests without a usable id and non-requests pass through untracked.
- Every tracked request gets exactly one answer: the app's, or `app_unavailable` when the connection ends. On a failed write the reader gets 1 s to pass on what it has first.
- When the app's side ends it answers what is waiting, then exits with success, closing stdout. When stdin closes it closes the app connection at once, and the app still finishes what it was asked.
- An oversized frame from the browser is skipped with a log line and no answer, and the session goes on. An oversized frame from the app ends the session.
- Answers it writes itself use only codes in protocol version 1, since it reads no agreed version (D32.10).
- Starts the app from the bridge's own folder with `--background`, stdio null, working folder that folder. On Windows it uses the shell as parent when the shell is the same user at no higher integrity (D41.3), otherwise it starts the app directly and tries to break away from the browser's job. On Linux it uses `setsid`.
- `test-overrides` adds three environment overrides. It is never on in a shipped build, and which extensions are trusted never depends on it.

## `crates/e2e`

- Test-only: real bridge executable, real `Manager`, real endpoint, local HTTP server. `bridge_exe` builds the bridge with `test-overrides`, or uses `WIRECATCH_TEST_BRIDGE`.
- `App::start_at` turns `ask_before_download` off. A test wanting the window turns it back on.
- `wirecatch-e2e-app` exits when its first client ends, or after 60 s.
