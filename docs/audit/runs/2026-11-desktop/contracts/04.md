# Contract 04: core-run-lifecycle

## Public API (`wirecatch-core`)

- `Manager` is a cheap clone over `Arc<Inner>`. `Manager::open(config)` must be called inside a Tokio runtime; afterwards methods work from any thread, as all work goes on the stored `Handle`.
- Synchronous and effective at once: `pause`, `resume`, `retry`, `cancel`, `refresh_link`, `move_to_queue`, `reorder`, `pause_all`, `resume_all`, `list_downloads`, `get_download`. Asynchronous: `add_download`, `remove`, `shutdown`.
- `remove` and `set_download_folder` run to the end even if the caller stops waiting (`to_the_end`). `remove_in_background` hides at once.
- After `shutdown`, operations return `CoreError::Closed`. Once it returns, the database file is closed. The shell wraps it in `QUIT_PATIENCE` (15 s), because `shutdown` itself waits on each run's `exited` with no limit (see below).
- Events: `subscribe` (`UiEvent`, buffer 1024) and `subscribe_events` (wire `Event`, buffer 64) only describe changes. A receiver that lags must reload.
- `Clock` is injected: `SystemClock` sleeps at most 60 s at a time and `sleep_until` may return early; `ManualClock` moves only when told.

## Run lifecycle

- All state sits behind one `Mutex<State>`, never held across `.await`. A poisoned lock is taken over as it is.
- At most one `Entry::run`. `state.running` matches runs, `state.unfinished` holds every not-Completed download (and finished ones until `prune_finished`); nothing puts a Completed download back in it. `state.claimed` holds every not-Completed download's path, plus `reserve`d paths. `assert_consistent` checks these in debug builds on each tick.
- `start_run` is called only by `reconcile`, which does nothing once `closed`. It sets `Connecting`, and a refused start sets `Failed` without calling `reconcile` again (finding 04-2).
- A run ends through `RunGuard`, exactly once: normally with its result, or as `RunEnd::Vanished` if panicked or aborted. Either way only after `FileWork::finished()`, and only then is `run.exited` cancelled. So a waiter on `exited` knows the files are closed, but that wait has no limit if file work hangs.
- `stop_run` asks once, then aborts the task after `stop_timeout` (default 5 s). `exited` still waits for file work.
- `Entry::stop` precedence: a person's choice (`Pause`, `Cancel`, `Restart`, `Remove`) always replaces the current reason; an app reason (`Requeue`, `Shutdown`, `ReadAsVideo`, `FileExists`) never replaces a person's. `settle.rs` writes `FileExists` and `ReadAsVideo` straight to `run.stop`.
- `finish` decides the new status: Completed wins over every stop. `Pause` or `Remove` end `Paused`; `Requeue` ends `Queued`; `Shutdown` keeps the status so the next start continues (`Processing` becomes `Downloading`); `Cancel` ends `Cancelled` and deletes partial files in the background; `Restart` does that and ends `Queued`. `run.stop == None` with `TargetTaken` moves the files to the next free name (`Hold::Moving`, status `Queued`). `found` is applied after all of it (finding 04-3).
- `Hold`: `Free`, `Moving(token)`, `Removing { after_move }`. A removing download is hidden from `entry`, `entry_mut` and `visible`, and is never started. `reconcile` starts only `Queued`, no run, `Hold::Free` (`is_waiting`). `cancel` and `pause` do not check for a move.
- `entry.cleanup` makes a later run wait for a deletion. `launch` takes it.
- Stranded (a failed move left files in two folders): the path stays reserved and is saved; `refresh_link` and moving refuse; `requeue` releases it.
- `Entry::summary()` hides link passwords; `row` keeps the real link. Never hand out `row` directly.
- `mark_completed` clears `waiting` and the error and wipes `origin` (cookies, headers).

## Progress and saves

- The ticker samples running gauges every `PROGRESS_TICK` (100 ms) and emits at most one `DownloadsChanged` per tick, with only changed, non-removing rows. When nothing runs it sleeps on `rows_changed`.
- `store.save_progress` every 2 s writes only `done` and `total`; status and the rest are saved on change through `Manager::save`. So the stored status of a running download stays `Connecting`, and a crash loses at most 2 s of the row's counter, not the engine's own resume state.
- A row's `done` and `total` follow the gauge only once `answered`. A run that never got an answer keeps the earlier values.
- The Mark of the Web goes on the part file once answered (ticker, best effort, for engine runs only), and `download_marked` marks the finished file before the run reports it.

## Restore

- `restore` is pure over `Snapshot` and `Surroundings`. Running statuses come back `Queued` with `resume_first`, and their queue's gate resumes its run. `Completed` and `Cancelled` are left as they are.
- Any other download with `naming.settled` and `finished_size(path) == Some` is marked Completed. This trusts `settled` too far for media and Replace (finding 04-1).
- Not saved, gone after restart: `on_existing`, `video_check`, `expect`, open questions, `Hold`, `through_proxy`. A question's download stays Paused and is judged again when resumed.
- Settings are written back only when restoring changed them; queues always (finding 04-6). An orphan's queue becomes the default queue. Id counters take the highest of stored and seen, so ids are never reused.
- `Manager::startup_notices()` and `set_aside_list()` report a repaired list or a data folder not private.
