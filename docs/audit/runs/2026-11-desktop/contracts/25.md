# Contract 25: main-window

As the code really behaves. Most of this is private to `crates/desktop`; other chunks use the items below.

## Used from outside `main_window`

- `run(library, cx)`: holds the library for the app's life in the `Running` global and answers its `Asked` events. Call once, after `bind_keys`.
- `bring_up(asked, cx)`: brings the main window up, opening it if needed, then answers `Asked::Window`, `Links`, `BrowserSettings` or `Reveal`. A failure to open a window says so and quits the app. `lifecycle::start_again_later` may swallow the request.
- `bring_up_with(cx, work)`: as above, then runs `work` in that window. `is_open(cx)` says whether it is open, in front or not.
- A closed window drops `MainWindow`: selection, sort, view, folded groups and speeds start fresh when it reopens. None of them is saved.
- `add_dialog::open(library, urls, queue, window, cx)` returns a weak form, alive while the dialog is. Callers that want later links to join it must keep it (`MainWindow::new_download` does; `empty_queue` does not, 25-10).
- `Reveal` (D98): clears the search, shows the queue or All downloads, unfolds the rows' groups and selects `ids`; its settings flags open Settings instead.

## What the list and selection guarantee

- `applies::can_pause`, `can_resume`, `can_retry`, `can_cancel`, `can_refresh_link`, `offers_new_link`, `can_move_to` are pure, and hold on the status only. The selection bar, menu and palette use them; the details' footer and the row's hover buttons do not (25-11).
- `selected_rows` gives the selected rows that are shown (view, search and folded groups applied), in list order. Everything except a drag and `nudge` acts through it, so those act only on visible rows. `self.selected` itself may hold hidden and removed ids (25-4).
- Commands read rows when the menu or bar is drawn, so statuses may be stale. `selection::each` filters with `takes`, runs every id and reports the first refusal. `confirm::cancel` stops at the first refusal (25-3).
- `Remove` passes `RemoveFiles::Delete` only when the box was ticked and at least one asked row was finished; core deletes only completed rows' files that way, and always unfinished rows' partial files. The words match that.
- Row indexes in `Line` are valid only for the frame that built them; `row` tolerates a missing index.
- A queue's view shows `queue_line` in library order, which is the running order only from load or after `Library::reorder` (25-5). Sorting never changes it, or Up next.
- A live sort (Progress, Speed, Time left) keeps its ranks until the sort or the set of ids changes; other sorts are computed on each `lines` call.
- `order::placed` and `order::nudged` return `None` when nothing would change. They keep the moved rows' own order. `order::apply` tells the manager first, then the list; a refusal shows as a notification and leaves the list alone.
- The default queue is `queues.first()` here and never leaves first place by a drag or the menu.

## Keys

- `keymap::bind` is the one table of shortcuts and the source of the Keyboard shortcuts page. All are in context `MainWindow`, except Down leaving the search (`MainSearch > Input`). The list's keys have handlers only while the downloads show; elsewhere they fall through.
- A dialog's focus sits outside `MainWindow`'s context, so these do not fire in dialogs. They do reach the search field unless its own table binds the key (25-1).

## Writes through other chunks

Only through `wirecatch_shell::api`, by `backend::act` (synchronous, a refusal shows in the window) and `backend::command` (async). The main window keeps no state of its own that crosses to the manager.
