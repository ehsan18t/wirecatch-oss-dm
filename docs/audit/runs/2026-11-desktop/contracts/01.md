# Contract 01: engine-disk-resume

How `wirecatch-engine`'s download path really behaves, for chunks that rely on it.

## Entry

`download(DownloadRequest, Arc<Progress>, CancellationToken) -> Result<Outcome>`. Options are checked by `DownloadOptions::validate` before any request (`Error::InvalidOption`), after the HTTP clients are built. Limits: `MAX_CONNECTIONS` 64, `MAX_BUFFER_SIZE` 64 MiB; zero values are refused.

## Where the file goes

- `exact_path`, or the path from `resolve_path`: the caller owns the name. `sanitize` is not applied. An earlier run there continues whatever its URL was. `if_exists` decides the finish: `Replace` (default) or `Refuse` (`Error::TargetTaken`, data kept beside a resume file saying it is complete).
- Otherwise a name in `dest_dir`: `naming::sanitize`, then continue only under the unnumbered name with the same URL and no file there, else `create_free_part` (`create_new`, passes over a name with a file or a resume file). The finish never replaces anything; `Outcome::Completed::path` can differ from `Progress::path`. Only the CLI and the public API use this path.
- Part file `<final>.wcpart`, resume file `<final>.wcstate` (`naming::part_paths`), plus a passing `<final>.wcstate.tmp` during each save. Nothing is at the final name until the data is complete and flushed.
- The engine has no lock on these files. Two runs at once on one path are the caller's to prevent.

## Resume

- Continues only when the saved state and the server agree: `ranged` on both sides, known total, same total, same `ETag` and `Last-Modified` (a validator that appears or vanishes counts as a change; both absent counts as the same), ranges in order and inside the file, and part file length equal to the total. Otherwise it starts over and deletes both files. An unreadable resume file is logged, never reported.
- The URL is compared only for a download into a folder. Passwords are never saved in the resume file.
- Unknown size or no ranges never resumes.
- `resume_file_url(path)` reads a resume file's link without exposing its format.

## Durability

- A save reads the done ranges, flushes the part file, writes a flushed temporary file, renames it over the resume file. So a resume file never counts bytes not on the disk, after a crash or a power cut (D30.1).
- Saves run every `checkpoint_interval` (default 1 s), serialised, and once at the end. A failed checkpoint only logs; a failed final save replaces the outcome with `Error::Io` (`IoAction::SaveResume`).
- The finished file is flushed before its rename. The rename may be lost to a power cut; the part and resume files then finish it on the next run. A crash between rename and deleting the resume file leaves both.

## Segments

- Offsets `flushed <= claimed <= end` per segment. Splits cut only above `claimed`, on a 64 KiB boundary where possible. `flushed` moves only for a write continuing from it, so a hole is never counted.
- Write errors are not retried: the connection gives up and its segment goes back from `flushed`. Another connection may take it; the download succeeds if the file completes, whatever errors connections gave.
- Network errors retry from `claimed`, which equals `flushed` by then, since a stretch's end writes everything out first.

## Cancelling and dropping

- Cancelling the token: every connection writes what arrived, the state is saved, `Outcome::Paused`. A complete file still finishes as `Completed`.
- Dropping the future: queued file work checks a flag and changes nothing, but a write under way or already queued still runs, and a moment remains between each check and its change. An owner that deletes the files or starts another run on the path first awaits `FileWork::finished` on the request's `file_work`. `FileWork::spawn_blocking` adds the owner's own work to that wait.

## Progress and outcome

- `Progress::done` includes bytes kept from an earlier run and bytes not yet flushed; failed writes take bytes back. `path` is set once the server answered, `None` if the first request failed. `total()` is `None` for an unknown size.
- `Outcome::Paused::remaining` is meaningless (near `u64::MAX`) when the size is unknown.
- `resumed_from` is `total - remaining` at the start.

## Names

- `sanitize` returns at most 200 bytes, is idempotent, never a Windows device, and `is_safe_name` accepts it. `is_safe_name` allows up to 247 bytes so that part and resume files fit. `move_to_free_name` and `rename_no_replace` never replace, except on a file system with neither `RENAME_NOREPLACE` nor hard links (a check then a rename, documented).

## Speed limits

`RateLimiter` is shared across connections and downloads; `set_limit` wakes waiters and takes effect at once. Bytes are charged after they are written, one limiter after another. A pause ends a wait at once. `None` is unlimited; 0 is treated as 1.
