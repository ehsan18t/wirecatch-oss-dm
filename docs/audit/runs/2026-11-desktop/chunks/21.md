## Findings

### 21-1 [P2] A website's FTP link is not held to the `Block` rule, so it can reach the local network

- Where: `crates/engine/src/download.rs` `download_with` (the guard is built only for `http` and `https`), `crates/engine/src/transport.rs` `open` (the FTP arm ignores `guard`), `crates/engine/src/ftp/mod.rs` `Target::new` and `Target::resolve`
- Category: wrong implementation
- Failure: a website's link (D39: `ChosenBy::Website`, which runs under `PrivateNetwork::Block`) in one of these forms connects to a local FTP server, logs in with the user name and password the link chose, and saves the file:
  - `ftp://rebind.example/f`, where the name answers a public address during the capture check and a local one when the engine connects, or answers both (`refuses` declines only when every address is local, and `Target::resolve` tries them all).
  - `ftps://%31%32%37.0.0.1/f`: `ftps` and `ftpes` hosts are opaque to `url`, so `host_str()` keeps the percent-encoding. `address_in` then sees no address and `addresses` finds nothing, so neither `refuses` nor `refuses_address` declines it. `Target::new` afterwards decodes it to `Host::Ipv4(127.0.0.1)` and connects. TLS certificate checks usually stop this form after the connection is made.
- Evidence: `download_with` matches `"http" | "https"` for `private_guard`, with `_ => None` otherwise. `Target::resolve` uses `tokio::net::lookup_host` with no address filter. `crates/sites/src/local_network.rs` `refuses` says of a name that answers local at connection time that it "is still refused by the engine", and that a name with no answer in time "goes on to the engine, which decides". Neither holds for FTP. `DownloadOptions::private_network` documents "`ftp` links are not covered", but no decision in `docs/DECISIONS.md` accepts this for a website's link, and D39.1 says such a link runs under `Block`. Impact is bounded: the attacker chooses what is fetched and where it is saved under the app's naming, but does not get the bytes back. The same unnormalised `host_str()` also reaches `Proxies::ftp_route` in `transport::open`, so an exception cannot match an international `ftps` host.
- Confidence: certain for the code path; the severity depends on what a local FTP server would hand out

### 21-2 [P2] `;type=i` in an FTP link ends up in the saved file's name

- Where: `crates/engine/src/ftp/mod.rs` `Target::new` (`display_url`), `crates/engine/src/transport.rs` `open` (`final_url`), `crates/engine/src/naming.rs` `from_url`, callers `crates/engine/src/target.rs` `suggested_name` and `crates/core/src/naming.rs` `file_name` and `settled_name`
- Category: bug
- Failure: `ftp://host/a.iso;type=i` is requested correctly as `a.iso` and saved as `a.iso;type=i`. The extension is lost, so the file does not open by double click, and category rules and queue rules by file type see the wrong extension.
- Evidence: `Target::new` strips `;type=` only from its private `path`. `display_url` keeps it and becomes `final_url`. `naming::from_url` returns the last path segment as it is, and `clean` does not replace `;`. No test in `crates/engine/tests/ftp.rs` or `src/ftp/tests.rs` downloads such a link; `paths_and_credentials_come_from_the_url` checks only `t.path`.
- Confidence: certain

### 21-3 [P3] FTP tests race the machine against a throttled transfer or a short stall limit

- Where: `crates/engine/tests/ftp.rs` `plain_download_is_byte_identical_over_parallel_connections`, `completes_within_session_limit`, `the_size_from_the_transfer_reply_is_used_without_size_support`; `crates/engine/src/ftp/tests.rs` `explicit_tls_download_is_byte_identical`, `implicit_tls_download_is_byte_identical`; `crates/engine/src/ftp/control.rs` `tests::control_reading`
- Category: fake test
- Failure: on a busy machine these fail with no fault in the code, which breaks `docs/ENGINEERING.md` section 7.
  - The first group asserts that a second transfer ran in parallel (`max_transfers >= 2`, or `== 2`, with `refused >= 1`), yet only a throttle (`data_bps = 8 MiB/s` over 4 to 8 MiB) gives the other connections time to log in. The first transfer ends the whole file in 0.5 to 1 second if they have not joined by then. The TLS tests add handshakes to that login.
  - `control_reading` gives `Control` a 2 second stall limit, which nothing under test needs, and `multi_line_replies_end_with_the_code_alone_too` fails with `Stalled` if the spawned server is not scheduled in that time.
- Evidence: the comment in the first test says "Slow enough per connection that the other connections join in". `FtpConfig` has no hold that keeps the first transfer open until a second one starts (`hold_probe` sends nothing at all and is meant for resuming). The `test-timing` check does not look at a limit passed to `Control::new` or at a rate.
- Confidence: likely

## Suggestions

### 21-S1 Accept FTP links whose path is not UTF-8

- Today: `Target::new` refuses `ftp://host/%FCbung.bin` as `InvalidUrl` ("contains characters that are not valid UTF-8"), and `urls_that_cannot_be_sent_safely_are_refused` holds that in place. Commands are built as `&str`, so a Latin-1 name on an older server cannot be asked for.
- Better: curl and wget send the percent-decoded bytes as they are. Build commands from bytes, keeping the refusal of `\r`, `\n` and `\0`.
- Value: files with non-ASCII names on older FTP servers can be downloaded instead of failing with a message the person cannot act on.
