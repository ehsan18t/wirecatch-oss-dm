### 31-1 [P3] The `Range` header is parsed four times in the crate, and the HTTP/3 copy answers a range past the end differently

- Where: `crates/test-support/src/http3.rs` (`range`, `asked`), `crates/test-support/src/http.rs` (`parse_range`, `asks_too_much`, `Seen::range`)
- Category: duplicate
- Failure: `http3::range` is `http::parse_range` plus a `start < end` check, and `http3::asked` repeats the parse in `asks_too_much`. The copies have drifted: a request for `bytes=<past the end>-` gets `416` from `TestServer` and `FileServer`, but `200` with the whole body from both HTTP/3 servers. A test of a client that resumes past the end over HTTP/3 would see a different server from the same test over HTTP/1.1, and a fix to the parsing must be made in up to four places.
- Evidence: `http3.rs` already imports `index` from `crate::http`, and `parse_range` is `pub(crate)` over the same `http` crate's `HeaderMap`, so nothing stops it from being reused. `http3::answer` turns `None` from `range` into `StatusCode::OK`, and `http::serve_file` and `files::answer` have an arm for `start >= len` that answers `416`.
- Confidence: certain

### 31-2 [P3] `bytes_sent` is kept by the HTTP and FTP servers and read by nothing

- Where: `crates/test-support/src/http.rs` (`Stats::bytes_sent`, `TestServer::bytes_sent`, the update in `body`), `crates/test-support/src/ftp.rs` (`FtpStats::bytes_sent`, the update in `send_file`)
- Category: dead code
- Failure: every chunk sent updates a total that no test, example or script reads. Its doc also invites the check that docs/ENGINEERING.md section 7 warns about, since a total counts what buffers took in, and a comment in `crates/core/tests/manager/lifecycle.rs` explains why tests stopped using one. Tests count per answer through `Seen::sent` and `FtpStats::transfers_sent`.
- Evidence: `git grep bytes_sent -- crates scripts` finds it only in `crates/test-support/src`.
- Confidence: certain

### 31-3 [P3] `drop_first` on the HTTP server does not break off after the bytes it names, and never breaks off a short answer

- Where: `crates/test-support/src/http.rs` (`Config::drop_first`, `body`)
- Category: wrong implementation
- Failure: the doc says "The first `n` responses break off after `after` bytes". `body` checks `sent >= after` only between chunks of 64 KiB and does not shorten a chunk to `after`, so `Some((1, 100_000))` sends 131,072 bytes. An answer of at most one chunk, such as `Some((1, 1000))` on a 10 KB file, is sent whole and ends cleanly: `pos >= end` is checked first, so no disconnect happens. A new test of retrying on such a file would pass without any retry. The FTP server's `drop_first` with the same doc cuts exactly (`end.min(limit)`).
- Evidence: read of `body` and `send_file`. Checked every current use (`engine/tests/download.rs`, `fetch.rs`, `hardening.rs`, `request_limit.rs`): all serve at least 400,000 bytes with `after` far below the answer's size, so all do break off, and none is affected today.
- Confidence: certain

### 31-4 [P3] `FileServer` records a request when it is answered, while its docs say when it arrived

- Where: `crates/test-support/src/files.rs` (`serve`, `FileServer::seen`, `FileServer::requests`), `crates/test-support/src/http.rs` (docs of `Seen::at` and `Seen::wall`)
- Category: wrong implementation
- Failure: with `delay` set, `Seen::at` and `Seen::wall` hold the end of the delay rather than the arrival ("When it arrived"), `seen()` is in answer order rather than "the order they arrived", and `requests()` does not count a request still inside its delay. `TestServer` records the arrival time correctly, so the same field means different things on the two servers.
- Evidence: `serve` builds `Seen` with `Instant::now()` after `tokio::time::sleep(file.delay)`, while `http::serve` takes `arrived` first. No test reads `at` or `wall` from a `FileServer`. The one place this could bite is `resuming_with_a_refreshed_link_keeps_the_segments` in `crates/streams/tests/hls.rs`, which sets a 40 ms delay and uses `server.seen().len()` at the pause as the line between two runs: a request of the paused run still inside its delay is not in that count. It normally disappears when hyper sees the client close and drops the handler, so it counts for the second run only if the delay ends first. No failure of that test was seen.
- Confidence: certain for the wrong times and order; likely, and narrow, for the effect on that test
