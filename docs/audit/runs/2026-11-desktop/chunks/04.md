## Findings

### 04-1 [P1] A waiting video whose name is already taken is marked finished at the next start

- Where: `crates/core/src/manager/restore.rs`, `restore_entry`; `crates/core/src/naming.rs`, `finished_size`; `crates/core/src/manager/downloads.rs`, `insert` and `add_entry`
- Category: bug
- Failure: a video or stream is added whose planned name already exists in the folder (the same video downloaded before, say), and it is queued or paused (Download later, a full queue, a closed schedule) so it has not run yet. The app restarts. The download becomes Completed, with the older file's size as its own, its cookies and headers wiped, and nothing downloaded. No question is asked, against D96. The same happens to a plain download the person answered Replace for: `replace_at` makes its path final and it is Queued or Connecting with no part file yet, so a restart in that window reports the old file as the finished replacement.
- Evidence: `insert` picks a media path with `unclaimed_path`, which ignores files on disk on purpose ("a file already there is left for the download to decide about when it puts its file in place"). `add_entry` sets `naming.settled = media_job.is_some()`, so the path counts as final from the start. `restore_entry` trusts any settled, not cancelled, not completed download whose `finished_size` is `Some`. `finished_size` only looks for part and resume files and for the work and stream folders, and the work folder is created when the run starts (`media_run/mod.rs`, `page.rs`). So an unstarted video has none of them. The comment above the check says a provisional path's file "is someone else's", but `settled` does not mean the file is this download's for media or Replace. `restart.rs` covers only plain downloads with an answered path.
- Confidence: certain from the code, not run

### 04-2 [P2] A download that fails to start leaves its slot empty and the next one waits

- Where: `crates/core/src/manager/run.rs`, `start_run` and `fail_to_start`; `crates/core/src/manager/scheduling.rs`, `reconcile`
- Category: bug
- Failure: a queue holds A, B and C, waiting. A is a website's link to a local address, refused at start (`local_network::refuses_address`). The last running download finishes, and `reconcile` plans to start only A, since one slot came free. A fails to start. B and C stay Queued with "in line" as the reason and no download running, until something unrelated calls `reconcile` (another command, or the minute tick of a queue with a schedule). With no schedule and nobody at the machine, the queue stops.
- Evidence: `reconcile` computes `plan.start` once and calls `start_run` for each. `fail_to_start` only sets the status and calls `save`, and `save` wakes the ticker, not the planner. Every other path that frees a slot (`finish`, `pause`, `cancel`) calls `reconcile`. `run_scheduler` only wakes on queue edits and, when a queue has a schedule, each minute. `refuses_address` is checked only in `engine_request` and `start_media_run`, so such a capture is added and fails later, which is how it comes to wait in line. The first `reconcile` after a restart can stall the same way.
- Confidence: certain from the code, not run

### 04-3 [P2] A run's found duplicate overrides what the person chose while it stopped

- Where: `crates/core/src/manager/run.rs`, `finish`; `crates/core/src/manager/file_exists.rs`, `on_found`
- Category: bug
- Failure: a run has found a file already at its name (`run.found`, or `MediaDone::FileExists`), and before `finish` runs the person presses Cancel or Pause. `finish` honours that stop (Cancel marks it cancelled and deletes the partial files, including a video's finished file waiting in the work folder) and then calls `on_found` regardless. With the setting on Replace the cancelled download goes back to Queued and starts over; on Keep existing it becomes Completed; on Ask it becomes Paused with a question open. A Pause is lost the same way. If Shutdown overrode the stop and the setting is Replace, the row is saved Queued and settled, which feeds 04-1.
- Evidence: `Entry::stop` lets a person's choice replace `Stop::FileExists` and leaves `run.found` set. In `finish`, `found` is taken before the `match` and `if let Some(found) = found { self.on_found(...) }` runs after it with no look at `run.stop`. A media job's `FileExists` result has no `Stop::FileExists` at all, so any stop set while it places its file reaches this. For a plain download the window is short: from the resolver's refusal to the run's end.
- Confidence: certain from the code; the window is narrow, longest for a video placing a large file

### 04-4 [P2] Resume all and Refresh link leave the file-exists question open

- Where: `crates/core/src/manager/downloads.rs`, `resume_all` and `refresh_link`; `crates/core/src/manager/file_exists.rs`, `answer_file_exists`
- Category: bug
- Failure: a download is Paused with its question open. Resume all (or a new link) puts it back in line without closing the question. While the run goes on, answering the question fails with "That download no longer exists" (`e.run.is_none()` is false). If the person had dealt with the file meanwhile, the run finds nothing and finishes, and the question stays open with nothing left to close it. Answering Replace or Keep both then sets a Completed row to Queued, or Cancel sets it to Cancelled and deletes partial paths. That row left `unfinished` at the last prune and its path has no claim, so it never starts again, and `assert_consistent` fails in debug builds.
- Evidence: `requeue` and `cancel` both call `close_file_exists`; `resume_all` and `refresh_link` do not. `answer_file_exists` checks that the download exists, is not being removed and has no run, but not its status. `State::unfinished` documents "only adding one puts it here". `ask` closes an older question only if the duplicate is found again.
- Confidence: likely; the interface was not checked for closing the question on its own

### 04-5 [P3] A removal under way when the app closes is forgotten

- Where: `crates/core/src/manager/downloads.rs`, `finish_removing`; `crates/core/src/manager/mod.rs`, `shutdown`
- Category: bug
- Failure: the person removes a running download and quits within its stop time. It is back in the list after the next start as Paused, with its partial files. The same applies to a failed capture's attempt hidden through `remove_in_background`, which reappears as a Paused row although the browser kept the file.
- Evidence: `finish_removing` takes `lock_open()?` after waiting for the run, and `shutdown` has set `closed` by then, so it returns `CoreError::Closed` without `delete_downloads`. `Hold::Removing` is not saved, `Stop::Remove` ends as Paused in `finish`, and `shutdown` waits only for runs' `exited`.
- Confidence: certain from the code, not run

### 04-6 [P3] Opening the app deletes a queue this build cannot read

- Where: `crates/core/src/manager/mod.rs`, `Manager::open`; `crates/store/src/lib.rs`, `read_queue` and `save_queues`
- Category: design
- Failure: a queue saved by a newer build holds a value this build cannot read (a later build's kind of rule, say), and the person goes back to the older build. Its row is deleted for good at the first open and its downloads move to the default queue, also saved, with no notice. Fields this build does not know are stripped from the queues it can read. So going forward again does not bring them back.
- Evidence: `read_queue` returns `None` for unreadable settings, and `open` calls `save_queues` on every start, which runs `DELETE FROM queues` and writes back what was read. `restore_entry` marks the moved downloads as `fixed`. The comment two lines above in `open` writes settings back only when changed, "so what another build saved and this one cannot read ... survives", and unreadable downloads are kept with a notice (`Recovery::UnreadableKept`). Queues have neither protection.
- Confidence: certain from the code; reached only by going back to an older build

### 04-7 [P3] A lifecycle test gives waits that must succeed a fixed five seconds

- Where: `crates/core/tests/manager/lifecycle.rs`, `a_server_that_never_answers_cannot_hang_the_app`
- Category: fake test
- Failure: on a busy runner a correct removal or shutdown that takes over 5 s fails the test. The test wants to show that nothing waits forever, which `PATIENCE` bounds.
- Evidence: `let patience = Duration::from_secs(5);` then `tokio::time::timeout(patience, ...)` around `remove` and `shutdown`, with `.expect`. `docs/ENGINEERING.md` section 7 forbids this. The gate's `test-timing` check does not catch it because the duration sits in a variable rather than in the call.
- Confidence: certain
