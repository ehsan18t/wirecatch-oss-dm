## Findings

### 09-1 [P2] A website's FTP link is not kept off the local network

- Where: `crates/engine/src/download.rs`, `download_with`; `crates/engine/src/ftp/mod.rs`, `Target::resolve` and `probe`; the promise in `crates/sites/src/local_network.rs`, `refuses`
- Category: wrong implementation
- Failure: a capture with `ChosenBy::Website` and the link `ftp://x.evil.example/f`, whose name answers a public address plus `192.168.1.1`, or public at capture and local when the run starts. `refuses` lets both through, since not every address is local. The run has `PrivateNetwork::Block`, but the engine connects to every address the name gives, local ones included, signs in anonymously and saves what it gets. With a port in the link, the FTP commands go to any local service.
- Evidence: `download_with` makes a guard only for `http` and `https` (`_ => None`). `Target::resolve` calls `tokio::net::lookup_host` with no filter and `probe` tries each address in turn. `core::parse_url` accepts the FTP schemes for captures, and `engine_request` only stops links written as a local address (`refuses_address`). The doc comment of `refuses` says a name that turns local "is still refused by the engine", which is false for FTP. D39.1 makes no exception for FTP; `DownloadOptions::private_network` does say "`ftp` links are not covered", and core does not act on that. Severity is P2 because browsers rarely hand over FTP downloads, so the usual way in is a capture sent over the bridge, and nothing read is sent back to the website.
- Confidence: certain

### 09-2 [P2] A Windows `socks=` proxy fails on sites whose first address is IPv6

- Where: `crates/engine/src/proxy.rs`, `Proxies::adopt` (the `socks4://` value), with `reqwest` `connect::socks::connect`
- Category: broken feature
- Failure: Windows proxy set to `socks=host:1080`, on a machine where name lookups give an IPv6 address first, downloading from a site with both address families. Every request fails with a SOCKS connection error, and the same site works in a browser. A `socks4://` value copied from the system fails the same way.
- Evidence: `adopt` writes `socks4://`. For that scheme reqwest uses `DnsResolve::Local`: it takes `.next()` from the resolver and puts that address in the destination. `hyper-util` `SocksConfig::execute` returns `SocksV4Error::IpV6` for an IPv6 destination. Its own search for an IPv4 address runs only for a name and only with `local_dns`, which reqwest never sets. The existing test (`the_system_proxy_counts_when_no_variable_sets_one`) compares only the value handed to the client. Not run; address order on the machine decides whether it shows.
- Confidence: likely

### 09-3 [P2] An IPv6 exception written in brackets never matches

- Where: `crates/engine/src/proxy.rs`, `exceptions`
- Category: wrong implementation
- Failure: exceptions `[::1]` or `[fd00::5]`, the way an IPv6 address is written in a URL and in Windows' bypass list. A download from `http://[fd00::5]/f` goes through the proxy instead of directly, and usually fails there. `ManualProxies::exceptions` promises "addresses".
- Evidence: `exceptions` passes the entry on as it is. `NoProxy::from_string` fails to parse `[fd00::5]` as an address, so it becomes a domain entry. `NoProxy::contains` strips the brackets from the host, parses it as an address and looks only in the address list. Only `::1` without brackets is tested. D62.5 records other wildcards as matching nothing, not this.
- Confidence: certain

### 09-4 [P2] Cancelling does not interrupt the guard's name lookups

- Where: `crates/engine/src/net_guard.rs`, `private_guard` and `NetworkGuard::check`, as called from `download_with`, `Fetcher::with_private_network` and `http::send`
- Category: wrong implementation
- Failure: pausing or cancelling a download while the name server does not answer. Under `Auto`, the start lookup and then the first check each wait up to `stall_timeout` (30 s by default), so the run can ignore the cancel for up to 60 s. `Block` waits up to 30 s.
- Evidence: `resolve` is bounded only by its timeout and has no token. `private_guard(...).await` in `download_with` and `(guard.0)(&url).await?` in `send` stand outside the `select!` on `session.cancel`, while the doc comment of `send` says it returns `Error::Cancelled` "as soon as the download is cancelled".
- Confidence: certain

### 09-5 [P3] The DNS rebinding tests never reach the filtering resolver

- Where: `crates/engine/src/net_guard.rs`, test `a_download_cannot_be_rebound_to_the_local_network`; `crates/engine/tests/fetch.rs`, test `a_start_name_that_resolves_to_the_local_network_is_blocked_when_asked`
- Category: fake test
- Failure: removing `clients.set_resolver` from `download_guarded` or `.dns_resolver` from `Fetcher::with_private_network` turns off the protection against a name that changes after the check, and these tests still pass.
- Evidence: both use `localhost`, which answers local at the check too, so `NetworkGuard::check` refuses before any connection. The first test's comment says the name resolves local "whatever an earlier lookup by the caller saw", but nothing makes an earlier lookup differ. `the_resolver_never_hands_out_local_addresses` tests the resolver alone, not that the clients use it. A guard whose `names` cache already holds `localhost` as allowed would test the wiring. Found by reading the tests; no mutation run.
- Confidence: likely

### 09-6 [P3] A refusal by the resolver ends as a plain network failure

- Where: `crates/engine/src/net_guard.rs`, `FilteringResolver::resolve`
- Category: wrong implementation
- Failure: a name that answers public at the check and only local at the connection. The download is retried as a network failure and ends with `Error::Network`, whose message offers a retry, instead of `Error::PrivateNetwork` with the D39.6 wording and no retries.
- Evidence: the resolver returns a plain text error, which reqwest wraps as a connect error. Nothing maps it back: the text appears only there and in `Error::PrivateNetwork`'s message (`error.rs`), and `a_download_cannot_be_rebound_to_the_local_network` asserts only `is_err()`. The connection is still blocked, so only the message and retries are wrong.
- Confidence: likely

### 09-7 [P3] `direct_uses_no_proxy` passes whatever `Direct` does

- Where: `crates/engine/tests/proxy.rs`, `direct_uses_no_proxy`
- Category: fake test
- Failure: with `ProxyChoice::Direct` behaving as `System`, the test passes on any machine without a proxy, CI included, because no proxy is set for it to avoid. On a machine with a proxy it could fail for the wrong reason.
- Evidence: the test sets no environment and no proxy and checks only the size of the download. The real proof is the unit test `direct_and_manual_read_neither_the_environment_nor_the_system`.
- Confidence: certain

### 09-8 [P3] `NetworkGuard::check` repeats `all_private`

- Where: `crates/engine/src/net_guard.rs`, `NetworkGuard::check` and `all_private`
- Category: duplicate
- Failure: the rule that decides whether a name counts as local (it has addresses and all are local) is written twice in one file, once for `Auto` and once for the check, so a change to one can miss the other. `check`'s match on the host also repeats `host_addresses`.
- Evidence: `!addrs.is_empty() && addrs.into_iter().all(is_private)` in `check`, and `!addrs.is_empty() && addrs.iter().all(|ip| is_private(*ip))` in `all_private`.
- Confidence: certain

### 09-9 [P3] The module docs describe proxy behaviour that has changed

- Where: `crates/engine/src/proxy.rs`, module header; `crates/engine/src/net_guard.rs`, `PrivateNetwork`, section "With a proxy"
- Category: wrong implementation
- Failure: the `proxy.rs` header says FTP "is refused (it cannot go through one yet)", but `ftp_route` carries FTP through SOCKS5 and `ftp_direct` lets it go around. The `PrivateNetwork` section says the proxy looks up each name and lists only the environment and the system as sources, but `socks4://` and `socks5://` resolve here through the filter, and `ProxyChoice::Manual` is a third source. An engine user reading them is told the wrong thing about a security rule.
- Evidence: `Proxies::ftp_route`; `reqwest` `connect_socks` (`DnsResolve::Local` for those schemes); `Proxies::manual`.
- Confidence: certain

## Checked and found correct

- `AddressKind`: every IPv4 and IPv6 range against its doc and D34.6, including the edges and the embedded IPv4 forms.
- Redirects: `http::send` checks the guard on each hop, follows only `http` and `https`, and turns off reqwest's own redirects. QUIC is off whenever a guard exists.
- Links written as decimal or hex addresses: the URL parser normalises them for `http` and `https`.
- PASV: the data connection uses only the port, so a server cannot point it at another host.
- The routing rules (`proxy_for`, `excluded`, `ipv4_wildcard`, `adopt`, `as_manual`), logins kept out of `Debug` and `ProxyRoute`, and `without_credentials`.
