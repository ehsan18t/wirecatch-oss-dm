## Findings

### 11-1 [P2] A repair downloads every part again and puts yt-dlp back to the pinned version

- Where: `crates/core/src/manager/addons/mod.rs`, `Manager::addon_plan` and `Manager::wanted_components`; `crates/core/src/manager/addons/install.rs`, `swap_in`
- Category: wrong implementation
- Failure: yt-dlp was moved past the pin by the update check, say to 2026.10.05 against the pinned 2026.08.19, and one file of another part goes missing (an antivirus takes `avcodec-63.dll`). The add-on shows as damaged and the person presses Try again. All three parts are downloaded (about 138 MB on Windows, for one DLL), and the healthy yt-dlp 2026.10.05 is replaced by 2026.08.19 with its cache emptied. The older yt-dlp then stays until the next update check: up to 24 hours later with automatic updates on, because `last_update_check` is kept, and until the person presses Check for updates with them off. An old yt-dlp is what stops video sites working.
- Evidence: `addon_plan` returns all of `wanted_components` when `slot.tools` is `None`, skipping the `outdated` filter, which is the only code that keeps a yt-dlp newer than the pin. `wanted_components` gives the pin unless `ytdlp_releases` holds a mature release, and that list is filtered to releases newer than the installed one and is empty after a restart, so the installed yt-dlp is never among them. `swap_in` replaces whatever is at the target with no version check. `addons::tools` answers `None` for the whole add-on when any one file of any part fails. This also contradicts the comment in `swap_in` ("the next install repairs only what is missing") and D38.4 ("A release older than the installed one or the pin is never offered"). `a_program_taken_away_is_reinstalled` and `a_fresh_release_waits_two_days_on_every_install_path` repair only at the pinned version, so neither can see it.
- Confidence: certain

### 11-2 [P2] The update check acts on what it read before its network wait: a removed add-on comes back, and a finished update's record is overwritten

- Where: `crates/core/src/manager/addons/updates.rs`, `Manager::check_addon_updates`
- Category: bug
- Failure, removal: a check is waiting on GitHub (the daily one, or the Check for updates button) and the person removes the add-on. When the check resumes, `save` makes the deleted folder again and writes `installed.json` with the old parts, so the next look at the disk (at the latest the next start) reports "The media add-on is damaged" rather than not installed. With `auto_update_addons` on (the default) it does worse first: `tools` is now `None`, so `addon_plan` returns every part and the check starts a quiet install of the whole add-on the person just removed.
- Failure, update: an update started by the Update button is running when the hourly look finds a check due, and finishes during the check's network wait. The check then saves the record it cloned before the wait, which names the old yt-dlp with the old size. The running app keeps its newer record in memory, but on the next start or rescan the size check fails, the add-on shows as damaged and everything is downloaded again (and 11-1 applies).
- Evidence: `record` is cloned from the state at the top of the function, before `new_ytdlp_releases().await`, which makes several requests with retries. `saved` is that clone with only `last_update_check` changed, and `to_save.save(&dir)` writes it whole. `Record::save` goes through `wirecatch_files::whole_file::replace`, whose `create_dir_all` remakes a removed folder. After the wait nothing looks at `state.addon.tools` again before `addon_plan` and `start_addon_op`. Neither `check_addon_updates` nor the `due` test in `run_addon_updates` looks at `state.addon.op` before the wait, and `remove_addon` knows nothing of a running check. No test runs a check across a removal or an install. The window is the length of the check's requests, so seconds, more on a slow connection.
- Confidence: certain for the code path; how often the window is hit is not measured

### 11-3 [P3] An update offer names a yt-dlp older than the one installed

- Where: `crates/core/src/manager/addons/mod.rs`, `Manager::addon_info` (`latest_version`); shown by `status` in `crates/desktop/src/main_window/settings/addon.rs`
- Category: bug
- Failure: yt-dlp was moved past the pin by the update check, then an app update changes the ffmpeg or Deno pin. The state is `UpdateAvailable` and Settings says "Version yt-dlp 2026.08.19, ffmpeg 9.1, Deno 2.9.7 is ready to install.", though yt-dlp will not be touched and its installed version is newer than the one named.
- Evidence: `latest_version` is `describe` over `wanted_components`, which gives the pin whenever `ytdlp_releases` holds no mature release, without looking at the record. `addon_plan` filters the same list with `outdated`, so the plan and the text disagree. `UpdateAvailable` is the only state that shows the field, and no other code reads it.
- Confidence: certain

### 11-4 [P3] Release files of a version that is never installed stay in the work folder for good

- Where: `crates/core/src/manager/addons/install.rs`, `swap_in` and `Manager::fetch_part`
- Category: inefficiency
- Failure: an update downloads yt-dlp X, whole or in part, and does not install it: the app closes during a quiet update, X's version check cannot run (an antivirus, say), or the swap fails because a video is being processed. A later check finds X+1 and installs that. `yt-dlp-X.download`, or its part and resume files, stays in `.work` until the add-on is removed: up to 18 MB on Windows and 40 MB on Linux for each release skipped this way, adding up over the life of the install, and nothing shows it.
- Evidence: the only deletions in `.work` are, in `swap_in`, the release file of the version just installed and the `old-` folder; in `fetch_part`, a refused release; in `verify_and_unpack`, a file that fails its checksum; and the whole folder in `cancel_addon_operation` and `remove_addon`. `release_file` puts the version in the name, so a newer release never reuses or replaces the older file. `WORK_FOLDER` has no other user outside these files and their tests.
- Confidence: certain

### 11-5 [P3] `swap_in` spells out the release file's name instead of using `release_file`

- Where: `crates/core/src/manager/addons/install.rs`, `swap_in` and `release_file`
- Category: duplicate
- Failure: the name is written with `format!("{}-{}.download", ..)` in both functions of one file. A change to one alone leaves `swap_in` deleting nothing, and installed releases then pile up in `.work`; the check that `.work` ends empty in `install_downloads_checks_and_unpacks_only_the_expected_files` would catch it.
- Evidence: `swap_in` could call `release_file(id, component.version())`; `release_file` is in the same file.
- Confidence: certain

## Suggestions

### 11-S1 Try a folder move again briefly before failing it

- Today: `swap_in` calls `std::fs::rename` once for each part. On Windows an antivirus often holds programs just unpacked or just run (a new yt-dlp has just been run for its version check), and the rename then fails with access denied. The person sees "could not be put in place" and presses Try again; a quiet update waits a day.
- Better: repeat the move a few times over a second or two when the error is access denied, as rustup does for the same cause. `rename` is already a parameter of `swap_in`, so the tests stay as they are.
- Value: fewer failed installs on first use, the moment a person has just asked for a video.

## Checked and clean

Reported so the validation need not repeat them.

- Checksum to unpack: one open file is hashed and unpacked, sharing read only on Windows; the cap applies before hashing; a mismatch is deleted before anything is unpacked. Installed files are hashed as written, through a writer `io::copy` cannot bypass.
- Archives: entry names are only compared, targets come from the manifest through `safe_join`, links, folders and devices under an expected name are refused, each file is cut off past 1 GiB, and files are created with `create_new`. The zip crate may merge duplicate names, so `claim` guards tar only, but archives are opened only after a pinned checksum matched.
- Signature: the pinned fingerprint is compared before the key is used, bindings are verified, only document signatures count, and the bytes verified are the bytes parsed for the checksum. Tags reach a URL only after `newer` parsed them as dotted numbers (a `+` before a number parses, and is harmless in a path).
- Maturity and replay: every install path goes through `wanted_components`, `Origin::Found` is carried from the check, and `confirm_version` is bounded and cancellable.
- First check: `UnixMillis::since` saturates, so `i64::MIN` for "never checked" is due at once.
- Failure ends: each `op` ends through `end_addon_op` and `ended`; a stopped install leaving pages in `NeedsAddon` is deliberate, since a window can offer the install again and the wait expires.
- The pins, checked against the real hosts on 2026-11-04: all six release addresses answer 200 with exactly the pinned size; the Windows ffmpeg zip holds `ffmpeg.exe` and all seven DLLs under the expected top folder; both Deno zips hold the program at their root. The SHA-256 values and the Linux tar's contents were not checked here (the Linux job runs that build, D54).
- Tests: none found that cannot fail. No crate build or test run was needed for these findings.
