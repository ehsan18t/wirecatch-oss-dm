## Findings

### 10-1 [P2] A page address that is not a web address counts as a page on the person's network

- Where: `crates/sites/src/local_network.rs`, `ChosenBy::of_capture` and `is_local_by_itself`
- Category: bug
- Failure: a capture whose page addresses are all `chrome-extension://abcdef/viewer.html`, `moz-extension://<uuid>/page.html` or any other scheme with a dotless authority gets `ChosenBy::LocalPage`, so its link runs under `PrivateNetwork::Auto` and `refuses` lets it through. A link to `http://192.168.1.1/x` on a viewer extension's page (a PDF or file list another extension shows, whose links come from a website) reaches the local network through "Download with Wirecatch", though no page on that network chose it.
- Evidence: `of_capture` only requires `Url::parse(page)` to succeed, with no check of the scheme. The `url` crate gives a non-special scheme an opaque host, so `host_str()` is `abcdef`; it has no dot and `is_public_suffix` is false for it, so `is_local_by_itself` answers true. `cookie_scope::site_of` does refuse every scheme but http and https, so the crate holds the other rule next door. Nothing earlier filters it: the protocol does not check `page_url`, `frame_url` or `referrer`; in the extension `should-capture.ts` refuses internal referrers (`chrome-extension:` among them) for browser downloads only, and the context menu path (`planMenuClick`, then `hub.ts`) checks only the link's own scheme and sends `click.pageUrl` and `click.frameUrl` as they are. `D39.1` says a page is local "by its own address", meaning a host on the network. The tests cover `"not a link"` but no address with another scheme.
- Confidence: certain for the classification; likely for the context menu being offered on another extension's page in a tab.

### 10-2 [P2] A top-level domain the list holds only through a wildcard rule counts as a local name

- Where: `crates/sites/src/public_suffix.rs`, `SuffixList::is_public_suffix`; reached from `crates/sites/src/local_network.rs`, `is_local_by_itself`
- Category: wrong implementation
- Failure: `is_public_suffix("jm")` is false, so a page at `http://jm/` is local by itself and its captures are `ChosenBy::LocalPage`. The same holds for `ck`, `er`, `fk`, `mm`, `np` and `pg`, the top-level domains the built-in list holds only as `*.jm` and so on, and for any that a later list writes this way. D39.1 refuses exactly this case: "a single label that is not a top-level domain on the Public Suffix List (`nas`, but not `ai`, where public DNS has served records at the top level itself)". Only the registry of such a domain could serve that host, so the reach is narrow. `UNRESERVED_LOCAL_SUFFIXES` has the same gap: a future `*.lan` rule alone would not turn off `lan`.
- Evidence: for a single label, `Psl::find` in `psl-types` sets `info.typ = node.leaf.map(...)`. The node for `jm` exists only as the parent of `*`, so it has no leaf and `typ` is `None`; `is_known()` is then false. The `.dat` has `*.ck`, `*.er`, `*.fk`, `*.jm`, `*.mm`, `*.np` and `*.pg` and no plain rule for any of them. The test `the_list_knows_both_its_sections_and_its_wildcards` asserts `anything.ck` but never `ck` itself, and `a_host_is_local_by_its_own_address_or_name` covers only `ai`, `com` and `xn--p1ai`.
- Confidence: certain

### 10-3 [P2] A list that could not be saved tells the person to check their internet connection

- Where: `crates/core/src/manager/suffix_list.rs`, `NotTaken::advice` and `Manager::newer_suffix_list`
- Category: wrong implementation
- Failure: Check now fetches a good list and the disk is full or the data folder is not writable. The person reads "Wirecatch could not update its list of public domains (the new list could not be saved: ...). It keeps using the list it has; check your internet connection, then try again." The connection is fine, and checking it fixes nothing.
- Evidence: `NotTaken::Failed(String)` holds both a failed fetch and a failed `whole_file::replace` (its doc says so), and `advice` answers "check your internet connection" for every `Failed`. The test `a_list_refused_or_not_kept_leaves_the_list_in_use` matches only the error's variant for the case it cannot keep, not its text. `docs/ENGINEERING.md` section 8 requires an error to say how to fix it; section 4 asks for a variant per cause a caller may act on, which is what is missing here.
- Confidence: certain

### 10-4 [P3] The test for "this host is that name or under it" is written three times

- Where: `crates/sites/src/video_sites.rs`, `on_site`; `crates/sites/src/local_network.rs`, `is_under`; `crates/queues/src/sites.rs`, `SitePattern::covers` with its `is_under`
- Category: duplicate
- Failure: the two functions in `crates/sites` have the same body, in one crate. Their callers have already drifted: `is_listed` and `is_local_by_itself` trim a trailing dot before asking and `video_site_for` does not, so `https://youtube.com./watch?v=x` is not read as a video page, while `https://wiki.corp.example.com./` counts as a listed site. A fix to one reaches only that one.
- Evidence: both bodies are `strip_suffix` then `rest.is_empty() || rest.ends_with('.')`. `crates/queues` spells the same test as `host == name || is_under(host, name)`, where its `is_under` also serves the `*.` rule. `docs/ENGINEERING.md` section 3 never accepts a third copy.
- Confidence: certain

### 10-5 [P3] A test races the machine against the 3-second limit of the code under test

- Where: `crates/sites/src/local_network.rs`, test `only_a_websites_link_into_the_local_network_is_refused`
- Category: fake test
- Failure: `refuses(ChosenBy::Website, "http://localhost/a")` does a real lookup under `CAPTURE_CHECK` (3 seconds). On a busy runner where the blocking lookup takes longer, `addresses` returns nothing, `refuses` answers false and the assertion fails with no fault in the code. The same test also sends `no-such-host.invalid` to the system resolver, and its answer is "not refused" whether the lookup failed, timed out or was never made, so that line does not show which of those happened.
- Evidence: `docs/ENGINEERING.md` section 7 forbids racing a time limit of the code under test ("drive the clock"). `refuses` takes no timeout and the test does not pause the clock. The `test-timing` check does not see it because no duration is written in the test.
- Confidence: likely
