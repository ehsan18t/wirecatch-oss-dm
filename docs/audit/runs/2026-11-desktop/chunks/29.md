## Findings

### 29-1 [P2] Uninstalling on Windows while the app runs leaves its program in Program Files

- Where: `crates/desktop/packaging/windows/installer.iss`, `[Setup]`, `[Files]` and `CurUninstallStepChanged`
- Category: bug
- Failure: the app is running (in the tray, or a browser holds a `wirecatch-bridge.exe` open) and the person uninstalls. Nothing stops those processes, so the in-use `.exe` files cannot be deleted. They and the install folder stay in Program Files after the uninstaller reports its end, and the app keeps running with its browser registration gone. Nothing removes them at the next restart either.
- Evidence: `CloseApplications=force` covers Setup only: the help says Setup closes programs using files "that need to be updated by the [Files] or [InstallDelete] section" through Restart Manager, and nothing about the uninstaller. The two uninstaller mechanisms are both absent: there is no `AppMutex` (and `crates/desktop/src/main.rs` creates no named mutex; a single copy is held by the endpoint and the database lock), and no `[Files]` entry has `uninsrestartdelete`, the flag the help gives for a file in use at uninstall time. There is no `[UninstallRun]`. `CurUninstallStepChanged` only runs the bridge's `uninstall` and `--remove-start-entry`, which acts and returns without touching a running copy (`crates/desktop/src/main.rs`). PACKAGING.md describes closing a running copy for the install only.
- Confidence: likely (from the script and Inno Setup's documentation; not run)

### 29-2 [P2] The AppImage's library folder leaks into every program the app starts

- Where: `scripts/package.mjs`, `appRun`
- Category: wrong implementation
- Failure: AppRun exports `LD_LIBRARY_PATH="$HERE/usr/lib..."` and execs the app, so everything the app starts inherits it: `xdg-open` for "Open file" and "Open folder" and therefore the person's viewer, player or file manager, yt-dlp, ffmpeg, and the replacement AppImage after an update. Those programs load `libxkbcommon`, `libxkbcommon-x11` and `libxcb-xkb` copied from the build machine instead of the system's. On a distribution with a newer libxkbcommon than the build machine's, a program needing a newer symbol stops with a symbol lookup error when opened from Wirecatch, yet starts normally from the desktop menu. D110.2 keeps every other library the system's because libraries must match the system; these three are forced on unrelated programs too.
- Evidence: `LD_LIBRARY_PATH` appears nowhere else in the repository (repository-wide search), so no spawn removes it; `crates/streams/src/process/run.rs` removes other variables only. `open_with_system` in `gpui-pre-linux` runs `xdg-open` through `new_std_command` with the environment inherited and only the graphical variables applied. `crates/desktop/src/files.rs`, `notices.rs`, `tray.rs` and `about.rs` call it. The update path in `crates/shell/src/updates.rs` and `crates/desktop/src/lifecycle.rs` spawn with the inherited environment as well.
- Confidence: likely (the leak is certain from the code; a visible failure needs a program using a symbol the bundled copy lacks; not run)

### 29-3 [P3] `--target aarch64-unknown-linux-gnu` on an x64 machine cannot work, though PACKAGING.md gives it as the example

- Where: `scripts/package.mjs`, `architecture`, `tool`, `linux`, `bundleLibraries`; `crates/desktop/PACKAGING.md`, "Building installers"
- Category: bug
- Failure: `node scripts/package.mjs --target aarch64-unknown-linux-gnu` on x64 Linux compiles (given a cross linker), then fails. `arch` comes from the target triple and also chooses which tool to download, so the arm64 `nfpm` is fetched and run on the x64 host, which stops with an exec format error. Past that, the arm64 `appimagetool` would have the same fault, and `bundleLibraries` runs the host's `ldd` and `dpkg-query` on a foreign binary. Only CI's native builds work, and those never pass `--target`.
- Evidence: `const arch = architecture(triple)`, then `tool('nfpm', arch)` and `run(join(nfpmDir, 'nfpm'), ...)`; the same `arch` indexes `LINUX_TOOLS`. PACKAGING.md: "`--target <triple>` picks another, such as `aarch64-unknown-linux-gnu`". `release.yml` runs `node scripts/package.mjs` with no option.
- Confidence: certain

### 29-4 [P3] ARM64 Linux packages are drafted without the fresh-system check

- Where: `.github/workflows/release.yml`, job `linux-packages`; `crates/desktop/PACKAGING.md`, "Releases and updates"
- Category: bug
- Failure: an ARM64 `.deb`, `.rpm` or AppImage that lacks a library or does not start, or whose removal leaves the bridge registered, still reaches the release draft, because `linux-packages` tests only x64. PACKAGING.md says the workflow "checks each Linux package on a fresh system", and the job's own comment says each package. The ARM64 build runs on another image (`ubuntu-24.04-arm`), and `LINUX_DEPENDS` and the bundled libraries are only ever proved on x64.
- Evidence: the job downloads the artifact `desktop-Linux-X64` only and `runs-on: ubuntu-latest`; `draft` uploads all of `release/*`, which holds `desktop-Linux-ARM64` too.
- Confidence: certain

### 29-5 [P3] The `.deb` and `.rpm` state no C library version, so they install where the app cannot start

- Where: `scripts/package.mjs`, `LINUX_DEPENDS`
- Category: wrong implementation
- Failure: on a distribution older than the build machine (for example Ubuntu 22.04 or Debian 12 with a package built on Ubuntu 24.04), the package manager installs the package without complaint, then the app fails at launch with a `GLIBC_x.y not found` message that a person starting it from the desktop menu never sees: nothing appears to happen. The package manager's job is to refuse this, and neither format is told to.
- Evidence: `LINUX_DEPENDS` names `libfontconfig1`, `libxcb1` and the like with no version and has no `libc6`/`glibc` entry; nfpm computes no dependencies. The other libraries have no minimum either. `scripts/ci/linux-package-check.sh` installs only on the same base as the build, so its "dependencies must cover every library" check cannot see it.
- Confidence: likely (which symbols the binary needs was not read from a built binary; none was built)

### 29-6 [P3] The icon holds its own copy of the mark's strokes, unchecked

- Where: `crates/desktop/assets/icons/icon.svg`
- Category: duplicate
- Failure: changing the mark in `packages/ui/src/mark.json` updates the title bar and the extension's `AppMark`, while the installer, tray, taskbar and Linux icons keep the old mark with no check failing. D108.3 says the icons are "rendered from the same file", but nothing renders them: the SVG's points and widths are typed in, and no script or gate check reads `icon.svg` or compares it with `mark.json`. The values match today.
- Evidence: the `polyline` points and stroke widths in `icon.svg` equal the `strokes` in `mark.json`; a search of `scripts/` finds neither `icon.svg` nor a reader of `mark.json`; the only reader in Rust is `crates/desktop/src/ui/mark.rs`. docs/ENGINEERING.md, section 1, gives data two packages need one file.
- Confidence: certain

## Suggestions

### 29-S1 Build the x64 Linux packages on a named, older base

- Today: x64 builds run on the moving `ubuntu-latest`, ARM64 on `ubuntu-24.04-arm`, and the check container is `ubuntu:24.04`. The AppImage needs the glibc of its build machine or newer, and that floor rises without a commit when `ubuntu-latest` moves.
- Better: name the image for both architectures, on the oldest base still supported, as AppImage's own guidance and established apps do, so the AppImage runs on more systems.
- Value: an AppImage that starts on older distributions, and a release whose requirements change only by a commit.
