# Chunk 28: failure-messages

## Files read

crates/core/src/error.rs
crates/core/tests/manager/ftp.rs
crates/messages/Cargo.toml
crates/messages/src/lib.rs

## Findings

### 28-1 [P2] "The part already downloaded is kept" is told for downloads that cannot resume

- Where: `crates/messages/src/lib.rs`, `describe` (arms `Stalled` and `PrematureEof`), `http_status` (the `Worked::Before` arm) and `stopped_unexpectedly`
- Category: wrong implementation
- Failure: a server with no range support, or one that sends no size, drops the connection or stalls at 90% of a large file. The person reads "Try again; the part already downloaded is kept." and presses Try again; the run starts from byte 0 and deletes the part and resume files.
- Evidence: the engine continues only with `ranged` on both sides and a known total, otherwise it starts over and deletes both files (contract 01, Resume: "Unknown size or no ranges never resumes"). None of these message functions gets anything saying whether the download can resume: `describe` takes only the error, the folder and `Worked`, and `Worked` says only that the link answered or that bytes exist. The promise is therefore made unconditionally.
- Confidence: certain

### 28-2 [P2] Replacing a file that another program has open blames the folder and offers the wrong fix

- Where: `crates/messages/src/lib.rs`, `disk_failure` (the `PermissionDenied` arm), reached from `describe` for `EngineError::Io`
- Category: wrong implementation
- Failure: a download answered with "Replace" whose existing file is open in a media player or viewer finishes, and the last rename fails. The person is told "Wirecatch is not allowed to save files in {folder}. Choose another folder." with the Change folder button. The folder is fine; the real fix is to close the program and try again, and that is neither said nor offered as the fix.
- Evidence: `crates/engine/src/storage.rs`, `Finish::Replace`, calls `std::fs::rename` with `IoAction::Finish`, and `crates/core/src/manager/run.rs` selects it for `OnExisting::Replace`. A small program on this machine (Windows 11, `rustc` standalone) renamed over a file held open without delete sharing and got `kind=PermissionDenied raw=Some(5)`, both with read-only sharing and with read and write sharing. `disk_failure` looks only at the kind; the `action` and `path` in `EngineError::Io` go only into the `what` text, which this arm does not use.
- Confidence: certain

### 28-3 [P2] Add-on installs and app updates tell the person to refresh a link they do not have

- Where: `crates/messages/src/lib.rs`, `describe`; callers `crates/core/src/manager/addons/install.rs` (the install download) and `crates/core/src/manager/app_update.rs` (the installer download)
- Category: wrong implementation
- Failure: a release asset answers 404: "yt-dlp could not be downloaded: The server says this file does not exist (error 404). Check the link, or refresh it with one copied from the page." An update says the same after "The update could not be downloaded:". There is no link, no page and no button. The same happens for 401, 403, too many redirects and a broken redirect. A refused size reads "The update could not be downloaded: the installer is not the size its list of files gives", which also ends without a full stop, against the house style the crate's tests hold.
- Evidence: both callers keep only `.message` of `describe(&e, ..., Worked::Never)` and drop `.fix`, while the words written into the message assume a download row with a Get a new link button. `describe`'s comment on `TargetRejected` ("Only the manager's own resolver refuses a file") is untrue: both of these callers set `resolve_path`, with reasons that are lower-case fragments (`fits` in `install.rs`, the size check in `app_update.rs`).
- Confidence: certain

### 28-4 [P2] A stream manifest over the size limit falls into the catch-all and offers a retry that cannot help

- Where: `crates/messages/src/lib.rs`, `describe` (the `other` arm, reached with `EngineError::TooLarge`); caller `crates/media/src/describe.rs`, `E::Request`
- Category: wrong implementation
- Failure: a captured or added stream link whose address answers with more than `MANIFEST_LIMIT` bytes, such as a link that no longer leads to a playlist, fails with "The download failed (https://host/path?token=... sent more than N bytes, more than expected for it; the link may not point to what was expected). Try again." and the Try again button. Trying again gets the same answer; the engine's own text says the link is the problem. The message also shows the whole address, with any query token, and a raw byte count.
- Evidence: `crates/streams/src/source.rs` calls `fetcher.get(..., MANIFEST_LIMIT)`; `Fetcher::get` returns `Error::TooLarge`; `map_engine` wraps it as `streams::Error::Request`; `media::describe` passes it to `wirecatch_messages::describe`, which has no `TooLarge` arm. `TooLarge` is an existing variant, so the catch-all's comment ("added to the engine after this was written") does not describe it. The neighbouring `E::Manifest` and `E::NotAStream` in `media::describe` offer `RefreshLink`. `InvalidOption` went through the same catch-all and was fixed one variant at a time (see the test `an_option_out_of_range_is_not_offered_a_retry`).
- Confidence: certain

### 28-5 [P3] `invalid_link` ignores its argument, and its doc and test claim something untrue

- Where: `crates/messages/src/lib.rs`, `invalid_link` and the test `a_saved_link_that_no_longer_parses_reads_as_one_refused_when_added`
- Category: no-op code, fake test
- Failure: the callers in `crates/core/src/manager/run.rs` and `media_run/mod.rs` format the parser's error with `e.to_string()` and pass it in; it is thrown away, since `describe`'s `InvalidUrl` arm ignores the text. The doc says the result uses "the same words a link refused when it was added gets", but a link refused when added gets `CoreError::InvalidUrl` ("\"x\" is not a valid link. Check that it starts with..."), other words from another crate. The test compares `invalid_link(x)` with the exact `describe` call `invalid_link` makes, so it cannot fail while that one line stands, and it never looks at the add-time words its name promises.
- Evidence: the `EngineError::InvalidUrl(_)` arm in `describe`; `parse_url` in `crates/core/src/manager/downloads.rs` for the add path; the body of the test.
- Confidence: certain
