## Findings

### 13-1 [P2] Blank lines of standard error count for nothing in the tail: memory is unbounded and a blank last line hides the reason

- Where: `crates/streams/src/process/tail.rs`, `StderrTail::push`, `StderrTail::error_line`; `crates/streams/src/process/run.rs`, `Ran::reason`
- Category: bug
- Failure: (a) A program that writes a long run of blank lines to standard error, for instance a message with many newlines passed on from a site, or a misbehaving tool that repeats them for as long as it runs: each `\n` becomes one `String` entry of about 24 bytes in the `VecDeque`, kept for the whole run, since nothing is dropped. There is no limit on the count. (b) A program that fails and ends standard error with a blank or whitespace-only line, after saying why on the lines before: `error_line` finds no `ERROR` and returns that blank line, `Ran::reason` filters it out and says `it gave no reason (exit code: 1)` although the tail holds the reason. ffmpeg's `FfmpegError::Failed` takes `ran.reason()` directly, and yt-dlp's `refusal` falls back to it.
- Evidence: `forward` sends an empty string for a blank line, and `run` calls `tail.push` on it. `push` adds `line.len()`, here 0, to `self.bytes` and pushes the entry; the only eviction is `while self.bytes > STDERR_TAIL_BYTES`, so entries of 0 bytes never cause one. `error_line` falls back to `self.lines.back()` unfiltered, while `summary` in the same file does filter out empty lines, so the two disagree. `docs/ENGINEERING.md` section 6 says the tail is kept bounded. No shipped tool is known to write endless blank lines, so (a) needs an unusual program or message; the fix for both is one check in `push` that skips a line with nothing in it.
- Confidence: certain for the code; likely for how often it is reached

### 13-2 [P3] A run whose outputs are held open loses all of its collected standard output, even when the program succeeded

- Where: `crates/streams/src/process/run.rs`, `run` (the grace branch), `Readers::abort`, `finish`, `collect`
- Category: wrong implementation
- Failure: On Unix, `RunOptions::collect()` with a program that exits with success but left a child outside its group holding standard output. After `OUTPUT_GRACE` the collecting task is aborted, its buffer goes with it, and `finish` returns `stdout: []`, `stdout_truncated: false`, success. For `extract_once` (`yt-dlp -J`) a complete JSON answer already read becomes `YtDlpError::BadOutput` from parsing an empty slice. The same happens on either system if the machine stalls for more than 2 seconds after the program ended, since the branch that fires is chosen at random among those ready.
- Evidence: `Readers::abort` calls `self.collected.abort()`; the bytes live in a local `Vec` of that task. `finish` maps the `JoinError` to `(Vec::new(), false)` and logs "what it wrote is lost". The comment in `collect` states the opposite aim for a failed read: what arrived is kept, "so a cut-off answer is not taken for a malformed one". The only test of this path, `a_child_that_left_the_group_does_not_hold_the_run`, runs in `RunOptions::lines()` and does not look at standard output. yt-dlp, ffmpeg and Deno are not known to detach a child on normal paths, hence the severity.
- Confidence: certain for the code; likely for the stall case

### 13-3 [P3] The test that a child outside the group does not hold the run passes without the grace

- Where: `crates/streams/tests/process.rs`, `a_child_that_left_the_group_does_not_hold_the_run`; `crates/streams/examples/fake_program.rs`, `LINGER`
- Category: fake test
- Failure: Remove `OUTPUT_GRACE` so the run reads until the outputs close: the detached `linger` child ends by itself after 60 seconds, the outputs close, the run returns success, and the test passes, because `run` in the test only fails after `PATIENCE` (120 seconds). The behaviour the name claims is not checked, on the only path that exercises the grace branch.
- Evidence: `LINGER` is 60 seconds and `PATIENCE` is `Duration::from_secs(120)`. The test asserts only `ran.success()`. Its sibling `what_a_program_leaves_running_ends_with_it` shows the way: it reads the log for "outputs stayed open". Here the test would assert that line is present, which only the grace branch writes. Unix only, so it runs on Linux CI and not on Windows.
- Confidence: certain

### 13-4 [P3] Two tests race the machine against a real-clock limit of the code under test

- Where: `crates/streams/tests/process.rs`, `a_stalled_program_keeps_what_it_wrote`, `what_a_program_leaves_running_ends_with_it`
- Category: fake test
- Failure: `a_stalled_program_keeps_what_it_wrote` runs on the real clock with a 300 ms idle limit that starts as soon as the program is spawned, and asserts the error holds the line the program writes. If the fake program takes more than 300 ms to start and write, which a busy CI runner or an antivirus scan of a new executable can cause, the run stalls with an empty tail, `error_line` is `None` and the test fails on correct code. `what_a_program_leaves_running_ends_with_it` asserts the log lacks "outputs stayed open", which holds only if the readers see the end of the outputs within the real 2 second `OUTPUT_GRACE`; a longer stall after the program ends fails it the same way.
- Evidence: Neither test has `start_paused`. The note on `SHORT` says only that a run expected to stop at the limit may take longer and still pass; this test also needs the program to have written first. `docs/ENGINEERING.md` section 7 forbids racing a limit of the code under test. The `test-timing` check does not catch either, since neither has a `Duration` in a wait or a measured time. `Stepped` in the same file already drives a paused clock for exactly this purpose.
- Confidence: certain for the race; likely for it failing on a loaded runner

### 13-5 [P3] Two copies of cutting text at a character boundary, and the no-reason wording written twice

- Where: `crates/streams/src/process/run.rs`, `cut`, `Ran::reason`; `crates/streams/src/process/tail.rs`, `cut_bytes`; `crates/streams/src/process/mod.rs`, `NO_REASON`
- Category: duplicate
- Failure: `cut(line)` is `cut_bytes(line, MAX_LINE)` written out again, in two files of one small module; each is unit tested separately. `Ran::reason` writes `"it gave no reason ({status})"` by hand beside `NO_REASON`, so a change of wording must be made in two places. The same loop also appears in `crates/files/src/zone.rs` and twice in `crates/engine/src/naming.rs`.
- Evidence: Both functions take the minimum of the length and the limit, walk back with `is_char_boundary` and copy the slice. `tail` is already imported by `run.rs`.
- Confidence: certain

## Suggestions

### 13-S1 Bound the wait after killing a program

- Today: every stopped run ends with `child.kill().await`, which waits without limit for the process to be gone. A process stuck in the kernel cannot die until the call returns, and `STALL_TIMEOUT` names a hung encoder driver as a reason for a stall, so in that rare case the run that was stopped for hanging hangs too, and so does the cancel a person asked for.
- Better: wait for the end under a named limit, then log it and return the error, leaving the process to tokio's own reaping. The group has already been sent its kill by then.
- Value: a download stuck on a broken driver can still be cancelled and frees its place in the queue.
