## Findings

### 25-1 [P1] A space cannot be typed in the main search field, and pressing it pauses or resumes the selected downloads

- Where: `crates/desktop/src/main_window/keymap.rs`, `shortcuts` (`on("space", PauseOrResume)`), and `crates/desktop/src/main_window/mod.rs`, `list_keys`
- Category: bug
- Failure: focus in the search field on the downloads screen, with or without a selection. Type `some file` and press Space. The field gets no space. If rows are selected, they are paused, or resumed if none can pause. Searching for a name with a space cannot be done by typing, and a keystroke meant for text changes downloads.
- Evidence: the binding's context is `MainWindow`, on the root `div` that also holds the search `Input`, and `KeyBindingContextPredicate::depth_of` matches at any depth of the path, so it applies with the field focused. The comment on `KEY_CONTEXT` says "a text field's own keys come first", but the input's table in `gpui-base` `input/base/state.rs` has no `space`, so nothing deeper wins. `Window::dispatch_key_event` dispatches bindings unless `input_preference` is `CharacterInput`, which needs `prefer_character_input`. `gpui-pre-windows` `process_key` returns `(key_char, false)` for a key with no modifier (true only for a dead key), and the X11 and Wayland clients always send `false`. `list_keys` handles `PauseOrResume` while the downloads show, so the action counts as handled, `dispatch_key_event` returns, and `handle_keydown_msg` answers handled, so no character is produced. Dialogs are not affected, as they sit beside the window's view under `Root`. Not run: read from the code, since no built app was at hand; stage 2 should prove it with a keystroke test on the search field.
- Confidence: likely

### 25-2 [P1] "Try again" on the could-not-save banner saves nothing and hides the problem

- Where: `crates/desktop/src/main_window/notices_bar.rs`, `storage_banner`; `crates/core/src/manager/preferences.rs`, `apply_settings`
- Category: broken feature
- Failure: the database fails a save, and the banner says recent changes may be lost when the app closes. The person frees the disk and presses Try again. The banner goes away and no save is attempted, so the person is told nothing while the changes are still unsaved. If nothing else saves later, those changes are lost at close with no warning left on screen.
- Evidence: the button clears `storage_problem`, then calls `api::change_settings(manager, AppSettingsPatch::default())`, under the comment "An empty change goes through the save like any other". An empty patch applies to a clone of the settings, so `apply_settings` finds `state.settings == new` and returns on its first line, before `store.save_settings`. No store call happens, so the failure handler cannot fire again to bring the banner back. Even where a save ran, it would be the settings, not the download rows the banner is about.
- Confidence: certain

### 25-3 [P2] Cancel on a selection holding a finished download stops at it, and later downloads keep running

- Where: `crates/desktop/src/main_window/confirm.rs`, `cancel`; `crates/desktop/src/main_window/row_menu.rs`, `ending`
- Category: bug
- Failure: select a finished download and a running one that comes after it in the library's order, right-click, choose Cancel and confirm. The question says "Cancel 2 downloads?". An error says the download has already finished, and the running one is not cancelled.
- Evidence: `ending` offers Cancel when any row `can_cancel` but passes every id, finished ones included. `Asked::read` keeps them, in library order. The command is `ids.iter().try_for_each(|id| api::cancel(&manager, *id))`, and `Manager::cancel` returns `WrongState` for `Completed`, which ends the loop. `selection::each`, used by every other selection command, filters with `takes` and keeps going past a refusal. The title's count also includes rows that cannot be cancelled.
- Confidence: certain

### 25-4 [P2] Dragging moves rows the selection no longer shows, is refused over removed rows, and shuffles their order

- Where: `crates/desktop/src/main_window/drag.rs`, `dragged_rows`; `crates/desktop/src/main_window/mod.rs` (`selected`, never pruned); `crates/desktop/src/main_window/queue_header.rs`, `nudge`
- Category: wrong implementation
- Failure: three ways, all from dragging the raw `self.selected`:
  1. Select three rows, type a search that leaves one, then drag it to another queue. All three move, and any running one restarts. The bar says "1 selected" and the pointer says "3 downloads". The same happens for rows that left a status page after changing state, or that sit in a group folded after selecting; a heading's circle on a folded group also ticks rows the bar does not count. Alt+Up and Alt+Down (`nudge`) move hidden rows the same way.
  2. Ctrl+click two rows, press Delete and confirm, then Ctrl+click two others and drag one to a queue. `selected` still holds the removed ids, so `move_to_queue` answers `DownloadNotFound` and nothing moves. The pointer says "4 downloads". While such ids stay and `picked` is true, `shows_circle` also shows every row's circle with nothing selected.
  3. A drag of several rows from one queue to another lands them in `HashSet` order, not list order, since `move_to_queue` gives each the next position in the order it receives. The selection bar, the row menu and the palette pass list order.
- Evidence: `dragged_rows` is `self.selected.iter().copied().collect()` with `self.selected.len()` for its label, where the other commands go through `selected_rows`, which filters to what is shown and orders it. `search` changes only `cx.notify()`, the library observer does not touch `selected`, and only `show`, `pick`, `clear_selection`, `select_all` and a range replace it. `Manager::move_to_queue` documents that an unknown id moves nothing.
- Confidence: certain

### 25-5 [P2] A download moved to another queue shows at the wrong place in that queue's numbered line

- Where: `crates/desktop/src/main_window/list.rs`, `queue_line` and `lines`; `crates/desktop/src/library.rs`, `apply`
- Category: wrong implementation
- Failure: queue A (first) holds `x`, queue B holds `y`. Move `x` to B. The manager puts it last, so `y` runs first, but B's view shows `1 x`, `2 y`. The list's numbers, documented as "the order it runs", stay wrong until the next start or a reorder in that queue. A later Alt+Up or drag then sends this wrong line as the new order.
- Evidence: `queue_line` filters `library.downloads` in its own order, which `list_downloads` sorts by queue and position only at load. `DownloadsChanged` replaces a known row in place, and `DownloadSummary` carries no position. `order::apply` says "the list, which no event tells" and fixes up only a reorder. `Manager::move_to_queue` and queue deletion assign a new position. Up next in All downloads, which also uses library order, is likewise out of date after a move or `set_queue_order`.
- Confidence: certain

### 25-6 [P2] Every frame recomputes the whole list several times, quadratically for a large selection

- Where: `crates/desktop/src/main_window/selection.rs`, `selected_rows`, `shown_ids`, `selection_bar`, `every_circle`; `crates/desktop/src/main_window/list.rs`, `lines`, `members`; `crates/desktop/src/main_window/sort.rs`, `compare`
- Category: inefficiency
- Failure: with a long list, each redraw (each progress tick, each row the pointer crosses) does list-sized work several times: `render` calls `lines` through `list`, `selected_rows` and `every_circle`, and each visible heading calls `members` again. Two cases are slow on their own. After Ctrl+A, `selected_rows` runs a linear `find` per selected row. Sorted by Name, every `lines` sorts every group with two `to_lowercase` allocations per comparison. `dragged_rows` also copies the selection for each visible row.
- Evidence: a bench of those two operations with `rustc -O` on one core, once per call: `selected_rows` shape took 8.8 ms at 5,000 rows and 33 ms at 10,000; the Name sort took 7.3 ms at 5,000 and 16 ms at 10,000. At 3 or more `lines` calls per frame, the Name sort alone passes a 16.7 ms frame at 5,000 rows, on the UI thread, while downloads run. The bench is a copy of the shape, not the app itself. `docs/ENGINEERING.md` section 10 asks for no work proportional to the list on a progress update. `Frozen` caches only the live sort keys.
- Confidence: likely

## Suggestions

### 25-S1 Copy link gives a link that works

- Today: `Entry::summary` hides a link's password in `row.url` for display, and every Copy (row line, menu, details) copies that, so `ftp://user:pass@host/file` copies as `ftp://user:***@host/file`, which the server refuses. `text::link_for_display` then masks the already masked link a second time. No decision records the copy as deliberate.
- Better: copy the full link through a call to the manager when the person asks for it, or say in the toast that the password was left out. Display keeps the mask, and `link_for_display` can go for rows.
- Value: a copied link does what the button implies, and the person knows when it will not.

### 25-S2 The palette offers Cancel

- Today: `palette.rs` says "every command the window offers", and the row menu has Cancel, but `selected_commands` does not.
- Better: add it, using `confirm::cancel` once 25-3 is fixed.
- Value: a keyboard user can cancel a download without the menu key.
