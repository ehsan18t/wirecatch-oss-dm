## Findings

### 22-1 [P2] A quit past its time limit does not exit: dropping the runtime waits for stuck file work

- Where: `crates/shell/src/quit.rs` (`quit_sequence`, `QUIT_PATIENCE`), `crates/desktop/src/backend.rs` (`Backend::stop`, the `runtime` field), `crates/desktop/src/lifecycle.rs` (`quit`)
- Category: bug
- Failure: a blocking file task is stuck when the person quits (a write to a network share or failing disk that does not return, through `engine/src/writer.rs` and `FileWork`). `Manager::shutdown` waits for it without limit, `quit_sequence` logs "exiting anyway" after 15 s, and the process does not exit: the windows and tray icon are gone, and it stays until the blocking call returns. Until then the database lock stays held, because `store.close` is after the wait in `shutdown` and `Core` drops only after the runtime. A new launch gets the endpoint (the listener task is dropped when the runtime shuts down), fails `Manager::open` with `AlreadyOpen` after `LOCK_WAIT`, says "Wirecatch is already running, look for its icon in the tray", and closes, with no window or tray icon anywhere to go to. The `OPEN_PATIENCE` path has the same shape while `prepare` or `Manager::open` holds a blocking thread.
- Evidence: `quit_core` is called with `|| ()` as `exit` (`Backend::stop`), so nothing ends the process at the limit. `lifecycle::quit` then calls `cx.quit()`. On Windows `PostQuitMessage` ends the loop in `Platform::run`, the quit callback runs `App::shutdown`, which clears windows but not globals, and `Application::run` returns. Only `Application.0` and the launch closure hold a strong `Rc<AppCell>` (every platform callback and `AsyncApp` hold a `Weak`), and GPUI's own doc says the state is kept alive by that stack frame. So the `App` drops with its globals, including `Backend`, whose `tokio::runtime::Runtime` drop blocks until all `spawn_blocking` work ends (tokio documents that this can take an indefinite time). No `shutdown_timeout`, `shutdown_background` or `process::exit` exists on this path. Contract 04 records that `exited` has no limit if file work hangs, and that the shell relies on `QUIT_PATIENCE` as the backstop.
- Confidence: likely (read from the code of GPUI and the documented behaviour of tokio; not run)

### 22-2 [P2] `ftpes://` links from a command line reach an Add dialog that cannot read them; no window of the app can add one

- Where: `crates/shell/src/launch.rs` (`LINK_SCHEMES`), `crates/desktop/src/links.rs` (`LINK`), `crates/desktop/src/add_dialog.rs` (`urls`, hint text)
- Category: broken feature
- Failure: `wirecatch-app ftpes://files.example.com/x` opens the Add dialog holding the link (the case the launch tests accept). The dialog reads its field with `links::extract`, finds no link, says "One line has no link in it and is left out" and has nothing to start. The same happens when an `ftpes://` link is pasted in the dialog, the command bar, the clipboard path or the refresh dialog. The engine, the CLI and core's link check all accept `ftpes://` (`crates/engine/src/url.rs`, the invalid link message in `crates/core/src/error.rs`, the docs in `crates/engine/src/lib.rs`).
- Evidence: the regex is `(?i)\b(?:https?|ftps?)://...`, which cannot match `ftpes://`. `LINK_SCHEMES` is a separately written list with five schemes, and the two have drifted. No test in `links.rs` uses `ftpes`.
- Confidence: certain

### 22-3 [P2] A launch handed over while the running copy's list is still opening fails: a background start pops up a modal box, and links are lost

- Where: `crates/desktop/src/main.rs` (the `AlreadyInUse` arm), `crates/shell/src/launch.rs` (`hand_over_on`, `ANSWER_WAIT`), `crates/desktop/src/backend.rs` (`serve`)
- Category: wrong implementation
- Failure: copy A has the endpoint and its manager takes over 5 s to open (a cold disk at sign-in, a large list, a damaged list being repaired, a data folder being moved). `serve` starts accepting only after `core.opened()`, so copy B's hello goes unanswered until `ANSWER_WAIT` (5 s) and ends in `HandOverError::Timeout`. Then:
  - B started with `--background` (the sign-in entry, or the bridge, when both start at sign-in) shows the modal "Wirecatch is already running for you, so this copy will close" although the person launched nothing and the launch asked for nothing visible. The same box appears when the hello is refused by a copy whose list failed to open (`serve_unavailable` answers it with `AppUnavailable`).
  - B started with links drops them: the person gets the box, and the links never reach the dialog of the window that is already showing.
- Evidence: `hand_over_on` always does the hello first, and `Launch::call` returning `None` is reached only after it. `main.rs` calls `say_already_running` on any error without looking at `launch.shows_window()`. D103.2 says "nothing for `--background` alone" and D103.4 says a failed hand-over shows the box, so the decision did not cover a launch with nothing to hand over; the failure above is the cost.
- Confidence: certain for the code path; likely for how often the 5 s is passed

### 22-4 [P2] A command-line argument that is not valid Unicode aborts the app at start

- Where: `crates/desktop/src/main.rs` (`main`)
- Category: bug
- Failure: `wirecatch-app` with one non-UTF-8 argument (on Linux, any byte string such as a Latin-1 file name; on Windows, an unpaired surrogate) panics, and the release profile aborts (`panic = "abort"`), with no message shown since the release build has no console. `links_from_args` documents that "anything else on the command line is ignored".
- Evidence: `std::env::args().collect()` is the only read; the standard library documents that `args()` panics on such an argument. `docs/ENGINEERING.md` section 4 rules out panics on data from outside the process. A running copy is not affected, only this launch.
- Confidence: certain

### 22-5 [P3] A failed browser registration logs no reason

- Where: `crates/shell/src/bridge.rs` (`run_bridge`, `BridgeError::Failed`), `crates/bridge/src/install/mod.rs` (`run`, `print_report`)
- Category: bug
- Failure: an item of `wirecatch-bridge install` fails (a registry key refused, a manifest not writable), it exits 1, and the app's log says only `... install failed (exit code: 1): ` with nothing after it. The reason is also absent from the bridge's own log. The person who reports "the extension cannot find the app" leaves no trace of why.
- Evidence: `Report::fail` lines go only to stdout through `print_report`; `run` logs nothing about them. `run_bridge` captures both streams and reports only `output.stderr`. `run_bridge`'s `subcommand` has only one caller value, `"install"`.
- Confidence: certain

### 22-6 [P3] The autostart `Exec` line escapes reserved characters once, so a path with `$`, a backtick, `"` or `\` gives an entry desktops reject

- Where: `crates/shell/src/autostart.rs` (`exec_word`, and its test `a_program_path_stays_one_word_of_the_exec_line`)
- Category: wrong implementation
- Failure: on Linux an AppImage at `/home/a/Wire$cat.AppImage` with start at sign-in on writes `Exec="/home/a/Wire\$cat.AppImage" --background`. The Desktop Entry Specification applies the string escape rule before the quoting rule, so the quoted form needs `\\$` in the file. GLib's key file parser treats `\$` as an invalid escape, so the entry would not start on desktops that read it through GLib. The setting stays on and nothing says it failed.
- Evidence: `exec_word` pushes one backslash before these characters; the test asserts that single-backslash form, so it fixes the wrong output in place. The path must hold one of these characters, so it is rare.
- Confidence: likely (read from the specification; Linux not run)

### 22-7 [P3] `quit_core` and `quit_sequence` take an `Option` and an `exit` that nothing uses

## Suggestions

### 22-S1 Stop downloads at sign-out and system shutdown

- Today: the app registers no `on_app_quit`. On Windows, `WM_ENDSESSION` makes GPUI run `App::shutdown` and then `process::exit(0)`, so downloads end as in a crash, and SIGTERM on Linux does the same. The restore path recovers them, with up to 2 s of each row's counter lost.
- Better: on session end, ask every download to stop and flush what fits in GPUI's 200 ms `SHUTDOWN_TIMEOUT`, and handle SIGTERM on Linux through `lifecycle::quit`. Established download managers treat a system shutdown as a normal stop.
- Value: a clean stop at the most common way a day ends, instead of relying on crash recovery every time.

### 22-S2 Let a second launch bring up the window of a copy whose list failed to open

- Today: `serve_unavailable` refuses the hello, so `ShowWindow` is never sent. After the person closes the error window, the app stays in the tray (`keeps_running` treats settings `None` as "on"), and starting Wirecatch again only shows "already running".
- Better: answer `show_window` in that state, or quit when the main window closes on a copy that has no list.
- Value: the message "Restart Wirecatch" can be followed from the Start menu without finding the tray's Quit first.
