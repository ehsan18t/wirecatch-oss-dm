## Findings

### 01-1 [P2] Running the same request again starts over when the first run took a numbered name

- Where: `crates/engine/src/target.rs`, `plan_in_folder`; `crates/engine/src/naming.rs`, `create_free_part`
- Category: bug
- Failure: `report.pdf` is already in the folder, so a download into that folder takes `report (1).pdf`, and is then paused (Ctrl+C in the CLI). Running the same request again looks only at `report.pdf.wcstate`, finds none, and goes to `create_free_part`, which passes over `report (1).pdf` because its resume file is there. The second run starts from zero as `report (2).pdf`. `report (1).pdf.wcpart` and its resume file stay in the folder for good, holding the data already downloaded. The same happens when a file appears at the preferred name between the runs: `!preferred.file.exists()` is false, so the paused `f.bin.wcpart` is left behind and the run starts as `f (1).bin`.
- Evidence: `plan_in_folder` only ever builds `preferred` from `dir.join(&name)` and never tries a numbered name. `lib.rs` and `Outcome::Paused` promise that running the same request again continues, and the CLI prints "Run the same command again to continue." Tests cover only a resume under the preferred name (`resumes_after_pause_without_downloading_again`) and a file saved during the second run (`a_continued_download_never_replaces_a_file_saved_meanwhile`). The app is not affected: core, add-ons and app updates all use `exact_path` or `resolve_path`, so this reaches the CLI and the engine's public API.
- Confidence: certain

### 01-2 [P2] A second running download of one link into one folder takes over the first one's files

- Where: `crates/engine/src/target.rs`, `plan_in_folder`
- Category: bug
- Failure: two runs of one link into one folder at once, for example two `wirecatch <link>` commands. `plan_in_folder` trusts a resume file with the same URL without knowing whether its download is still running.
  - Server without ranges or size: the first run's resume file cannot continue, so the second deletes the first's part file and creates its own under the same name. The first run keeps writing to the deleted file. When it ends, `finalize` opens the second run's part file, sets it to full length, renames it to the final name and reports `Completed`, while that file holds only what the second run has written so far, the rest zeros. If the second run stops early the final file stays corrupt under a run that reported success. If it carries on, its `finalize` fails with the part file missing.
  - Server with ranges and size: the second run resumes on the first's part file and resume file. The bytes stay correct, but once the first finishes the second's checkpoints put a resume file back next to the finished file, and its own finish fails.
- Evidence: `create_free_part` and D30.7 say downloads racing for a name each get their own, but that path is reached only when the URLs differ (`same_download`). Nothing marks a part file as in use. `downloads_of_one_name_in_one_folder_never_share_a_file` uses two different URLs. The app is not affected, for the reason in 01-1.
- Confidence: likely (the path follows from the code; not run)

### 01-3 [P2] A file too large for the disk is not noticed until the disk is full

- Where: `crates/engine/src/storage.rs`, `reserve`
- Category: wrong implementation
- Failure: a 100 GB download onto a volume with 10 GB free. On Linux `fallocate` answers `ENOSPC`, and `linux::fallocate(file, len).or_else(|_| file.set_len(len))` discards that for a sparse `set_len`, which succeeds. On NTFS `set_sparse` plus `set_len` allocates nothing at all. Either way the download starts, uses 10 GB of bandwidth, fills the disk (which other programs also need) and only then fails.
- Evidence: `or_else(|_| ...)` treats every `fallocate` error alike, though only "not supported" should fall back. `README.md` ("Space is reserved up front") and the module doc ("reserves `total` bytes") promise a reservation. No code in `crates/` asks a volume for its free space (no `GetDiskFreeSpace`, `statvfs` or similar). Not checked by a run: it needs a small volume, which `fault-tests` records as a person's call.
- Confidence: certain for the code; the Windows behaviour is how sparse files work and was not run

### 01-4 [P2] A resume file is rewritten and flushed every second even when nothing changed

- Where: `crates/engine/src/checkpoint.rs`, `ResumeSaver::save`
- Category: inefficiency
- Failure: a download waiting out a `Retry-After` of up to five minutes, stalled, or on a slow link. `flushed` moves only when a whole buffer (1 MiB by default) has been written, so at 100 KB/s a connection changes the ranges about once in 10 seconds. Every second `save` still flushes the part file, creates and flushes `.wcstate.tmp` and renames it over an identical file: thousands of journal commits an hour per download, which keeps a hard disk from sleeping and adds writes on an SSD for no gain in what can be recovered.
- Evidence: `save` reads `remaining` and always writes; nothing keeps the last saved ranges to compare. D30.1 accepted one flush per interval for a download that makes progress, measuring the cost in time; it does not cover saves with nothing new. Comparing `remaining` with the last save, inside `Saving`, keeps every guarantee.
- Confidence: certain

### 01-5 [P2] A failed write takes more back from the progress count than was ever added

- Where: `crates/engine/src/worker.rs`, `stream`; `crates/engine/src/writer.rs`, `Writer::push`, `Writer::wait`
- Category: bug
- Failure: a write fails while `push` waits for it. `push` has already added the current chunk to `unwritten`, and `wait` moves all of `unwritten` into `dropped`. `stream` breaks out on the `Err` before `shared.progress.add(allowed)`, then calls `take_back(take_dropped())`. The current chunk is subtracted without having been added, so `Progress::done` stays below the true count by one network chunk for the rest of the run, and a file finished by the other connections never reaches its total in the progress count.
- Evidence: order of the calls in `stream`. The unit test `a_failed_write_is_never_covered_by_the_next_one` asserts 8 dropped bytes, including the `BBBB` whose `push` failed, so it holds the wrong count in place: it checks the writer alone and never the pair of `add` and `take_back`.
- Confidence: certain

### 01-6 [P2] A paused download of unknown size reports about 16 EiB left

- Where: `crates/engine/src/download.rs`, `finish`; `crates/engine/src/segment.rs`, `remaining_bytes`
- Category: bug
- Failure: pause a download whose server sent no size. `remaining_bytes` is `UNKNOWN_END - flushed`, close to `u64::MAX`, and goes out as `Outcome::Paused { remaining }`, documented as "Bytes still to download". The CLI prints "Paused with 16.0 EiB left for ...".
- Evidence: `SegmentTable::new(None, ..)` sets `end` to `UNKNOWN_END`; `finish` passes the sum on unchanged; `crates/cli/src/main.rs` formats it with `HumanBytes`. `remaining` is a plain `u64`, so it cannot say "unknown" as it stands.
- Confidence: certain

### 01-7 [P2] `filename*` in another charset gives a damaged name, and beats a good plain `filename`

- Where: `crates/engine/src/naming.rs`, `from_content_disposition`
- Category: wrong implementation
- Failure: `attachment; filename="cafe.pdf"; filename*=ISO-8859-1''caf%E9.pdf`. The charset is thrown away and the bytes are decoded as UTF-8 with replacement, so the file is saved as `caf<U+FFFD>.pdf`, and the good plain name is ignored because `filename*` returns at once.
- Evidence: `val.splitn(3, '\'').nth(2)` skips the charset, then `decode_utf8_lossy`. The function's doc cites RFC 5987, which defines ISO-8859-1 as well as UTF-8 for this field. A value that is not valid in its charset should fall back to `filename`.
- Confidence: certain

### 01-8 [P2] A resume file's temporary file can be left in the download folder for good

- Where: `crates/engine/src/state.rs`, `ResumeState::save`; `crates/core/src/naming.rs`, `partial_files`
- Category: bug
- Failure: a save fails at `write_all` or `sync_data` (disk full), or the process dies between `File::create` and the rename, which happens once a second and includes a flush. `<name>.wcstate.tmp` stays. A later successful save uses it up, but when the person instead removes or cancels the download (the natural step after a full disk) it stays in their Downloads folder forever. Moving a download to another folder leaves it behind in the same way.
- Evidence: the closure in `save` removes the temporary file only on the abandoned path, not on an error. The engine's name for it is a private detail of `save`: core's `partial_files` returns only the part and resume paths from `naming::part_paths`, and `delete_files` removes those. `a_dropped_download_never_writes_its_resume_file_again` in `tests/download.rs` knows the name but only waits for it to go.
- Confidence: certain

### 01-9 [P3] Two test helpers wait for progress with no deadline

- Where: `crates/engine/tests/download.rs`, `pause_midway`, `another_program_saves_meanwhile`
- Category: fake test
- Failure: the download under test fails before reaching `at_least` bytes. `while progress.done() < at_least` then loops forever, since nothing looks at the task, and the test run hangs instead of failing with the download's error. About ten tests go through these two helpers.
- Evidence: neither loop has a deadline, and neither checks `task.is_finished()`. Other tests in the same file bound the same wait with `PATIENCE`. `docs/ENGINEERING.md` section 7: "A test that can hang forever is a bug." The `test-timing` check does not see this form.
- Confidence: certain

### 01-10 [P3] The option tests give a wait that has to succeed a fixed 10 seconds

- Where: `crates/engine/tests/options.rs`, `within_deadline`, `DEADLINE`
- Category: fake test
- Failure: on a busy machine the wait can run out on a correct engine. Before `validate` runs, `download` builds the HTTP clients, and the first time in a process that reads the system's certificate store on the blocking pool (`Clients::new`), so the time is not bounded by the check being tested. The test then fails with "hung the download".
- Evidence: `finished.recv_timeout(DEADLINE)` with `DEADLINE = 10 s`; `docs/ENGINEERING.md` section 7 bounds such a wait by `PATIENCE`. The `test-timing` check catches `timeout(Duration::..)` and misses `recv_timeout` with a named constant, so the check is too weak for this form.
- Confidence: likely

## Suggestions

None. The range splitting, flush order, resume decision, cancellation and step-back logic held up under review: `claimed`, `flushed` and `end` stay ordered on every path read, a retry always restarts from a fully flushed offset because write errors are not retryable (`Error::is_retryable`), and a failed write cannot be counted as done (`mark_flushed`).
