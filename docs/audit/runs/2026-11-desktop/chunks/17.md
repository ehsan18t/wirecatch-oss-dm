## Findings

### 17-1 [P1] A new media download takes over parts another download left in the same work folder

- Where: `crates/core/src/manager/media_run/workdir.rs`, `Downloaded::read`; `media_run/page.rs`, `page_attempt` and `fetch_part`; `manager/downloads.rs`, `insert`
- Category: bug
- Failure: a `<name>.wcmedia` folder holds `downloaded.json` and parts from an earlier download that is no longer in the list (left by 17-2, by a list set aside on repair, or by a folder `discard::dir` could not delete). A new page download of a different video is given the same planned path, for example the same typed name in the same folder. Its run finds the list, skips reading the page and downloading, and saves the earlier video as this download. With the setting Replace it overwrites the file in the folder with the wrong video. The row shows Completed with nothing to tell the person.
- Evidence: `insert` uses `naming::unclaimed_path` for `Kind::Media`, which looks only at claims, and `is_free_on_disk` does not look at work folders, so the folder does not move the new download to another name. `Downloaded` and the `<role>.done` markers record no link and `Downloaded::read` and `fetch_part` compare none. `PLACING` was given a link digest for exactly this case (`waiting_to_place`, test `a_waiting_file_belongs_to_its_link`), so one of the three leftovers in the folder is guarded and two are not.
- Confidence: likely

### 17-2 [P2] Answering Replace when the file's extension differs from the planned name downloads everything again and leaves the old work folder behind

- Where: `crates/core/src/manager/media_run/placement.rs`, `place`; `crates/core/src/manager/file_exists.rs`, `replace_at`; `media_run/mod.rs`, `run`
- Category: bug
- Failure: the person types `clip` in the quality window (the field holds no extension, its placeholder is the title), or yt-dlp's fallback saves another container, and `clip.mp4` is already in the folder under the default setting Ask. `place` asks about `clip.mp4`, and the finished file waits in `clip.wcmedia`. On Replace, `replace_at` sets the row's path to `clip.mp4`. The next run works in `clip.mp4.wcmedia`, which does not exist, so `waiting_to_place` and `Downloaded::read` find nothing: the page is read again, the video downloaded and converted again. `clip.wcmedia`, with the whole finished file and its parts, stays on disk for good, because `Entry::partial_paths` is derived from the new path. It then feeds 17-1.
- Evidence: `Placed::Asks` carries `wanted` (from `final_path`), not `planned`. `settle_at` writes that into `row.path`. `Job::output` is `entry.path()`, and `work_dir` is derived from it in `run`, `run_stream` and `page_attempt`. The only test of the flow, `a_stream_whose_name_is_taken_asks_and_then_replaces`, uses a name whose extension matches, so the paths stay equal. KeepBoth keeps the path and is not affected.
- Confidence: certain

### 17-3 [P2] A typed file name containing a dot loses the words after its last dot

- Where: `crates/core/src/manager/media_run/placement.rs`, `final_path`; `manager/media.rs`, `insert_chosen`
- Category: bug
- Failure: the person types `Dr. Who` or `Episode 1.5 - Finale` as the name. The finished file is `Dr.mp4` or `Episode 1.mp4`. Two typed names `Part 1.5` and `Part 1.7` collide on `Part 1.mp4`.
- Evidence: `insert_chosen` says "A typed name keeps its words; the finished file gets the extension of the format it is in", and the form sends the typed text as it is (`media_form.rs`). `final_path` compares the file's own extension with whatever follows the last dot of the planned name and calls `planned.with_extension(ext)`, which replaces that text. Only names made by `wirecatch_media::file_name` always end in a real extension; no test uses a typed name with a dot that is not an extension.
- Confidence: certain

### 17-4 [P2] Speed limits do not apply when yt-dlp downloads a format itself

- Where: `crates/core/src/manager/media_run/page.rs`, `page_attempt`; `crates/media/src/ytdlp/download.rs`, `download_args`; `ytdlp::Context`
- Category: broken feature
- Failure: an app or queue speed limit is set, and a video uses a format Wirecatch cannot fetch (`Transport::YtDlp`: DASH and others), or a failed row is retried (`record_media_failure` stores no format, so `wanted` is empty and yt-dlp always downloads). yt-dlp downloads at full speed, using the bandwidth the person limited, while the row sits in the limited queue.
- Evidence: `options.rate_limiters` from `RunPolicy` reach only engine and stream parts. `Context` has no limit field and `download_args` passes no `--limit-rate`. `docs/DECISIONS.md` and `docs/ROADMAP.md` record no such exception; `network.rs` records the local network exception for this fallback, and nothing does so for speed.
- Confidence: certain

### 17-5 [P2] An HLS format whose address is refused fails at once instead of reading the page again

### 17-6 [P2] An HLS part of a page video runs outside the run's file work

- Where: `crates/core/src/manager/media_run/page.rs`, `fetch_part`
- Category: bug
- Failure: a page video's HLS part is still decrypting or writing when `stop_run` aborts the task after `stop_timeout` (a slow disk, a Remove or Cancel). `RunGuard` waits only on `Job::file_work`, so the run reports `exited` while that blocking work goes on. The deletion of the work folder, or the next run on the same path, then meets a write still under way, the case `FileWork` exists to prevent (contract 01, Cancelling and dropping).
- Evidence: the engine branch sets `request.file_work = job.file_work.clone()`, and `stream_request` does the same for a stream job. The HLS branch of `fetch_part` builds `StreamRequest::new` and never sets it, so it keeps the fresh `FileWork` from `StreamRequest::new`, and `wirecatch-streams` runs its blocking work on that one.
- Confidence: certain

## Suggestions

### 17-S1 Replace a video's subtitle files when the video is replaced

- Today: subtitle files are always placed under Keep both, so replacing `clip.mp4` leaves the old `clip.en.srt` beside the new video and adds `clip.en (1).srt`, a name players do not pair with it.
- Better: follow the answer given for the video when the file is replaced.
- Value: the subtitles a player opens belong to the video in the folder.

### 17-S2 Stop the other part as soon as one part fails for good

- Today: `fetch_parts` waits on `join_all`, so a video part that fails (a full disk, a refused address) is reported, or refreshed, only after the audio part finishes, and the reverse for a large video.
- Better: on a `PageError::Failed` cancel a child token for the sibling, keeping what it wrote.
- Value: the person hears of a failure when it happens, and a refresh of a refused address starts sooner.
