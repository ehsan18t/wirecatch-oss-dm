## Findings

### 24-1 [P2] Install and download loses the person's choice when anything in the list changes before the install starts

- Where: `crates/desktop/src/download_windows/media_form.rs`, `MediaForm::addon_moved` and `install_then`
- Category: bug
- Failure: a quality that needs ffmpeg, the add-on not installed, and another download running. The person presses "Install and download". The next library change that arrives before the core's first `AddonsChanged(Installing)`, such as that other download's progress tick, runs `addon_moved` with the state still `NotInstalled` (or `Failed`). It takes the `_` arm and sets `awaiting_addon = None`. The form goes back to its normal state with no message, the add-on keeps installing out of sight, and no download starts when it is ready. The person's choice has to be made again by a second click.
- Evidence: `addon_moved` is subscribed with `cx.observe(&library, ...)`, and `Library::apply` calls `cx.notify()` for every `DownloadsChanged`, not only for add-on changes. `Manager::install_addon` first awaits `rescan_addon(Check::Hashes)`, off the async threads and hashing every file of a damaged install, and only then `start_addon_op` emits `Installing`, so the gap is real and for a damaged add-on long. `rescan_addon` can itself emit `AddonsChanged` with the old state. `view.rs` has the guard for this exact gap (`addon_asked`, "Install was pressed and the install has not been seen to start yet"); the form has none. Not run.
- Confidence: certain about the logic; how often it happens depends on the tick falling in the gap

### 24-2 [P2] The quality form shows nothing when the add-on install fails

- Where: `crates/desktop/src/download_windows/media_form.rs`, `MediaForm::install_then` and `addon_moved`
- Category: bug
- Failure: "Install and download" with no connection, or a refused install. The busy state ends and the form looks as it did before the click: same note ("first installs the media add-on"), same button. The reason never shows in this window.
- Evidence: `install_then` turns any non-`Ok(Ok(Ok(())))` result into `awaiting_addon = None` and drops the error. `addon_moved` drops `AddonState::Failed { message }` the same way. `MediaForm` has no field for a problem and `MediaAnswer` no variant for one, so `DownloadWindow::problem` cannot be set from it. `DownloadWindow::install_addon` and `addon_step` in `view.rs` show the same failures properly for the add-on question. `Manager::install_addon` documents that a failed install arrives only as `AddonsChanged`.
- Confidence: certain

### 24-3 [P2] A failed add-on update blocks video qualities that the installed add-on can still download

- Where: `crates/desktop/src/download_windows/media_form.rs`, `MediaForm::needs_install`
- Category: wrong implementation
- Failure: the add-on works, and an update started from Settings failed (the release host is unreachable, say). `addon_info` now reports `AddonState::Failed` while `slot.tools` is still present. For any quality with `needs_ffmpeg`, the form says the add-on must be installed first and "Download" becomes "Install and download". Every click goes through `install_then`, fails again and, by 24-2, says nothing, so that quality cannot be downloaded from this window although the core would accept it. "Download later" is held the same way. During a quiet update, `Installing` likewise relabels the button and holds the choice until the update ends, for a tool that is there.
- Evidence: `needs_install` is true unless the state is `Installed` or `UpdateAvailable`. `Manager::take_choice` asks only `state.addon.tools.is_none()`. `end_addon_op` sets `failure` for a visible failed install whatever `tools` holds, and `addon_info` checks `failure` before `installed`. `AddonInfo` carries no field that says the tools are usable.
- Confidence: likely (traced in code, not run)

### 24-4 [P2] The "already in the folder" question hides whether it is the same file

- Where: `crates/desktop/src/download_windows/view.rs`, `DownloadWindow::file_exists`
- Category: broken feature
- Failure: a download named `report.pdf` meets an unrelated `report.pdf` in the folder. The window says only "A file with this name is already in <folder>." with Replace as the main button, the same words it uses for an identical copy. The person can replace a different file without being told it is different.
- Evidence: D96 promises "The person always knows which case it is: the question says either that the file in the folder looks like the same file ... or that a different file has the same name". The core computes it and sends `FileExistsQuestion::same_file`, with `size` and `saved_at`. No code under `crates/desktop` reads any of the three; `heading` is even passed `None` for the size.
- Confidence: certain

### 24-5 [P2] Confirming a file without editing its name stops the server from naming it

- Where: `crates/desktop/src/download_windows/view.rs`, `DownloadWindow::confirm`
- Category: wrong implementation
- Failure: a capture of `https://example.com/get?id=7` proposes the name `get`, and the server answers `Content-Disposition: filename=report.pdf`. The person presses Download without touching the name. The file is saved as `get` in the folder picked for that name, instead of `report.pdf`. A proposed name that `checked` refuses fails the download, where an unchosen name would have been changed.
- Evidence: `name_from` fills the field with the core's proposal, and `confirm` sends `file_name: Some(field)` whenever the field is not empty, without comparing it to `core_name`. `Manager::insert_confirmed` says "Only what the user changed is a choice; the proposal was a guess that the server's answer may still improve", and passes the value as `Wanted::file_name`, which `add_entry` keeps as `NameChoice::name`. `naming::settled_name` returns a `Some` choice at once and never reaches the server's name. `MediaForm::answer` does not have this fault: its field starts empty with the title as a placeholder.
- Confidence: certain about the code path; only a capture whose proposal differs from the server's name shows it

### 24-6 [P2] Answering "already in the folder" opens a second progress window for the same download

- Where: `crates/desktop/src/download_windows/view.rs`, `DownloadWindow::became`; `crates/shell/src/download_windows.rs`, `Registry::became_download`
- Category: bug
- Failure: with the default settings (`when_file_exists: Ask`, `show_progress_windows: true`), a browser file already in the folder. Download turns the window into download 5's progress. The server answers, and the core pauses download 5 and asks in a new window. Replace or Keep both turns that second window into download 5's progress too, so two windows follow one download, against D23.5 ("One window per download"). A repeated link or anything using `window_showing` reaches only the older one. Cancel takes the same path: the question's window stays open as a cancelled download's progress, once more alongside the first.
- Evidence: `settle` goes through `answer`, and `api::answer_file_exists(...).map(Some)` returns the download id for every choice, Cancel included (`Manager::answer_file_exists`). `became` sets `shows` without asking whether a window already shows that download. `became_download` overwrites `shows` with no check, unlike `show_download`, which focuses the existing window.
- Confidence: certain

### 24-7 [P2] Cancel in a progress window discards the partial file at one click, with no question

- Where: `crates/desktop/src/download_windows/view.rs`, `progress_buttons`
- Category: wrong implementation
- Failure: a 40 GB download at 90%. One click on Cancel, the left neighbour of Hide, removes the partial file at once. "Try again starts over." The main window asks first for the same action.
- Evidence: `progress_buttons` wires `progress-cancel` straight to `api::cancel`, documented as "Stops a download and discards its partial file". D23.4 says "Cancel (asks first, then removes the download and its partial file)", and neither D52 nor D114.2 drops that. `main_window/confirm.rs` `cancel` is "Asks before cancelling `ids`: they stop and lose what was downloaded".
- Confidence: certain

### 24-8 [P2] Nothing opens a download's progress window: Hide cannot be undone

- Where: `crates/desktop/src/download_windows/mod.rs`, `show_download` (no caller but `follow`); the missing entry belongs to the main window's row actions
- Category: broken feature
- Failure: the person presses Hide on a running download and wants the graph back, or wants progress for a download added inside the app. No row, menu or command opens one. The only way is to click the same link in the browser again, for a download not finished yet (D89.2).
- Evidence: D23.8 says "Every row offers 'Show progress window'", and `Registry::show_download` documents `"Open in its own window"` and "Not limited: the person asked for it". The only call of `download_windows::show_download` is the `CaptureRepeated(Repeated::Download)` arm of `follow`. No text "progress window" or "own window" exists under `crates/desktop/src` outside `download_windows/`. `docs/ROADMAP.md` does not list it as open.
- Confidence: certain

### 24-9 [P2] After missed events, open download windows keep showing the old step

- Where: `crates/desktop/src/download_windows/mod.rs`, `restore`; `crates/shell/src/download_windows.rs`, `Registry::restore`; called from `Library::load`
- Category: bug
- Failure: the interface thread falls more than `UI_EVENT_BUFFER` (1024) events behind, so the library gets `RecvError::Lagged` and reloads. A window still "Reading the video" whose choice arrived in the gap keeps its spinner with only Cancel, and pressing Cancel throws the question away. A window whose question closed in the gap still offers Download, and says it failed only when pressed. The complete window keeps rows that were removed or changed in the gap, since `FinishedBook` only follows events.
- Evidence: `Library::load` is documented as "the way back after events were missed", and calls only `restore(&open_questions)`. `Registry::restore` returns steps only for questions with no window, and never calls `closed`. Nothing calls `refresh` or `reload` on the open views; the one-second `_tick` only redraws progress windows and never rereads a question.
- Confidence: likely (needs the lag, which was not produced)

### 24-10 [P3] The complete window stays open and blank once its rows are removed

- Where: `crates/desktop/src/download_windows/finished.rs`, `follow`, `FinishedView::render`
- Category: bug
- Failure: the window lists one finished download, and the person removes that download from the main window. `FinishedBook::follow` empties the list, and "Downloads finished" stays on screen with an empty body and the foot's button.
- Evidence: `follow` only notifies the view. `render` has no empty state and nothing closes the window when `list().groups` is empty. The shell's test `the_list_follows_what_happens_to_its_downloads` shows the list really does become empty.
- Confidence: certain

### 24-11 [P3] Items left over from the Tauri app, unused outside tests

- Where: `crates/shell/src/download_windows.rs`: `is_download_window`, `Registry::shows`, `Registry::windows`, `Registry::waiting`, and the doc on `LABEL_PREFIX`; `crates/shell/src/finished.rs`: `FinishedBook::lists`, `next_key` and the `FinishedGroup::key` it fills
- Category: dead code
- Failure: each is public API that no product code calls. `is_download_window` has no caller at all, and the other three methods are called only from their own tests. `key` is "for keyed lists", and `FinishedView::render` never reads it. The `LABEL_PREFIX` doc points at `capabilities/download-windows.json`, a file no longer in the repository, and the complete window's `download-finished` label from D52.6 no longer exists either.
- Evidence: a search of `crates/` finds these names only in their definitions and tests, and `git ls-files` finds no `capabilities/` path. Removing `key` also touches the generated `FinishedGroup` type, whose only other mentions are generated files and the `packages/protocol` export.
- Confidence: certain
