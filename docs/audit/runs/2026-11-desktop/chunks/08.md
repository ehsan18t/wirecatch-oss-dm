## Findings

### 08-1 [P0] The connector trusts a pipe made by a lower-integrity program of the same user

- Where: `crates/ipc/src/windows.rs`, `connect` and `verify_owner`; `crates/ipc/src/key.rs`, `write_private` through `create_private_file` and `private_sddl`
- Category: wrong implementation
- Failure: Wirecatch is closed, and a low-integrity program of the same user is running (not restricted and not in an `AppContainer`). It reads `endpoint-key`, then creates `\\.\pipe\wirecatch-app-<SID>-<key>` naming the user as the owner. The bridge opens that pipe, sees the owner it expects, and sends it what the browser sends, including download cookies and headers. Opening the real app does not recover: `bind_keyed` gets `AlreadyInUse`, `crates/desktop/src/main.rs` hands the launch and its links to the fake server and exits, and the key is not renewed. The listener keeps such a program out of the real pipe, but the connector has no matching check, so a program kept out of the app can stand in for it.
- Evidence:
  - `connect` compares only the owner SID. Nothing reads the pipe's mandatory label or the server's integrity level.
  - `private_sddl` gives the key file no label, so it has Windows' default, which stops low-integrity writes but not reads. The label on the pipe (`owner_only_sddl`) has no-read-up, but the key file does not.
  - `classify_taken` turns an owner equal to the user into `AlreadyInUse`.
  - The probe, on a thread with a low-integrity copy of the token: read a file with descriptor `O:userD:P(A;;FA;;;user)`, all 32 characters. It created a first pipe instance with `O:user`. A medium-integrity client opened it and read the owner as the user's SID. The medium-integrity listener's first instance then failed with error 5, the path into `classify_taken`.
  - Not run end to end against the real bridge. The probe ran from an administrator's session; without naming the owner, the pipe got that token's default owner, Administrators, so only the case that names the user applies. It should be repeated from an unelevated token.
- Confidence: likely

### 08-2 [P2] A name held under the key lock is not always renewed, so another account can still stop the bridge endpoint

- Where: `crates/ipc/src/lib.rs`, `Listener::bind_keyed` and `IpcError::is_taken_by_someone_else`; `crates/ipc/src/windows.rs`, `PipeListener::bind_with` and `classify_taken`
- Category: bug
- Failure: another account saw the name once (any account can list pipes) and, while Wirecatch is closed, creates that pipe with a descriptor that lets the user in and a low instance limit.
  - With a limit of 1, `CreateNamedPipe` fails with `ERROR_PIPE_BUSY`, which `bind_with` reports as a plain `Io` error. `crates/desktop/src/main.rs` logs it and starts with no listener, so browser downloads cannot reach the app and the window does not say so.
  - With a limit of 2 and one client on it, the first instance fails with error 5 and the probe gets `ERROR_PIPE_BUSY`, which `classify_taken` reports as `AlreadyInUse`. The launch then tries to hand over and tells the person Wirecatch is already running, and it exits.
  - Neither case writes a new key, so this lasts as long as the other account keeps the pipe. D41.6 says taking the name "never" keeps Wirecatch from starting.
- Evidence:
  - `bind_keyed` renews only on `EndpointTaken` or `UnsafeDirectory`, although its own doc says no copy of ours can hold the name while the lock is held. Under the lock, any existing pipe with this name is therefore not ours.
  - The busy arm of `classify_taken` calls the case "our own app under load", which is true for a plain `bind` but cannot happen under `bind_keyed`.
  - The probe, within one account: limit 1 and idle gave first instance error 231. Limit 2 with one client gave first instance error 5 and probe error 231. Limit 1 with a client gave first instance error 231 and probe error 231.
  - A real second account was not used. No test covers these cases.
- Confidence: likely

### 08-3 [P2] A client that meets a squatter usually gets a plain error, so the bridge never starts the app to renew the key

- Where: `crates/ipc/src/windows.rs`, `connect`; `crates/ipc/src/unix.rs`, `endpoint`; `crates/bridge/src/app.rs`, `attempt`
- Category: broken feature
- Failure: Wirecatch is closed and another account holds the keyed name.
  - On Windows, a pipe made with that account's default descriptor or one that shuts the user out makes `connect` fail with `ERROR_ACCESS_DENIED`, returned as `IpcError::Io`, not `WrongOwner`.
  - On Linux's `/tmp` fallback, `endpoint_for` returns `UnsafeDirectory` for a folder another account made.
  - `attempt` treats both as `Attempt::Failed`, which never launches. The browser gets an error, and nothing changes until the person opens the app by hand. Only a squatter that lets the user open its pipe reaches the `WrongOwner` path that starts the app.
- Evidence:
  - D41.6: "A client that reaches a squatter gets `WrongOwner` and sends nothing; the bridge then starts the app". The docs of `Listener::bind_keyed` and `connect` make the same promise.
  - In `connect`, only `ERROR_PIPE_BUSY` and `ERROR_FILE_NOT_FOUND` have their own arms. `classify_taken` already reads the same refusal on the listener's side as someone else's pipe ("Our own pipe always lets us in").
  - `attempt` matches `NotRunning`, `NoEndpointKey` and `WrongOwner` for retry, and fails on everything else.
  - The bridge tests stand in for a squatter with a made-up `WrongOwner` (`squatted`), so they do not see these two errors.
- Confidence: certain for the error paths, read from the code. No second account was used.

### 08-4 [P3] On Linux a link in place of the key is a raw system error, not `BadEndpointKey`

- Where: `crates/ipc/src/key.rs`, `stored` and `open_for_reading`
- Category: wrong implementation
- Failure: `endpoint-key` is a symbolic link on Linux. `O_NOFOLLOW` fails with `ELOOP`, and `stored` returns `IpcError::Io` with "Could not open ...". The docs of `endpoint_in` promise `BadEndpointKey`, whose message tells the person to delete the file, so the person gets no advice. The refusal itself is correct and nothing is read through the link. Windows does return `BadEndpointKey`, because its link opens and `check_private` refuses it.
- Evidence: in `stored`, only `NotFound` has its own arm. The Unix test `a_key_others_can_read_or_a_link_in_its_place_is_refused` asserts only `is_err()`.
- Confidence: certain from reading the code; not run on Linux.

## Checked and found sound

- A client handle left on a closed server does not keep the name: the probe's new first instance succeeded, so a bridge still holding the old connection does not block a restart.
- `accept` keeps a waiting instance on every path, is cancel-safe, and reverts impersonation with no `.await` in between.
- The key does not reach any `Endpoint` display, `IpcError` text or log line followed through this chunk. `as_os_str` outside the crate is used only by tests and test overrides.
- `Listener` drops its socket before its locks, and the failure paths of `bind_keyed` release the lock.
