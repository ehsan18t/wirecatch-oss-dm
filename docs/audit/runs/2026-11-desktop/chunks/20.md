## Findings

### 20-1 [P2] An apostrophe in a link ends the link for the redaction, so the password or signed query after it stays in the log

- Where: `crates/logging/src/redact.rs`, `ends_a_link`, as used by `hide_link_credentials` and `hide_queries`
- Category: wrong implementation
- Failure: `text_for_log("GET https://cdn.example.com/bob's.mp4?st=TOK&e=1 failed")` returns the text unchanged, `st=TOK` included. `text_for_log("https://ada:pa'ss@example.com/f")` and `url_for_display` of the same link also return it unchanged, password included. D40.4 and the module documentation promise that every link's password and every query value are hidden. The same holds for any other byte in `ends_a_link` written raw inside a link (`"`, `<`, `>`, a backtick, a backslash) and for a raw space before the query, but only the apostrophe survives parsing.
- Evidence: Hand-traced, no test run (machine load). `ends_a_link` stops at `'`, which is there for quoted links such as ffmpeg's `Opening 'https://..' for reading`. In `hide_queries` the word before the `'` holds no `?`, and the word after it (`s.mp4?st=TOK&e=1`) has no `://` and does not start with `/`, so its query is left alone; `st` and `e` are no secret names, so `hide_named_secrets` keeps them too (`sig=` or `token=` would be caught there; `st`, `Policy`, `Expires` and similar are not). In `hide_link_credentials` the link end is the `'`, the host part is `ada:pa`, and the `@` is past the end, so `.filter(|at| *at < end)` drops it and nothing is hidden. The `url` crate leaves `'` as it is in paths and in user information, so a parsed link printed with `Display` keeps it: `reqwest` errors carrying the URL and ffmpeg or yt-dlp stderr lines (`StderrTail` calls `text_for_log`) reach this path. `url_for_display` feeds core's rows (`manager/state.rs`, `manager/media.rs`, `manager/captures.rs`), so the password also reaches what the interface is sent. `redaction.json` has no sample with an apostrophe inside a link; the only quoted sample is the ffmpeg one, where it closes the link.
- Confidence: certain

### 20-2 [P3] A file name or host holding a secret word, followed by a colon, loses the rest of its line in the log

- Where: `crates/logging/src/redact/named.rs`, `kind_of` and `secret_value`; `crates/protocol/src/secrets.rs`, `segments`
- Category: wrong implementation
- Failure: `https://h.example/enc.key: Server returned 403 Forbidden` becomes `https://h.example/enc.key: ***`, and `GET https://auth.example.com:8443/f.zip failed` becomes `GET https://auth.example.com:***`. Also `session-01.mp4: Permission denied`, and a panic located in `crates/media/src/ytdlp/cookies.rs:12:3:` loses its line and column. D40.10 says the log keeps hosts and paths because diagnosing a download needs them, and D40.6 keeps the diagnostics after a value; here the failure's cause is what is lost, on ffmpeg's usual `path: reason` lines, where an HLS key fetch is a common failure.
- Evidence: Hand-traced, no test run. `is_name_byte` takes `.` and `-`, so a whole file name or host is one name; `segments` splits it at `.` and `-`, so `enc.key`, `auth.example.com` and `session-01.mp4` pass `is_secret_name` through one segment, and `kind_of` gives `Kind::Value`. `secret_value` takes the `:` as the separator (only `//` after it is refused) and `field_end` runs to the end of the line unless a `name=` follows. `in_path` protects only a segment after `::`. `StderrTail` applies this per line, so a person's message built from the tail's most telling line (D40.5) loses the same text. Existing samples pin only module paths (`wirecatch_core::cookies:`), and `auth.token` style dotted names must stay secret, so the fix has to separate the two, for example by a name right after `/`, or a `:` followed by a port.
- Confidence: certain

## Looked at and found sound

- `redact`: every string slice falls on an ASCII position or a text end, every scan loop advances, and no input reachable from outside can panic. Each pass is linear on the patterns tested and on the ones tried by hand.
- `file.rs`: the move-on, retry, emptying and two-writer behaviour matches D40.7, including a failed back-rename. A failed `append_to` after a move leaves the held file and recovers on a later line.
- `sink.rs`: `holder` is cleared before the lock is released, so it can equal a thread only while that thread holds the file. A panic with the file held does not wait on itself.
- `fields.rs`, `lib.rs`: span fields go through the same formatter, `log.*` fields are dropped by name only, and the panic report reaches both sinks whatever the filter. All four binaries call `start` then `write_to` at once.
- `secret.rs`: `Address` hides a sign-in with or without a parse, including `https://user:pa/ss@host/f`.
- The tests can fail: the shared cases assert exact output and absent secrets, `panics.rs` runs a real process, and the step count covers every scan.
