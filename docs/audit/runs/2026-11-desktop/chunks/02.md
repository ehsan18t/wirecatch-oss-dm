## Findings

### 02-1 [P1] An expired redirect target fails the download although the link the person gave still works

- Where: `crates/engine/src/transport.rs` (`Opened::final_url`), `crates/engine/src/download.rs` (`RequestContext { url: final_url, .. }`), `crates/engine/src/http.rs` (`fetch`)
- Category: wrong implementation
- Failure: a link redirects to a short-lived signed address, as release and object-storage hosts do. Every request after the first goes straight to that address for the whole run: each new split, each reconnect after a dropped connection, each piece under `max_request_bytes`. Once it has expired, the next such request gets `403` (or `401`, `404`, `410`). The connection gives up, the others finish their parts, and the download ends failed with "The download link has expired", offering only Refresh link. The original link was valid all along and would have given a fresh address. A slow or long download is the one that reaches this, so an unattended queue stops on it.
- Evidence: `RequestContext.url` is set once from `final_url` and never changes; `fetch` sends only to `request.url`; `Error::is_retryable` is false for these statuses, so `Attempts::after_failure` returns `GiveUp`; `worker` returns the error; `join_workers` keeps it and `finish` reports it. Nothing in the engine holds the original URL past `transport::open` except the resume file's text (`saved_url`). A later run does probe the original link again, which is why Try again recovers and why the part file is not lost. No decision in `docs/DECISIONS.md` records this choice, and no test in `crates/engine/tests` covers a redirect target that stops answering.
- Confidence: likely (the engine's path is certain; how long a host's signed address lives is outside the code)

### 02-2 [P2] A `Content-Disposition` holding one raw non-ASCII byte loses the whole file name, `filename*` included

- Where: `crates/engine/src/http.rs`, `probe_range`
- Category: wrong implementation
- Failure: a server sends `attachment; filename="résumé.pdf"; filename*=UTF-8''r%C3%A9sum%C3%A9.pdf` with raw UTF-8 or Latin-1 bytes in the plain parameter, or only `filename="отчёт.zip"`. `HeaderValue::to_str` fails on the first byte above 126, so `file_name` is `None`, and the file is named from the URL (`download.php`, `12345`). The correctly encoded `filename*` in the same header is thrown away with it.
- Evidence: `.and_then(|v| v.to_str().ok()).and_then(naming::from_content_disposition)`. `http` 1.4 and 1.5 `to_str` return an error unless every byte is visible ASCII or tab. `from_content_disposition` takes `&str` and already handles `filename*`, so nothing below it sees the header. The tests in `naming.rs` start from a `&str`, so none reaches this path. It affects links added in the app, and any capture that does not name the file itself.
- Confidence: certain

### 02-3 [P2] `Fetcher` does not count skipped bytes against the speed limit, though its docs say every byte counts

- Where: `crates/engine/src/fetch.rs`, `Fetcher::attempt`
- Category: wrong implementation
- Failure: a server ignores ranges (`200`), or a retry has to ask for a whole resource again. The bytes before the wanted range are read and dropped with no pacing, because `data.is_empty()` continues before `pace`, and `n` counts only what was kept. With a speed limit set, a stream with byte ranges on such a server, or a retry late in a large segment, uses the network at full speed for as long as the skip lasts. The bytes after a range's end are not read, so only the skip is affected.
- Evidence: the `Fetcher` doc says "Every byte counts against `DownloadOptions::rate_limiters`". `pace(&self.inner.rate_limiters, n, ..)` runs only after the `is_empty` check. `worker.rs` does the same (`pace` on `allowed`, after `skip_start`), so a plain download's retry on a server without ranges behaves alike; that path belongs to chunk 01 and is noted here because the cause is one.
- Confidence: certain

### 02-4 [P3] A range past the end of a file that shrank is reported as a server error, not as a changed file

- Where: `crates/engine/src/http.rs`, `fetch`; `crates/engine/src/http/range.rs`, `check_same_file`
- Category: wrong implementation
- Failure: the file is replaced by a shorter one during a download. A worker whose range starts inside the new size gets `RemoteChanged`; one whose range starts past it gets `416` with `Content-Range: bytes */<new size>`. That goes through `check_status` to `HttpStatus { status: 416 }`, and the person reads "The server rejected the download (error 416)" instead of "The file changed on the server". Which message appears depends only on which worker asks first. Try again recovers, because the new probe sees the new size.
- Evidence: `probe_range` reads `content_range` on a `416`, but `fetch` and `Fetcher::open` do not, and `http3::check_response` hands it to TCP, which ends the same way. `Error::RemoteChanged` documents "another size".
- Confidence: certain

### 02-5 [P3] The "delay past the normal backoff" test in the step-back rule is true only because of jitter

- Where: `crates/engine/src/retry.rs`, `Attempts::after_failure` (`long_wait`)
- Category: wrong implementation
- Failure: `delay > backoff.max` cannot mean a long wait. Without a `Retry-After`, `delay` is `pause(failures)`, at most `max` plus jitter, so the test is true only when the pause has reached the cap and jitter is above zero. So a single refusal there steps back at once, against `REFUSALS_BEFORE_STEPPING_BACK` ("one refusal can be a fluke"): after enough timeouts in a row with the defaults, and on every first refusal for any `Backoff` whose `first` equals `max`. No case exists where the clause does what D69.1 describes, since a server's long wait is already caught by `retry_after.is_some()`.
- Evidence: `Backoff::pause` is `first * 2^n` capped by `.min(self.max)`, then `+ self.jitter()`. `Backoff::delay` is the only source of `delay`. No test in `retry.rs` reaches the cap with a refusal.
- Confidence: certain

### 02-6 [P3] `Fetcher::save` docs promise the data survives dropping the future, but up to 256 KiB is lost

- Where: `crates/engine/src/fetch.rs`, `Fetcher::save`
- Category: wrong implementation
- Failure: the docs say "Cancelling (by the token or by dropping this future) keeps what arrived in the file". On a drop, `Sink::finish` never runs and the `BufWriter` (`SAVE_BUFFER`, 256 KiB) is dropped unflushed, so bytes already reported through `on_bytes` are not in the file. Cancelling by token does flush. The one caller today, `crates/streams/src/download/fetch.rs`, does not rely on a partial part file, so the cost is a public promise of a published crate that is false.
- Evidence: `sink.finish().await` is reached only when `transfer` returns; `tokio::io::BufWriter` has no flush on drop.
- Confidence: certain

### 02-7 [P3] `bench_local serve` sleeps for no time after each accept

- Where: `crates/engine/examples/bench_local.rs`, `serve`
- Category: no-op code
- Failure: `tokio::time::sleep(Duration::ZERO).await` at the end of the accept loop does nothing: the loop already yields at `listener.accept().await`, and the forwarding runs in its own task.
- Evidence: the statement has no comment or effect, and no state is read after it.
- Confidence: certain

### 02-8 [P3] Two private copies of a test data generator next to the shared one

- Where: `crates/engine/src/http3/tests.rs` (`test_data`), `crates/engine/examples/bench_http3.rs` (`run`)
- Category: duplicate
- Failure: both write `(i * 31 + i / 509).to_le_bytes()[0]` by hand, although `wirecatch_test_support::test_data` exists and `bench_local.rs` and the other engine tests use it. `docs/ENGINEERING.md` section 3 says test helpers come from shared test support. The two share no reason to differ: wrapping the shared result in `Bytes::from` gives what they need.
- Evidence: the formula appears in exactly these two places; `crates/test-support/src/lib.rs` has `test_data` and `seeded_data`.
- Confidence: certain

## Suggestions

### 02-S1 Ask again without a range when the first `206` cannot be read

- Today: a first answer of `206` with no `Content-Range`, or one written `bytes=0-99/100`, fails at once with `RangeNotHonored` (not retried), so the download never starts, although the same server may answer a plain `GET` correctly.
- Better: on the first request only, treat that answer as "ranges do not work here" and ask once more with no `Range`, then download as a server without ranges.
- Value: a download that otherwise cannot start works, at the cost of no resume on that server.

### 02-S2 Check a first answer whose range stops short with no size

- Today: `bytes=0-` answered `206` with `Content-Range: bytes 0-99/*` becomes `ranged: false, total: None`, and the body's end counts as the end of the file. RFC 9110 lets a server send less than was asked, so that would be reported complete at 100 bytes. No real server doing this is known here, which is why it is not a finding.
- Better: after such an answer ends, ask for `bytes=100-`; a `416` confirms the end, a `206` carries on.
- Value: a truncated file is not reported as finished.

### 02-S3 Keep cookies set during a redirect chain

- Today: `Clients::builder` sets no cookie store and `http::send` follows each hop with the caller's headers only, so a `Set-Cookie` on a redirect is dropped. A site that sets a cookie and redirects back to itself ends in `TooManyRedirects`, whose message suggests a loop. wget and aria2 keep such cookies; curl keeps them only when asked to.
- Better: within one `send`, carry `Set-Cookie` values from a hop to later hops of the same origin, without saving them.
- Value: links behind a cookie check download in the app without going through the browser.
