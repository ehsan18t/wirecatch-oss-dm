### 32-1 [P2] The pause line gives a size of 16 EiB and promises a continuation that will not happen

- Where: `crates/cli/src/main.rs`, `summary` (and the module doc); `crates/engine/src/download.rs`, `Outcome::Paused`
- Category: wrong implementation
- Failure: Ctrl+C during a download from a server with no range support or no known size. With an unknown size (a chunked response, no `Content-Length`) the line reads "Paused with 16.00 EiB left for file. Run the same command again to continue." With a known size and no ranges the size is right but the promise is still false. Running the same command discards the part and resume files and starts again from byte 0, so a script or person waiting to continue loses all of it, having been told otherwise.
- Evidence: `SegmentTable::new` uses `UNKNOWN_END` (`u64::MAX`) as the end for an unknown size, and `remaining_bytes` sums `end - flushed`, which `finish` passes as `Outcome::Paused::remaining` unchanged. `summary` feeds it to `HumanBytes` with no check. `plan_in_folder` finds the same URL, `continues` is false because `can_resume` needs ranges and a known total, and it returns `Plan::Planned(preferred, None)`, whose `prepare` arm discards both files. `Outcome::Paused` carries nothing that says whether it can continue, so the CLI cannot word this correctly without an engine change. `summary` has no test. Read from code, not run.
- Confidence: certain

### 32-2 [P2] Ctrl+C before the server answers exits 1, with an error, not 130

- Where: `crates/cli/src/main.rs`, `main` (`result?`), module doc
- Category: bug
- Failure: Ctrl+C while connecting or waiting for the first answer (a slow server, a long redirect chain, an FTP sign-in). The person sees "Pausing..." and then `Error: cancelled before the download started`, and the exit status is 1. The module doc says 130 "when the download was paused or stopped with Ctrl+C", and `Ending::Stopped` is documented as what a script relies on. A script that treats 130 as "interrupted, run again" and 1 as "failed" takes the wrong branch.
- Evidence: `http::send` and the FTP path return `Error::Cancelled` when the token fires before the answer; `Error::Cancelled`'s doc says only a later cancel gives `Outcome::Paused`. `main` applies `?` to `download`'s result, so the error reaches anyhow's exit 1. Nothing in `summary` or `main` maps `Cancelled` to `Ending::Stopped`. Read from code, not run.
- Confidence: certain

### 32-3 [P2] Ctrl+C with a closed stderr pipe panics before it cancels, so the process aborts instead of pausing

- Where: `crates/cli/src/main.rs`, `stop_on_ctrl_c`
- Category: bug
- Failure: `wirecatch URL 2>&1 | tee log`, then Ctrl+C. The signal reaches the whole foreground group, so `tee` can be gone by the time the handler runs. `eprintln!("Pausing...")` then fails with a broken pipe and panics, and `cancel.cancel()` on the next line never runs. A release build aborts (`panic = "abort"`): the exit status is the abort's rather than 130, no final save runs, and the bytes since the last checkpoint (up to 1 s) are fetched again. A build that unwinds is worse: the task dies, the signal stays caught, and Ctrl+C no longer does anything for the rest of the download.
- Evidence: `eprintln!` panics on a failed write (std's documented behaviour; only a closed handle, EBADF, is ignored, and std ignores SIGPIPE so a closed pipe is an error, not a kill). The print comes before the cancel. `docs/ENGINEERING.md` section 4 calls for a named handler where stderr may be closed and treats a reachable panic as critical; the same file handles the closed pipe on stdout carefully in `exit_code`. `exit_code`'s own `eprintln!` has the same fault when stdout and stderr have both failed. It is a race, and was not run.
- Confidence: likely

### 32-4 [P2] After a resume, the shown speed and ETA are wrong for about half a minute

- Where: `crates/cli/src/main.rs`, `spawn_progress_bar`
- Category: wrong implementation
- Failure: Continue a download with 10 GiB already kept. The bar starts at position 0, and the first tick after the server answers sets it to 10 GiB, which indicatif reads as 10 GiB received in a fraction of a second. The speed shows many GiB/s and the ETA about 0 s at first. The leftover excess works out to about 170 MiB/s after 15 s and 16 MiB/s after 30 s, and it scales with the bytes kept.
- Evidence: `Progress::done` includes bytes from an earlier run (its doc, and `Progress::start` storing `already_done`). `set_position` feeds the estimator through `Estimator::record`, which turns the jump into one sample of `delta / delta_t` with a 15 s decay to a tenth. Nothing calls `reset_eta` or starts the bar at the kept position. Estimate worked from the estimator's formula, not measured.
- Confidence: certain

### 32-5 [P3] A redirect from https to http tells the person to allow something the CLI cannot allow

- Where: `crates/cli/src/main.rs`, `build_request`, `Args`; `crates/engine/src/error.rs`, `Error::InsecureRedirect`
- Category: broken feature
- Failure: a link on https redirects to http. The download stops with "...so the download was stopped. Allow insecure redirects to download it anyway". `wirecatch` has no flag for it, so the fix the message offers does not exist and the person is left at a dead end.
- Evidence: `DownloadOptions::allow_insecure_redirects` defaults to false, and `build_request` sets `proxy`, `connections`, `http3` and `headers` only. `--help` lists no such option.
- Confidence: certain
