## Findings

### 07-1 [P1] With no window, a capture of a file already in the folder closes its own question and goes back to the browser

- Where: `crates/core/src/manager/captures.rs`, `capture_arrived` and `await_answer`; `crates/core/src/manager/file_exists.rs`, `ask`; `crates/core/src/manager/state.rs`, `Entry::server_answered`
- Category: broken feature
- Failure: `ask_before_download` off ("Start downloads without asking"), `when_file_exists` at its default Ask (D88.2), and a finished file at the name the server gives. The person clicks the link in the browser. The question "the file is already in the folder" opens and closes at once, the download is removed from the list, and the extension is told `not_started` with "It stopped before the server answered.", although the server did answer. The browser downloads the file itself. D88.3 promises that asking pauses the download and waits for Replace, Keep both or Cancel.
- Evidence: `settle_path_checking` calls `stop_for_duplicate`, which sets `Stop::FileExists` and returns `Err` before `answered` is cancelled or `naming.settled` is set. `finish` calls `on_found`, and for Ask `ask` only sets `Paused` and emits `FileExistsRequested`, leaving `naming.settled` false (Replace and KeepExisting go through `settle_at`, which sets it). `RunGuard::report` then cancels `exited`, which wakes `ended_in_time`. `await_answer` finds `server_answered()` false and `row.error` empty, so it returns `Err`; `capture_arrived` removes the handover and calls `remove_in_background`, whose `remove` runs `close_file_exists`. The confirmed path is not affected: it adds with `handover: None`, so nothing waits. No test combines the two: `tests/manager/file_exists.rs` never calls `add_capture`.
- Confidence: certain

### 07-2 [P2] A capture joining an unfinished download is answered `Started` before any server has answered

- Where: `crates/core/src/manager/captures.rs`, `join_unfinished`; `crates/core/src/manager/downloads.rs`, `capture_action`
- Category: wrong implementation
- Failure: a download of a link is `Connecting` (added in the app without cookies, confirmed in a window, or another handover still waiting). The person clicks the same link in the browser, signed in there. The new handover is answered `Started` at once, and a later withdrawal of it answers `AlreadyStarted`, so the extension erases the browser's copy. If the server then refuses the app (403, because the row has no cookies), the row fails or is removed, the browser's signed-in download is gone and its cookies were thrown away. The person has to click the link again. When the row is another capture still being decided and that one fails, its own browser copy is resumed, so the file survives there, but the app has still told this handover something untrue.
- Evidence: `AddAction::Started` is documented as "The server answered the app with the file ... Only now may the extension erase the browser's copy", and `add_capture`'s docs say the same. `capture_action` maps `Connecting` to `Started` and says so itself ("provisionally, until the server answers"); `remember_handover` covers that with `deciding` and `capture_arrived` with `await_answer`, but `join_unfinished` uses the same mapping with `deciding: None` and `Target::Confirmed`, and returns straight away. `a_link_already_downloading_shows_that_download` only asserts the action is not `AwaitingConfirmation`.
- Confidence: certain

### 07-3 [P2] The same link with another `#fragment` opens a second question and a second download when windows ask first

- Where: `crates/core/src/manager/captures.rs`, `hold_for_confirmation`, against `same_address`
- Category: bug
- Failure: `ask_before_download` on, `https://example.com/a.pdf` waiting for an answer, and the person clicks `https://example.com/a.pdf#page=2`. A second window opens instead of the first coming to the front (D89.1). Answering both downloads the file twice, under two names.
- Evidence: `hold_for_confirmation` finds the question with `p.capture.url == url_text`, an exact comparison with the fragment in it. `join_unfinished` and `earlier_download` use `same_address`, which ignores the fragment because it never reaches the server, and `a_confirmed_file_returns_its_id_and_later_adds_it_paused` proves that for `a.pdf#again` against a paused download. `a_link_waiting_for_confirmation_shows_that_question` only sends the identical link.
- Confidence: certain

### 07-4 [P3] The browser's word that a direct media file is audio is dropped when the server answers

- Where: `crates/core/src/manager/captures.rs`, `direct_category`, `wanted_by`; `crates/core/src/manager/settle.rs`, `settle_path_checking`
- Category: no-op code
- Failure: a direct capture of `talk.mp4` or `talk.webm` with `mime: audio/...`. The row is Audio only until the server answers; then it becomes Video and the file goes to the Video folder. `NewDownload::mime` is documented as what "tells audio from video for a direct media file".
- Evidence: `settle_path_checking` works out `category` from `category_of(name)`, then from the server's content type, sets `entry.row.category` and picks the folder from it, without reading the wanted category, which `add_entry` does not keep. For a file with a name the rules do not know, the server's type decides. So `direct_category` has an effect only on a row that has not reached a server, and the only test of it (`a_direct_media_file_downloads_like_any_file`) uses `video/mp4` with a `.mp4` name, which passes without it.
- Confidence: certain

### 07-5 [P3] A withdrawal can land between the check and the record of a capture's answer, and both sides get contrary answers

- Where: `crates/core/src/manager/captures.rs`, `capture_arrived`, the `Ok(())` arm after `await_answer`
- Category: bug
- Failure: `await_answer` returns `Ok` and drops the lock; before `capture_arrived` takes it again, `withdraw_capture` runs on another worker. `deciding` is still set, so it answers `Withdrawn` and removes the download. `decide` then finds nothing, and the add still answers `Started`. The extension resumes its copy, then gets a late sure confirmation, and D27.4 makes that the two-copies warning, with no copy in the app. No file is lost, and the window is a few instructions wide.
- Evidence: `await_answer` holds `self.lock()` only for its own checks, and the `Ok` arm uses a new `self.lock()`, ignoring whether `decide` found the handover. Serve requests run side by side by design (`start_request`).
- Confidence: likely

### 07-6 [P3] `RecvError::Closed` in the server's loop can never happen

- Where: `crates/server/src/lib.rs`, `serve_connection`
- Category: dead code
- Failure: the arm "The manager is gone; nothing more will happen" is never taken. The sender lives in `Inner` (`wire_events`) and `serve_connection` owns a `Manager`, a strong reference to it, for its whole life. A connection therefore does not end when the manager shuts down; it ends only when its client leaves or the shell stops its task. A reader relying on the comment would conclude otherwise.
- Evidence: `Manager::subscribe_events` subscribes to `inner.wire_events`, a plain `broadcast::Sender` in `Inner`; `manager` is used by `start_request` and `snapshot` in the same loop, so it stays alive to the end of the function.
- Confidence: certain

### 07-7 [P3] Each test file writes its own whole `NewDownload`

- Where: `crates/core/tests/manager/again.rs` (`click`), `protocol.rs` (`capture`), `windows.rs` (`file_capture`), and outside the chunk `ftp.rs`, `queues.rs`, `media_support.rs` (`media_capture`), `crates/core/src/manager/tests.rs`, `crates/e2e/src/app.rs`, `crates/sites/src/local_network.rs`
- Category: duplicate
- Failure: `NewDownload` has no default, so a new field must be added by hand in about nine places. `frame_url` and `cookie_jar` were added this way. ENGINEERING section 3: test helpers come from the shared test support, and a third copy is never acceptable.
- Evidence: `grep "NewDownload {"` over `crates/`: each listed file writes every field out. `crates/test-support` already holds the same kind of base for rows (`downloads::download`).
- Confidence: certain

## Checked and clean

Suspicions followed to the end, so the next reader need not repeat them:

- Non-ASCII cookie values are not dropped by `to_map`: `HeaderValue::from_str` goes through `try_from_generic` and `is_valid`, which allows bytes above 127, whatever its docs say.
- A repeated add cannot fail on `arrival` where the first succeeded: `State::place` with `QueueRequest::Browser` never errs.
- Cookies do not follow a redirect by these headers alone: the engine's redirect loop asks `session.headers.for_url` on every hop.
- Finished rows keep no cookies (`mark_completed` clears `origin`), and restored rows are `Queued` before `start_run`, so `forget_if_old` sees them.
- A queue deleted under an open question moves the question to the fallback queue (`queues.rs`).
- Totals of site lists are bounded by `validate`, after `check_sites` bounds what is read.
- The frame reader is cancel safe and the skip of an oversized body stores nothing. Responses wait in an unbounded channel, but no new request is read while a write is blocked, so at most the 64 in flight can queue.

## Suggestions

### 07-S1 Forget a password in a captured link along with the rest of the sign-in

- Today: `forget_if_old` removes cookies and sign-in headers after a week, while a `https://user:password@host/` link stays in the row, and on disk, for as long as the row exists, a finished download included. The database file is private to its owner (D17).
- Better: at the week's end, or when a download finishes, keep the link without its password and fail with the existing "get a fresh link" note if it is needed again.
- Value: a password never sits in the list for longer than the sign-in beside it. `Copy link` and `Try again` on a finished download would lose it, so this is a trade-off for the person to accept.
