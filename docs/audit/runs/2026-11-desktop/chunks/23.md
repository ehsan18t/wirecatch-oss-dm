## Findings

### 23-1 [P2] A download moved to another queue shows in the wrong place in that queue's line until the app restarts

- Where: `crates/desktop/src/library.rs`, `Library::apply` (`UiEvent::DownloadsChanged`); the order is read by `main_window/list.rs` (`members`, `queue_line`) and `main_window/sort.rs`
- Category: wrong implementation
- Failure: queue B holds a waiting download with id 5. Download 2, listed before it, is moved to B from any of the five move paths. The manager gives 2 a new, last place in line, so B runs 5 first and 2 is "2nd in line". The window keeps 2 at its old index and draws it above 5. Alt+Up on 2 does nothing because the window believes it is first, and the row's order flips at the next start. Likewise the All view: a new row is pushed at the end of the whole list rather than after its queue's rows, and a queue dragged to a new place leaves the rows in the old order, both of which change at the next start.
- Evidence: `Manager::move_to_queue` sets `entry.position = state.ids.position()`, and `list_downloads` sorts by `(queue index, position)`. `DownloadSummary` carries no position. `apply` replaces a known row in place (`*known = row`) and pushes an unknown one. `Library::reorder` is the only local reorder and only `order::apply` calls it; its doc says no event carries order. `Library::load` runs only after `Lagged` or a failed open. `sort.rs` promises "a queue's line keeps the order it runs in" and returns library order untouched for `QueueOrder` and `UpNext`.
- Confidence: certain

### 23-2 [P2] A pasted link is silently cut at an apostrophe or loses a closing bracket, so the wrong address is downloaded

- Where: `crates/desktop/src/links.rs`, `LINK` and `extract`
- Category: bug
- Failure: `https://example.com/Bob's%20file.zip` gives `https://example.com/Bob`, and `https://example.com/report_(final)` gives `https://example.com/report_(final`. Both parse, so the Add dialog, paste, tray and search box offer a different link with no warning. `lines_without_links` does not count such a line either. A trailing `]`, `!`, `?` or `:` is cut the same way.
- Evidence: the regex stops at `'`, although its comment says "the first character no link holds"; `'` is valid in a path and browsers leave it raw when copying a link's address there. `trim_end_matches` removes `)` and `]` without checking for an opening one inside the link. The tests cover only the sentence case.
- Confidence: certain

### 23-3 [P2] An unfinished download reads 100%, against the function's own contract, including while it merges or converts

- Where: `crates/desktop/src/text.rs`, `percent`; shown by `main_window/list.rs` (`figure`) and `main_window/details.rs`
- Category: bug
- Failure: all bytes received but the file not finished: the row's figure says `100%` while its status says `Converting, 40%` and its bar, from `per_mille`, is at 40%. The same holds for a download still writing out its last bytes.
- Evidence: the doc says "never 100: everything may be downloaded while the file is still written, and 100% would say it is done", but the first branch returns 100% on `row.done >= total` for any status, making the later `.min(PERCENT_MAX - 1)` dead. `figure` calls it for `Processing`. `status_short` has the correct `.min(99)` guard. No test covers `percent`.
- Confidence: likely (a media row reaching `Processing` with `total` set is inferred from `per_mille` and `size`, not run)

### 23-4 [P2] The details panel says "Merging video and audio" for every processing step

- Where: `crates/desktop/src/text.rs`, `status_label`; used by `main_window/details.rs` in the header
- Category: bug
- Failure: an audio download converting to MP3, or a video adding subtitles, shows "Merging video and audio" in the details header, while the list says "Converting" or "Finishing the file" and the sentence below describes the real step.
- Evidence: `status_label(DownloadStatus::Processing)` is a fixed string and has no access to the step. `status_short` handles the step, but `details.rs` calls `status_label(row.status)` directly; that is its only caller outside `text.rs`.
- Confidence: certain

### 23-5 [P2] Settings has no Check now, publication day or last check for the Public Suffix List that D44.4 records

- Where: `crates/shell/src/api.rs`, `suffix_list`, `check_suffix_list`; the missing part belongs in `main_window/settings/general.rs`
- Category: broken feature
- Failure: a person who turned the weekly check off, or wants a new list now, has no way to ask for one, and cannot see which list is in use or when it was last checked. Only the switch exists.
- Evidence: D44.4 lists the day published, when last checked, and Check now. A search of `crates` finds no caller of either function outside `api.rs`, and `crates/desktop/src` mentions only `update_suffix_list` for the switch. `docs/ROADMAP.md` does not list it as open.
- Confidence: certain

### 23-6 [P2] Choosing a folder on Linux without a file chooser portal does nothing and says nothing

- Where: `crates/desktop/src/files.rs`, `choose_folder`
- Category: bug
- Failure: on a Linux desktop with no XDG file chooser portal, "Change" and "Change folder" appear dead: no dialog, no message, no log line. The fix-a-failure flow that offers Change folder cannot be completed.
- Evidence: `picked.await.ok()?.ok()??` drops the inner `Err`. `gpui-pre-linux` 0.3.10 `prompt_for_paths` sends `Err(anyhow!(FILE_PICKER_PORTAL_MISSING))` for that case, a message written to be shown. The same function already shows a refused path's message in the window in front. docs/ENGINEERING.md section 4 forbids discarding an error with `.ok()`.
- Confidence: likely (read from the code; Linux is not run in this audit)

### 23-7 [P2] The system accent breaks the promised 4.5:1 contrast with stock Windows colours

- Where: `crates/desktop/src/theme.rs`, `accent_colors`
- Category: wrong implementation
- Failure: in the dark scheme, near-black text on a primary button measures 2.83:1 for Windows' stock `#6B69D6`, 3.05:1 for `#8E8CD8`, 3.31:1 for `#0037DA` and 3.90:1 for `#744DA9`; pure blue measures 2.34:1. In the light scheme, a custom pure yellow gives 3.92:1 with white text. The same tone is used for links and selected text on the dark background.
- Evidence: the doc says "each pair at 4.5:1 contrast or more" and "at Wirecatch's own lightness, so its text keeps that contrast". Equal HSL lightness is not equal luminance across hues. Computed by WCAG formula from the code's own lightness (0.261 light, 0.547 dark) and `ON_ACCENT_*`. All ten fixed accents pass, from 4.91:1 up.
- Confidence: certain

### 23-8 [P2] A finished download whose file or folder is gone gets advice that cannot be followed

- Where: `crates/shell/src/api.rs`, `file_to_open`, `item_to_reveal`
- Category: wrong implementation
- Failure: opening a finished download whose file was deleted says "Download it again with Retry". No Retry is offered, and calling it would answer "This download has already finished." Show in folder on the same row, with its folder deleted, says "does not exist yet. Wirecatch creates it when the download starts", which is false for a download that finished.
- Evidence: `file_to_open` only reaches that message for `DownloadStatus::Completed`. `main_window/applies.rs` `can_retry` allows only `Failed` and `Cancelled`, and `Manager::requeue` refuses `Completed` with `WrongState`. `item_to_reveal` uses one message for every status.
- Confidence: certain

### 23-9 [P2] The start's warnings show again after the list reloads from missed events

- Where: `crates/desktop/src/library.rs`, `Library::load`
- Category: bug
- Failure: the app started with a damaged list set aside. Later a burst of more than 1,024 events outruns the window, the library reloads, and "the list was damaged" appears again as a new notification, as if it had just happened.
- Evidence: `tell_startup_notices` takes `library.startup_notices` with `mem::take` so each shows once, but `load` refills it from `manager.startup_notices().to_vec()`, a field the manager keeps for its whole life. The main window's observer tells it again at the next update. `load` also runs on `RecvError::Lagged`.
- Confidence: certain

### 23-10 [P3] The "could not save" banner stays after a later save succeeds

- Where: `crates/desktop/src/library.rs`, `Library::storage_problem`
- Category: wrong implementation
- Failure: a save fails once (a locked or full disk), then every save after it succeeds. The banner still says the list could not be saved and that recent changes may be lost, until dismissed.
- Evidence: the field's doc says "until it saves again or is dismissed". Nothing clears it on a successful save: `UiEvent` has `StorageFailed` and no counterpart, and only the banner's two buttons in `main_window/notices_bar.rs` set it to `None`.
- Confidence: certain
