## Findings

### 05-1 [P0] Replace puts two downloads on one path, so they write the same part file

- Where: `crates/core/src/manager/file_exists.rs`, `replace_at` (called from `answer_file_exists` and `on_found`)
- Category: bug
- Failure: two downloads settle on one name that is already a finished file in the folder, for example two links whose server names both `report.pdf`. Each one's run stops with a `Found`, and each one's path stays provisional. Under Ask (the default) both questions open and can wait as long as the person takes; answering Replace to both, even with "remember" on the first, makes both run at `report.pdf`. Under the Replace setting the same happens when the second server answers before the first run's `finish`. Both engines then use `report.pdf.wcpart` and `.wcstate`. The second run's `prepare` may discard and recreate the part file the first has open, and the two write different bytes into it. The finished file is corrupted, or the first file is finished and the second run's work is lost.
- Evidence: `replace_at` calls `state.claimed.insert(path)` without checking `contains`, and `Claimed` is a set, so the second insert is silent. A pending question holds no claim on `Asked::path`: only the provisional path is claimed. `found_existing` checks `taken_by_another` only at the moment of the server's answer, and neither `answer_file_exists` nor `on_found` looks again. `Destination::Exact` (`engine/src/target.rs`) continues or recreates whatever is at the path and takes no lock; the engine has no exclusive open. This breaks the promise at the top of `naming.rs` ("two downloads never share a file"). `State::assert_consistent` would panic on it in a debug build; a release build has no check. No test covers two questions on one path.
- Confidence: certain

### 05-2 [P1] "If the file is already in the folder" is skipped when the server gives no name of its own

- Where: `crates/core/src/naming.rs`, `settled_name`; with `crates/core/src/manager/downloads.rs`, `insert` (`naming::unique_path`) and `crates/core/src/manager/settle.rs`, `settle_path_checking`
- Category: broken feature
- Failure: `report.pdf` is in the folder. The person adds `https://example.com/report.pdf` with no typed name (Add dialog with the name left empty, or a captured link), and the server sends no `Content-Disposition`, or one naming the same `report.pdf`. No question is asked and Replace and Keep existing do nothing: the file downloads as `report (1).pdf` whatever the setting says. That is the behaviour D88 and D96 removed, and it is probably the most common case.
- Evidence: `insert` picks the provisional path with `unique_path`, which skips names on disk, so `row.file_name` is already `report (1).pdf`. In `settled_name`, `suggested` equals `from_link`, so `server_named_it` is false, and the name becomes `provisional`, which is `report (1).pdf`. `settle_path_checking` then tests `candidate(dir, name, 0)` = `report (1).pdf` for a duplicate, finds nothing, and `naming::same_path` accepts it as the download's own path. Only `Kind::Media` uses `unclaimed_path`, the name without the disk check.
- Why the tests miss it: every test in `tests/manager/file_exists.rs` goes through `add_into`, which sets `file_name`, so `settled_name` returns the person's choice and never reaches the provisional branch.
- Confidence: certain

### 05-3 [P1] A captured download that meets Ask is removed, and the browser saves its own copy

- Where: `crates/core/src/manager/captures.rs`, `capture_arrived` and `await_answer`; cause in `crates/core/src/manager/file_exists.rs`, `ask`
- Category: broken feature
- Failure: `ask_before_download` is off (its default is on, and a person can turn it off from a download's window) and `when_file_exists` is Ask (the default). A browser download is captured and the server names a file already in the folder. The question opens, then closes at once, the download leaves the list, and the extension is told `NotStarted`, so the browser keeps its download and saves its own copy. The person never gets to answer.
- Evidence: `stop_for_duplicate` returns `Err` without cancelling `answered`, so `ended_in_time` wakes on `exited`. `finish` has run `on_found`, then `ask`, which sets `Paused` and leaves `naming.settled` false. `Entry::server_answered` is `naming.settled || Completed`, so `await_answer` returns `Err("It stopped before the server answered.")`. `capture_arrived` then removes the handover and calls `remove_in_background`, whose `finish_removing` calls `close_file_exists`. `ErrorCode::NotStarted` is documented as "The browser keeps its own download". Replace and Keep existing pass because they settle or complete the row. No test captures a file that is already in the folder.
- Confidence: certain

### 05-4 [P2] Moving a finished file to another drive drops its Mark of the Web

- Where: `crates/core/src/manager/relocate.rs`, `move_file`
- Category: wrong implementation
- Failure: a finished program is moved through the app to a folder on another NTFS drive. `rename_no_replace` fails, so `move_file` copies with `io::copy`, which copies only the main data stream. `Zone.Identifier` stays on the deleted original, so SmartScreen no longer checks the program when it runs. A move in Explorer keeps the mark.
- Evidence: the fallback opens both files and calls `io::copy`. `zone::mark` is called only from `ticker.rs`, `run.rs` (`download_marked`) and `media_run/placement.rs`, none of them on this path. A finished file gets no new run, unlike a partial one, whose next run marks it again. The decision that gave up the browser's check relies on this mark ("a finished download carries the Mark of the Web", DECISIONS.md).
- Confidence: certain

### 05-5 [P2] The file-exists question carries the link's password to the UI

- Where: `crates/core/src/manager/file_exists.rs`, `ask`
- Category: bug
- Failure: a download of `https://user:secret@example.com/a.zip` meets Ask. `FileExistsQuestion.url` holds the password in `UiEvent::FileExistsRequested` and in `pending_file_exists`, where every other path hides it.
- Evidence: `url: entry.row.url.clone()`. `Entry::row` "keeps the real link", and `Entry::summary` and every question in `captures.rs` and `media.rs` go through `redact::url_for_display`. This is the only place that does not.
- Confidence: certain

### 05-6 [P2] An answered Replace is forgotten on restart, and the file finishes under another name

- Where: `crates/core/src/manager/file_exists.rs`, `replace_at`; `crates/core/src/manager/state.rs`, `Entry::on_existing`
- Category: wrong implementation
- Failure: the person chooses Replace for a large file, then the app restarts before it finishes (a pause and a reboot is enough). The download finishes and, instead of replacing the file, moves to `name (1)` with no question. The person ends with two files and a list row pointing at the new name, and nothing says the choice was dropped.
- Evidence: the field's doc says "after a restart a duplicate is judged again", but `replace_at` saves `naming.settled = true` and the path, so the next run is `Target::Exact` and never reaches `found_existing`. `restore.rs` sets `on_existing: None`, `engine_request` then uses `ExistingFile::Refuse`, and the engine's `TargetTaken` leads to `take_next_free_name`. No data is lost; the choice is. Keep both does behave as the doc says, since it stays unsettled and is asked again.
- Confidence: certain

### 05-7 [P2] An open question outlives Resume all, a new link and a move, and answering it later acts on the changed download

- Where: `crates/core/src/manager/file_exists.rs`, `answer_file_exists`; missing `close_file_exists` in `downloads.rs` (`resume_all`, `refresh_link`) and `relocate.rs` (`set_download_folder`)
- Category: bug
- Failure, three cases. (a) Resume all, or a refreshed link, while asked: the download runs again with the question still open. If the setting has since become Keep both or the file has gone, nothing closes it; the download completes, and answering Replace sets the finished row back to `Queued` over a different path, leaving its finished file unlisted. Cancel marks a finished download cancelled. (b) A move while asked: the partial state goes to folder G, then Replace sends the row back to the question's path in folder F and replaces the file there, against the person's latest choice. (c) An answer while that move is under way: `replace_at` changes `row.path` and claims F, then `finish_move` overwrites `row.path` and F's claim is never released.
- Evidence: D88.3 says resuming, cancelling or removing closes the question; `resume`, `retry` (through `requeue`), `cancel` and `finish_removing` do, these three do not. `answer_file_exists` tests only `!hold.is_removing() && run.is_none()`: not that the row is still `Paused`, and not that no move is under way. `ask` closes an older question only when the same download asks again.
- Confidence: certain for (a) and (b) in the code; (c) needs an answer inside the move's time

### 05-8 [P2] Choosing the folder the guess already points at is not remembered

- Where: `crates/core/src/manager/relocate.rs`, `set_download_folder`
- Category: bug
- Failure: a link `.../report.pdf` is guessed into Documents and the server has not answered. The person presses Change and picks Documents. The server's `Content-Disposition` says `movie.mp4`, and the file goes to Video instead of the folder the person chose.
- Evidence: the early `return Ok(())` when `entry.path().parent() == Some(dir)` runs before `naming.folder` is set. `finish_move` sets it for an unsettled download, and `finish_moving` handles the same case correctly when it arises after a run exits (`moved = Ok(old_path)`), so only the early return loses it. `settle_path_checking` uses `folder_for` when `naming.folder` is `None`.
- Confidence: certain

### 05-9 [P2] The path resolver blocks a runtime thread on the disk

- Where: `crates/core/src/manager/settle.rs`, `settle_path` and `settle_path_checking`; `crates/core/src/manager/file_exists.rs`, `found_existing`
- Category: wrong implementation
- Failure: downloads into an unreachable network folder. Each `exists`, `metadata` and resume file read in the resolver blocks a tokio worker until the system gives up, several calls per name tried. Several downloads into that folder take all the workers, which stalls every other download's task and the ticker, on the same runtime.
- Evidence: `engine/src/target.rs`, `Destination::choose`: "the resolver is the caller's, which must not block", called directly from the async `download`. `core` has no `block_in_place` around it. The disk calls are `naming::finished_size`, `saved_at`, `is_free_on_disk` and `left_by`. `settle_path_checking` releases the manager's lock for just this slow-folder case, but the thread is still held. ENGINEERING.md section 4 forbids blocking calls on async tasks.
- Confidence: likely (the stall needs a slow folder; the blocking itself is certain)

### 05-10 [P2] A partial file left by a crash is not picked up again when the link has a password

- Where: `crates/core/src/naming.rs`, `left_by` and `normalized_url`
- Category: bug
- Failure: `https://user:secret@example.com/a.zip`; the app stops after the engine began the file, before the settled path was saved. On the next run `left_by` says the files are not its own, so the download starts over as `a (1).zip` and `a.zip.wcpart` and `.wcstate` stay on disk for good. The test `a_part_file_left_by_a_crash_is_picked_up_again` covers only a link with no password.
- Evidence: the engine records `without_password(&request.url)` in the resume file (`download.rs`, `saved_url`), while `settle_path` passes `entry.row.url`, the real link. `normalized_url` only reparses, so the two strings differ. The engine has its own rule for this, `same_download` in `target.rs`, which is private to it.
- Confidence: certain

### 05-11 [P2] Keep existing and Replace leave the wrong category on the row

- Where: `crates/core/src/manager/file_exists.rs`, `keep_existing` and `replace_at`
- Category: bug
- Failure: (a) Keep existing with a link `dl?id=1` and a server name `Holiday Movie.mp4`: the row completes with the Video folder's file but keeps the provisional category `Other`, so the category filter is wrong for good. (b) Replace for a file with no extension placed by its content type (`audio/mpeg`, in Music): `replace_at` recomputes from the name alone and gives `Other`.
- Evidence: `keep_existing` and `settle_at` never touch `row.category`. `replace_at` uses `category_of` only, while `settle_path_checking` also uses `category_from_mime`. `settle_path_checking` has the right category when it stops for the duplicate, but `Found` does not carry it.
- Confidence: certain

### 05-12 [P2] Cancel or Pause in the moment after a duplicate is found is overridden

- Where: `crates/core/src/manager/run.rs`, `finish` (the `if let Some(found)` after the status match); `crates/core/src/manager/state.rs`, `Entry::stop`
- Category: bug
- Failure: the setting is Replace and the person cancels just as the server's answer found a duplicate. `Entry::stop` replaces `Stop::FileExists` with `Stop::Cancel`, but `run.found` is still set. `finish` marks the row cancelled and discards its files, then `on_found` runs anyway: `replace_at` sets `Queued` and `OnExisting::Replace`, so the cancelled download restarts and replaces the file. Pause is lost the same way, and Keep existing turns a cancelled row into a completed one.
- Evidence: `stop` lets any user's choice override, since `is_users_choice` excludes `FileExists`. `found` is taken from the run regardless of `run.stop`. The window is the time between `stop_for_duplicate` and `finish`, normally milliseconds.
- Confidence: likely

### 05-13 [P3] A finished row gives up a claim that another download holds

- Where: `crates/core/src/manager/relocate.rs`, `finish_move`; `crates/core/src/manager/state.rs`, `remove_entry`
- Category: design
- Failure: A is finished at `x`. The same link again, with Replace, makes B the owner of `x`, queued or running. Moving A, or removing it from the list, calls `claimed.remove(x)`, so B's path is no longer claimed. A debug build panics in `assert_consistent`. In a release build, once A's move has emptied `x` and while B has no part file yet, a new download can take `x` and share it with B, which is the outcome of 05-1 by a longer route.
- Evidence: `Claimed` is a set of paths with no owner, and both callers remove a finished row's path though a finished row never held a claim (`insert_entry` claims only unfinished rows). In `finish_move`, the `new_path != old_path` branch does not check `completed`.
- Confidence: likely

### 05-14 [P3] `the_same_server_name_twice_gets_a_free_name` fails when the first download wins the race

- Where: `crates/core/tests/manager/settle.rs`, `the_same_server_name_twice_gets_a_free_name`
- Category: fake test
- Failure: the test assumes the first download still holds its claim when the second one's server answers. With a 4 KiB body and no rate limit, a loaded machine can finish the first first. The second then finds a finished `report.pdf`, and under the default Ask it pauses with a question. `wait_status(second, Completed)` never succeeds, and the test fails after `PATIENCE`.
- Evidence: the harness leaves `when_file_exists` at Ask, since only `file_exists.rs` and `media.rs` among the core tests set it. `found_existing` returns `None` for `taken_by_another` only while the claim exists; `complete` releases it. ENGINEERING.md section 7 says to hold the server rather than race the machine.
- Confidence: likely
