## Findings

### 18-1 [P2] A queue's run ends while its last download only waits for an answer or a move, and that download then waits for the next start

- Where: `crates/core/src/manager/scheduling.rs`, `evaluate_gates` and `view_of`; `crates/queues/src/schedule.rs`, `Gate::is_open`
- Category: bug
- Failure: a queue runs by "Start now", or by a schedule with no stop time, and has one download left. Any of these happens to it: its file already exists and the setting is Ask; the person changes its folder while it runs; its server answers with a web page. The run ends at that moment. After the person answers Keep both, or the move finishes, or the page's video is added, the download is `Queued` with `QueueSchedule` and sits until the next scheduled start (up to a week with weekdays set). For Start now, the person sees it stop right after pressing Start now and answering the question.
- Evidence: `has_work` is `busy.contains(id)`, and `busy` comes from `view_of`, which answers `None` for an entry with no run that is not `is_waiting`. `finish` in `run.rs` takes the run, and `on_found` sets `Paused` (file exists), or the hold is `Moving` (`set_download_folder` calls `begin_move`, then `stop_run(Requeue)`), or the status is left as it was with `Stop::ReadAsVideo`; then `finish` calls `reconcile`. In that reconcile `has_work` is false, so `running_outside_schedule` is cleared and `Gate::is_open` resets `running_until_empty`. The answer in `file_exists.rs` (`FileExistsChoice::KeepBoth`) sets `Queued`, and `finish_move` reconciles with the gate already closed. Traced from the code, no test run; no test in `tests/manager/queues.rs` or `schedule.rs` covers a question or a move during a run.
- Confidence: certain

### 18-2 [P2] For a schedule with no stop time, the sidebar and the Start now button follow a different answer from the one that decides what runs

- Where: `crates/queues/src/schedule.rs`, `allows`; used by `crates/desktop/src/main_window/sidebar.rs`, `outside_schedule` (and through it `queue_header.rs`, `queue_actions`, and `sidebar.rs`, `queue_menu`)
- Category: bug
- Failure: a queue with start 22:00 and no stop. At 22:30 the person adds a download (or the run has already ended). The core keeps it `Queued` with "starts at 22:00" (test `a_start_time_without_stop_runs_until_the_queue_is_empty` proves it waits). The sidebar says "1 waiting", shows no "Starts at", and neither the header nor the queue's menu offers Start now until midnight, so the one way to run it now is missing for the rest of the day. The reverse: a run still going after midnight, or the morning after on an unlisted day, is `allows == false`, so the queue's tooltip reads "Starts at 22:00" and Start now is offered while it downloads.
- Evidence: `allows` is true from `start` until the day ends on a listed day, and knows nothing of `Gate`. The gate's `running_until_empty` is private to the core and not in `QueueStatus`, so the window cannot read it. `outside = outside_schedule(queue).is_some() && !paused` is the only condition for showing Start now in both places. The doc on `allows` says the gate decides when the queue really starts; a search of `docs/DECISIONS.md` for Start now found only that a queue's header carries it, and no choice to hide it here.
- Confidence: certain

### 18-3 [P2] A restart keeps a schedule's run only if a download of the queue was running at that moment

- Where: `crates/core/src/manager/restore.rs`, `restore_entry`; `crates/queues/src/schedule.rs`, `Gate`
- Category: wrong implementation
- Failure: a queue Night with start 02:00 and no stop has crossed its start and has work, but none of its downloads is running because the app's limit is full with other queues' downloads, or because the queue is paused for a moment. The app restarts at 03:00. Night's gate comes back closed, last_checked is the restart time, so nothing runs in Night until 02:00 the next day, although its run had not ended. In the other direction: Start now on such a queue, restart while a download runs, then pause and resume the queue. `resume_run` opened the gate, so the queue carries on, where without the restart pausing ends the run and resuming follows the schedule (the behaviour `start_now_and_its_end_by_pausing_survive_a_restart` proves for a window schedule).
- Evidence: `running_until_empty` is not stored. Its only restoration is `slot.gate.resume_run()` for a row whose stored status is `Connecting`, `Downloading` or `Processing`, whichever reason it was running for. `running_outside_schedule` is stored, so the two kinds of run differ across a restart.
- Confidence: certain

### 18-4 [P2] When a queue closes, its slots are given away in the same plan, so the app's limit is exceeded until those downloads stop

- Where: `crates/queues/src/plan.rs`, `plan`
- Category: wrong implementation
- Failure: app limit 3, Night running 3, Main with 3 waiting. Night's window closes or Night is paused. The plan stops Night's 3 and starts Main's 3 in one pass, so 6 downloads run until Night's have stopped, which takes as long as the stop timeout for a server that has gone quiet. A person who set the limit to spare a slow line, or a server limiting connections, sees twice the limit.
- Evidence: a `Running` download found `over` is pushed to `out.stop` and `continue`s without adding to `running_total` or `held`, so the fill loop below sees the room free. The function's doc says "a stopping download keeps its slot until it stops", and `reconcile` applies `stop` and `start` together; only from the next plan do those downloads count, as `Stopping`. `plan(&[closed A, open B], [1 Running in A, 2 Waiting in B], 1)` answers stop 1, start 2. Lowered limits are not affected, since `running_total` and `held` are already at the limit. `closed_queue_stops_its_downloads` has one queue only.
- Confidence: certain

### 18-5 [P2] Regular expressions that differ only in case are treated as the same rule, and the second is dropped without a word

- Where: `crates/queues/src/rules.rs`, `cleaned`
- Category: bug
- Failure: an auto queue with the regular expression rules `\d+\.mkv` and `\D+\.mkv` (or `\s` and `\S`, `\b` and `\B`, `(?-i)A` and `(?-i)a`) saves with only the first. Files only the second matches go elsewhere, and saving says nothing.
- Evidence: `seen.insert(read.to_lowercase())` decides what is a repeat for every kind of rule. `checked` passes `file_names` through it with either syntax. Case is meaningful in a regular expression's escapes and with `(?-i)`, which `NameSyntax::Regex`'s doc says a rule may use. Ignoring case is right for sites, file types and wildcards.
- Confidence: certain

## Suggestions

### 18-S1 A start time passed while the app was closed could count, as one passed during sleep does

- Today: `start_crossed` finds a start up to 7 days back when the computer sleeps through it, since `last_checked` keeps its value. A restart sets `last_checked` to the start-up time, so a queue with no stop time whose 02:00 passed with the computer off waits for the next 02:00. A queue with a window opens as soon as the app starts inside it.
- Better: store when schedules were last checked, and let the first check after a start look back from there, within `MAX_CATCH_UP_DAYS`. Established managers mostly only act at the time while running (IDM starts a queue at its time), so this would go beyond them.
- Value: a night queue still runs on a computer that was off or booted late.
