## Findings

### 12-1 [P1] An `APPIMAGE` variable inherited from another program makes the update overwrite that program

- Where: `crates/shell/src/updates.rs`, `install_kind` and `replace_appimage`
- Category: bug
- Failure: Wirecatch installed from a `.deb` or `.rpm` is started from a process that itself runs from another AppImage, such as a terminal inside an editor shipped as an AppImage, or an AppImage launcher. The AppImage runtime exports `APPIMAGE` and children inherit it, so the variable names the other program, for example `~/Apps/Editor.AppImage`. `install_kind` returns `AppImage` for it, the check offers "Install and restart", and `replace_appimage` renames the Wirecatch AppImage over `~/Apps/Editor.AppImage` and starts it. The other program is gone, replaced by Wirecatch, and a system-package install stays on the old version.
- Evidence: `install_kind` tests only `var_os(APPIMAGE_VAR).is_some()`; `replace_appimage` takes the rename target from the same variable with no check that the running program came from that file. Nothing compares `current_exe` with `APPDIR` or the mount. `autostart::program` and `bridge::register_on_start` (`crates/shell/src/autostart.rs`, `crates/shell/src/bridge.rs`) trust the variable the same way, so in this state the start-at-sign-in entry and the browser launcher also name the other program. Severity is P1 rather than P0 only because the trigger is uncommon and the lost file can usually be downloaded again; a validator may raise it.
- Confidence: certain for the code path; the inheritance is how the AppImage runtime behaves and was not run here.

### 12-2 [P2] Installers are never removed from the updates folder

- Where: `crates/core/src/manager/app_update.rs`, `fetch_app_update`; `crates/desktop/src/app_update.rs`, `install`
- Category: inefficiency
- Failure: every update leaves a whole installer in `<data folder>/updates`: on Windows the setup that ran, on Linux the AppImage, which `replace_appimage` copies rather than moves. A download cancelled and never resumed leaves a full-size `.wcpart` and its resume file, whose name holds the version, so a later release never picks it up. The folder grows by one installer per release for the life of the install.
- Evidence: `UPDATES_FOLDER` is read only by `fetch_app_update`, and the only deletion in the flow is the one for a file that fails its check. No `.rs` file outside `manager/app_update.rs` names the folder, and neither startup nor the next update clears it.
- Confidence: certain

### 12-3 [P2] The AppImage restart races the old copy's exit and can end with no app running

- Where: `crates/shell/src/updates.rs`, `replace_appimage`; `crates/desktop/src/app_update.rs`, `install`
- Category: bug
- Failure: `replace_appimage` starts the new AppImage before the old copy has begun quitting, and the old copy holds the endpoint until its process exits. The new copy's `bridge::bind` then finds it in use and hands its launch over. If that lands while the old copy is still stopping downloads, `lifecycle::start_again_later` catches it and the app restarts correctly. If it lands after `lifecycle::quit` has taken `Quitting::again` and before the process has exited, the launch is recorded where nothing reads it (or `bring_up` never runs), and the new copy returns: no copy is left running. If the connection breaks during the hand-over, `launch::say_already_running` tells the person the app is running when it is about to be gone.
- Evidence: order in `install`: `updates::install`, which spawns the program, then `lifecycle::quit`. In `lifecycle::quit`: `again.take()`, then `cx.quit()`, with the serving task still accepting between them. `crates/desktop/src/main.rs` returns right after `hand_over`, or after `say_already_running` when it fails. The window is short, but a program's start time on a busy machine moves freely across it. `start_again_later` already holds the correct mechanism: start after the endpoint is freed.
- Confidence: likely (from the code; Linux was not run)

### 12-4 [P3] The AppImage replacement is renamed into place without being flushed

- Where: `crates/shell/src/updates.rs`, `replace_appimage`
- Category: wrong implementation
- Failure: power loss or a system crash right after an update, on a file system that does not flush on rename, can leave the only copy of the app empty or truncated at its own path. A failed `set_permissions` or `rename` also leaves `.wirecatch-update.AppImage` beside the app.
- Evidence: `std::fs::copy`, `set_permissions`, `rename`, with no `sync_all` on the staged file or the folder. `write_private` in `crates/shell/src/appimage.rs`, the same crate, calls `sync_all` before its rename.
- Confidence: likely

### 12-5 [P3] Declining the administrator prompt reads as "could not be started (error 5)"

- Where: `crates/shell/src/updates.rs`, `InstallError::Start` and `run_setup`
- Category: wrong implementation
- Failure: the person answers No at the UAC prompt, the most ordinary way this step fails. `ShellExecuteW` returns `SE_ERR_ACCESSDENIED`, and the banner shows "The update could not be started (error 5)." It does not say what happened or what to do, as `docs/ENGINEERING.md` section 8 requires.
- Evidence: every value at or below 32 becomes `Start(usize)`, whose text is only the number. The value for a declined prompt comes from the system's documented behaviour and was not run here.
- Confidence: likely

### 12-6 [P3] No test holds the rule that a manifest must name its release's own version

- Where: `crates/core/src/manager/app_update.rs`, `check_app_update` and its `tests`
- Category: fake test
- Failure: deleting the `manifest.version` comparison leaves every test passing. That comparison is what stops a validly signed old manifest being attached to a newer tag to install an old version (D111.3).
- Evidence: `Harness::publish` always derives the manifest's version from the tag, and no file under any crate's `tests/` calls `check_app_update`. The same goes for `asset.size == file.size`: no test lists an asset whose size differs from the manifest. `docs/ENGINEERING.md` sections 7 and 11 ask for hostile cases.
- Confidence: certain

## Suggestions

### 12-S1 Keep a finished, checked installer for Try again

- Today: after a declined prompt or a failed start, Try again downloads the whole installer again, since the engine replaces a file at the exact path. A cancelled download does resume.
- Better: `fetch_app_update` first checks an existing file at the target against the manifest's size and SHA-256, and returns it when it matches.
- Value: a second click starts the setup at once, with no second download.

### 12-S2 Check the signature against the product's public key in the release workflow

- Today: `manifest.mjs` signs with whatever `UPDATER_PRIVATE_KEY` holds. A secret that does not pair with `config/product.toml`'s key still yields a draft that looks right, and every installed copy then refuses that release.
- Better: after signing, the script verifies with `[updates] public_key` and fails the workflow when it does not match.
- Value: a key mix-up stops at the draft rather than reaching people as a failed update check.

### 12-S3 Let installed copies read manifests from later versions

- Today: `Manifest` and `UpdateFile` use `deny_unknown_fields`, and `System`, `Arch` and `FileKind` are closed enums, so one new field or one new kind of installer in a manifest makes every installed copy refuse the whole release.
- Better: ignore unknown fields once the signature has passed, and skip file entries whose system, architecture or kind is unknown. The signature already proves the origin.
- Value: a later release can add a package format without cutting older copies off from updates.
