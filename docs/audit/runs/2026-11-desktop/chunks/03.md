## Findings

### 03-1 [P1] One unreadable cell stops the app opening at every start

- Where: `crates/store/src/lib.rs`, `Store::open_with`, `is_damage`, `load`, `read_download`, `read_queue`, `read_value`, `migrate`
- Category: bug
- Failure: a value in a stored row that passes `PRAGMA integrity_check` but cannot convert to the type asked for: invalid UTF-8 in a TEXT cell (`url`, `path`, `origin`, `status`, a settings value), a TEXT cell whose record header turned into BLOB, or text in `done` or `added_at`. A single flipped bit by a failing disk or a bad sync tool is enough; it can also come from a negative `user_version` in the file's header. `Store::open` then returns `StoreError::Database`, and the app shows "Check that Wirecatch's data folder can be written to and the disk is not full, then restart Wirecatch" on every start. Nothing is set aside and no restart can help. The person must find and delete the database by hand.
- Evidence: `read_download` reads with `row.get(..)?`, and only `category` and `status` go through the `StoredRow::Unreadable` path after their text was read. `row.get` maps these cases to `Error::Utf8Error`, `InvalidColumnType` or `IntegralValueOutOfRange`, not to `SqliteFailure`. `sqlite_error_code()` is `None` for all of them, so `is_damage` is false and `open_with` takes `Err(e) => return Err(e)`. `integrity_check` does not look at UTF-8 or at the declared type of a non-STRICT column. The doc on `Store::open` promises "a power cut or a bad sync tool never stops Wirecatch from opening", and the doc on `read_download` says "A row that cannot be understood is reported rather than failing the whole start". `read_queue` and `read_value` have the same gap. Reproduce with `UPDATE downloads SET url = CAST(x'FF' AS TEXT) WHERE id = 1` between two opens. No test covers a cell of the wrong type or bad text; `unreadable_rows_are_skipped` only uses a valid text that names no status.
- Confidence: certain

### 03-2 [P2] Settings, queues and proxy passwords that cannot be read are replaced for good, without telling the person

- Where: `crates/store/src/lib.rs`, `read_value`, `read_queue`, `load`, `Snapshot`, `Recovery`; `crates/core/src/manager/restore.rs`, `restore`; `crates/core/src/manager/mod.rs`, `Manager::open`
- Category: wrong implementation
- Failure: the `app` settings value does not deserialize, for example a `categories` entry or a nested `media` value naming a variant an older build does not know after going back a version, or a damaged value. `snapshot.settings` is `None`, the same as a first start, so `restore` takes the defaults with `settings_changed = true` and `Manager::open` calls `save_settings`: the person's folders, limits and proxy choice are overwritten by defaults, with only a `warn` in the log. A queue whose settings cannot be read is dropped from the snapshot, and `Manager::open` calls `save_queues` on every start, whose `DELETE FROM queues` then erases it for good while its downloads silently join the default queue. An unreadable `proxy_passwords` value loses every proxy password the same way. No startup notice appears in any of these cases.
- Evidence: `Recovery` has only `Damaged`, `UnreadableKept` and `ValuesReset`, so the store has no way to say it. Downloads get the opposite treatment: an unreadable row is kept hidden for a version that can read it and is reported (`UnreadableKept`). The comment in `Manager::open` says settings are written back only when restoring changed them "so what another build saved and this one cannot read ... survives", which holds only for the top-level fields using `known_or_default`. The schema version does not guard this: a new enum value adds no migration, so `TooNew` does not fire.
- Confidence: certain

### 03-3 [P2] A write that can never pass raises a system notification for every batch

- Where: `crates/store/src/lib.rs`, `write_until_closed`, `apply_one_by_one`, `may_pass_later`; `crates/desktop/src/notices.rs`, `storage_failed`
- Category: bug
- Failure: the database becomes damaged while the app runs, or a table is missing, so each write fails with an error `may_pass_later` refuses. With downloads running and the main window closed to the tray, each progress batch ends in another `on_failure`, and each one calls `system.show(..)`: a new notification every time progress is saved, for as long as downloads run.
- Evidence: `write_until_closed` reports when `retried == 0`, and its comment says "Reported once per spell of failures". `apply_one_by_one` drops writes that can never pass, so `kept` stays empty, `retried` is 0 on the next batch, and every batch counts as a new spell. `storage_failures` publishes each report and `notices::storage_failed` applies no limit. The test `a_write_that_keeps_failing_is_reported` sends only one failing batch, and the one-report test (`writes_that_fail_while_the_database_is_busy_...`) covers only the busy case.
- Confidence: certain

### 03-4 [P2] The "could not save" banner is wrong in both directions: Try again hides it while saving still fails, and it stays after saving recovers

- Where: `crates/store/src/lib.rs`, `FailureHandler`, `write_until_closed`; `crates/desktop/src/library.rs`, `storage_problem`; `crates/desktop/src/main_window/notices_bar.rs`, `storage_banner`
- Category: broken feature
- Failure, Try again: the disk is full and writes are kept. The person clicks Try again. The banner's handler sets `storage_problem = None` first, then sends an empty settings change. Writes are still kept, so `retried > 0`, `fresh` is false and `on_failure` stays silent. The banner is gone though nothing was saved, and it does not return during this spell; the person believes the list is safe, and the changes are lost when the app closes.
- Failure, recovery: a backup tool holds the database for 30 seconds, the banner appears, then the kept writes land on their own. The banner keeps saying "could not save its download list ... Recent changes may be lost" until it is clicked.
- Evidence: `FailureHandler` is the store's only signal: failure, at the start of a spell. There is no signal for "everything kept has landed" and no way to ask whether writes are still kept. The field doc in `library.rs` promises "until it saves again or is dismissed", and only the two buttons clear it.
- Confidence: certain

### 03-5 [P2] A damaged list set aside can be deleted at the next start instead of being kept a month

- Where: `crates/store/src/lib.rs`, `remove_old_copies`, `set_aside`, `KEEP_COPIES_FOR`
- Category: bug
- Failure: the database file was last written over 30 days before the damage is found: the app was not opened for a month, or a sync tool restored an old file with its old time. `set_aside` keeps it and the notice tells the person where it is. On the very next start `remove_old_copies` deletes it, with its journal, and that may be minutes later. The only copy that can be recovered by hand is gone.
- Evidence: age comes from the file's `modified()` time, and a rename keeps that time. The time it was set aside is in the name (`.damaged-<unix ms>`) but is never read. `KEEP_COPIES_FOR`'s doc says a month "leaves time to recover a list by hand". `old_copies_of_the_list_are_removed` sets the old time on the copies directly, so it cannot see this. `.bak-v` copies are not affected, since `VACUUM INTO` writes a new file.
- Confidence: certain

### 03-6 [P3] The samples test does not cover the enum columns or the queue reason, so a rename hides rows unnoticed

- Where: `crates/store/tests/samples.rs`, `KINDS`; `crates/store/src/lib.rs`, `save_download`, `read_download`
- Category: fake test
- Failure: a `serde` rename of `DownloadStatus::Completed` or `Category::Video` in `crates/protocol`, or of a `QueueReason` variant, passes every store test, since the round trip writes and reads the new name. On a released build every stored row with the old name becomes `StoredRow::Unreadable` and disappears from the list; an old queue reason falls silently to the default.
- Evidence: `KINDS` has no entry for `status`, `category`, `chosen_by` or `queue_reason`, all of which the store saves. Only `insert_old_download` in the unit tests holds literals (`archive`, `paused`), so other values are not pinned. `docs/ENGINEERING.md` section 4 says a variant whose meaning changes gets a new name "so the samples test sees the change", and D81.3 says the samples cover what is saved.
- Confidence: certain

### 03-7 [P3] Store tests race the machine against the two-second lock wait

- Where: `crates/store/src/lib.rs`, tests `migrations_run_once`, `negative_counts_are_repaired_and_reported`, `unreadable_downloads_are_kept_without_their_sign_in`, `unreadable_rows_are_skipped`
- Category: design
- Failure: on a busy runner, closing the connection (a checkpoint with a flush to disk) takes over `LOCK_WAIT` (2 s), and the next `Store::open(..).unwrap()` panics with `AlreadyOpen`, so an unrelated test fails.
- Evidence: `let (_, snapshot) = Store::open(..)` and `drop(Store::open(..).unwrap())` drop the handle without waiting. The thread closes on its own, and the next open only has `LOCK_WAIT` to find the lock free. `unreadable_rows_are_skipped` calls `store.close(Duration::from_secs(5))`, whose timeout only logs, instead of `PATIENCE`. `docs/ENGINEERING.md` section 7: "A test never races the machine against a time limit of the code under test". The `close` helper in the same file does it correctly. The `test-timing` check cannot see these.
- Confidence: likely

### 03-8 [P3] Docs say failed writes are never dropped, and the code drops them

- Where: `crates/store/src/lib.rs`, doc of `run`, `apply_one_by_one`, `trim_kept`, doc of the test `a_write_that_can_never_pass_is_dropped_and_the_others_are_saved`
- Category: bug
- Failure: a delete that fails with an error `may_pass_later` refuses is logged and dropped, so the removed download returns at the next start with its cookies, the exact case the `run` doc says cannot happen ("never dropped: a lost delete would bring back a removed download"). `trim_kept` also drops the oldest writes past `MAX_KEPT`, deletes among them. The test's doc says the write "is itself kept and tried again later rather than dropped", while its name and assertions say the opposite. A later change made on the strength of these docs would rely on a guarantee that is not there.
- Evidence: the `Err(e)` arm of `apply_one_by_one` ("never will be; dropping it"), and `kept.drain(..)` in `trim_kept`.
- Confidence: certain

### 03-9 [P3] `lock_path` repeats `with_suffix`

- Where: `crates/store/src/lib.rs`, `lock_path`; `crates/files/src/lib.rs`, `with_suffix`

- Failure: three lines rebuild what `with_suffix(database, ".lock")` does; the same file imports and uses `with_suffix` for every other side file.

## Suggestions

### 03-S1 Save what can be read from a damaged list

- Today: one damaged page sets the whole list aside and starts empty, losing every download's progress and link, the settings, the queues and the proxy passwords, even when nearly every row is readable. The kept file can only be recovered by hand with SQLite tools.
- Better: before starting empty, copy what still reads into the new list, table by table and row by row (or through SQLite's recovery extension), and say how many rows were saved. Part files on disk could then still resume. How other download managers handle this was not confirmed from their own sources.
- Value: a damaged page costs a few rows instead of the whole list and every setting.
