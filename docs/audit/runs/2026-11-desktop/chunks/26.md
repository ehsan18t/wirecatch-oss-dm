## Findings

### 26-1 [P2] An open failure notice in the browser loses its buttons after 32 later notices of any kind

- Where: `crates/shell/src/browser_notices.rs`, `KEPT_NOTICES` and `BrowserNotices::register`, `ask`, `pressed`, `outdated_by`
- Category: wrong implementation
- Failure: a "Download failed" notice is open in the browser (it stays until closed). 32 more notices are registered, for example a playlist or a run of captures with their brief "Download added" notices. Pressing Try again or the notice's text then does nothing, with no message. The notice also can no longer be taken back when the download is retried or removed (D97.4).
- Evidence: `register` pops the oldest entry of one `kept` queue regardless of kind or whether the notice is still open. `pressed` returns `None` for a forgotten id, and `outdated_by` only walks `kept`. Notices that lasted 3 seconds hold slots as long as failures that wait for the person. `ask` also registers before finding that no browser is connected, and `give_up` leaves the entry in `kept`, so notices no browser ever received push out live ones. The system side avoids exactly this: `system_notifications.rs` holds brief toasts apart "so a run of them never drops a kept one" (D63.2).
- Confidence: certain

### 26-2 [P2] Clicking the speed limit or proxy that is already checked removes its tick

- Where: `crates/desktop/src/tray.rs`, `menu`, `follow`, `on_click`; `crates/shell/src/tray_speed.rs`, `crates/shell/src/tray_proxy.rs`
- Category: bug
- Failure: open the tray's Speed limit (or Proxy) submenu and click the checked entry. The setting does not change, but the entry shows unchecked and no entry in the submenu is checked, until something else changes the menu. The same happens for any entry whose `switch` fails, and for a queue whose toggle fails.
- Evidence: entries are `CheckMenuItem`s. muda 0.20.0 flips an item's check itself on click (`handle_item_activate`, `MenuItemAction::Toggle`: `state.checked = !state.checked`) before sending the event. `follow` rebuilds the menu only when `Tray::choices` differ, and the app's state is unchanged, so `tray.choices != choices` is false and muda's flipped state stays. Checked in muda's Windows source; the Linux backend was not traced.
- Confidence: certain

### 26-3 [P2] A queue or proxy name containing `&` shows wrongly in the tray menu

- Where: `crates/desktop/src/tray.rs`, `menu` (`checks`); `crates/shell/src/tray_queues.rs`, `items`; `crates/shell/src/tray_proxy.rs`, `items`
- Category: bug
- Failure: a queue named `Music & Video` or `R&D` loses the ampersand in the tray's Queues submenu and underlines the next character (`RD`); same for a proxy profile's name.
- Evidence: labels are the person's text passed unchanged to `CheckMenuItem::with_id`. muda's docs for it: "To display a `&` without assigning a mnemenonic, use `&&`". tray-icon's Linux backend (`to_ksni_mnemonic`) reads `&` the same way, turning it into `_`.
- Confidence: certain

### 26-4 [P2] A tray action that fails tells the person nothing

- Where: `crates/desktop/src/tray.rs`, `on_click`, `AppShell::open_folder`; `crates/shell/src/tray.rs`, `perform`
- Category: broken feature
- Failure: click "Open downloads folder" when the default folder is missing or on a disconnected drive, or "Pause all" or "Resume all" while the list is opening or after it failed to open: nothing happens on screen. The only trace is a log line. After a failed open, the text in the log also says "still starting", which is untrue.
- Evidence: every `Err` in `on_click` goes to `tracing::warn!`, and `open_folder`'s `None` branch only logs. `perform`'s docs say pausing and resuming "then explain that", and `pausing_before_the_manager_opens_explains_why_it_cannot` asserts the message text, but no code shows the message. `Pause all` and `Resume all` stay enabled in `menu` in those states. `notices.rs` already has the rule and the means: `could_not`, "What cannot be done is told in a notification of its own, since no window asked."
- Confidence: certain

### 26-5 [P2] A download that is retried or removed just after it ended is still told as ended, and can be counted twice

- Where: `crates/shell/src/teller.rs`, `Teller::ended`, `take_due`; `crates/desktop/src/notices.rs`, `watch`, `ask_browser`; `crates/shell/src/browser_notices.rs`, `outdated_by`
- Category: wrong implementation
- Failure: three cases.
  - A download fails, and the person presses Try again within `NOTIFY_BATCH` (3 s). "Download failed" still appears 3 s after the failure while the download is running.
  - The retry fails again inside the same batch: `Teller::failed` holds the row twice and the notice reads "2 downloads failed: a.zip and a.zip". A row removed during the batch is told too, and its Open or Try again then gives "could not do that".
  - A notice is made outdated while the browser's answer is awaited (1 s): `outdated_by` removes the `waiting` sender, so `answered` returns false at once and `ask_browser` shows the system notification for the download that was just retried or removed. The browser notice is withdrawn and the toast replaces it.
- Evidence: `Teller` only ever adds to `finished` and `failed`; nothing removes on later `DownloadsChanged` or `DownloadsRemoved`, and `watch` passes it only `Ended`. `follow` works only on notices already registered, so D97.4 misses the batch. `answered` is `timeout(..).await.is_ok_and(|r| r.is_ok())`, which cannot tell a dropped sender from no answer.
- Confidence: certain

### 26-6 [P2] The notice of a failed save ignores the Do Not Disturb setting

- Where: `crates/desktop/src/notices.rs`, `storage_failed`
- Category: wrong implementation
- Failure: with "Show notifications during Do Not Disturb" off, the main window closed and the database failing to save, the toast is still marked urgent and asks to come through Do Not Disturb.
- Evidence: `storage_failed` passes a literal `true`. D64.2 lists this notice under the setting, read with the current settings; only the notice sent before the list opens may use the default. `could_not` in the same file does it properly with `Backend::now`.
- Confidence: certain

### 26-7 [P3] The tray rebuilds a whole-list map on the interface thread at every progress tick

- Where: `crates/desktop/src/tray.rs`, `follow`
- Category: inefficiency
- Failure: while anything downloads, the tray's observer runs on each `Library` notify, up to 10 times a second (`PROGRESS_TICK`), and builds a new `HashMap` of every row in the list, finished ones included, only to count the active ones and add their speeds. It also rebuilds and formats every submenu's items to compare them. The cost grows with the list on the thread that draws the window, against ENGINEERING section 10. Not measured.
- Evidence: `follow` makes `Activity::default()` and calls `load(&library.downloads)` on each call; `Library::apply` calls `cx.notify()` for each `DownloadsChanged`. A plain walk over the rows gives the same two numbers with no allocation.
- Confidence: likely

### 26-8 [P3] The decision logic of what is told when has no tests

- Where: `crates/shell/src/teller.rs`, whole file
- Category: design
- Failure: batching, each queue's choice, the rule that failures ignore the queue's choice, how each `NotifyOnFinish` choice maps to a telling, the staying time of a failure notice and `told_as_started` (D52, D63, D65, D67) can all break without a test failing. The type's docs say "so tests give it the time", but none exist.
- Evidence: `tools.md` reports 0% of 93 lines. There is no test module in the file and `Teller` is named in no test in the workspace. `crates/desktop/src/notices.rs::watch`, its only caller, is not covered either.
- Confidence: certain

### 26-9 [P3] Two messages name the product with a literal

- Where: `crates/shell/src/notifications.rs`, `SHOW_IN_APP`; `crates/shell/src/tray.rs`, `perform`
- Category: design

- Confidence: certain

## Suggestions

### 26-S1 Tell what ended during a lag

- Today: after `RecvError::Lagged`, `reload` calls `Activity::load`, which treats everything as already known. A download that finished or failed in the missed events is never told, and `BrowserNotices::follow` misses withdrawals. The buffer holds 1024 events, so this needs a large burst.
- Better: `load` could compare the old and new rows and return `Ended`, as `apply` does.
- Value: a failure is told even after a burst of events, such as a bulk action on a long list.
