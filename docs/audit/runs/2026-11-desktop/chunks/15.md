## Findings

### 15-1 [P1] A segment answered with a page or nothing instead of media gives a damaged video reported as complete

- Where: `crates/streams/src/download/fetch.rs` `fetch_piece`, `crates/streams/src/download/join.rs` `mux`, `move_single_track`, `crates/streams/src/ffmpeg.rs` `InputFormat::detect`, `run`
- Category: bug
- Failure: a server answers one or more plain segments with status 200 and a body that is not media: a sign-in or "session expired" page, a rate-limit page, or an empty body. The segment is saved and logged as done like any other, and appended to its track. The result depends on where it lands:
  - Inside an fMP4 track, with ffmpeg: everything after the bad segment is lost, ffmpeg exits 0, and `Outcome::Completed` is returned with a video cut short.
  - Inside an MPEG-TS track, with ffmpeg: the segment's time is a hole, ffmpeg exits 0, and `Outcome::Completed` is returned.
  - Without ffmpeg, any position: the bytes are joined as they are. Every segment bad, or every segment empty, still gives `Outcome::Completed`: `move_single_track` uses `unwrap_or(FALLBACK_FORMAT)`, so an HTML page or a file of 0 bytes is saved as a `.ts` video, where the same track with ffmpeg is refused with `Error::UnknownFormat`.
- Evidence: `fetch_piece` only checks transfer errors; an encrypted segment gets a check from its padding (an empty one is refused), a plain one gets none. `Fetcher::save` returns the byte count and drops the content type. `detect` reads only the head of the first segment of the track. `ffmpeg::run` takes exit 0 as success and `join` never compares the result with the plan. Run with ffmpeg 9.0.2 and the arguments of `copy_arguments`: three 2-second fMP4 fragments with an HTML page in place of the second gave exit 0 and `Duration: 00:00:02.00` (6 s without the page); the same with MPEG-TS gave exit 0, with the middle 2 s missing from a 6-second file. No test in `tests/hls.rs` or `tests/dash.rs` serves a bad body for a middle segment, or an empty one. The comment on `move_single_track` calls the fallback intended for formats it cannot name; it makes no case for text or for nothing.
- Confidence: certain for the code path and the ffmpeg results; how often servers do this varies by site, so the rank assumes it is uncommon but real.

### 15-2 [P2] Failing to delete the temporary folder turns a saved video into a failed download

- Where: `crates/streams/src/download/join.rs` `join`
- Category: wrong implementation
- Failure: the video is in place and `work.remove()` fails, for example because antivirus or the search indexer on Windows has a file of the folder open without delete sharing. `join` returns `Err(Error::Io)`: "Could not write the video to disk ... Check that the folder is writable and has free space." Core's `run_stream` then never reaches `finish`, so the download shows as failed and the saved file stays in its work folder. Trying again without ffmpeg: `track0` was moved away, so the `J` and `A` lines are dropped by `WorkDir::open`, the segments are gone, and the whole video is downloaded a second time. With ffmpeg: joined again, if the deletion did not already take the tracks; otherwise downloaded again too. When the extension changed, the second result takes another name such as `video (1).mkv` beside the first.
- Evidence: `blocking(... { let bytes = fs::metadata(&saved)?.len(); work.remove()?; Ok(bytes) })`, after `mux` or `move_single_track` has moved the result. The same crate's `discarded` exists for this kind of failure, and its doc says a failed delete "stops nothing". `remove` has no test for failure. Not run: it needs a second process holding a file.
- Confidence: certain for the code path; likely for how often it fires on Windows.

### 15-3 [P2] After a bad track was joined, the fix the error offers cannot work

- Where: `crates/streams/src/download/join.rs` `join`, `mux`, `crates/streams/src/workdir.rs` `WorkDir::open`, `crates/media/src/describe.rs` `unknown_format`
- Category: wrong implementation
- Failure: the first segment of a track was not media, as in 15-1, so a track joined and noted with `J` is refused with `Error::UnknownFormat`. The message says "open the video page again to get a fresh one", and the fix offered is `FixAction::RefreshLink`. `refresh_link` keeps the work folder. A fresh link whose segment paths are the same (only signing values differ) has the same fingerprint, by design, so `WorkDir::open` keeps the joined track, `queue` fetches nothing, and `mux` fails with the same error, however good the fresh link is. Trying again fails the same way. The same holds for `Error::Ffmpeg` from a bad track ("try again"). Only a restart that deletes the partial files gets out.
- Evidence: `a_track_in_an_unknown_format_is_never_given_to_ffmpeg` asserts the track is kept; `resuming_with_a_refreshed_link_keeps_the_segments` asserts a refreshed link keeps segments; `refresh_link` in core does not call `discard_partial`; `detect` runs on the kept file. `fingerprints_follow_paths_not_hosts_or_signing_tokens` shows the fingerprint does not change. Not run end to end.
- Confidence: certain

### 15-4 [P3] Two copies of the "read until full" loop have drifted

- Where: `crates/streams/src/crypto.rs` `fill`, `crates/streams/src/ffmpeg.rs` `read_up_to`
- Category: duplicate
- Failure: the two functions do the same job in one crate. `fill` retries on `ErrorKind::Interrupted`; `read_up_to` returns it as an error, so `detect` can fail where `fill` would carry on. A fix to one misses the other.
- Evidence: same signature apart from the reader's type; `fill` is already generic over `Read` and would serve both.
- Confidence: certain
