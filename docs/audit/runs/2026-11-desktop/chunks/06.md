## Findings

### 06-1 [P2] A damaged endpoint key stops the bridge from starting the app that would repair it

- Where: `crates/bridge/src/app.rs`, `attempt` and `connect_or_launch`; `Unavailable::from_ipc`
- Category: wrong implementation
- Failure: Wirecatch is closed and `endpoint-key` holds something that is not a key (empty or garbled, for example). The person starts a download in the browser. The bridge answers `app_unavailable` without starting the app, telling them to close Wirecatch, delete a file and open it again. The app is the one thing that would fix this by itself, and it is never started. Every later bridge does the same until the person opens Wirecatch by hand.
- Evidence: `wirecatch_ipc::endpoint` returns `IpcError::BadEndpointKey` for a damaged key (`ipc/src/key.rs`, `read`, `Stored::Damaged`). `attempt` treats only `NotRunning`, `NoEndpointKey` and `WrongOwner` as `NotYet`; `BadEndpointKey` lands in the catch-all and becomes `Attempt::Failed`, and `connect_or_launch` returns before `launcher.launch()`. D41.4 says a damaged key "is refused by clients and replaced by the listener", so a launch repairs it, the same way a launch renews a squatted key (D41.6) and writes a missing one (D41.5). The not-private case must stay refused, but `BadEndpointKey` covers both, so the bridge cannot tell them apart. The message also comes out as two conflicting pieces of advice: `from_ipc`'s `other` arm wraps the key error's "Close Wirecatch, delete the file, then open Wirecatch again." and adds "Open Wirecatch, then try again." No bridge test covers this error.
- Confidence: certain for the code path; the state itself is rare, since the key is written by rename

### 06-2 [P3] `async_and_blocking_reads_agree` never does a blocking read

- Where: `crates/bridge/src/raw_frame.rs`, test `async_and_blocking_reads_agree`
- Category: fake test
- Failure: `read_blocking` could start returning different bytes from `read_async` and this test would still pass.
- Evidence: the test calls only `read_async`, and compares the result with the bytes it fed in. `read_blocking` does not appear in its body. Each reader has its own frame-filling code (`read_blocking` also has the oversized path), so agreement is a real property that nothing checks directly.
- Confidence: certain

### 06-3 [P3] Test limits shorter than what the machine may take

- Where: `crates/bridge/src/app.rs`, tests `a_key_that_does_not_exist_yet_starts_the_app_and_is_read_again` and `a_keyed_name_another_account_holds_starts_the_app_and_reads_the_new_key`; `crates/e2e/src/bin/wirecatch-e2e-app.rs`, `LIFETIME`; `crates/bridge/tests/bridge.rs`, `LINGER` with `the_app_is_started_when_it_is_not_running`
- Category: design
- Failure: on a busy machine these fail with no product fault, which is what `docs/ENGINEERING.md` section 7 forbids.
  - The two keyed tests must connect within `START_BUDGET` (5 s of real time) while a task sleeps 200 ms and then generates and writes a key and binds. The neighbouring test `starts_the_app_and_connects_once_it_listens` passes `PATIENCE` for this reason, and says so.
  - `wirecatch-e2e-app` quits after 60 s, whatever happens. `the_bridge_starts_the_app_when_it_is_not_running` gives the bridge `PATIENCE` (2 minutes) for the start and each call, so past 60 s the app closes under the test, which reports a lost connection.
  - The fake app leaves 10 s after the bridge does, and the test then requires `connect` to succeed ("the fake app should still be running"). A stall of 10 s between the two turns a correct bridge into a failure.
- Evidence: the constants above. The `test-timing` gate check does not catch them, since the limit is a named constant or sits in another process. Not seen failing: a suspicion from reading, under the project's own rule.
- Confidence: likely

### 06-4 [P3] The bridge's test override names are written in two crates

- Where: `crates/bridge/src/app.rs`, `test_overrides`; `crates/test-support/src/bridge.rs`, `ENDPOINT_VAR`, `LAUNCH_VAR`, `START_BUDGET_VAR`
- Category: duplicate
- Failure: renaming one copy of `WIRECATCH_BRIDGE_TEST_ENDPOINT` or `WIRECATCH_BRIDGE_TEST_LAUNCH` makes the bridge ignore what the tests set. The bridge under test then connects to the person's real endpoint and starts whatever app build sits beside it, the opposite of "no test ever starts anything real" (`tests/bridge.rs`), before the test fails.
- Evidence: the same three strings are literals in both files, with no check tying them together. `docs/ENGINEERING.md` section 1 gives data two packages need one home. The bridge's non-test code cannot read them from `wirecatch-test-support`, a dev-dependency, so the home has to be something both already depend on.
- Confidence: certain

## Suggestions

### 06-S1 Test `start_app: false` and the held-frame limit on the real executable

- Today: `first.allows_starting_the_app()` choosing `Start::Never` in `main.rs` is exercised by no test: `hello` in `tests/bridge.rs` and `hello_call` in `crates/e2e` always send `start_app: true`. The pieces are tested separately (`raw_frame::tests`, `app::tests`). `MAX_HELD_WHILE_CONNECTING` has no test at all.
- Better: one executable-level test sending `start_app: false` with nothing listening, which expects `app_not_running` and no launch, and one relay test that fills the held frames and checks that none are lost and the order holds.
- Value: "a Wirecatch you closed stays closed" (D25) is held by the wiring in `main.rs`, which a mistake could invert unnoticed.
