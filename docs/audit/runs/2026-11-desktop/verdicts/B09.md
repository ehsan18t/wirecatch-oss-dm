# Verdicts: B09 The store: reading, failure signal and repair

Checked at 02284bbd0 by reading the batch's code and running the proofs below. Rust checks run: only the four proof tests, in `wirecatch-store` and `wirecatch-core`.

## Verdicts

### G47 Stored data that cannot be read

- 03-1: confirmed, P1. Proven: `proofs/03-1.patch`. One bit flipped in the raw file (the first byte of a stored link) leaves `PRAGMA integrity_check` saying `ok`, then `Store::open` returns `StoreError::Database` ("invalid utf-8 sequence") on every start, with nothing set aside. The same refusal was run for a BLOB path, text in `done` and `added_at`, bad UTF-8 in the settings value and in a queue's settings, and `user_version = -1`. `is_damage` looks only at `sqlite_error_code()`, which is `None` for all of these. It breaks the promise in the doc of `Store::open`. Not P0: the file is untouched and can be repaired by hand, but no start gets past it and the message points at the wrong cause (folder rights, full disk).
- 03-2: confirmed, P2. `read_value` and `read_queue` turn a failed parse into `None`, `restore` treats `None` settings as a first start with `settings_changed = true`, and `Manager::open` saves the defaults. `save_queues` at every open erases a queue that could not be read. `categories` holds the plain `Category` enum with no `known_or_default`, so one new variant fails all of `AppSettings`. One correction: proxy passwords are not overwritten at start, because `Manager::open` never calls `save_proxy_logins`. They read as empty for that session and the stored value goes at the next proxy change (`proxy.rs`, `preferences.rs`). The rest stands, and nothing tells the person: `Recovery` has no variant for it.
- 04-6: confirmed, P3. The same code as the queue half of 03-2, and one fix closes both; this entry stays P3 because it describes only the path through an older build. The merged item takes 03-2's P2. The stripped-fields claim is true: `save_queues` writes `to_json(&q.settings)`, losing what this build does not know.
- 03-6: confirmed, P3. `KINDS` has no entry for `status`, `category`, `chosen_by` or `queue_reason`. Nothing else pins them: `crates/protocol/released` holds none of these types, and the only literals are `archive` and `paused` in `insert_old_download`. A rename would change generated TypeScript, which is visible in a diff but fails no check against stored rows.
- Xdatabase-migrations-5: confirmed, P3. `database_with_settings` writes `to_json(&sample_settings())`, and `samples/settings/defaults.json`, the only settings sample, holds `show_progress_windows`. So `every_saved_sample_loads` does not catch a removed default either, and the assertion reads the stored value.

### G48 The store has only one signal

- 03-3: confirmed, P2. Proven: `proofs/03-3.patch`, three failing batches gave three reports where one is promised. `apply_one_by_one` drops what `may_pass_later` refuses, `kept` stays empty, `retried` is 0 next time. `notices::storage_failed` shows a system notification each time while no main window is open, and the Windows and Linux paths of `system_notifications.rs` set no tag or replace id, so they pile up. With the window open the banner returns after every Dismiss.
- 03-4: confirmed, P2. Try again half proven by `proofs/25-2.patch`. Recovery half: `UiEvent` has only `StorageFailed`, and only the two buttons clear `storage_problem`. The test `writes_that_fail_while_the_database_is_busy_are_kept_until_they_pass` pins the silence during a spell. One limit on the wording: the changes are lost at close only if the failure continues to the close, since `last_try` runs then.
- 23-10: confirmed, P3. The recovery half of 03-4; the merged item takes P2.
- 25-2: downgraded to P2, the button does save nothing, proven by `proofs/25-2.patch` (empty patch, no settings write, `apply_settings` returns on `state.settings == new`). But its story that a person who frees the disk still loses the changes is wrong: `write_until_closed` retries kept writes every `RETRY_KEPT_AFTER` (5 s) by itself and once more at close, so they land with or without the button. What remains is a button that does nothing and hides a warning while the failure lasts: wrong state and false reassurance, not a failed recovery. Same bug as 03-4, as GROUPS says.
- Xfeature-behaviour-3: confirmed, P2. Same bug as 03-4 and 25-2; proven by the same patch. Its second reason (`on_failure` fires only when `retried == 0`, so the banner cannot return in the spell) is correct.
- 03-8: confirmed, P3. The doc of `run` says "never dropped", the test doc at `a_write_that_can_never_pass_is_dropped_and_the_others_are_saved` says "kept and tried again later rather than dropped", while the `Err(e)` arm of `apply_one_by_one` and `trim_kept`'s drain drop writes, and the same test asserts the drop. Reaching a dropped delete needs a refused write or more than `MAX_KEPT` distinct rows, so this is a false doc rather than a likely loss.

Not tested: forcing a held file needs a second process, and the code path has no branch left to doubt. Reach is small: only a data folder an earlier version left in the roaming profile, on Windows.

## Conflicts settled

- GROUPS asks whether 03-4 and 25-2 give different reasons why Try again saves nothing. Both hold, at different layers. 25-2: the empty patch never reaches the store. 03-4: even a write that did reach it would stay silent while `retried > 0`. A fix must deal with both, and a retry through settings would still be the wrong write: the banner is about the kept writes, which the store already retries.
- Severity across the same bug: 03-4, 23-10, 25-2 and Xfeature-behaviour-3 merge at P2. 03-2 and 04-6 merge at P2. 03-5 and Xdatabase-migrations-1 are both P2.

## New findings

### B09-1 [P2] A proxy server that cannot be read silently moves downloads off it

- Where: `crates/store/src/lib.rs`, `load_proxy_servers`; `crates/core/src/manager/restore.rs`, `forget_missing_profiles`; `crates/core/src/manager/mod.rs`, `Manager::open`
- Category: wrong implementation
- Failure: the stored `proxy_servers` value, or the one profile the app or a queue uses, cannot be read (damaged text, or a field a newer build added as required). The app's proxy becomes `ProxyUse::System` and is saved, and a queue's becomes `Setting::Global` and is saved by `save_queues`. Downloads meant to go through that server then go through the computer's proxy or directly, with no notice. The next `save_proxy_servers` also erases the unreadable profile for good.
- Evidence: same cause as 03-2: `read_value` and the `filter_map` in `load_proxy_servers` turn a failed parse into absence with only a `warn`. `forget_missing_profiles` documents the fallback, `Recovery` has no variant for it, and the search of `docs/DECISIONS.md` for it found no decision. A person who chose a proxy for privacy gets their address exposed unaware. `ProxyServerSettings::kind` uses `known_or_default`, so an unknown kind alone does not trigger this.
- Confidence: certain from the code; not run. Reached only after damage or going back a version.

### B09-2 [P3] Id counters and queue batches that cannot be read are lost without a notice

- Where: `crates/store/src/lib.rs`, `load` (`LAST_IDS_KEY`, `BATCHES_KEY`); `crates/core/src/manager/restore.rs`, `restore`
- Category: wrong implementation
- Failure: an unreadable `last_ids` value reads as zero, so `ids.download` becomes the highest readable row. A download deleted earlier then has its id reused, which `LastIds`'s doc says never happens, and a hidden `StoredRow::Unreadable` row with a higher id can be replaced by `INSERT OR REPLACE` under the reused id. An unreadable `queue_batches` value silently drops what each queue had finished so far (D52).
- Evidence: `read_value(..).unwrap_or_default()` for both in `load`; `restore` folds only readable rows and queues over `snapshot.last_ids`. Hidden rows are not counted. Nothing reports either case.
- Confidence: certain from the code; not run. Needs a damaged value, and for the hidden row a second fault.
