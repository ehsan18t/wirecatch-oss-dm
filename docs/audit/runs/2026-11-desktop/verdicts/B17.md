## Verdicts

### G80

- 24-4: confirmed, P2. `file_exists` reads only `id`, `file_name`, `url` and `folder`, and passes `None` as the size to `heading`. No product code outside core and the generated types names `same_file`, so D96's "The person always knows which case it is" is not met, with Replace as the primary button. Not P0: the window does say a file of that name is there and the person presses Replace.
- 30-1: confirmed, P2, same bug as 24-4.
- 24-6: confirmed, P2. A capture's window goes to `Shows::Download(5)` through `became`. The core's `ask` raises a new `QuestionId`, `Registry::ask` opens a second window for it, and `settle` goes through `answer` to `became` again. `became_download` overwrites `shows` with no look at `window_showing`, whose `find` then returns only the older window. `answer_file_exists` returns the download for Cancel too, so Cancel takes the same path. D23.5 says one window per download, and this is the default flow whenever a question window came first.
- U-7: confirmed, same bug as 24-6, so it takes that finding's P2. Filed as P3 because it describes only the two windows.
- U-6: downgraded to P3. `Paused` is a recorded decision: D88.3 says "Asking pauses the download", the doc of `FileExistsQuestion` says the same, and `close_file_exists` makes Resume close the question as D88.3 asks. That part is not a fault. What remains is wording, all real: `Paused at Size unknown` comes from `list.rs` and `text::size` for any paused row with no total and nothing done, the row keeps the provisional `(1)` name until the answer since `settle_path_checking` stops before it writes the path, and `run_panel` says "The partial file was removed" for every cancelled row. No action goes wrong because of any of them.

### G81

- 30-2: confirmed, P2. `progress_buttons` and `row_buttons` take only a status and offer Try again for every failure. A search of `crates/desktop`, `crates/shell` and `crates/server` finds no `Reveal::details` and no read of `.details`, so `MainWindow::reveal` ignores it. D23.4 promises "any error with its fix". Not P1: the failure's message shows and the main window's row has the fix. `main_window::fixes::run` cannot simply be called from these windows, since its `RefreshLink` and `ChangeQueue` arms open dialogs through `super::library`.
- Xfeature-behaviour-5: confirmed, P2, same bug as 30-2. `notifications::retry_helps` is the only reader of `RETRY_FIXES`.

### G82

- 24-5: confirmed, P2, with one claim of the finding wrong. `name_from` fills the field from the proposal, `confirm` sends `file_name: Some(field)` without comparing it to `core_name`, `add_entry` keeps it as `NameChoice::name`, and `settled_name` returns a `Some` choice before it looks at the server's name. `insert_confirmed`'s own comment says only what the user changed is a choice, and `hint_name` already carries the proposal, so `None` would work. Wrong: "A proposed name that `checked` refuses fails the download". The proposal passed `naming::file_name`, which runs `checked`, when the capture was asked. Also narrower than filed: a name with no known type still takes its folder from the content type through `category_from_mime`.
- 24-7: confirmed, P2. `progress_buttons` wires `progress-cancel` straight to `api::cancel`, in the running and the paused state; its doc says it discards the partial file. D23.4 says "asks first", D114.2 changes only the layout, and `main_window/confirm.rs::cancel` asks. Not P0: the file itself comes back by downloading again, and the person pressed Cancel.
- U-14: confirmed, same bug as 24-7, so it takes that finding's P2. Filed as P3 under design.
- 24-8: confirmed, P2. The only call of `download_windows::show_download` is the `CaptureRepeated(Repeated::Download)` arm of `follow`, and no text under `crates/desktop/src` outside `download_windows/` offers it. D23.8 promises the row's entry, and D48.6 lists the download's own window behind the details' "…". Not P1: the download keeps running and the main window shows its progress.
- 24-10: confirmed, P3. `follow` only notifies, `render` has no empty state, and `the_list_follows_what_happens_to_its_downloads` shows the list can empty. Only a blank window that closes normally.

### G83

- 26-1: confirmed, P2. `register` pops the front of one `kept` queue for every kind, and `ask` registers before it learns no browser is connected, with `give_up` leaving the entry. `pressed` answers `None` for a forgotten id and `watch` drops that silently. The bound is documented and has a test (`only_the_newest_notes_keep_their_buttons`), but the test is of a single kind; `system_notifications.rs` keeps brief toasts apart for this very reason, and a failure's notice stays until closed. A run of captures reaches 32.
- 26-5: confirmed, P2. All three cases hold. `Teller` only adds, and `watch` gives it only what `Activity::apply` calls ended. Retried inside the batch, `apply` sees Failed again as a new status, so `Teller.failed` holds the row twice and `failed_in` takes the two-row arm ("2 downloads failed", "a.zip and a.zip"). `outdated_by` removes the `waiting` sender, so `answered` is false at once and the toast shows. The third case is narrow: it needs the event within the wait, before a browser answered.
- 26-6: downgraded to P3. `storage_failed` does pass a literal `true`, against D64.2, and `could_not` shows the way. It needs Do Not Disturb on, the switch turned off from its default, the main window closed and the database failing, and the result is only an urgent mark on a notice the person needs anyway. No window asked, and the system has the last word (D64.3).
- 26-8: confirmed, P3. `teller.rs` has no test module, and `Teller` is named only there and in `notices.rs`.

### G84

- Where: `crates/core/src/naming.rs`, `checked`; `crates/shell/src/api.rs`, the invalid-text and folder messages; `crates/shell/src/appimage.rs`, its error messages; `crates/shell/src/bridge.rs`, its error messages
- Category: design
- Failure: the messages read "Wirecatch" in a build whose channel is "Wirecatch Dev", and a change to `config/product.toml` leaves them behind, against ENGINEERING section 1. 26-9 counts two literals in its own files; the same cause is in every file above.
- Evidence: a search for string literals holding the name under `crates/shell/src` finds them at `api.rs` (the name that is not valid text, the folder not created yet), `appimage.rs` and `bridge.rs`, and `checked` in `crates/core/src/naming.rs` says "Wirecatch uses those for downloads in progress". No gate check catches it.
- Confidence: certain

### B17-2 [P3] The download complete window lists a download retried or removed during the batch, and a removed one stays

- Where: `crates/desktop/src/download_windows/finished.rs`, `add`; `crates/shell/src/teller.rs`, `Teller::take_due`
- Category: bug
- Failure: "When a download finishes" is the download complete window. A download fails and the person removes it within `NOTIFY_BATCH` (3 s). When the batch is due, the window opens or gains a row for a download no longer in the list, with Try again, which fails with "could not do that". The row stays until the window is closed. A download retried within the batch is listed as Failed until its next change arrives.
- Evidence: same cause as 26-5, in the consumer 26-5 does not name. `Tell` carries the rows as they were when they ended, and `add` filters them only by whether a progress window shows them. `FinishedBook::follow` removes a row only if it was already listed when `DownloadsRemoved` arrived, which was before `add`, and no later event names that download. A row retried is corrected by the next `DownloadsChanged`, since `follow` replaces listed rows.
- Confidence: certain from the code; not run
