# Verdicts: B18 Settings pages, links and text

Judged from the code, as the batch is P2 and below. Nothing was built or run. Contrast figures were computed again from the code's own values.

## Verdicts

### G85 Public Suffix List controls were never drawn

- 23-5: confirmed, `settings/general.rs` `updates` draws only the switch; `api::suffix_list` and `api::check_suffix_list` have no caller outside `api.rs`, and D44.4 promises the date, the last check and Check now. The core's check and its tests work, so the loss is the controls only. P2.
- 30-3: confirmed, same bug. `Library`'s event handling ends in `_ => return` with no `SuffixListChecked` arm, nothing outside core reads `SuffixListInfo`, so `check_failed` never reaches a person. P2.
- Xfeature-behaviour-4: confirmed, same bug. P2.

### G86 The link rule is written twice with two contents

- 22-2: confirmed, `LINK` is `(?:https?|ftps?)://`, which cannot match `ftpes://`, while `LINK_SCHEMES`, `FTP_SCHEMES` and core take it. `AddForm::urls` is `links::extract`, so the launch link stays in the box, counts as a line with no link, and `submit` answers `NO_LINK`. Not P1: `ftps://host:21` asks for the same AUTH TLS (`security_and_port`), though no text says so. P2.
- Xpath-normal-download-4: confirmed both cases. (a) is the same bug as 22-2. (b) `is_launch_link` checks only length, control characters and scheme, so `https://example.com/a b.zip` passes, and `extract` stops at the space and offers `https://example.com/a` with no note, as the line does hold a link. P2.
- Xrepeated-logic-1: confirmed, same bug as 22-2. `links::extract` is the only way in for `add_dialog`, `command_bar`, `refresh_dialog`, `paste_links` and `tray`. P2.
- 23-2: confirmed, `[^\s<>"'`]+` stops at `'`, and `trim_end_matches` removes a closing `)` or `]` without looking for its opener, so `report_(final)` becomes `report_(final`. Both parse, and `lines_without_links` does not count the line. The Add dialog downloads the shortened address with no warning. P2.

### G87 Status and failure text

- 23-3: confirmed, the `row.done >= total` branch of `percent` contradicts its doc and makes the `.min(PERCENT_MAX - 1)` dead. It is reachable: `MediaProgress::read` keeps `total` and `done` from the finished parts while `step` is set, so `figure` says `100%` beside `Converting, 40%`, and `details.rs` says the same. A `Part::File` whose real size passes its `expected` also reads 100% while downloading. `download_windows/view.rs` is not affected during processing, as its `moving` leaves `Processing` out. P2.
- 23-4: downgraded to P3, the fact holds (`status_label(Processing)` is fixed, and `details.rs` passes only `row.status`), but the same panel's sentence from `status_detail` and the list's `status_short` name the real step, and nothing a person does depends on the header word.
- 23-8: confirmed, `file_to_open` reaches the message only for `Completed`; `can_retry` is `Failed` and `Cancelled` only, `RowAction::offered` gives a finished row Open and Show in folder, and `requeue` answers "This download has already finished." `item_to_reveal` uses "does not exist yet. Wirecatch creates it when the download starts" for a finished row too. P2. The button is also named "Try again", not Retry, in `fix_label` and `RowAction::offered`.
- U-9: confirmed, `refusal` only strips `ERROR:` and a trailing dot and cuts the length with `for_a_person`, so `[generic] id:` and `(caused by <HTTPError ...>)` reach `describe::ytdlp`'s `({reason})`. P3.

### G88 Settings pages and dialog display

- 27-6: confirmed, `remember_media_choice` saves any `option.height`, `validate` refuses only `Height(0)`, `QUALITIES` has six heights, `choice` answers an empty string for an unlisted value, and `DropdownField` falls back to that value as its label. The saved value still works; only its display is lost. P2.
- 27-7: confirmed, `command` returns silently on `Ok`, both buttons discard the result, `copy_system_proxy` emits only when something was added, and `check_addon_updates` emits an unchanged list. A failed check does answer, through `UpdateCheckFailed`. P3.
- U-1: confirmed as P3, with a narrower failure and the cause found. It lasts only until the next mouse move, not "until another page is picked". `SidebarMenuItem` sets `hover_style` only while not active. GPUI's `compute_style_internal` reads the stored `hover_state` at layout, where the text colour is taken, and the live hitbox at paint, where the background is drawn. While the item is active no listener clears that flag, so it stays true from the click. Once another page is picked, the old item draws the hover text colour with no background, until the next `MouseMoveEvent` clears it. Posted messages send no further move, which is why every capture showed it. The cause is in gpui-pre and gpui-component, not in `settings/mod.rs`.
- 23-6: confirmed, `picked.await.ok()?.ok()??` drops the inner `Err`, and `gpui-pre-linux`'s `prompt_for_paths` sends `FILE_PICKER_PORTAL_MISSING` there and logs nothing itself. P2.
- 23-7: downgraded to P3, the figures are right (recomputed: 2.83, 3.05, 3.31, 3.90, 2.34 dark, 3.92 light; fixed accents from 4.91), so the doc's promise is false. But the default accent is Cyan, `Accent::System` is opt-in, Windows' default `#0078D4` gives 6.40, and the text stays readable at the failing pairs. A design fault with a concrete cost, not a broken control.
- Xpath-normal-download-7: confirmed, `folder_row` reads a folder only from `picked_queue`, so Automatic gives `FOLDER_BY_TYPE`, while `add_download` uses `state.folder_for(new.placed.queue, ...)`, which returns the placed queue's `Setting::Own`. `Route` keeps the queue's name only, so the dialog has the place but not the folder. The row states a folder the file does not go to. P2.

## New findings

### B18-1 [P2] Export and Import settings do nothing and say nothing when the file chooser fails

- Where: `crates/desktop/src/main_window/backup_dialog.rs`, `BackupForm::export`, `BackupForm::preview`
- Category: bug
- Failure: on a Linux desktop with no XDG file chooser portal, Export or Import in Settings opens no chooser, shows no message and logs nothing. The dialog looks as if the button did nothing.
- Evidence: `let Ok(Ok(Some(path))) = picked.await else { return Ok(None) }` and the same for `paths` treat an `Err` as a cancel. `gpui-pre-linux` sends `Err(anyhow!(FILE_PICKER_PORTAL_MISSING))` from both `prompt_for_paths` and `prompt_for_new_path`. Same cause as `23-6`; docs/ENGINEERING.md section 4 forbids dropping the error.
- Confidence: likely (read from the code; Linux is not run in this audit)

### B18-2 [P3] The main navigation keeps a page's old hover colour after leaving it

- Where: `crates/desktop/src/main_window/sidebar.rs`, the Settings entry and the navigation tile
- Category: design
- Failure: click a navigation tile or Settings, then move to another and click it. The item left behind draws `theme.foreground` in place of `muted_foreground`, with no hover background, until the next mouse move.
- Evidence: both use `.when(current, ...)` and `.when(!current, |item| item.hover(... text_color(theme.foreground)))`, the toggled `hover_style` that `U-1` traces in GPUI's `hover_state`. `rail.rs` always has its hover style, and the queue row and the entry at `.hover(|item| item.bg(theme.list_hover))` change no text colour, so neither shows it.
- Confidence: likely (from the code; not run)

### B18-3 [P3] Raw ffmpeg output in a failed join or conversion message

- Where: `crates/media/src/ffmpeg.rs`, `FfmpegError::Failed`; `crates/media/src/describe.rs`, `join`, `conversion`
- Category: wrong implementation
- Failure: ffmpeg fails while joining or converting. The message a person reads holds ffmpeg's own last error line inside its brackets, as in "ffmpeg could not join the video and audio (<ffmpeg's line>). Try again".
- Evidence: `Failed { reason }` is documented as "its own last error line" and displays as `{reason}`, set from `ran.reason()` with only a trailing dot removed; `join` and `conversion` put the error in the sentence with `({other})` and `({error})`. Same cause as `U-9`: a program's text passed on as the words for a person, against D3.
- Confidence: likely (the line's content depends on what ffmpeg prints; not run)
