## Group notes

- **Conflicts.** 04-5 (Paused) and Xconcurrency-2 (running again) are both right: if `finish_removing` asks first the stop is `Stop::Remove` and `finish` saves Paused; if `shutdown` asks first the stop is `Stop::Shutdown` and the status is kept. `Stop::is_users_choice` keeps a `Remove` from being replaced, and `lock_open` keeps a late `Remove` from arriving. On G11's note, `second-review-resume` is right that the engine side of Xcrash-and-resume-2 is sound: `plan_exact` starting over with no part file is correct on its own, and `finalize` refusing under `Finish::Refuse` is what the request asked. The fault is core not reading the state.
- **G09 is really one finding.** 04-8 shares only the function; it is fixed by moving a doc line and needs no order against the P0. The folder branch of `delete_files` is needed only by `partial_paths`, so the Completed path should not go through it.
- **G10 shares one cause:** `Hold::Removing` is memory only and `lock_open` ends the removal once `closed` is set. B02-3 is a third entrance to it.
- **G11 does not share one cause. Split it into three.**
  - G11a (04-1, Xcrash-and-resume-1, Xsecond-review-resume-1): `settled` is read as "this row's file is at the path". The fix belongs in what the row records.
  - G11b (Xcrash-and-resume-2, Xpath-normal-download-6): the reverse direction, a real finished file read as unfinished because `finished_size` treats a resume file alone like a part file. The fix can be local to core's reading of "file and resume file, no part file".
  - G11c (Xcrash-and-resume-3, Xsecond-review-resume-8): media placing has no durable step between `place` and `discard::dir`. The fix belongs in `placement.rs`, for example a marker written before placing.
  - Order: fix G11a first, since its false completion also feeds Xcrash-and-resume-3's worst ending and B02-2. A G11a fix must not break G11b: a recorded "ran here" flag has to tell the two apart.
- **G11a is wider than the findings say.** `restore_entry` excludes only Completed and Cancelled, so a Failed row counts too. A Replace whose next run fails before the server answers leaves a Failed, settled row with the older file and no partial files; the next start turns it Completed and clears the error. So this is not limited to the wait for a slot. By reading, not run. A Cancelled row retried after Replace reaches the same state. `mark_completed` overwrites a known `total`, so a size mismatch that could have refused this is lost. The test `a_file_that_finished_before_the_restart_is_not_downloaded_again` pins that: it writes 5 bytes for a 512 KiB download and expects Completed, so a fix must change it.
- **G12 does not share one cause. Split it into three.**
  - G12a (05-6, Xcrash-and-resume-5): choices and checks missing from `StoredDownload`.
  - G12b (Xpath-normal-download-3): the opposite fault, `expect` lives too long; nothing to do with saving.
  - G12c (Xcrash-and-resume-6): the row is deleted before its replacement is durable.
  - Order: G12b before or with G12a. Saving `expect` alone removes the only way out of Xpath-normal-download-3 today, which is a restart.
- **Xcrash-and-resume-2 may not need a crash.** `finish` in `crates/engine/src/download.rs` runs `abandoned.check()?` between `finalize` and `discard(&target.state)`. A run aborted by `stop_timeout` while `finalize` is flushing a large file ends there with the same two files, and the row ends Paused or kept rather than Completed. By reading, not run; B03 reads the engine's finish and can confirm it.

## New findings

### B02-1 [P3] A file beside a leftover part or resume file is never asked about

- Where: `crates/core/src/manager/file_exists.rs`, `found_existing`; `crates/core/src/naming.rs`, `finished_size`
- Category: wrong implementation
- Failure: a new download's name is taken by `x.bin` in a folder that also holds a stale `x.bin.wcstate`, `x.bin.wcpart` or `x.bin.wcmedia` (from a removed row whose deletion failed, or the state in Xcrash-and-resume-2). The setting is Ask, Replace or Keep existing. Nothing is asked or applied: the download silently takes `x (1).bin`, against D96.
- Evidence: `found_existing` uses `naming::finished_size(path)?`, which returns `None` when a partial file or work folder exists, so `stop_for_duplicate` returns `Ok`. The loop in `settle_path_checking` then finds `is_free_on_disk` false and `left_by` false (`path.exists()`) and moves to the next name. `place` avoids this on purpose with its own metadata check ("Not `finished_size`"). Not run.
- Confidence: certain from the code

### B02-2 [P2] "Remove and delete" on a falsely completed row deletes the older file

- Where: `crates/core/src/manager/downloads.rs`, `finish_removing`; `crates/core/src/manager/restore.rs`, `restore_entry`
- Category: bug
- Failure: 04-1 turns a row Completed on a file it never downloaded. The person sees a wrong row and removes it with its file. The older file, which no run of that row wrote, is deleted for good. A fix that only checks `is_file` in `delete_files` does not stop this.
- Evidence: `finish_removing` deletes `entry.path()` for any Completed row. The row keeps no record that its run wrote the file. The first half is proven by `proofs/04-1.patch`; the deletion is the plain Completed branch, not run as a chain. It ends when G11a is fixed, so it needs no separate fix if that lands first.
- Confidence: certain from the code

### B02-3 [P3] A withdrawn capture comes back if the app quits while it stops

- Where: `crates/core/src/manager/captures.rs`, `withdraw_capture`; `crates/core/src/manager/downloads.rs`, `remove_in_background`
- Category: bug
- Failure: the extension gives up waiting and withdraws a capture. The app answers `Withdrawn` and the browser resumes its copy. The app then quits before the attempt has stopped. The row is restored and downloaded as well: two copies with no warning.
- Evidence: `withdraw_capture` answers without waiting for the removal, and `remove_in_background` only logs when `remove` fails with `Closed`, as Xshutdown-2's path does. It needs the quit inside the stop time, so it is narrow. Same fix as G10. Not run.
- Confidence: certain from the code
