# Batch B08 verdicts: hostile stream manifests and running programs

Commit: `02284bbd0`. Proofs built in a temporary worktree with the cargo profile `b08` and run on Windows. The wall-time runs of 14-2 used `--release` with LTO off. Linux was not run.

## G44 Stream limits

- 14-1: confirmed, P1. `substitute_into` pushes the id for each `$RepresentationID$` with no limit, and `MAX_URL_LEN` is first checked in `join`, on the finished text. `representation` lets an id up to `MAX_MANIFEST_NAME_BYTES` through, and nothing limits `media`. Proven at reduced size by `proofs/14-1.patch`: a manifest of 1 MiB held 258 MiB, and the refusal names an address of 268,435,456 characters. The product scales: 233,000 x 4 MiB is the finding's 977 GiB, past any machine's memory, and an allocation failure aborts the process. The full size was not run, because it would exhaust this machine; the abort itself is therefore inferred, not observed. It stays P1 and not P0: the app stops, but no file or list data is shown to be damaged.
- 14-2: confirmed, P1. The loop in `auto_picks` has no await and calls `select` for each quality, and `variant_named` and `audio_with` are both linear, so the work is quadratic. `proofs/14-2.patch` counted 24,163,538 allocations for 4,000 qualities, about 3 x n^2 / 2. Wall time, on a machine busy with other builds: 64 s at 50,000 qualities (1 MiB), 375 s at 100,000 (2 MiB), 108 s at 20,000 with `CODECS`. The 399,000 run was stopped unfinished; it projects to at least 100 minutes, and 270,000 with `CODECS` to hours. The finding's "minutes" is low for the largest size. `MAX_MANIFEST_ENTRIES` cannot fire from a fetched playlist: 800,000 entries of 21 bytes do not fit in 8 MiB. That the cancel token cannot stop it follows from the code, and was not run separately.
- 14-3: confirmed, P2. `update_keys` joins with no budget, each line makes a new `Arc<Url>`, and each piece keeps its own through `encryption`, so sharing does not help across key lines. `check_web_address` allows 8 KiB, and 8 MiB / 45 bytes stays under `MAX_SEGMENTS`. `keys.retain` removes only the same format, so the `KEYFORMAT` form grows `keys` too. Read only; the sizes follow from the constants. No proof run.

## G45 Selection, container and the key error

- 14-4: confirmed, P2. `paired_audio` filters on `r.url.is_some()` before looking for `default`, so an English `DEFAULT=YES` rendition with no `URI` is never seen and French is picked. The arguments in `crates/streams/src/ffmpeg.rs` then map only `0:v?` from the video input. A download without ffmpeg gave `Error::NeedsFfmpeg` in `proofs/14-4-and-14-5.patch`. The form is RFC 8216's own: no `URI` means the audio is in the variant.
- 14-5: confirmed, P2. `Codec::from_name("wvtt")` is `None`, which `Container::holds` treats as Matroska only; `extension` gave `mkv` for `avc1,mp4a,wvtt`, and `mp4a,wvtt` with no resolution was listed as a video (`proofs/14-4-and-14-5.patch`). `container_for` reads the same `Track::codecs`, so the download agrees with the forecast. The file still plays, so it goes no higher than P2.
- 14-6: confirmed, P3. `Error::Key` holds `url.to_string()` from `fetch.rs`, and `describe::stream` uses `error.to_string()` as the message. `Error::Manifest` keeps only the host. The address is at most 8 KiB by `check_web_address`. The finding's "into what is saved" was not traced past `describe`. The token reaches the person's own screen and data, hence P3.

## G46 Running programs

- 13-1: confirmed, P2. `push` adds 0 bytes for a blank line, so the eviction loop never runs: 100,000 pushes kept 100,000 lines. With a blank last line `error_line` gave `Some("")` where the line before said "Conversion failed!", and `reason` then filters it to "it gave no reason" (`proofs/13-1.patch`). `crates/media/src/ffmpeg.rs` and `crates/media/src/ytdlp/mod.rs` both read `reason`. The unbounded half needs a program that writes endless blank lines, which neither shipped program is known to do; the hidden reason is the half that matters.
- 13-2: confirmed, P3. `Readers::abort` aborts the task that holds the only copy of the bytes, and `finish` maps the `JoinError` to an empty `Vec` with `stdout_truncated: false`, so `extract_once` would parse nothing. The grace branch needs a detached child on Unix, or a stall over 2 seconds after the end, since `select!` picks among ready branches at random. Neither is known on normal paths. No proof: the detached form is Unix only, and the stall form cannot be forced without racing the machine.
- 13-3: confirmed, P3. `LINGER` is 60 seconds and `PATIENCE` is 120, and the test asserts only `ran.success()`. Without `OUTPUT_GRACE` the run reads until the child ends at 60 seconds, returns success, and the test passes. Read only: the test is `cfg(unix)` and was not run here.
- 13-5: confirmed, P3. `cut` in `run.rs` is `cut_bytes(line, MAX_LINE)` written again, and `Ran::reason` writes "it gave no reason" beside `NO_REASON`. `crates/files/src/zone.rs` has the same loop. The two in `crates/engine/src/naming.rs` also walk back to a boundary, but each computes its own limit and joins the result differently, so only the walk is shared.
- Xshutdown-4: downgraded to P3, the `SIGTERM` half only. The crash half is what `docs/ROADMAP.md` already lists and drops out. For `SIGTERM` the code facts hold: no `crates/` code outside the CLI and examples handles a signal, and `Tree::kill` runs only from a live process. The claimed result is weaker than stated, and read only, since Linux was not run: when the app dies the pipes' read ends close, so a program that writes progress gets `EPIPE` or `SIGPIPE`, and how yt-dlp and ffmpeg each answer that was not checked. "Goes on downloading, unseen" is therefore not established for either, and "two programs write there" depends on it. The fix the roadmap names (a supervisor that kills the group when the pipe closes) would cover both halves.

## Group notes

- G44 does not share one cause; split it. 14-1 is a length check that runs after the text is built, and is fixed in `substitute_into`. 14-3 is memory outside the budget, and is fixed in `update_keys` and `encryption`. 14-2 is not about memory: it is quadratic lookups with no limit on HLS qualities, fixed by a limit like `MAX_REPRESENTATIONS` or by lookups that are not linear. The fix for 14-2 should take in B08-1.
- G45 has no shared cause, as GROUPS.md says. Three separate fixes.
- G46 has no single cause, as GROUPS.md says. 13-1 and 13-5 touch `tail.rs` and `run.rs` together and can go in one change. 13-2 and 13-3 both concern the grace branch: the assertion 13-3 needs belongs with the fix for 13-2.
- GROUPS.md records no conflict among these findings, and none appeared.

## New findings

### B08-1 [P2] Listing a large master's qualities repeats the quadratic work after inspection

- Where: `crates/media/src/choice.rs`, `from_stream`; `crates/streams/src/model.rs`, `StreamInfo::extension` and `listed`
- Category: inefficiency
- Failure: a master playlist of qualities with no `RESOLUTION`, as in 14-2. All of them stay in `no_height`, and `from_stream` calls `extension` for each, whose `listed` scans `info.video`. It then makes one offer per quality, so hundreds of thousands of offers go on to the choice shown to the person. What happens to that many offers in the window was not checked.
- Evidence: the same loop over `extension`, without the rest of `from_stream`, took 20 s at 50,000 qualities and 112 s at 100,000, on a machine busy with other builds (the ignored test in `proofs/14-2.patch`). `from_stream` was read, not run. A limit on HLS qualities fixes this and 14-2 together; a faster `auto_picks` alone does not fix this.
- Confidence: likely
