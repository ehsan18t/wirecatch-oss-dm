# Batch B04: Local endpoint and bridge

## Verdicts

- 08-1: downgraded to P1, the code path is real and proven (`proofs/08-1.patch`, failing at high and at medium integrity, the medium run answering the finding's request for an unelevated repeat): a low-integrity token reads the key, makes the pipe naming the user, `connect` serves it and it receives the bytes, and the real app's `bind_keyed` gets `AlreadyInUse`. Not P0 because the conditions are narrow: the attacker already runs code at low integrity outside any restricted token or `AppContainer`, and Wirecatch must be closed when it makes the pipe, since it cannot close a medium-integrity app itself. Such a program can already read the user's files (no-read-up is not the default), so the gain is live download cookies and headers plus holding the endpoint. The boundary it crosses is one the crate's own docs promise, so it stays a serious finding. The proof uses an impersonating thread, as the crate's tests do, not a separate process or the real bridge binary. That restricted and `AppContainer` tokens cannot read the key follows from the key's access list; this was not run.
- 06-1: confirmed, P2. `attempt` sends `BadEndpointKey` to `Attempt::Failed`, so nothing is launched; a failing test (`proofs/B04-p2-checks.patch`) gave launches 0 and a message carrying both pieces of advice. The doc of `connect_or_launch` says any other error never launches, but that restates the code: D41.4 records only that clients refuse the key and the listener replaces it. Rare, since the key is synced and renamed into place.
- 08-2: confirmed, P2. Failing tests in `proofs/B04-p2-checks.patch`: limit 1 gives `Io` with error 231, and limit 2 with one client gives `AlreadyInUse`; neither renews the key, against the promise in D41.6 and in the doc of `bind_keyed`. The squatter stood in within one account; no second account was used. Denial of service only, and it needs a name seen earlier.
- 08-3: confirmed, P2. A failing test shows `connect` returning `Io` with error 5 where D41.6 promises `WrongOwner`; `attempt` then fails with no launch. The Linux half (`UnsafeDirectory` from `endpoint_for` reaching the catch-all in `attempt`) is confirmed from the code only, not run. The bridge's tests use a made-up `WrongOwner`, as the finding says.
- 08-4: confirmed, P3. `stored` gives `NotFound` its own arm and sends everything else to `Io`, so `ELOOP` from `O_NOFOLLOW` is `Io`, while the doc of `endpoint_in` promises `BadEndpointKey`. The refusal itself is correct. From the code; not run on Linux.
- 22-3: confirmed, P2. `Backend::start` serves only after `core.opened()`, while the pipe instance already exists, so the client opens it and its hello waits out `ANSWER_WAIT`. `hand_over_on` always says hello before looking at `launch.call`, and `main` shows the box on any error. The same follows from `serve_unavailable`'s refusal. From the code; not run. D103.4 chose the box for a failed hand-over but did not consider a launch with nothing to hand over.
- 22-4: confirmed, P2. `std::env::args()` in `main` is the only non-example read in a shipped binary, the standard library documents its panic, and the release profile has `panic = "abort"`. It stays P2, not P1, because only an odd launch is hit and a running copy is not affected; the Linux entry's `Exec=... %U` does pass outside arguments. Not run.
- 06-2: confirmed, P3. The test calls only `read_async`. The other tests that use both readers do not compare them.
- 06-4: confirmed, P3. The three strings are literals in `crates/bridge/src/app.rs` and `crates/test-support/src/bridge.rs`, and no check ties them. `crates/bridge/tests/needs_overrides.rs` does not catch a renamed variable.
- 22-9: confirmed, P3. `BACKGROUND_FLAG` and `BACKGROUND_ARG` both hold the value, and each crate's tests check their own copy. The bridge already depends on `wirecatch-protocol` and `wirecatch-product`. The shell's `REMOVE_ENTRY_FLAG` has a test that ties it to the installer, which shows the check is possible.

## New findings

### B04-1 [P3] On Windows a folder in place of the key is a raw system error, not `BadEndpointKey`

- Where: `crates/ipc/src/key.rs`, `stored` and `open_for_reading`
- Category: wrong implementation
- Failure: `endpoint-key` is a folder on Windows. Opening it fails with error 5, and `stored` returns `IpcError::Io` with "Could not open ...", so the person gets no advice. The doc of `endpoint_in` promises `BadEndpointKey`. This is the Windows counterpart of `08-4`.
- Evidence: failing test in `proofs/B04-p2-checks.patch`, which gave `Io` with error 5. `a_folder_in_place_of_the_key_is_refused` asserts only `is_err()`.
- Confidence: certain

### B04-2 [P2] A squatter whose instances are all busy also gets a plain error, after a two-second wait

- Where: `crates/ipc/src/windows.rs`, `connect`; `crates/bridge/src/app.rs`, `attempt`
- Category: broken feature
- Failure: another account holds the keyed name with a low instance limit and one client connected. `connect` retries `ERROR_PIPE_BUSY` for `BUSY_WAIT`, then the arm no longer matches and it returns `IpcError::Io`. `attempt` fails with no launch, so the key is not renewed. This is a further path of the cause in `08-3`, which covers only the refusal.
- Evidence: the guard on the busy arm in `connect` sends the expired case to the catch-all `Err(e)`, and `attempt` treats `Io` as `Attempt::Failed`. Read from the code; not run. A real app always keeps one instance waiting, so this does not depend on load in normal use.
- Confidence: certain from reading the code

### B04-3 [P3] The variable that names the tests' bridge is written in two languages

- Where: `crates/test-support/src/bridge.rs`, `BRIDGE_VARIABLE`; `scripts/gate/rust.mjs`, `BRIDGE_VARIABLE`
- Category: duplicate
- Failure: renaming one copy of `WIRECATCH_TEST_BRIDGE` makes tests build their own bridge during the gate, which relinks the executable while other test processes run it, the case the module's doc calls harmful. Nothing fails with a clear cause.
- Evidence: both hold the literal; the only link is a comment. `docs/ENGINEERING.md` section 1. Same cause as `06-4`.
- Confidence: certain

### B04-4 [P3] Tests write the key file's name again

- Where: `crates/ipc/src/key.rs`, `KEY_FILE`; `crates/ipc/tests/keyed.rs`, `KEY_FILE`; `crates/bridge/src/app.rs`, test `a_key_that_never_appears_is_reported_with_its_own_advice`
- Category: duplicate
- Failure: renaming the file changes one copy only. `keyed.rs` then fails on a path mismatch, and the bridge test goes on passing with a name that no longer exists, since it only builds an error from it.
- Evidence: `KEY_FILE` is `pub(crate)`, so integration tests and other crates cannot read it, and each wrote its own copy. Same cause as `06-4`.
- Confidence: certain
