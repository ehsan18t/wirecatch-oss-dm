# B16 Queues and queue forms: verdicts

Judged from the code, as the batch is P2 and below; no test was run and no proof was needed. Severities were checked against the table in `AUDIT-PLAN.md`, where a wrong implementation is P2 whatever its size, so the size of each effect is stated for ordering in stage 3.

## G76 A queue's run is not one thing

- 18-1: confirmed, P2. `has_work` comes from `view_of`, which answers `None` for an entry with no run that is not `is_waiting`. All three paths reach `finish`'s `reconcile` with nothing else in the queue: `ask` sets `Paused`; `set_download_folder` holds it `Moving`, so it is `Queued` but not free; `Stop::ReadAsVideo` leaves the status as it was and the run is gone. That reconcile clears `running_outside_schedule` and `Gate::is_open` resets `running_until_empty`. `answer_file_exists` (Keep both) and `finish_move` then reconcile with the gate closed. Replace and the Keep both setting are not affected, because they set `Queued` before the reconcile. The person can press Start now again when the window offers it, which 18-2 sometimes prevents; nothing is lost.
- 18-2: confirmed, P2. `allows` for a schedule with no stop is true from `start` to the day's end on a listed day and knows nothing of `Gate`. `outside_schedule` is its only reader, and it alone gates Start now in `queue_actions` and `queue_menu`. At 22:30 after the run ended, the core says `QueueSchedule` (the core test proves the wait), `summary` says "1 waiting", and no Start now shows. The reverse holds too: after midnight during a run `allows` is false, so `describe` (the rail's tooltip) reads "Starts at" and Start now shows while it downloads. `summary` and `queue_tile` check running first, so only the tooltip and the buttons are wrong in that direction.
- 18-3: confirmed, P2. `running_until_empty` is not stored, and `restore_entry` is the only restoration, through a row stored as `Connecting`, `Downloading` or `Processing`. A queue past its start with only waiting rows comes back closed, and `last_checked` is the restart time, so nothing reopens it until the next start. The other direction also holds: `resume_run` opens the gate after a Start now run, `set_queue_paused` clears only `running_outside_schedule`, so resuming continues the run. It applies only to schedules with no stop, since `is_open` returns `window_open` before reading the flag. The first direction needs a restart while the queue holds work and none of it runs, so it is not common.

## G77 What frees or takes a slot

- 04-2: confirmed, P2. `reconcile` computes `plan.start` once. `fail_to_start` sets `Failed` and calls `save`, which only notifies `rows_changed`. Both failure paths (`engine_request`, `start_media_run`) reach it only from `reconcile`'s loop, since `start_run` has no other caller. `run_scheduler` wakes on queue edits and, with a schedule, each minute, so an unscheduled queue stays stopped until an unrelated command. Not raised to P1: the trigger is narrow in practice (a website's link to a local address; a stored link that does not parse), and any later command recovers it.
- 18-4: confirmed, P2. A `Running` download found `over` is pushed to `stop` and `continue`s without counting, so the fill loop sees the room free, against the doc on `plan` ("a stopping download keeps its slot until it stops"). The overrun lasts until the stops finish, bounded by `DEFAULT_STOP_TIMEOUT` (5 s) in `stop_run`, and it corrects itself, so it belongs low in its severity. One correction: the finding says lowered limits are not affected. That holds for the app's limit but not for a queue's own: app limit 5, queue A lowered from 3 to 1 with 3 running, B waiting. A's two stops are not counted, so B may start 4 and 7 run until A's have stopped. The same fix covers it.

## G78 Rule reading

- 18-5: confirmed, P2. `cleaned` uses `seen.insert(read.to_lowercase())` for every kind of rule. `\d+\.mkv` and `\D+\.mkv` have one key, and the second is dropped with no message. `(?-i)` is allowed by `NameSyntax::Regex`'s doc. Only the regular expression syntax is affected, and such a pair is rare, so it belongs low in its severity.
- 27-10: confirmed, P3. `HELP` says "the one highest in the sidebar wins"; `best_site` keeps the highest `specificity` across queues, and `the_most_specific_site_wins_whatever_the_order` pins that.
- Xrepeated-logic-5: confirmed, P3. `clean_extensions` keeps `tar.gz` through `normalize_file_type`, the Files page accepts it, and `category_of` looks up only the text after the last dot, so the entry can never match. `file_type_rule` honours the same entry by the end of the name.

## G79 Queue forms and queue display

- 27-3: confirmed, P2. `ask` installs no `on_ok`. The input's `enter` calls `cx.propagate()` for a single line (gpui-base 0.8.1, `input/base/state.rs`). gpui-base's dialog binds Enter to `Confirm`, and `ok_handler` in gpui-component's `dialog/dialog.rs` defaults to one that returns true, which closes the dialog. The `delete` check and the disabled button are not on this path, so the queue stays. Nothing is lost except the typed name.
- 27-5: confirmed, P2. `read` always sends the field's text through `speed_limit` while the limit is on, and `in_unit` rounds to a tenth of the unit `Unit::of` picked. 1075 KB/s shows "1" and saves 1,048,576 bytes; 1100 KB/s shows "1.1" and saves 1126.4 KB/s. One correction: 300 KB/s to MB/s and back shows 307.2, not 307. The drift is at most 0.05 MB/s at each save, and it does not grow on later saves.
- U-5: confirmed, P3. `queue_line` keeps every row that is not `is_over`, so failed, paused and running rows all take a place, and `time_cell` prints the place for anything not `Downloading` or `Paused`. D47.4's numbering covers the line but does not say a failed row is in it. It also disagrees with `wait_reason`, which counts only waiting rows, so a row can read "2" while its reason says "1st in line".
- U-11: confirmed, P3. `marks` clones `server.settings.name` unchanged, and `summary` formats `via {proxy}`. `proxy_dialog::shown_name` already falls back to the address, and core's `proxy_route` and `network.rs` both handle the empty name. A name of only spaces does the same.
- U-12: confirmed, P3. The line is `flex_1`, `min_w_0`, `truncate` with no tooltip, the buttons keep their width, and the current state comes last in `format!("{facts} · {summary}")`. The exact width where it starts is taken from the capture, which was not looked at again; the code loses the end whenever the line does not fit.
- U-13: confirmed, P3. `queue_dialog::open` never calls `focus_after_opening`, which `add_dialog`, `refresh_dialog` and `queue_delete` call.

## Group notes

- G76 shares a cause only in part. 18-2 and 18-3 share one: whether a queue is in a run lives in a private, unsaved `Gate` flag beside the saved and published `running_outside_schedule`. One saved flag in `QueueStatus` fixes 18-3, and gives the window what 18-2 needs. 18-1 is separate: what counts as work (`has_work`) is too narrow, and it would remain after that change. Split: G76a `18-2`, `18-3`; G76b `18-1`. Fix G76a first, since 18-1's remedy of pressing Start now depends on 18-2.
- G77 does not share a cause. 04-2 is a missing re-plan after a start fails; 18-4 is `plan` counting a stop as a free slot. Split them. They touch the same loop in `reconcile` only, and neither fix helps the other.
- G78 and G79 have no shared cause, as `GROUPS.md` says.
- Not reported: a start time crossed while the app was not running is not caught up, since `last_checked` starts at the restart time. A schedule with no stop then waits for its next start and says so on the row, which works as described; catching up would be a suggestion.
- Not reported: `held_for_another_name` has the same `has_work` gap as 18-1, but only for the short rename in the same folder, and `finish` skips its reconcile on that path. Only a minute tick falling inside the rename could end a run, so any fix to 18-1 should cover `Hold::Moving`, and no separate finding is needed.
- `settings/speed.rs` rounds the app's limit for display too, but writes only when the person types, so 27-5's cause does not appear there.
