# Batch B10 verdicts: moves, quit and start

Proofs were run under a `b10` cargo profile. The core tests used a private target folder on C: because D: ran out of space during the run; the app reproduction used `target\audit-proofs\b10`.

## G51 Moves

- Xshutdown-1: confirmed, P1. `shutdown` collects only `run.exited`; `Hold::Moving` is not waited for, and `finish_move`'s save reaches a closed store. Proven: `proofs/Xshutdown-1.patch` fails for a finished file (the reopened row names a path with no file) and for a partial download (row at the old path, part file in the new folder). The file still exists, so not P0. The run also shows `shutdown` returning with the mover held.
- Xconcurrency-4: confirmed, same bug as Xshutdown-1, so it carries P1 rather than its own P2. Its open question (which end happens) is settled: the blocking copy runs to its end, because the runtime's drop waits for it (see Xshutdown-3), and the save is dropped. Proof as above.
- Xcrash-and-resume-4: confirmed, P2. Paths (a) to (d) hold in the code: no record of a move exists on disk, `restore` marks a settled unfinished row completed when `finished_size` answers `Some`, which gives (d). (c) and (d) have a window of one commit. Read from the code, not run.
- Xsecond-review-disk-writes-7: confirmed, P2. `create_new(to)` then `io::copy`, and `discard` runs only in a process that lives. `unique_path` then skips the name, and `found_existing` and `keep_existing` accept the cut-off file under Keep existing. The original stays on disk, so nothing is lost: not P0. Read from the code, not run.
- 05-4: confirmed, P2. Proven: `proofs/05-4.patch` fails across drives, with no `Zone.Identifier` on the moved file. A same-drive move keeps the mark, because it is a rename.
- Xrepeated-logic-4: confirmed, P3. `place` falls to `std::fs::rename` on any `hard_link` error other than `AlreadyExists`, and that replaces on both systems. `rename_no_replace` is public, and `relocate` already uses it. The window is short and needs a drive without hard links.

## G52 The quit limit

- Xshutdown-3: confirmed, P1. Proven by reproduction in the real app: `proofs/Xshutdown-3.patch` seeds one stuck `spawn_blocking` task and quits through `lifecycle::quit`. The process was still alive 30 s after the quit, `Application::run` had not returned, and it exited within 0.2 s of the task's release. A control with the task already finished exited in the same second as the quit. This settles the "App being dropped" doubt: GPUI drops its globals and `Backend`'s runtime blocks. Not run: a task stuck inside a run's `FileWork`, so the 15 s limit, the skipped `store.close` and the held database lock are read from the code (`RunGuard` waits for `file_work.finished()`, `Backend` drops `runtime` before `core`).
- 22-1: confirmed, same bug as Xshutdown-3, so it carries P1 rather than its own P2. Its further claims about the second launch (`AlreadyOpen`, "look for its icon in the tray") are read from the code, not run.
- 22-7: confirmed, P3. The only call is `quit_core(Some(&core), || ())`, `quit_sequence`'s only caller is `quit_core`, and neither has a test.

## G53 Start and registration

- 22-5: confirmed, P3. `Report::fail` lines reach only stdout, `run_bridge` pipes stdout and reports only stderr, and `run` logs nothing about them. `"install"` is the only non-test value of `subcommand`.
- 22-6: confirmed, P3. `exec_word` writes `\$`, and its test fixes that form. The Desktop Entry Specification applies the string escape rule first, so `\\$` is what it asks for. Read from the specification and code; GLib's rejection of `\$` was not run, as Linux is out of scope.
- 22-8: confirmed, P3. `Launcher` has one implementation in `crates/shell` (the `Launcher` in `crates/bridge/src/app.rs` is another trait). `apply` and `follow` run in no test.
- U-2: confirmed, P3. `TitleBar::title_bar_options` gives `title: None`, `window_options` keeps it, and `crates/desktop/src` never calls `set_window_title`. Not rerun in the app.

## Group notes

- G51 does not share one cause; split it into four:
  - Shutdown ignores a move: Xshutdown-1 = Xconcurrency-4.
  - The move has no crash-safe form: Xsecond-review-disk-writes-7 and Xcrash-and-resume-4 (a), (b), through copying to the final name; Xcrash-and-resume-4 (c), (d) through having no record of a move on disk. A staged copy fixes the first two paths only.
  - 05-4 is a separate fault in the same copy; a staged copy does not fix it by itself.
  - Xrepeated-logic-4 is in `place` and shares only the topic.
- Order matters across G51 and G52. If the quit limit is fixed by ending the process, a copy longer than the limit is cut off on an ordinary quit, which makes Xsecond-review-disk-writes-7's truncated file reachable without a crash. The staged copy should land first or together. A `shutdown` that waits for moves also needs a decision on what the limit does to a long copy.
- G52: 22-1 and Xshutdown-3 are one bug. 22-7 shares only the code; the unused `exit` closure is what hides the bug, and a fix may give it a use.
- G53: GROUPS.md is right that there is no shared cause. They can be fixed independently.
- Conflicts settled: Xshutdown-1 (P1) over Xconcurrency-4 (P2), and Xshutdown-3 (P1) over 22-1 (P2).

## New findings

### B10-1 [P3] Moving a finished video leaves its subtitle files in the old folder

- Where: `crates/core/src/manager/relocate.rs`, `move_download_files`; `crates/core/src/manager/media_run/placement.rs`, `finish`, `sidecar_path`
- Category: bug
- Failure: a finished video with subtitles saved beside it as `<name>.<language>.srt` is moved to another folder. Only the video moves, so a player no longer finds the subtitles, and the row knows nothing of the files left behind.
- Evidence: for a completed download `move_download_files` moves `from` alone; `partial_files` covers only unfinished downloads, and no sidecar is listed. `set_download_folder` allows a completed media download. This is not the same cause as G51, but sits in the same function.
- Confidence: certain from the code, not run

### B10-2 [P2] A launch that arrives during a stuck quit starts a copy that cannot open the list

- Where: `crates/desktop/src/lifecycle.rs`, `quit`, `start_again`
- Category: bug
- Failure: a run's file work is stuck, the person quits, then launches again. After `QUIT_PATIENCE`, `quit` frees the endpoint and starts a new copy. The old process then blocks in the runtime's drop with the database lock held, because the dropped `shutdown` skipped `store.close`. The new copy fails with `AlreadyOpen` and closes, so the launch the app promised to honour is lost.
- Evidence: the same cause as Xshutdown-3, reached through `start_again` rather than a launch by hand. `Quitting.again` is honoured whether or not `stopped` finished cleanly, since `quit_core` hides the timeout from its caller.
- Confidence: likely, read from the code; the blocking drop is proven by `proofs/Xshutdown-3.patch`, this path is not run
