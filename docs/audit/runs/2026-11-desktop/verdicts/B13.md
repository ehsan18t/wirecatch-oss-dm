# Batch B13 verdicts: main window and Library events

## Verdicts

### G64

- 23-1: confirmed, `move_to_queue` sets `entry.position = state.ids.position()` (last in the new queue), `list_downloads` sorts by `(queue index, position)`, `DownloadSummary` has no position, and `Library::apply` replaces a known row in place. `set_queue_order` sends only `QueuesChanged`, so the All view keeps the old queue order too. `nudged` returns `None` for a row the window holds first, so Alt+Up does nothing. P2 holds: the order is wrong on screen, and a later reorder sends it to the manager.
- 25-5: confirmed, the same bug as 23-1: `queue_line` numbers rows in library order. `Manager::reorder` then gives the stale line the places those rows hold, so the wrong order becomes the real one.

### G65

- 25-6: confirmed, `render` runs `lines` at least twice per frame (`list`, then `selection_bar` through `selected_rows`), a third time through `every_circle` while the bar shows, and each visible heading runs `members` again. `selected_rows` does a linear `find` per selected row. Only the figures come from a bench of the same shape (not rerun here), so the cost is measured at 5,000 rows and up, not in the app. A live sort also rebuilds `Frozen`'s `BTreeSet` of every id per group per `lines` call, which the finding does not count. Against ENGINEERING section 10.
- 23-9: downgraded to P3, the code is as described (`load` refills `startup_notices` from a list the manager keeps, the observer tells them again), but the result is one repeated notice and nothing else. Reaching it needs 1,024 unread events: the ticker sends one event per 100 ms at most, so ticks alone need a stall of about 100 seconds. Same bug as Xdatabase-migrations-3.
- Xdatabase-migrations-3: confirmed at P3, the same bug as 23-9, settling the two severities. One detail is wrong: "Try again" only runs after a failed open, when no notice has been told yet, so that path shows them for the first time and does not repeat them. Only `Lagged` repeats them.
- 24-9: downgraded to P3, the code is as described: `Registry::restore` skips questions with a window (`place_question` returns `None`), never calls `closed`, and nothing calls `reload` on an open view; `_tick` redraws only `Shows::Download`. `FinishedBook` only follows events. Not produced. The trigger is the same rare lag as 23-9, and the person can recover by closing the window or sending the link again.
- 26-7: confirmed, `Activity::load` collects every row into a map on each notify, and `follow` rebuilds the three submenu lists to compare them. Not measured, so P3 stands.
- 27-8: confirmed, the `listing` observer runs on every `Library` notify. `Select::set_selected_value` calls `clear_query`, then `_set_selected_index`, which sets the cursor and calls `scroll_to_selected_item`. `set_items` alone keeps the cursor, so the second call is the one at fault. It also clears anything typed in the list's search, if it has one. Read from gpui-component 0.8.1, not run.

### G66

- 25-1: confirmed at P1 and proven, see `proofs/25-1.patch`. A keystroke test with the real keymap and `Input`, on a copy of the window's element tree, typed `a space b`: the field held `ab` and `PauseOrResume` ran once; its control without the window's bindings held `a b`. In the real app (`target/ui/wirecatch-app.exe`, scratch data folder, keys sent with `PostMessage`), clicking the search field and sending VK_A, VK_SPACE, VK_B left the field holding `ab` (capture `screens/B13-space-typed.png`). The Windows path is `translate_accelerator`: it sends the key down to `handle_keydown_msg` before `TranslateMessage`, and a handled key never becomes `WM_CHAR`. The key is bound in `MainWindow` and handled by `list_keys` on the downloads screen whether or not rows are selected. On Settings, Shortcuts and About no listener exists, so a space is typed there. Pausing selected rows follows from `pause_or_resume`; the proof counts the action and does not run a real pause.

## Group notes

- G64: one cause, split not needed. 23-1 and 25-5 are one finding.
- G65: not one cause, split in two. **Notify cost** (25-6, 26-7, 27-8): the Library has one notify for everything, and observers and `render` do list-sized work or reset state on it. 25-6 is really about `lines` having no cache, so a finer notify would help it only partly. **Reload** (23-9 = Xdatabase-migrations-3, 24-9): `load` after `Lagged` is not a clean way back. - G67: not one cause, split in three. 25-4 is the raw `selected` this group describes. 25-3 is different: its ids come through `selected_rows` correctly, and the fault is the unfiltered ids in `ending` plus `try_for_each`. U-4 is layout.

## New findings

### B13-1 [P2] Enter in the search field also opens the selected finished download

- Where: `crates/desktop/src/main_window/keymap.rs`, `shortcuts` (`on("enter", OpenSelected)`); `crates/desktop/src/main_window/mod.rs`, `list_keys`
- Category: bug
- Failure: click a finished download, close its details, focus the search and type part of its name so the row stays shown, then press Enter. The file opens. A program still asks first (`ask_to_open`); any other file opens at once with its default app.
- Evidence: the field's `enter` in gpui-base `input/base/state.rs` calls `cx.propagate()` for a single-line input, so `dispatch_key_event` goes on to the next matching binding, `OpenSelected` on the window root. `proofs/25-1.patch` includes a test for this, run: `a enter` in the field ran `OpenSelected` once. The opening itself was not run. Same cause as 25-1, and the comment on `KEY_CONTEXT` ("a text field's own keys come first") does not hold here either.
- Confidence: certain

### B13-2 [P3] An empty Paused page offers Resume all

- Where: `crates/desktop/src/main_window/list.rs`, `group_command`; `crates/desktop/src/main_window/command_bar.rs`, `page_command`
- Category: design
- Failure: open Paused with nothing paused. The bar offers "Resume all" beside "Nothing paused".
- Evidence: `Group::Paused => Some(("Resume all", GroupCommand::ResumeAll))` has no check of the page's rows, the same as U-3. Read from the code, not captured.
- Confidence: certain

### B13-3 [P3] More whole-list walks on each progress tick

- Where: `crates/desktop/src/library.rs`, `apply` (`DownloadsChanged`); `crates/desktop/src/main_window/mod.rs`, `keep_queue_speeds`; `crates/desktop/src/main_window/sidebar.rs`, `sidebar` and `describe`; `crates/desktop/src/main_window/rail.rs`, `rail_items`
- Category: inefficiency
- Failure: while anything downloads, each tick walks the list for every changed row (`find` in `apply`), once more for the queue speeds, seven times for the navigation's counts, and once per queue for each queue's description. The cost grows with the list on the thread that draws the window, on top of what 25-6 and 26-7 report. Not measured.
- Evidence: each is a plain `iter()` over `library.downloads` with no index or kept count, against ENGINEERING section 10.
- Confidence: likely
