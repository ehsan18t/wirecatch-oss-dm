## New findings

### B12-1 [P2] The folder rule on Windows also lets a settings file into the app's data folder and other folders whose files get run or trusted

- Where: `crates/settings/src/folders.rs`, `protected_folders` (Windows) and `is_protected`
- Category: wrong implementation
- Failure: a file sets a folder to `{Home}/AppData/Local/Wirecatch`, `{Home}/AppData/Local/Programs/<app>`, `{Home}/.ssh` or `{Documents}/WindowsPowerShell`, and sets "when a file exists" to Replace. A site then names its download after what lives there, such as `public-suffix-list.dat`, `authorized_keys` or `profile.ps1`. All are accepted with no flag, and Linux refuses the equivalents through the hidden folder rule. The result depends on each file's reader: a script needs an execution policy that lets it run, and `wirecatch.db` is held open while the app runs.
- Evidence: all six paths are listed as accepted by the test in `proofs/Xsecurity-path-handling-2.patch`. What each reader then does with the file was not run.
- Confidence: certain for the rule, likely for the results

### B12-2 [P3] A failed update hides Remove and Check for updates, and Try again can do nothing for good

- Where: `crates/desktop/src/main_window/settings/addon.rs`, `buttons`; `crates/core/src/manager/addons/mod.rs`, `install_addon`; `crates/desktop/src/download_windows/media_form.rs`, `install_then`
- Category: bug
- Failure: after a visible update fails, a working add-on shows `Failed`, so the card offers only Try again. If the plan has since become empty (a later check found no release, which any offline check causes), `install_addon` returns at `plan.is_empty()` without clearing `failure` or emitting. Try again then does nothing, and the state stays until the app restarts. In the quality form the same path leaves `awaiting_addon` set, with both buttons busy, until an unrelated library change clears it with no message.
- Evidence: only `start_addon_op`, a successful end, a cancel and a removal clear `failure`; the `plan.is_empty()` branch calls none of them. `buttons` shows Remove only for `Installed` and `UpdateAvailable`. Read, not run.
- Confidence: likely

### B12-3 [P2] A missing library can raise a system dialog that holds the ffmpeg run

- Where: `crates/streams/src/process/tree.rs` (`CREATE_NO_WINDOW | CREATE_SUSPENDED`, no error mode); `crates/media/src/ffmpeg.rs`, `run`
- Category: wrong implementation
- Failure: nothing in `crates/` sets `SetErrorMode` or `CREATE_DEFAULT_ERROR_MODE` handling, so Windows' error mode stays at its default and a missing or bad library in ffmpeg's folder raises a system message box. While it is up the process does not exit, so the run would report `Stalled` after `STALL_TIMEOUT`, not the exit code Xsecurity-addon-unpacking-2 describes, with a dialog on the person's screen naming a DLL. It is the same gap in what counts as a program that cannot start.
- Evidence: a temporary copy of the ffmpeg folder with `avutil-61.dll` taken away, started hidden from PowerShell with the default error mode, had not exited when the command's two-minute limit passed and had to be stopped by path; the same copy with system dialogs off exits `C0000135` at once. It was not run through `process::run`, to avoid more dialogs on the desktop, so `CREATE_NO_WINDOW` itself is not shown to behave this way.
- Confidence: likely
