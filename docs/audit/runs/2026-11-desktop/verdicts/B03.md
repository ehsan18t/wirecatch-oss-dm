# Verdicts: B03 Engine disk writes and resume

Checked against 02284bbd0. `git log a139e6a9d..HEAD -- crates/engine crates/cli` is empty, so the outputs recorded in `proofs/FT-kill.patch` and `proofs/FT-sizes.patch` still describe this code; those two were not re-run.

## G13

- Xsecond-review-disk-writes-1: downgraded to P1, the engine half is proven and the corruption half needs an uncommon system fault. `Checkpoints::spawn` only logs the `Err` from `save`, `mark_flushed` has already counted the ranges, and neither a later save nor `finalize` knows the flush failed. Proof: `proofs/Xsecond-review-disk-writes-1.patch` injects one failed flush in `flush_then` and the run ends `Completed { bytes: 4194304 }`. Not proven: that a later flush passes with the bytes gone. That is documented Linux behaviour (a failed write-back marks pages clean, the error is reported once) and was not reproduced on this Windows machine. It needs a flush that fails once and then passes, on a network drive, a quota or a failing disk; a local full disk refuses at the write instead, so it is not P0 by the realistic-conditions bar. It stays above P2 because the end is a file called complete that may hold zeros, and because the same run fails outright when the first save's flush fails (`download_guarded` applies `?`), so the swallowing is inconsistent.

## G14

- Xsecond-review-disk-writes-2: confirmed, P0 stands, proven. A size-unknown HTTP answer is always `ranged: false` (`probe_range`, also for a `206` with `bytes 0-99/*`), so every retry of one is a whole request with `skip = from`, and `check_whole` compares no size because `request.total` is `None`. `Ended::Eof` with `end == UNKNOWN_END` calls `close_unknown` whatever `skip` is left. Proof: `proofs/Xsecond-review-disk-writes-2.patch`: after 1 MiB and a cut connection, a `200` page of 20 bytes gives `Outcome::Completed` with 1048576 bytes, and `Fetcher::save` returns `Ok(1048576)`. The conditions are ordinary: a chunked answer, a dropped connection, then a login, captive portal or error page sent as `200`. The result is a cut file reported complete with no error.
- 02-3: confirmed, P2. In both `stream` and `Fetcher::attempt`, `data.is_empty()` continues before `pace`, and only kept bytes count, against the `Fetcher` doc's "Every byte counts".

## G15

- Xsecond-review-resume-4: confirmed, P2. `saved_state` answers `None` to any read error except not found, `part_len` the same, `plan_exact` then gives `Plan::Planned(target, None)` and `prepare` discards the part file. `WorkDir::open` clears the folder on any `stream.txt` read error. D30.3 records "set aside and logged, never reported", but on an exact path the part file is deleted, not set aside, so the decision does not cover this failure. Only the exact path deletes; `plan_in_folder` goes to `FreeName` instead (F-1).
- Xsecond-review-resume-5: confirmed, P2. The order is `discard(part)`, `discard(state)` unchecked, then `create_part`, which gives a full-length part file of zeros; if the first `saver.save()` also fails on its rename, the old resume file passes every check of the next run and its done ranges stay zeros. Two faults together, as the finding says, so P2 even though the result is silent corruption.
- Xsecond-review-disk-writes-5: confirmed, P2. `finalize` renames once and the `?` leaves `finish` at once. `same_file` needs ranges and a size, so the retry's `Plan::Planned(_, None)` deletes a complete part file on a server without them. With `Finish::Refuse` and ranges, the resume file saved before the rename makes the retry finish without fetching.

## G17

- 28-1: confirmed, P2. The strings are unconditional in `Stalled`, `PrematureEof`, `http_status` (`Worked::Before`) and `stopped_unexpectedly`; `Worked` carries nothing about resuming. `describe` has no other input that could.

## G18

- 01-1: confirmed, P2. `plan_in_folder` builds only `dir.join(&name)`; `create_free_part` skips a candidate whose resume file exists. Both variants in the finding follow.
- 01-2: confirmed, P2. Not run. `plan_in_folder` has no way to know a part file is in use, `discard` succeeds on an open file on both systems (Rust opens with delete sharing on Windows), and `finalize` opens by path, so it renames the other run's file. Needs two identical commands at once, which is why it stays P2 despite the corrupt result.
- F-1: confirmed, P2. `saved_state` answers `None` for damage as for absence, so the `if let` falls to `Plan::FreeName`, against `saved_state`'s own doc ("starts over and replaces it"). Recorded output in `proofs/FT-kill.patch`.

## G19

- 01-3: confirmed, P2. `linux::fallocate(file, len).or_else(|_| file.set_len(len))` discards `ENOSPC`; on NTFS, sparse plus `set_len` allocates nothing. No crate asks for free space (no match for `GetDiskFreeSpace`, `statvfs`, `available_space`). Not run. The README's "reserved up front" wording is the promise that fails.
- 01-4: confirmed, P2. `save` has no comparison with the last saved ranges, and D30.1 covers a flush per interval only for a download making progress.
- 01-5: downgraded to P3, the miscount is real and its cost is small. Order: `unwritten += len`, `wait` moves all of it to `dropped`, `stream` breaks before `progress.add`, then `take_back`. The count is short by one network chunk only when a write fails on one connection and others carry on to the end, and a finished download shows as completed whatever the count says. No wrong file, no wrong status.
- 02-5: confirmed, P3. `pause` is capped at `max` and then gets jitter, so `delay > backoff.max` is true only at the cap with non-zero jitter, or with `first == max`. `retry_after.is_some()` already covers the case D69.1 names. Reaching the cap with defaults takes six failures in a row and `max_retries` defaults to 6, so it is close to dead code at defaults.
- 02-6: confirmed, P3. `sink.finish()` is reached only after `transfer` returns; `BufWriter` does not flush on drop. `crates/streams/src/download/fetch.rs`, the one caller, renames the part only after `save` returns `Ok`.
- F-2: confirmed, P2. `stream` compares only with `request_end`, so a clean short `206` is `PrematureEof`; `progressed` resets `failures`, so each wait is `first` plus jitter. Recorded output in `proofs/FT-sizes.patch` (57 waits for 65 requests).

## New findings

### B03-1 [P2] The refresh dialog promises "What is already downloaded is kept" for downloads that cannot resume

- Where: `crates/desktop/src/main_window/refresh_dialog.rs`, the `note` text
- Category: wrong implementation
- Failure: a failed download from a server with no range support or no size. The dialog for pasting a fresh link says "What is already downloaded is kept." After the new link is pasted, the run starts from byte 0 and deletes the part and resume files.
- Evidence: the text is unconditional. Core runs with an exact path, so `plan_exact` finds `continues` false (`same_file` needs ranges and a size) and `prepare`'s `Plan::Planned(target, None)` arm discards both files. Same cause as 28-1, in a place that does not go through `crates/messages`.
- Confidence: certain from the code; not run
