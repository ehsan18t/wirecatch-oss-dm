# Verdicts: B14 The local network rule

Judged from the code at the run's commit; no test was run, since nothing here reached P1. The `publicsuffix` 2.3.0 and `reqwest` 0.13.5 sources were read where a finding depends on them. What the browser extension sends was not checked (outside the batch).

## G69 The local network rule stops at HTTP

- 09-1: confirmed, `download_with` builds a guard only for `http` and `https`, `transport::open` drops `guard` on the FTP arm, `Target::resolve` uses a bare `lookup_host` and `probe` tries every address, while the doc of `refuses` promises the engine refuses later. `DownloadOptions::private_network` documents the FTP gap, but no decision accepts it and D34.9 and D39.1 state the rule for every start. P2 stands: it needs an FTP link captured and a name that rebinds or mixes answers, and nothing read goes back to the site.
- 21-1: confirmed, same bug as 09-1 for its first form; for the second, `ftps` and `ftpes` hosts stay opaque, `address_in` and `addresses` see `%31%32%37.0.0.1` and `Target::new` decodes it to `127.0.0.1`. Its limit is right: the TLS check normally stops that form after the connection is opened. `ftp_route` also receives the undecoded `host_str`. P2 stands.
- Xsecurity-bridge-and-pipe-input-1: confirmed, same bug as 09-1 plus the mismatch between the host checked and the host connected to. One claim is too strong: for the percent-encoded form the engine does not log in unless the local server's certificate passes, because `ftps` starts with TLS and `ftpes` sends `AUTH TLS` before `USER`, so that form reaches only the connection, the greeting and `AUTH TLS`. Login and saving hold for the plain `ftp://` rebinding form. P2 stands.
- Xsecurity-bridge-and-pipe-input-2: confirmed, `capture_arrived` checks only the first host, `hold_media` spawns `analyse` at once, `read_page` runs `extract_once` with no address rule, and `page_attempt`'s else branch calls `ytdlp::download` outside `network_rule`, whose comment admits only the fallback; no decision covers the read, and `read_stream` for the other kinds does run under the rule. That yt-dlp follows the redirect was not run. P2 stands: a blind GET or a saved file, no cookies carried across hosts, and nothing sent back to the site.

## G70 What counts as a local page

- 10-1: confirmed, `of_capture` only requires `Url::parse` to succeed; `chrome-extension://abcdef/x` has the opaque host `abcdef`, which `is_local_by_itself` reads as a single label off the list, so the capture is `LocalPage`, runs under `Auto`, and `refuses` lets a link to a local address through. `cookie_scope::site_of` refuses those schemes next door. P2 stands; that a context menu click reaches this on another extension's page rests on the finding's reading of the extension.
- 10-2: downgraded to P3, the code fact is right (`find` takes `node.leaf` for the first label, and `jm` has a node only as the parent of `*`, so `is_known` is false; the snapshot has `*.ck`, `*.er`, `*.fk`, `*.jm`, `*.mm`, `*.np` and `*.pg` and no plain rule for them), but only the registry of those seven domains could serve a host at the bare label, so no realistic site gains from it. It breaks the wording of D39.1 and has no practical failure.

## G71 The guard's edges

- 09-4: downgraded to P3, `private_guard(...).await` in `download_with` and `with_private_network` and `(guard.0)(&url).await?` in `send` are outside any `select!`, and the doc of `send` promises otherwise, but `stop_run` aborts a run that has not exited after `stop_timeout` (5 s by default), so in the app the delay is at most that and only while the name server is silent. Nothing is lost by the abort, as no file is open yet. The 60 s holds only for a direct user of the engine.
- 09-5: confirmed, both tests use `localhost`, which `NetworkGuard::check` refuses before any connection, so removing `set_resolver` or `.dns_resolver` passes them; `the_resolver_never_hands_out_local_addresses` tests the resolver alone. `a_format_rebound_to_the_local_network_after_the_check_is_refused` in `media_run/tests.rs` is sound for what it asserts (core's rule reaches the engine), but its comment names the `net_guard` test as the proof of the refusal at the connection, which that test does not give.
- 09-6: confirmed, `FilteringResolver::resolve` returns a text error, `send` turns it into `Error::network`, which maps only proxy login and certificate problems, so the run is retried and ends as `Error::Network`, not `Error::PrivateNetwork`. The connection stays blocked. P3 stands.
- 09-8: confirmed, the rule is written twice in `net_guard.rs` (`check` and `all_private`), and `check` repeats the host match of `host_addresses`. P3 stands.
- 09-9: confirmed, the `proxy.rs` header says FTP is refused while `ftp_route` carries it through SOCKS5 and `ftp_direct` lets it go around; the `PrivateNetwork` section omits `ProxyChoice::Manual` and says the proxy resolves every name, while reqwest uses `DnsResolve::Local` for `socks4` and `socks5`. P3 stands.

## G72 "This host is that site" is written four times

- 10-4: confirmed, `on_site` and `local_network::is_under` have the same body in one crate, `queues` spells the test differently, and callers differ on the trailing dot: `is_listed` trims it, `video_site_for` does not. P3 stands.
- Xrepeated-logic-3: confirmed, each case follows from the code: `covers` compares the raw host, so `example.com.` misses, and `Url::host` gives `Host::Domain` for `ftps`, so a `Range` arm never matches and a mixed-case name stays mixed; `on_site` misses `youtube.com.`. P3 stands, as these are rare forms of a link.

## Group notes

- G69 does not share one cause. Split it in three:
  - G69a, the engine applies no rule on the FTP path: 09-1, 21-1 first form, Xsecurity-bridge-and-pipe-input-1 rebinding form. The fix is a filtered lookup in `Target::resolve`, plus a check of each address under `Block`.
  - G69b, `ftps` and `ftpes` hosts are read raw by every check and decoded only by `Target::new`: 21-1 second form, Xsecurity-bridge-and-pipe-input-1 encoded form, the `ftps` cases of Xrepeated-logic-3, B14-1. The fix is one normalised host at `parse_url`. It should also run `Host::parse` on what it decodes, as `Target::new` does, so a number such as `ftps://2130706433/a`, which `address_in` does not read as an address, is classified as one.
  - G69c, yt-dlp has no address rule: Xsecurity-bridge-and-pipe-input-2. The engine's guard cannot reach another process, so it needs a fix of its own.
- `09-1` = `21-1` = `Xsecurity-bridge-and-pipe-input-1` holds only for G69a. The other two carry G69b as well, so fixing the engine alone leaves the host mismatch for queue rules and proxy exceptions.
- G70 does not share a cause: 10-1 is a missing scheme check in `of_capture`, 10-2 a wildcard gap in `is_public_suffix`. They meet only in `is_local_by_itself` and can be fixed apart.
- G71 has no shared cause, as it says, with one link: the tests of 09-5 never reach the resolver, which is why the wrong error of 09-6 went unseen. A test with the name cached as allowed in `NetworkGuard::names` would cover both. 09-4 goes with B14-2.
- G72 shares its cause for the trailing dot and the copies. Its `ftps` cases belong to G69b. `queues::is_under` is not a plain copy, since it also serves the `*.` rule and requires a label before the name.

## New findings

### B14-1 [P3] The own-network check reads an `ftps` host raw, so a `<local>` queue rule misses it

- Where: `crates/sites/src/local_network.rs`, `is_local_by_itself`, `is_listed`, `is_under`; reached from `crates/core/src/manager/placement.rs` through `is_on_own_network`
- Category: wrong implementation
- Failure: `ftps://FILES.Home.Arpa/a.zip`, or the same host percent-encoded, is not on the person's network by these checks, so a queue rule `<local>` does not cover it and the download goes to another queue. A listed site misses it the same way.
- Evidence: `is_under` states that both names are lower case because the URL parser writes them so, which does not hold for `ftps` and `ftpes`, whose hosts are opaque (`Target::new` says so for its own decoding). Xrepeated-logic-3 reports this cause for `SitePattern::covers` only. `rules::find` passes every candidate URL here, and `parse_url` does not normalise the host. Not run.
- Confidence: likely

### B14-2 [P3] Core's early lookup of a format's address ignores a stop

- Where: `crates/core/src/manager/media_run/page.rs`, `fetch_parts`; `crates/core/src/manager/media_run/network.rs`, `network_rule`, `page_is_local`
- Category: wrong implementation
- Failure: pausing a page download while the name server does not answer. `fetch_parts` awaits `network_rule` for each format with no `select!` on `cancel`, and each call can wait `LOOKUP` (10 s), twice for a link the person chose. The stop is not seen until the lookups end, or until `stop_run` aborts the task after `stop_timeout`.
- Evidence: `local_network::addresses` takes no token and `fetch_parts` has no `cancel` branch around the loop, the same shape as 09-4 one layer up. In the app the delay is bounded by `stop_timeout`.
- Confidence: certain
