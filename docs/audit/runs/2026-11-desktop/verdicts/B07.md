# Batch B07: yt-dlp, what media offers, and names

Real tools used: the installed add-on's yt-dlp 2026.10.26 and ffmpeg, against a small local server. Tests: `proofs/Xpath-media-download-1.patch`, `proofs/Xpath-media-download-2.patch`, `proofs/B07-p2-tests.patch`. Each was applied alone to a temporary worktree and run under a cargo profile of this batch's own (`[profile.b07] inherits = "dev"`, `--profile b07`; `target\audit-proofs\b07\deps` confirmed in the output), so no other validator's binary ran. Every test failed as stated at the top of its patch. The commands at the top of the patches leave that profile out.

## Verdicts

### G38

- Xpath-media-download-1: confirmed, P1, proven. `audit_flac_offered_as_mp3_is_not_refused_after_the_download`: the offer lists MP3 for a FLAC source, the file downloads, then the row is Failed with `FixAction::RefreshLink`, not `KeepOriginal`, so `keep_original` is out of reach. The message is "The downloaded audio is not in a format Wirecatch can join", which differs in words from the finding. Real `a.flac`, `a.ogg` and `a.wav` start `fLaC`, `OggS` and `RIFF`, none of which `from_head` knows. A video paired with such audio takes the same path through `merge::join`, by reading.
- Xpath-media-download-10: confirmed, P2. `original_audio_action` and the re-encode branch both trust `has_audio`, and `add_maps` writes `{v}:a:0` with no `?`. Real ffmpeg with `-map 0:a:0` on a silent MP4 stops at "Error opening output files: Invalid argument". Needs no audio format on the page and a silent video without `acodec`, so it is uncommon; Keep the original is offered.

### G39

- Xpath-media-download-2: confirmed, P1, proven. Real yt-dlp `-J --cookies` on a local cookie-gated page gave the format `"cookies":"sid=abc123; Domain=127.0.0.1; Path=/; Expires=..."`, with no `Cookie` in `http_headers`; a request without it got 403; yt-dlp itself saved the file. `audit_a_format_that_needs_its_cookies_is_not_fetched_without_them` (the refusal simulated by the test server): 4 requests without the cookie, yt-dlp never tried, row ends "kept refusing". The comment on `a_format_never_prints_its_header_values` is wrong for this yt-dlp. `part_options` keeps the page's cookies off the engine on purpose, so a fix may fall back to yt-dlp after a refusal rather than send them.
- Xpath-media-download-3: confirmed, P2. Real yt-dlp `--load-info-json` on a top-level video printed no `formats`, with `protocol`, `http_headers`, `vcodec` and `acodec` at the top. `audit_top_level_hls_is_not_a_plain_file` (File, not Hls) and `audit_top_level_headers_are_kept` fail. `join_original` takes a single file as it is and `finish` checks no content, so a playlist's text ending Completed is by reading, not run end to end.
- Xpath-media-download-4: confirmed, P2. Real yt-dlp `--no-playlist -J` on a local page with two `<video>` tags: `_type: "playlist"`, 2 entries, no `formats`, `url` or `format_id`. `audit_a_page_with_several_videos_is_not_nothing` fails. No decision or roadmap line records it as a limit.

### G40

### G41

- 16-3: confirmed, P2. Real yt-dlp on two 200,000-byte formats with this template: `200000 200000 v`, then `200000 200000 a`. Counts are per format, never 400000, and `set_own` replaces the last report. Backwards bar by reading of `read`.
- 16-4: confirmed, P2. `audit_a_row_labelled_60_fps_downloads_60_fps`: "1080p, 60 fps" downloads `137+140`, the 30 fps MP4. The Save as WebM choice can still reach the 60 fps stream; the finding's "under Original" is exact. Needs codecs of one height to differ in frame rate.
- 16-5: confirmed, P3. `audit_huge_sizes_do_not_overflow` panics at the `x + y` in `video_offer` in a dev build. `[profile.release]` sets no overflow checks, so a shipped build shows a wrapped size. The other additions (`variant`, `estimate`, `MediaProgress::read`) by reading.

### G42

- 17-5: confirmed, P2. `audit_a_refused_hls_address_reads_the_page_again`: one 403 on the playlist ends the row Failed, where a file format would read the page again. The row offers `RefreshLink` with sign-in wording ("You may need to sign in on the page first"), not Try again as the finding says.
- Xpath-media-download-9: confirmed, P2, now run. Real yt-dlp with `-f 'b*[format_id="hls-2148"]'` on a page without it: "Requested format is not available". That is `YtDlpError::Refused`, always Retry, and the stored ids are never re-resolved.

## New findings

### B07-1 [P2] A page described at the top level as audio is offered as a video

- Where: `crates/media/src/ytdlp/info.rs`, `Info`, `Info::all_formats`
- Category: bug
- Failure: an extractor returns one `url` with `"vcodec":"none","acodec":"mp3"` and no `formats`. `all_formats` drops `vcodec`, `acodec`, `height`, `filesize` and the rest, so the unknown codecs read as present: the only row is "Best quality, MP3" with `audio_only` false, going to the video folder under the Video category, with no size, and no audio-only row or MP3 conversion choices.
- Evidence: same place as Xpath-media-download-3, different loss. Real yt-dlp keeps those fields at the top level. `audit_top_level_audio_is_offered_as_audio` in `proofs/B07-p2-tests.patch` fails with "Best quality, MP3".
- Confidence: certain for the offer; which extractors do it was not measured

### B07-2 [P2] The best audio is picked by rate alone, so a dubbed or described track can replace the original

- Where: `crates/media/src/output/variants.rs`, `best_by_rate`; `crates/media/src/choice.rs`, `best_audio`; `crates/media/src/ytdlp/info.rs`, `Format`
- Category: wrong implementation
- Failure: a page has audio in several languages, with the original marked by `language_preference`. A dubbed or audio-described track of a slightly higher rate is taken for the video and for "Audio only", and the person gets the wrong language with no choice of track.
- Evidence: `Format` reads no `language` or `language_preference`; `rate` uses only `tbr` and `abr`. yt-dlp's own sort uses these fields first. `audit_best_audio_prefers_the_original_language` in `proofs/B07-p2-tests.patch` picks `140-1` (hi, 130) over `140-0` (en, preference 10, 129). No decision records this. Same theme as G39: yt-dlp's answer is read only in part.
- Confidence: likely (the selection is certain; not run against a real multi-language page)

### B07-3 [P2] A refused address during yt-dlp's own download does not read the page again either

- Where: `crates/core/src/manager/media_run/page.rs`, `page_attempt`
- Category: wrong implementation
- Failure: a format with `Transport::YtDlp` whose address expires or is refused during a long download. yt-dlp stops with an HTTP 403 error and the row fails with Retry and "update the media add-on", where a file format would read the page again and go on by itself.
- Evidence: `ytdlp::download(..).await.map_err(|e| describe::ytdlp(&e, tools))?` always gives `PageError::Failed`, as the HLS branch does in 17-5. `run_page`'s doc promises the refresh for any refused format address. `SIGN_IN_MARKERS` already recognises `http error 403` in the text, so the cause is readable. By reading; not run.
- Confidence: likely

### B07-4 [P2] An audio format without a `vcodec` counts as a video

- Where: `crates/media/src/ytdlp/info.rs`, `Format::has_video`; `crates/media/src/output/arguments.rs`, `add_maps`
- Category: bug
- Failure: a format `{"ext":"mp3","url":...}` with no `vcodec`, on its own. It is listed as a video row with no audio-only offer, and any Save as that runs ffmpeg maps `{v}:v:0` from a file with no video, which ffmpeg refuses as in Xpath-media-download-10.
- Evidence: real yt-dlp `--load-info-json` on such a format printed `"acodec":"mp3"`, no `vcodec`, `video_ext: "mp3"`, `audio_ext: "none"`. `has_video` is `is_none_or(|c| c != "none")`. Same cause as Xpath-media-download-10 on the video side; `has_video` does not look at the extension except for `mhtml`. The ffmpeg refusal for this exact case is by reading.
- Confidence: certain for the offer; likely for how often extractors leave it out
