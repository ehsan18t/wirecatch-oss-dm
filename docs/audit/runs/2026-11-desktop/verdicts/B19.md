# Verdicts: B19 Tests, checks and dead code

Judged from the code, with no test built: nothing here reaches P1. Run for evidence: `timingRaces` from `scripts/gate/test-timing.mjs` on small samples (`recv_timeout(Duration::from_secs(1))`, `recv_timeout(SHORT)`, `took.as_millis() < 500`, a `let patience = Duration..` passed to `timeout`: 0 hits each; `timeout(Duration::from_secs(2), ..)`: 1 hit), and `git grep --untracked` in an empty folder outside a repository (status 128).

## G89 Tests race the machine

- 01-9: confirmed, `pause_midway` and `another_program_saves_meanwhile` loop on `progress.done() < at_least` with no deadline and never look at the spawned task; ten calls go through them, and a download that fails early hangs the test until the CI job's own limit.
- 01-10: confirmed, `recv_timeout(DEADLINE)` is 10 s, `download` builds `Clients` (on the blocking pool the first time) before `validate` runs in `download_with`, and the helper would catch the same hang under `PATIENCE`, so the short limit buys nothing.
- 33-2: downgraded to P3, the gap is real (both patterns need `\btimeout`, and `recv_timeout` has no word boundary there; `took.as_millis() < 500` also passes), but what it costs is one possible test failure on a very slow runner (01-10, its only live case: every other `recv_timeout` in a test uses `PATIENCE`), with no effect on the product.
- 03-7: confirmed, in exactly the four named tests: `let (_, ..) = Store::open` and `drop(Store::open(..))` leave the thread closing while the next open has only `LOCK_WAIT`, and `close(Duration::from_secs(5))` only logs on timeout. A scan of the file's tests found no fifth; the other reopen pairs wait with `close`.
- 04-7: confirmed, `let patience = Duration::from_secs(5)` then `.expect` on `timeout(patience, ..)` around `remove` and `shutdown`; the check does not see a local variable.
- 05-14: confirmed, the harness keeps `when_file_exists` at `Ask`, `taken_by_another` holds only while the first run's claim exists (`complete` removes it in `run.rs`), so a first download that ends before the second's answer sends the second to `on_found`, which asks, and `wait_status(second, Completed)` fails after `PATIENCE`.
- 06-3: confirmed, all three parts: the keyed tests pass `START_BUDGET` (5,000 ms) where the neighbour passes `PATIENCE` and says why; `wirecatch-e2e-app` quits at `LIFETIME` (60 s) while `FakeExtension` gives the bridge `PATIENCE` for the start and each call; the fake app's `LINGER` (10 s) races the `connect` the test requires. None is likely on a normal run, which P3 already reflects.
- 10-5: confirmed, `refuses(Website, http://localhost/a)` goes through `addresses(url, CAPTURE_CHECK)` on the real clock and an expired lookup answers false; the `.invalid` line passes whether the lookup failed, timed out or never ran.
- 13-4: confirmed, `Idle::new` arms the 300 ms limit straight after the spawn while `hang` writes its line only once running, and only that line lets the assertion pass; `what_a_program_leaves_running_ends_with_it` needs the readers to see the end within the real 2 s `OUTPUT_GRACE`. The note on `SHORT` covers only a run that stops late.
- 21-3: confirmed for the transfer tests, only the throttle lets other connections join, and `send_file` paces by elapsed time, so after a stall it sends in a burst with no sleep and shortens the window further. The `control_reading` part is real but very narrow: on the single-thread test runtime the server task runs at the reader's first await, so it needs a 2 s stall in that gap. No test in the module expects `Stalled`, so nothing needs the 2 s limit.

## Group notes

- **G89 does not share one cause; split it.** (a) No deadline at all: `01-9`. (b) A short limit the test itself chose: `01-10` = `33-2`, `04-7`, `06-3`, plus the `control_reading` part of `21-3`. (c) A real-clock limit of the code under test: `03-7`, `10-5`, `13-4`, `B19-1`, `B19-2`. (d) An order only timing decides, with no limit involved: `05-14`, and the transfer tests of `21-3`. Only (b) can be caught by widening `test-timing`; a pattern check cannot see (c) or (d), so those need the review rule. `33-2` is the check's own gap and belongs with (b), and the fix should cover `recv_timeout`, a local `Duration` variable passed to a wait, and a measured time compared through a method.
- **G90 has no shared cause,** as the group says. Keep the five as separate items; `33-1` is the only one that stops something working.
- **G91 splits in two.** Copies not shared: `31-1`, `02-8`, `07-7`, `17-9`. Servers unlike their docs, or unused: `31-2`, `31-3`, `31-4`. `31-1` belongs to both, since the copy has drifted.
- **G92 is only partly one cause.** `23-11`, `24-11`, `30-5` and `30-6` are the removed web interface with no reader left, and `B19-4` and `B19-5` join them. `19-10` is a test convenience left public, `07-6` a wrong comment, and `30-7` a data error in a live list: move `30-7` out, as it is the one item here a person can see.

## New findings

### B19-1 [P3] A bridge test must look the key up twice within a real 600 ms

- Where: `crates/bridge/src/app.rs`, test `the_last_attempt_decides_what_is_reported`
- Category: fake test
- Failure: the test runs on the real clock with `budget = 600 ms`, then asserts `resolved > 1`. A stall over 600 ms after the first attempt ends the budget with one lookup, and both that assertion and the reported reason fail on correct code.
- Evidence: plain `#[tokio::test]`, while `gives_up_when_the_app_never_listens` in the same module uses `start_paused` and says why ("a slow machine cannot stretch it"). `docs/ENGINEERING.md` section 7 forbids this race. Same cause as `06-3`. Not seen failing.
- Confidence: certain for the race; likely for it failing on a loaded runner

### B19-2 [P3] A removal test races the real 1 second stop limit

- Where: `crates/core/src/manager/tests.rs`, `a_download_being_removed_cannot_be_brought_back`
- Category: fake test
- Failure: `stop_timeout` is 1 s on the real clock. After `wait_until` sees the list empty, the test asserts `is_running` ("the run stopped too early to test anything"). A stall over 1 s after the removal starts lets the limit run out, the run ends, and the assertion fails on correct code.
- Evidence: `let stop_timeout = Duration::from_secs(1)`, passed to `manager_with`, and a multi-threaded test with no paused clock. The check cannot see it: nothing is measured and no wait has a duration. Not seen failing.
- Confidence: certain for the race; likely for it failing on a loaded runner
