# Verdicts: B05 App updates and packaging

Counts: 23 confirmed, 1 disproved, 2 downgraded. 2 new findings.

Build note: the desktop crate could not be built, because the D: drive filled up during the run (os error 112). The G25 proofs therefore read `crates/desktop/src/backend.rs` from a core test instead of calling `config`. They ran in a build folder on C:, not `target/audit-proofs`, since removed.

## Verdicts

### G25 `backend::config` never names the official sources

- Xfeature-behaviour-1: confirmed, P1. `config` calls only `with_official_suffix_list`, `new` leaves `app_releases` as `None`, `with_official_app_releases` has no caller, and `check_app_update` then returns `Ok(None)`, shown as "You have the newest version." Hidden today only by the placeholder key (`no_updates`). Proof: `proofs/Xfeature-behaviour-1.patch`, ran and failed: "a published, signed v0.2.0 was not found: None".
- Xpath-app-update-1: confirmed, same bug as Xfeature-behaviour-1, P1, same proof.
- Xsecurity-update-signatures-1: confirmed, same bug as Xfeature-behaviour-1, P1, same proof.
- Xfeature-behaviour-2: confirmed, P1, and live in every build today: `with_official_proxy_test` has no caller, so `run_test` answers `Unreachable` with no request. Proof: `proofs/Xfeature-behaviour-2.patch`, ran and failed: left `Unreachable { reason: "this build has no address to test the proxy with" }`, right `Works`.

### G26 An inherited `APPIMAGE` is trusted

- 12-1: confirmed, P1. `install_kind` tests only that the variable is set and `replace_appimage` renames over its value; `bridge.rs` and `autostart.rs` read it the same way, with nothing comparing `current_exe` or `APPDIR`. `crates/bridge/src/app.rs` and the app clear no environment. Not raised to P0: it takes a system package started under another AppImage, a published update and a click, and what is lost is a program file that can be fetched again. The update half stays unreachable until G25 is fixed; the bridge launcher and sign-in entry halves are live today. Proof: `proofs/12-1.patch`, the `autostart::program` test ran and failed on Windows; its `replace_appimage` test is unix only and was not run.
- Xpath-app-update-4: confirmed, same bug as 12-1; its P2 gives way to P1.
- Xsecurity-update-signatures-2: confirmed, same bug as 12-1, P1.

### G27 The app starts the installer, then quits without knowing it worked

- Xpath-app-update-2: downgraded to P2, the facts hold: the built `target/packages/Wirecatch-0.1.0-windows-x64-setup.exe` carries `requestedExecutionLevel level="asInvoker"` (read for this verdict), `run_setup` takes a value above 32 as success, `install` quits at once, the only restart is a `[Run]` entry, and `/SUPPRESSMSGBOXES` hides the setup's errors. So D111.4's failure path cannot be reached for a refused prompt or a failed setup. But nothing is lost: downloads continue at next start, the install stays as it was, and reopening the app works. A real prompt was not answered: the audit cannot drive UAC, so no proof is claimed.
- Xsecurity-update-signatures-5: confirmed, same bug as Xpath-app-update-2, P2.
- 12-5: disproved, it assumes the shell shows the prompt and returns error 5. With an `asInvoker` setup `ShellExecuteW` starts it without a prompt and returns above 32, so a refusal never reaches `InstallError::Start`. The text "error N" stays bare for rarer start failures, which is not this finding's failure.
- 12-3: confirmed, P2. The two reviewers read different windows, and both are right about theirs: `start_again_later` catches a launch only until `again.take()` in `lifecycle::quit`. After that the listener stays open until the process exits (`free_endpoint` runs only when `again` was set), so a `ShowWindow` is answered and lost, and an exit during the hand-over shows `say_already_running`. Linux only, reasoned from the code, not run.
- Xpath-app-update-3: confirmed, same bug as 12-3, P2.

### G28 What an update leaves on disk

- 12-2: confirmed, `UPDATES_FOLDER` is used only by `fetch_app_update` and its test, and only a file failing its check is deleted. A repeat of the same version does not fail: the engine's default `ExistingFile::Replace` renames over the kept file. P2.
- Xpath-app-update-5: confirmed, same bug as 12-2, P2.
- 12-4: confirmed, `replace_appimage` runs `fs::copy`, `set_permissions`, `rename` with no `sync_all`, while `write_private` in the same crate syncs, and an error leaves `.wirecatch-update.AppImage` behind. P3.

### G29 An offer's state and checks

- Xpath-app-update-6: confirmed, `download` is `None` for no kind, no system or architecture, no manifest entry, no asset, or a size that differs (`check_app_update`), and `update_available` always says "Install it with your package manager." and drops What's new. Wording half of the same bug as Xsecurity-update-signatures-3. P3.
- Xsecurity-update-signatures-3: confirmed, on Windows or an AppImage (`kind` is `Some`) an asset missing or of another size gives `Ok(Some(AppUpdate { download: None }))` with no log, and `install` then opens the page; a refusal path (`refused`) exists and is not used. A same-size swap is caught by the hash, a different-size swap sends the person to the file by hand. Needs write access to a release's assets, and the setup is unsigned for now. P2.
- Xsecurity-update-signatures-4: downgraded to P3, the code facts hold (`html_url` is a plain `String` kept unparsed; gpui-pre-windows `open_url` reaches `ShellExecuteW`), against the letter of D111.3. But it takes an attacker who holds a certificate the system trusts, a genuine signed manifest of a newer version, and a click, so not a hole under realistic conditions.
- Xpath-app-update-7: confirmed, `prerelease_updates` is read only in `check_app_update`; a quiet check returns early on `Available` and `InstallFailed`, and the `Available` arm of `app_update_field` has no check button. P3.
- 12-6: confirmed, `Harness::publish` derives the manifest's version from the tag and gives the asset and the manifest the same size, and no test outside this module calls `check_app_update`. Run with both checks removed from a temporary copy (`if false`, `true.then`): all 5 existing `app_update` tests passed. P3.

### G30 Installers and release workflow

- 29-1: confirmed, `installer.iss` has no `AppMutex`, no `uninsrestartdelete` and no `[UninstallRun]`, and `CurUninstallStepChanged` stops nothing. `CloseApplications=force` is documented for Setup's `[Files]` and `[InstallDelete]` only. Not run: an uninstall on this machine was not attempted. P2.
- 29-2: confirmed, `appRun` exports `LD_LIBRARY_PATH` and nothing removes it: `run.rs` removes Python variables only, and gpui-pre-linux `open_with_system` applies only the graphical environment. A visible failure needs a program using a libxkbcommon symbol newer than the build machine's, which is plausible on a rolling distribution. Not run. P2.
- 29-3: confirmed, `arch` from the triple also picks the tool, so x64 runs an arm64 `nfpm`; `release.yml` passes no `--target`, so only the documented example breaks. P3.
- 29-4: confirmed, `linux-packages` downloads `desktop-Linux-X64` only and runs on `ubuntu-latest`, while `draft` merges every artifact. PACKAGING.md says "checks each Linux package". P3.
- 29-5: confirmed, neither list names a C library or any version and nfpm computes none; `linux-package-check.sh` installs on the build's own base. Which symbols the binary needs was not read. P3.
- 29-6: confirmed, `icon.svg` repeats the points and widths of `mark.json` by hand (they match today), and only `mark.rs` and `AppMark.svelte` read `mark.json`. P3.

## Group notes

- G25: one cause, the two missing calls in `config`. A test on `config()` that every official source is set would catch this kind of omission; `ManagerConfig::new` leaving them off for tests is what hides it.
- G26: one cause, `APPIMAGE` read with no check that this process runs from that file. Fix it once, in `crates/shell/src/appimage.rs`.
- G27: split. Windows (Xpath-app-update-2, Xsecurity-update-signatures-5) is a false premise: D111.4, the comment on `run_setup` and PACKAGING.md say the shell asks for approval, and the setup is `asInvoker`. The AppImage race (12-3, Xpath-app-update-3) is an ordering fault that `start_again_later` can solve. They need different fixes. 12-5 falls away.
- G28: split. 12-2 and Xpath-app-update-5 are about cleanup; 12-4 is about flushing. They touch the same flow only.
- G29: no shared cause. Xpath-app-update-6 and Xsecurity-update-signatures-3 are one bug: `download: None` has several meanings. The other three stand alone.
- G30: no shared cause, as GROUPS.md says. The conflict over 29-2 settles for both readings: the leak is harmless for yt-dlp and ffmpeg, which do not use these libraries, and it matters for what `xdg-open` starts.

## New findings

### B05-1 [P2] A launch during a quit can start the program named by an inherited `APPIMAGE`

- Where: `crates/desktop/src/lifecycle.rs`, `start_again`; `crates/shell/src/autostart.rs`, `program`
- Category: bug
- Failure: a system package copy that inherited `APPIMAGE=/path/to/Other.AppImage` gets a second launch while quitting. `start_again` runs `autostart::program()`, so it starts the other program instead of Wirecatch, and Wirecatch does not come back.
- Evidence: `start_again` is a caller of `program` that the G26 findings do not name; `program` trusts the variable on every system, with no `cfg`. The `program` half is run in `proofs/12-1.patch`; the quit path was not run.
- Confidence: likely

### B05-2 [P3] `Manager::updater_proxy` has no caller

- Where: `crates/core/src/manager/proxy.rs`, `updater_proxy`; `crates/settings/src/proxy.rs`, `updater_proxy`
- Category: dead code
- Failure: its doc says it is the proxy the app updater uses, but updates take theirs from `update_options`, through `app_proxy`. A reader changes the wrong one. Same family as G25: code written for the app that the app never calls.
- Evidence: a search of `crates` finds the core method only at its definition, and the settings function only there and in its own tests.
- Confidence: certain
