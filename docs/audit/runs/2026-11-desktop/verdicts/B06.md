# Batch B06 verdicts: media work folders, placing and stream joining

Proofs were built in a temporary worktree at HEAD, in a cargo profile of their own (`--profile b06 --config 'profile.b06.inherits="dev"'`): crates of different worktrees share build hashes in the shared target folder, so the `debug` folder there ran another validator's test binary. Use that profile, or a target folder of your own, to run these patches.

## Verdicts

### G31 A media work folder's contents carry no identity

- 17-1: confirmed, P1, proven by `proofs/17-1.patch`. `run` on a link never read, with `downloaded.json` left in `Clip.mp4.wcmedia`, returned `Completed` and overwrote the file at that name under Replace, with no yt-dlp or request. A stale `video.done` is reused by `fetch_part` the same way. The folder gets stranded with no crash needed: `proofs/17-2.patch`. `unclaimed_path` and `is_free_on_disk` do not look at work folders, and a completed row holds no claim.
- Xsecond-review-resume-2: confirmed, P1, same bug as 17-1 and proven by the same patch. Its stream half is real but much rarer: the fingerprint leaves out hosts on purpose (a test holds it), so two sites need the same paths, piece count and final name.
- Xpath-media-download-6: confirmed, P2. `refresh_link` touches the row only; `page_attempt` reads the list before the page. The loop on a bad part and the silent save under a pasted other link both follow from the code. Read, not run.
- 15-3: confirmed, P2. A kept `J` track with the same fingerprint skips every fetch, `track_formats` detects the same bytes and `mux` returns `UnknownFormat`, whose fix is `RefreshLink`. Read, not run.

### G32 `final_path` and the row's path disagree

- 17-2: confirmed, P2, proven by `proofs/17-2.patch`. Through the manager, a typed name and Replace fetched the segments again and left `clip.wcmedia` on disk.
- Xpath-media-download-5: confirmed, P2, same bug as 17-2; the planned-mp4, finished-mkv path goes through the same `replace_at` and `work_dir`.
- 17-3: confirmed, P2, proven by `proofs/17-3.patch`: `final_path` gave `/v/Dr.mp4` for `/v/Dr. Who`. Streams end the same way: `with_extension` keeps `Dr. Who.mp4` in the work folder, and `final_path` then cuts it.
- Xrepeated-logic-2: confirmed, P2, same bug as 17-3. `wirecatch_streams::model::with_extension` holds the right rule and is `pub(crate)`.
- Xpath-media-download-7: confirmed, P2. Original with no extras keeps `output: None, keep_ext: None`, so `joined_container` takes the typed extension; `Webm` passes `is_video`. Real ffmpeg with `-c copy -f webm` on H.264 and AAC here: "Only VP8 or VP9 or AV1 video and Vorbis or Opus audio...", non-zero exit. `merge::join` tries one container and `keep_original` needs `output: Some`. Retry repeats it.

### G33 A page's HLS part runs outside the run's file work

- 17-6: downgraded to P3, the missing `file_work` is certain, but the harm is bounded. `concat` checks `cancel` before each segment, so past `stop_timeout` only one copy and sync overrun. The end is a retryable failure or a folder left behind on a slow disk, never wrong bytes.
- Xpath-media-download-8: downgraded to P3, same bug as 17-6. "A track saved this way is then trusted" overstates it: both writers put the same bytes at the same offsets from their own handles, and write the same `A` and `J` values.
- Xsecond-review-disk-writes-9: confirmed, P3, same bug; it already states that the bytes stay correct.
- Xsecond-review-resume-6: downgraded to P3, same bug as 17-6. Its failed new run recovers on retry, and its stranded folder needs a stop past the timeout on a slow disk first.

### G34 A finished media file has no durable last step

- Xsecond-review-disk-writes-3: confirmed, P2. `sync_all` and `sync_data` appear in no file of the path after `ffmpeg::run`, `merge::join` or yt-dlp; `finish` and `join` delete the sources at once. The engine's `storage.rs` and `concat` do flush. Not run: it needs a power cut.
- Xsecond-review-resume-7: confirmed, P2, same bug. Not run, as above.
- Xpath-media-download-11: confirmed, P2. `join` removes `.wcstream` before `finish`; a failed `place` writes no `placing.done`, so the next run finds nothing to continue from and `run_stream` fetches everything again. A realistic trigger on Windows: the setting Replace with the old file open in a player, where the rename is refused.

### G35 A plain segment's body is never checked

- 15-1: confirmed, P1, proven by `proofs/15-1.patch`. Without ffmpeg: a page in the middle, all pages and all empty bodies each gave `Completed` (3071, 142 and 0 bytes). With real ffmpeg, a page in place of the middle of three 2-second segments gave `Completed`: fMP4 with `Duration: 00:00:02.00`, MPEG-TS with `00:00:06.00` and a hole. Not raised to P0: the bytes were never delivered and nothing already saved is damaged, but a cut video is reported as finished.

### G36 The stream log and its last step

- 15-2: confirmed, P2. `work.remove()?` follows the move. One detail is smaller than stated: the second result's `video (1).mkv` is inside the work folder, so the person never sees it beside the first. Not run: it needs a second process holding a file.
- Xsecond-review-disk-writes-6: confirmed, P2, same bug as 15-2.
- Xsecond-review-disk-writes-4: confirmed, P2, proven by `proofs/Xsecond-review-disk-writes-4.patch`: a torn `A 0 5 12` wins over `A 3 1000000`. The parse is proven; the short write itself was not produced, and the window is narrow, so it stays P2 despite the silent damage.
- Xsecond-review-resume-3: confirmed, P2, same bug and same proof.
- 15-4: confirmed, P3. `fill` retries `Interrupted` and `read_up_to` does not; `fill` is generic over `Read`. The only cost is the second copy, since a regular file does not return `Interrupted` in practice.
- 15-5: confirmed, P3. `git tag` is empty and `docs/ROADMAP.md` has the first release still to come; the header, the branch and a test exist only for layout 1. The citations are weaker than the facts: D72.11 is about claiming a page's video, and D81 only says samples are frozen "from the first release on".
- 15-6: confirmed, P3. Nothing under `crates/streams` names `axum`, and `cargo check -p wirecatch-streams --all-targets` passes with the line removed.

### G37 Media run docs and one test

- 17-8: confirmed, P3. The test writes the URL itself on the first line where `remember_placing` writes `link_digest(url)`, so `waiting_to_place` returns `None` at the digest compare and never reaches `inside`. By reading; the mutation was not run.
- 17-10: confirmed, P3. `disk`'s doc describes another function, `MAX_NAME_ATTEMPTS` carries `place`'s description while `place` has none, and the test's doc opens with a sentence about a deleted queue.

## Group notes

- G31 does not share one cause; split it. **G31a, no identity in the folder:** 17-1, Xsecond-review-resume-2 and the other-video half of Xpath-media-download-6. **G31b, a stored part known to be bad can never be thrown away:** 15-3 and the loop half of Xpath-media-download-6. A link digest fixes G31a but not G31b: a refreshed stream must keep its segments (a test requires it), and a page's address usually stays the same on refresh. G31b needs `UnknownFormat` to discard the bad part or track. 17-1 and Xsecond-review-resume-2 are one bug.
- G32 has three causes; split it. **G32a:** `replace_at` moves the row's path away from the work folder (17-2, Xpath-media-download-5). **G32b:** `final_path` uses `Path::with_extension` (17-3, Xrepeated-logic-2). **G32c:** a typed extension picks the container, and `merge::join` has no fallback (Xpath-media-download-7). G32a also feeds G31a, so fix it first.
- G33 shares one cause: all four are the same missing line. One rank for all, P3.
- G34 has two causes; split it. **G34a:** no flush (Xsecond-review-disk-writes-3, Xsecond-review-resume-7). **G34b:** a stream's resume state is gone before placing (Xpath-media-download-11). A flush does not help the second.
- G35 is one cause, with one more place: B06-1.
- G36 has two real pairs (15-2 with Xsecond-review-disk-writes-6, Xsecond-review-disk-writes-4 with Xsecond-review-resume-3) and three unrelated P3s, as GROUPS.md says. The pairs share no cause with each other.
- G37 has no shared cause, as GROUPS.md says.
- No conflicts were listed for this batch. The severities differing within same-bug pairs are settled above: G31a P1, G31b P2, G33 P3.

## New findings

### B06-1 [P2] A page's single-format part answered with a web page is saved as the finished video

- Where: `crates/core/src/manager/media_run/save.rs`, `join_original`; `crates/core/src/manager/media_run/page.rs`, `fetch_part`
- Category: bug
- Failure: a page's chosen format comes as one file, its address answers 200 with an HTML page, and the output needs no ffmpeg pass. The body is saved as `video.mp4`, marked done, and `join_original` returns it as it is. `finish` places it and the row shows Completed. A format of two parts is refused, as `merge::input_format` detects each.
- Evidence: the arm `[single] => Ok(Some(single.clone()))` calls no `InputFormat::detect`, while `[video, audio]` reaches it through `merge::join`, and a pass reaches it through `inputs_for`. `fetch_part` checks only the engine's outcome, and the engine does not look at the content type; `is_web_page` in `settle.rs` serves only `video_check` file rows. Same cause as 15-1. Read, not run.
- Confidence: certain for the code path; how often a format address answers this way varies by site.

### B06-2 [P3] Failing to delete a decrypted segment's part file fails the download

- Where: `crates/streams/src/download/fetch.rs`, `fetch_piece`
- Category: wrong implementation
- Failure: an encrypted segment is decrypted and flushed, then `fs::remove_file(&part)?` fails because a scanner holds the part file. The whole download stops with a disk error, and the segment is not logged. A retry continues, but the message tells the person to check space and permissions.
- Evidence: the plain branch renames, and every other cleanup in this flow goes through `discarded`, whose doc says a failed delete "stops nothing". Same cause as 15-2. Read, not run.
- Confidence: certain for the code path; likely for how often it fires on Windows.
