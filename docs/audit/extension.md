# Extension audit (apps/extension)

> This audit is a snapshot: its paths and line numbers name the code as it was when the audit was made (it was recorded in commit 0bd101a). Some files have since moved or been split, so a path that no longer exists, or a line that no longer matches, refers to the code of that time; `git log -- <path>` shows the commit that moved or removed it.

## EXT-1 Quitting the app does not stick: the extension relaunches it within a second and on every background wake
- severity: high
- category: design
- location: apps/extension/src/lib/native/client.ts:73, apps/extension/src/lib/native/client.ts:348-362, apps/extension/src/lib/native/client.ts:271, apps/extension/src/lib/hub.ts:193-197, apps/extension/src/entrypoints/background.ts:125-137, crates/bridge/src/main.rs:121-138, crates/bridge/src/app.rs:271-302, apps/desktop/src-tauri/src/lib.rs:166-173
- problem: When the person quits Wirecatch from the tray, the bridge exits (`relay::Ended::AppClosed`), Chromium reports "Native host has exited.", `classifyDisconnect` maps it to `disconnected`, and `#fail` schedules a reconnect after `DEFAULT_BACKOFF[0]` = 1 s (the attempt counter was reset to 0 on the last successful hello). The reconnect starts a fresh bridge, whose `connect_or_launch` finds nothing listening and launches `app --background`; if the quit is still in progress, the desktop's single-instance hook even queues a relaunch (`relaunch_later`). Independently, every service-worker wake (any webRequest response, tab update, download) runs `defineBackground` again, constructs a new `NativeClient` and calls `hub.start()` -> `client.start()` -> `connectNative`, which again launches the app. Net effect: while any Chromium or Firefox window with the extension is open, the app cannot be quit; it comes back hidden in the background. For a commercial product this reads as malware-like behaviour and will generate support load and store-review complaints.
- fix: Make reconnection lazy and intent-driven. (1) Add a protocol event or bridge exit signal for "app is shutting down at the user's request" (e.g. `Event::AppQuitting` sent by core before the relay ends, or a distinct bridge exit message that `classifyDisconnect` maps to a new `ProblemKind` `app_quit`). (2) In `NativeClient`, on `app_quit` stop the backoff timer and enter an `idle` state; only `request()` (a download to hand over, a media send, a popup command) or the popup's "Try again" opens a new port. (3) In `background.ts`/`Hub.start`, do not call `client.start()` eagerly on every wake; connect when the first request or popup needs it, and keep the cached settings for judging until then. Document the rule in DECISIONS (D5 currently says the bridge starts the app "when needed", which the eager loop violates).
- cross-package: yes (crates/bridge, crates/protocol, crates/core or apps/desktop)

## EXT-2 Media button content script does layout work on every pointer move in every frame of every page, even with the setting off
- severity: high
- category: performance
- location: apps/extension/src/entrypoints/media.content.ts:363-395, apps/extension/src/lib/media/button.ts:284, apps/extension/src/lib/media/button.ts:289, apps/extension/src/lib/media/button.ts:297, apps/extension/src/lib/media/button.ts:367-376, apps/extension/src/lib/media/button.ts:393-398, apps/extension/src/lib/media/button.ts:429, apps/extension/src/lib/media/button.ts:467-490, apps/extension/src/lib/media/button.ts:530
- problem: The content script is statically injected into every http(s) frame (`allFrames: true`). Its `MediaButton` constructor walks up to 20,000 elements with `querySelectorAll('*')` (`findMedia(doc)`) and installs capturing `pointermove`, `scroll`, `focusin` and `keydown` listeners before it even knows whether "Show download button on videos" is on (`setEnabled` arrives later from storage). Every pointer move then schedules a rAF that runs `#hitTest`; on a page with no tracked media `#trackedAt` finds nothing, so `#findAt` calls `elementsFromPoint` on the document and up to 20 shadow roots, every frame the mouse moves. With tracked media it calls `getBoundingClientRect` on each one per frame. `#update` only checks `#enabled` after all of that. Every `focusin` on a non-trivial element re-runs `findMedia(target)` over its subtree. All of these force style/layout flushes on pages that are animating, across every ad iframe, for every user, including the ones who turned the button off.
- fix: (1) Gate all work on the setting: return early from `#onPointer`, `#onFocus`, `#onKey`, `#schedule` and the scroll handler while `#enabled` is false, and defer the initial `findMedia` and listener installation until the first `setEnabled(true)`. (2) Better: register the content script dynamically with `scripting.registerContentScripts` only while the setting is on (unregister on off), instead of a static `matches` entry; this also removes the duplicated `['http://*/*','https://*/*']` literal at media.content.ts:364 (`SITE_ORIGINS` exists). (3) Replace pointer-driven hit testing with `pointerenter`/`pointerover` on tracked media elements plus a `MutationObserver` (or the existing `loadedmetadata`/`play` capture listeners) to discover media, so pages without media do no work at all.
- cross-package: no

## EXT-3 Cookie scoping uses a hand-rolled Public Suffix List approximation, so Strict and Lax cookies are sent cross-site on shared hosting suffixes
- severity: medium
- category: security
- location: apps/extension/src/lib/cookies.ts:311-377, apps/extension/src/lib/cookies.ts:397-405, apps/extension/src/lib/cookies.ts:413-424
- problem: `registrableDomain` approximates the PSL with 19 country second-level labels and 18 hard-coded private suffixes. `isCrossSite` and `cookiesToSend` rely on it to decide whether `SameSite=Strict`/`Lax` cookies go to the app, which then replays them on its own request. Any private PSL suffix missing from the list (for example `myshopify.com`, `r2.dev`, regional `s3.<region>.amazonaws.com`) makes two different sites look like one: a page on `attacker.myshopify.com` that links to `victim.myshopify.com/export` is judged same-site, so the app sends the victim's `SameSite=Strict` cookies that the browser itself withheld. The result is a cookie-bearing GET of the attacker's choosing, saved to the user's disk. The reverse error (unlisted public suffixes treated as registrable domains) silently drops cookies and breaks logged-in downloads. The list is also a growing magic-value table nobody owns.
- fix: Replace the approximation with the real PSL: bundle `tldts` (or a build-time generated compact PSL snapshot) in the background bundle only, and use its `getDomain` for `registrableDomain`. Add tests for a few private-section suffixes. If bundle size matters, generate the snapshot in `scripts/` from the official list and refresh it in CI.
- cross-package: no

## EXT-4 Background state that the person must see is held only in memory and lost when the service worker or event page stops
- severity: medium
- category: state
- location: apps/extension/src/lib/hub.ts:165-173, apps/extension/src/lib/hub.ts:276-283, apps/extension/src/lib/hub.ts:690-741, apps/extension/src/lib/hub.ts:757-767, apps/extension/src/entrypoints/background.ts:109-123
- problem: `#notice` (for example "X is paused in the browser. Open the browser's downloads page and click Resume.", "X stayed in the browser: Wirecatch could not be reached", "may be downloading twice"), `#uncertain` and `#lateConfirmed` live only on the `Hub` instance. While the app is connected the native port keeps the worker alive, but these notices are raised exactly when the app is unreachable, i.e. when no port is open and Chromium stops the worker after about 30 s idle (Firefox's event page likewise). On the next wake a new `Hub` starts with `#notice = null`, and `makeBadge` starts with `last = ''`, so `#publish` actively clears the "!" badge the browser had kept. A download left paused in the browser can therefore end with no visible message at all.
- fix: Persist the current notice (and the badge state derived from it) in `storage.session` next to `IN_FLIGHT_KEY`, load it in `Hub.start()` before `#markReady()`, and write it in `#setNotice`. Keep `#uncertain`/`#lateConfirmed` in memory (they are tied to the port's request ids, which die with the worker anyway) but document that.
- cross-package: no

## EXT-5 hub.ts is a 768-line god module, and Hub and MediaCenter are wired through closures over a not-yet-initialised const
- severity: medium
- category: design
- location: apps/extension/src/lib/hub.ts:158-768, apps/extension/src/entrypoints/background.ts:155-187, apps/extension/src/entrypoints/background.ts:125-241
- problem: `Hub` owns settings sync and the display cache, the popup port protocol and command dispatch, the browser-download handover, the context-menu flow, media sending, late-answer reconciliation, notices and the badge. Each is independently testable logic but they share private fields, so tests (`tests/handover.test.ts` 765 lines, `tests/popup.test.ts` 493 lines) have to stand up the whole hub. In `background.ts`, `MediaCenter` is constructed with `send: (r) => hub.sendMedia(r)` and `ignoredSites: () => hub.knownSettings()` before `const hub` exists, and `media.start()` runs before `hub` is constructed: any refactor that calls those during construction or restore throws a TDZ `ReferenceError` in the worker. The `defineBackground` body is 103 lines and also defines the browser adapters (`tabInfo`, `cookieHeaderFor`, `inFlightStore`, `mediaStore`, `makeBadge`), which are therefore untestable.
- fix: Split `Hub` along its seams: `SettingsSync` (live/cache/adopt/publishButtonSetting/knownSettings, emits changes), `PopupHub` (ports, `asPopupRequest`, `#runCommand`, snapshots), `CaptureFlow` (`onDownload`, `onMenuClick`, notice text), `MediaSender` (`sendMedia`), `Notices` (notice + badge, persisted per EXT-4). Give `MediaCenter` a `SettingsSync` and a `MediaSender` instead of the hub, which removes the cycle. Move the browser adapters to `src/lib/browser/` (one module per adapter) so `background.ts` only composes and registers listeners.
- cross-package: no

## EXT-6 Runtime validators for protocol types are hand-written, partial and drift-prone
- severity: medium
- category: type-safety
- location: apps/extension/src/lib/cache.ts:187-218, apps/extension/src/lib/native/client.ts:79-91, apps/extension/src/lib/hub.ts:612-623, apps/extension/src/lib/popup/model.svelte.ts:19-23
- problem: `isSettings`/`isQueue` in cache.ts re-encode `ExtensionSettings` and `QueueSummary` field by field. Adding a field in `crates/protocol` regenerates the TypeScript type but the validator keeps passing old cache entries that lack it, and they are then typed as complete `ExtensionSettings` (`CachedSettings.settings`), so the popup and `shouldCapture` read `undefined` from a field the type says is present. `asMessage` checks only the outer frame and then casts `raw as Message`; `reply.data` and `event.data` are trusted as-is (for example `queues_changed` assigns `event.data` straight to `#queues`, and the popup calls `.some` on it). `isBackgroundMessage` in the popup checks only `type` and casts.
- fix: Generate validators from the single source of truth: emit a JSON Schema from `crates/protocol` (schemars) during `pnpm protocol:generate` and compile it to type guards (or emit zod/valibot schemas), export them from `@wirecatch/protocol`, and use them in `asMessage` for replies and events and in `asCachedSettings`. At minimum make the hand validator exhaustive at compile time with `satisfies Record<keyof ExtensionSettings, (v: unknown) => boolean>`.
- cross-package: yes (crates/protocol, packages/protocol)

## EXT-7 55 swallowed errors and no diagnostics anywhere in the extension
- severity: medium
- category: error-handling
- location: apps/extension/src/entrypoints/background.ts:54-56, apps/extension/src/entrypoints/background.ts:116-120, apps/extension/src/entrypoints/background.ts:193-206, apps/extension/src/lib/capture/register.ts:99-117, apps/extension/src/lib/hub.ts:514-516, apps/extension/src/lib/hub.ts:607-609, apps/extension/src/lib/media/listen.ts:186-201, apps/extension/src/lib/media/center.ts:585-587
- problem: `src/` has 55 `catch {}` / `.catch(() => undefined|null|false|[])` sites and zero `console.*` calls. Many are correct fallbacks, but together they make field failures invisible: `hub.onMenuClick(...).catch(() => undefined)` drops any unexpected bug in the context-menu flow; `registerCapture` swallows every `onDownload` rejection; `#refresh` hides a malformed settings reply; `contextMenus.removeAll().then(() => create(...))` is `void`ed so a failed `create` is an unhandled rejection with no trace; `cookieHeaderFor` silently degrades to no cookies. A commercial support team will have no way to tell why a download stayed in the browser.
- fix: Add a tiny `diag` module in `src/lib/diag.ts`: `diag.warn(scope, error)` writes to `console.debug` and appends to a bounded ring buffer in `storage.session`; route every intentional swallow through it (keeping the fallback behaviour), and add a "Copy diagnostics" action in the popup that includes the ring buffer, `ConnectionStatus`, browser info and extension version. Keep the empty `catch` only where the comment proves the error is expected (e.g. `port.disconnect()` on an already-closed port).
- cross-package: no

## EXT-8 Timeouts and size limits are literals coupled to bridge constants with no shared source
- severity: medium
- category: magic-value
- location: apps/extension/src/lib/hub.ts:395, apps/extension/src/lib/hub.ts:479, apps/extension/src/lib/hub.ts:490, apps/extension/src/lib/hub.ts:508, apps/extension/src/lib/hub.ts:585, apps/extension/src/lib/hub.ts:599, apps/extension/src/lib/native/client.ts:15, apps/extension/src/lib/native/client.ts:73, apps/extension/src/lib/native/client.ts:252, apps/extension/src/lib/native/client.ts:354, crates/bridge/src/app.rs:15, crates/protocol/src/frame.rs:14
- problem: Timeout defaults are repeated inline as `?? 6_000` (2x), `?? 10_000` (3x in hub plus the hello timeout), `?? 3_000`, and a `?? 30_000` fallback duplicating the last backoff entry. `connectWaitMs = 6_000` only works because the bridge's `START_BUDGET` is 5 s: the extension must wait longer than the bridge's cold-start budget plus the hello round trip, but nothing ties them, so raising `START_BUDGET` (a slow disk, a first-run migration) makes every cold-start capture fall back to the browser. `MAX_MESSAGE_BYTES = 1024 * 1024` duplicates `wirecatch_protocol::frame::MAX_FRAME_LEN`, while `PROTOCOL_VERSION` and `UNKNOWN_REQUEST_ID` are already exported from `@wirecatch/protocol` the right way.
- fix: Export `MAX_FRAME_LEN` and a `BRIDGE_START_BUDGET_MS` from `crates/protocol` into the generated `packages/protocol/src/index.ts` (same mechanism as `PROTOCOL_VERSION`), derive `connectWaitMs` from it (`BRIDGE_START_BUDGET_MS + HELLO_MARGIN_MS`), and move the extension's remaining defaults into one `src/lib/timing.ts` (`REQUEST_TIMEOUT_MS`, `WITHDRAW_TIMEOUT_MS`, `HELLO_TIMEOUT_MS`, `RECONNECT_BACKOFF_MS`) resolved once in the `Hub`/`NativeClient` constructors instead of at each call site.
- cross-package: yes (crates/protocol, crates/bridge, packages/protocol)

## EXT-9 Settings semantics re-implemented in three places: ignored-site normalisation and patch application
- severity: medium
- category: duplication
- location: apps/extension/src/lib/sites.ts:13-27, apps/extension/src/lib/protocol.ts:10-44, apps/extension/src/lib/hub.ts:571-579, apps/desktop/src/lib/components/Settings.svelte:321-325, crates/core/src/settings.rs:389-391, crates/protocol/src/extension.rs:180
- problem: An ignored site is normalised three different ways: core stores `trim().trim_end_matches('/').to_lowercase()`, the desktop editor strips the scheme and path, and the extension's `normalizeSite` also strips `*.`, ports and trailing dots. So the stored list differs depending on where the entry was typed, and matching only works because the extension re-normalises every entry on every download (`matchingSite`). `applyPatch` re-implements `ExtensionSettings::apply` in TypeScript; it is used for the popup's optimistic overlay and in `Hub.#updateSettings`, whose `else` branch is dead because `crates/core/src/server.rs:173-175` always replies `Reply::ExtensionSettings`. Any change to the Rust semantics (core lowercases additions) silently diverges from the overlay.
- fix: Make core the single normaliser: implement the extension's `normalizeSite` rules in `normalize_site` (with tests), store only normalised hosts, and have the desktop and extension editors send raw input and display what the app returns. Delete the dead `else` branch in `#updateSettings`, and either drop the optimistic overlay (the round trip is local and fast) or keep `applyPatch` but test it against fixtures generated from the Rust `apply` tests.
- cross-package: yes (crates/core, crates/protocol, apps/desktop)

## EXT-10 Every background wake runs the full startup, and the webRequest filter wakes it on every frame load
- severity: medium
- category: performance
- location: apps/extension/src/lib/media/listen.ts:154-157, apps/extension/src/lib/media/listen.ts:195-204, apps/extension/src/entrypoints/background.ts:162-168, apps/extension/src/lib/media/center.ts:429-439, apps/extension/src/lib/hub.ts:193-208
- problem: `FILE_REQUESTS` observes `main_frame` and `sub_frame` responses with `responseHeaders` on every site, and Chromium's `tabs.onUpdated` cannot be filtered, so the worker is woken for practically every navigation, iframe (ads included) and tab title change. Each wake re-runs the whole `defineBackground` body: `browser.tabs.query({})` over all tabs, a `storage.session` read of up to 1 MiB of media lists, a `storage.local` read of the cache, and a native connect (see EXT-1). Navigation clearing is already handled by `tabs.onUpdated` (`changeInfo.url` fires for full loads too), so `sub_frame` responses are only needed for media served as a frame document, which is rare.
- fix: Drop `sub_frame` from `FILE_REQUESTS` (keep `media`, `object`, `main_frame`) or limit frame observation to URLs with media extensions via a second filter as done for manifests; make `liveTabs()` lazy (only when a saved list exists, and query only those tab ids with `tabs.get`); defer the native connect per EXT-1. Measure wakes per minute of normal browsing before and after.
- cross-package: no

## EXT-16 Folder layout and naming obscure which code runs in which context
