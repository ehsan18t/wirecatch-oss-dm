# Wirecatch: Decisions and Glossary

Running record of what has been settled. Each decision lists what it means in practice.

## Glossary

- **App**: the desktop program (engine plus UI) installed on the PC. Single source of truth for all settings and download state.
- **Engine**: the background Rust process that does the downloading. Keeps running when the window is closed.
- **Extension**: the browser add-on for Chromium-based and Firefox-based browsers. A remote control and capture layer for the App; it stores no settings of its own.
- **Bridge**: the small native messaging host the browser starts. Relays messages between the Extension and the Engine, and starts the Engine if it is not running.
- **Add-on**: an optional, separately installed component of the App (for example the yt-dlp media extractor, ffmpeg).
- **Extractor**: an Add-on that turns a page URL plus cookies into a list of downloadable formats (direct URLs plus required headers). The Engine downloads the bytes.
- **Queue**: a named group of downloads with its own schedule and concurrency limit. Shown in the sidebar; a default queue always exists.
- **Handoff**: the moment the Extension passes a captured browser download to the App.
- **Settings profile**: the exported file containing all portable settings.

## Decisions

### D1. Platforms and stack
Windows and Linux required; macOS later. Engine in Rust (tokio, hyper/reqwest, rustls), state in SQLite, UI in Tauri 2, Extension built with WXT (TypeScript) for Chromium MV3 and Firefox MV3.

### D2. Media extraction is an optional Add-on
The core App ships without yt-dlp, Deno or ffmpeg. The core handles normal files, direct media files and HLS/DASH streams the Extension detects. yt-dlp is installed in one click as an Extractor Add-on, verified by checksum and updated quietly. ffmpeg is fetched the first time a download needs muxing. When a site needs an Extractor that is not installed, the Extension says so and offers the install button.

### D3. UX principles
1. What feels natural to the person decides the flow, not a click count (D36, which retired the earlier rule that every feature is visible or at most two clicks away). Nothing lives only in a context menu.
2. Queues are first-class in the sidebar with schedule and concurrency shown inline.
3. Smart defaults with no setup required; tuning knobs sit under Advanced.
4. Errors state the fix and offer it as a button.
5. Command palette (Ctrl+Shift+P since D47, Ctrl+K before) and searchable, plain-language settings.
6. Performance targets: window opens in under 200 ms, list stays smooth at 10,000 items, UI never blocks on the Engine.
7. Teach in context (empty states, one-time hints), no tours.

### D4. Handoff behavior
Superseded in part by D23: a captured download now opens its own window first by default. With that window turned off ("Start downloads without asking"), a file starts immediately and shows a non-blocking toast with destination, Change and Open folder, as decided here. The setting is reachable from the download window, the toast, the Extension popup and the App settings.

### D5. Settings live in the App; the Extension edits them remotely
- The App is the only store. The Extension reads and writes settings through the Bridge; nothing is kept in browser storage except a cache for display.
- A change made in the Extension appears in the App immediately, and the reverse. Because every browser talks to the same App, a change made in Chrome also shows up in Firefox.
- The Bridge starts the Engine when needed, so the Extension does not have an "App not running" state in normal use.
- Settings the Extension edits (the relevant subset), split between its two pages since the interface revamp (D36): the popup has what people reach for first, capture on/off, this site (ignore it or stop ignoring it), the page's media, show a window before each download (D23, which D4 keeps reachable from the popup) and pause/resume all; the Extension's options page has the rest, show the media download button on videos, sites to ignore, file types to capture, minimum file size to capture and default queue, one click from the popup.
- Everything else (queues, schedules, connection tuning, folders, Add-ons) is App-only.

### D6. Settings import and export
- Export produces one versioned JSON file (Settings profile). Import applies it, migrating older versions forward.
- Included: all settings, queues and schedules, categories and folder rules, site rules, Extension settings, list of installed Add-ons (reinstalled on import).
- Paths are stored portably, for example `{Downloads}/Video`, so a profile exported on Windows imports cleanly on Linux.
- Excluded by default: download history and saved site credentials. Credentials live in the OS keychain and are only exported if the user ticks an option, in which case the file is encrypted with a passphrase.

### D7. Open source
The whole project (Engine, App, Bridge, Extension) is open source and developed in public. Build and release pipelines must be reproducible from the public repository. Add-ons we distribute (yt-dlp, ffmpeg) are fetched from their official sources rather than rebuilt and rehosted.

### D8. License: GPL-3.0 for everything
Engine, App, Bridge and Extension are all GPL-3.0. Forks that ship must publish source. The project name will be protected separately (trademark) so official builds can be told apart from repackaged ones. yt-dlp and ffmpeg run as separate processes, so no license conflict.

### D9. Name: Wirecatch
Checked 2026-10-10. Free on crates.io, npm and as a GitHub name; wirecatch.com, .app and .dev unregistered. WIPO Global Brand Database (about 77 million records, 89 sources, includes US, EU, UK): the only exact match is a Toshiba mark in Japan, class 11, expired 1995. Similar live marks:
- WIREKASH, UK00004271032, class 9 (collaboration software, software applications, e-commerce software), registered 2025-12-19. Closest in sound and spelling; a possible objection if we file in the UK.
- VERICATCH, registered in US, EU, UK and Canada, classes 9, 35, 42, but for seafood traceability software. Unrelated goods.
- WIREWATCH, Spain, class 9 (electrical equipment), plus a pending Brazil class 42 application. Different word.

Not covered: Bangladesh (DPDT is not in the WIPO database). Needs a separate search before filing there. This was a screening search, not a legal clearance opinion.

### D10. Protocol scope for v1
In scope: HTTP and HTTPS (HTTP/1.1, HTTP/2, HTTP/3), FTP and FTPS, HLS and DASH streams. Out of scope: BitTorrent and magnet links. Build order inside v1 follows the roadmap: HTTP(S) first, since it carries almost all browser downloads.

### D11. Build order
Phase 1 is the Engine plus a CLI, with no UI or Extension yet. See [ROADMAP.md](ROADMAP.md) for the phases and the Phase 1 acceptance checklist.

### D12. Monorepo layout

### D13. One app process hosts everything
The desktop app process hosts `wirecatch-core` and the Engine. Closing the window hides it and leaves the process in the tray, so it opens again at once from the tray (about 40 ms, measured). Destroying it instead freed its memory but made every reopen take 1.5 to 2 seconds behind a blank white window, which the maintainer rejected. While hidden on Windows, the WebView2 is suspended like a sleeping Edge tab and asked to keep its memory low, and core events are not sent to it (it reloads its list when it wakes); measured, its processes hold about 25 MB in RAM once settled, against about 330 MB open. WebKitGTK has no such switch, so on Linux the window is only hidden. A new main window opens hidden and shows itself once its first view is drawn, so it never flashes blank. `--background` starts the process with no window. There is no separate daemon, so there is one source of truth and nothing to keep in sync. A webview crash cannot take downloads down, because WebView2 and WebKitGTK render in separate processes. The CLI stays standalone and uses the Engine directly.

### D14. Local connections
The Bridge talks to the app over a local socket: a named pipe on Windows, a Unix socket in `$XDG_RUNTIME_DIR` on Linux. Only the current user can connect (explicit pipe security descriptor on Windows, mode 0600 on Linux). Frames are a 4-byte little-endian length plus UTF-8 JSON, capped at 1 MiB, the same as browser native messaging, so the Bridge uses one codec on both sides. The first call on a connection must be `hello`, which settles the protocol version the connection speaks; a client that shares no version with the app is refused with a clear error (D32). The Bridge only accepts callers listed in its allowed extension origins.

### D15. Shared types
`wirecatch-protocol` is the single source of truth for every type that crosses a process boundary. TypeScript types are generated from it with `ts-rs` into `packages/protocol` (`pnpm protocol:generate`). Generated files are committed, and CI fails if they are stale.

### D16. Frontend stack
Svelte 5 (runes) and strict TypeScript everywhere. Desktop: plain Svelte 5 with Vite inside Tauri 2 (D36, which replaced SvelteKit). Extension: WXT with its Svelte module. Both style with Tailwind 4 and share `packages/ui` (D36). pnpm workspaces, Vitest, svelte-check, ESLint and Prettier.

### D17. Persistence
SQLite (`rusqlite`, bundled) in the per-user app data folder, with versioned migrations. Cookies and headers needed to resume a download are stored with it; the database file is readable only by the current user. When the data folder cannot be made private (a drive that keeps no permissions, a folder another account owns), the app still starts and tells the person at every start, naming the folder and the reason (CORE-22).

### D18. Quality bar (definition of done)
A change is done only when all of these hold:
1. `pnpm gate` passes: every check, from `scripts/gate.mjs`, the same checks CI runs.
2. The change follows [ENGINEERING.md](ENGINEERING.md), including the rules only a reviewer can check.
3. New behavior has tests that would fail without it; bug fixes add a regression test.
4. Every public Rust item has a doc comment. No `unwrap()` on input that comes from outside the process.
5. User-facing text follows the house style (no em dashes, plain language, errors say how to fix them).
6. An independent reviewer, not the author, has checked the work against its acceptance checklist.

### D19. Packaging, browser registration and updates
Decided by the lead while the user was away; easy to revisit before the first release.
- Windows: per-user NSIS installer from the Tauri bundler (no administrator rights needed). Replaced by D25: per-machine, in Program Files.
- Linux: `.deb`, `.rpm` and AppImage from the Tauri bundler. Flatpak waits, because sandboxed browsers and native messaging do not mix well yet.
- Browser registration: the app runs the Bridge's per-user `install` on every start (it is idempotent), so installers, AppImages and portable copies all register themselves and repair a broken registration. Uninstall runs `uninstall`.
- Updates: `tauri-plugin-updater` with signed update manifests on GitHub Releases, switched on once the GitHub organization and signing key exist. Until then the updater is compiled in but disabled.

### D20. One-click media add-on (yt-dlp, ffmpeg and a JavaScript runtime)
Decided by the user on 2026-10-11. ffmpeg is not bundled with the app (the static LGPL build alone is 134 MB). It ships inside one optional "Media add-on" together with yt-dlp and the JavaScript runtime yt-dlp needs for some sites (Deno). One click installs all of it; the app offers it at the moment it is first needed (a stream whose video and audio must be joined, or a page such as YouTube that needs extraction), and it also lives in Settings, Add-ons. Every component is pinned to an exact release and verified by SHA-256 before use (A8 lists the sources). Plain files and single-track streams never need it. A later improvement replaces the general ffmpeg build with a small remux-only LGPL build made in CI, which cuts the add-on download from about 60 MB to a few MB.

### D21. Security decisions from the final review
Decided by the lead on 2026-10-11 after the cross-component security review.
1. Media add-on updates verify yt-dlp's OpenPGP signature on `SHA2-256SUMS` against a fingerprint pinned in the app (pure-Rust `pgp` crate, verification only, in `wirecatch-core`). The 48-hour maturity delay applies to every install path (quiet update, Update button, repair, reinstall), not just quiet updates.
2. Program types (exe, msi, scripts, installers and similar) stay in the browser by default, so the browser's Safe Browsing and download warnings apply. Downloads the browser flags as dangerous are never taken over.
3. ffmpeg only ever reads local files of the formats we expect: explicit input format, `-protocol_whitelist file` and a format whitelist on every input. Pinned add-on sources must be long-lived; a remux-only ffmpeg built by our own CI and published with our releases replaces the general build once the GitHub organization exists.
4. CI keeps actions pinned by SHA and gets Dependabot for actions, Cargo and npm, plus `cargo audit`. The Dependabot part is superseded by D28.
5. The app's data folder moves to the local (non-roaming) app data folder, so cookies and add-on programs never follow roaming profiles.
6. Superseded by D22: every bridge build trusts the one Chromium id that follows from our extension key, and the `dev-extension` feature is gone.

Actions only the user can take: reserve the Firefox add-on id `extension@wirecatch.app` on addons.mozilla.org (an unlisted upload is enough) and register the `wirecatch.app` domain, so nobody else can claim them (see D9).

### D22. One Chromium extension id for every build
Decided by the user on 2026-10-11, after the release build refused the extension with "Access to the specified native messaging host is forbidden" because release bridges listed no Chromium id. The lead agreed after weighing the risk.
1. `chdgnmpjoipbgfeldicipccjjghmagki`, the id that follows from the public key in `config/product.toml` (`chromium_id`, `chromium_public_key`; `config/extension-ids.json` until D29), is the one Chromium id for development and store builds. Every bridge build trusts exactly that id and the Firefox add-on id; no cargo feature changes this. `install` writes `allowed_origins: ["chrome-extension://chdgnmpjoipbgfeldicipccjjghmagki/"]` for every Chromium browser, and the bridge still checks the caller's origin by exact match.
2. Every Chromium build of the extension carries the public key in its manifest, so an unpacked load gets this id. The package for the Chrome Web Store (`pnpm build:store`) leaves the key out, because the store does not accept it.
3. The private key is kept by the maintainer in a private place outside the repository, never in the repository or CI. It is used once: on the first Chrome Web Store upload, as `key.pem` at the root of the zip, so the store gives the item this same id. Later uploads never include it (`apps/extension/PUBLISHING.md`).
4. Residual risk, accepted: no store can give this id to anyone else, and a packed extension with it needs the private key. Another extension can claim the id only by being loaded unpacked in Developer mode, in a browser profile that does not already have ours. Such an extension could do comparable harm with its own permissions anyway, so trusting the id in release bridges adds little risk and makes development and store builds work with any installed Wirecatch.
5. Other Chromium stores (for example Microsoft Edge Add-ons) give their own ids, which the bridge does not trust; Edge users install from the Chrome Web Store.

### D23. A window for each download
Decided by the maintainer on 2026-10-11, after a question about a browser download (confirm a file, pick a video quality) was drawn inside the main window, which was never brought forward, so it sat behind the browser and nothing seemed to happen. It works like IDM now, and replaces D4's "start immediately with a toast" default.
1. A download caught from the browser opens its own small window, in front of the browser and focused, whether the main window is open, hidden in the tray or closed. The main window is not brought forward. Windows open always on top and drop it the first time they lose the focus after having had it, so they then behave like normal windows (some Wayland compositors ignore always on top; that is accepted).
2. A file's window shows its name (editable), size or "Size not known yet", Save to with Change, Queue, the site it came from, and Download now (main button), Download later and Cancel. A video's window shows that the video is being read, then its qualities, name, folder and queue in the same window; when the media add-on is missing, its install offer shows there and the download continues after the install.
3. "Start downloads without asking" in the file window turns the window off for files; it is `ask_before_download`, inverted. Its default is now on, and a database migration switches a stored setting on once, because the default changed before the first release while stored settings still held the old default nobody chose. Videos ask for a quality unless the person chose otherwise in Settings, Media (D50).
4. After Download now the same window becomes the download's progress window: name, status and why it waits, progress, done and total, speed, time left, connections in use, any error with its fix, media stages, Pause or Resume, Cancel (asks first, then removes the download and its partial file) and Hide (closes the window; the download continues). Once finished it offers Open and Show in folder and closes by itself after about five seconds unless the pointer is over it or it has the keyboard focus. "Close this window when downloads start" sets `show_progress_windows` (default on: the window stays), also in Settings, the settings profile and the command palette.
5. One window per download, each about 28 px down and right of the previous open one. At most five windows ask a question at once; later questions open as earlier windows close or start showing progress. A progress window is the same window continuing, so it keeps its place.
6. The main window never asks these questions itself. Its sidebar shows "Waiting for you" with how many downloads wait for an answer, and clicking it (or the command palette action) reopens their windows. Closing a question window with its X or Escape does not discard the download, since the browser has already let go of it: it stays waiting and counted. Only Cancel discards it. A question answered anywhere never comes back when a window opens or reloads, and one put aside does not open again by itself.
7. Download later adds the download to its queue paused; Resume (or Resume all) starts it.
8. Downloads added inside the app (Add download, paste, drop) open no window. Every row offers "Show progress window".
9. When the download being asked about is already in the list (the same address; for a video the same page, or the same video read from another link to it), the window says so in one line, for example "You downloaded this today at 18:38.", without blocking anything. Two captures of one video are asked about once.

### D24. Output formats for media
Decided by the maintainer on 2026-10-11, so a video can be saved in the format a person's player or editor needs, with its subtitles and chapters, without a separate converter. Applies to pages read with yt-dlp; direct media files and HLS or DASH streams stay as they come.
1. Under the quality list the window offers "Save as": Original (the site's own format, the default, so nobody's downloads change until they choose), MP4, MKV or WebM for a video, and MP3, M4A, Opus, FLAC or WAV when Audio only is picked. MP3, M4A and Opus also offer an audio quality (MP3 128 to 320 kbps, M4A 128 to 256, Opus 96 to 192); M4A and Opus can keep the downloaded audio as it is. Notes say when a bit rate is higher than the download's (it adds no quality) and when FLAC or WAV is made from lossy audio.
2. Every combination is offered. For each quality and format the core takes the streams of that height (and frame rate) that fit the container as they are: MP4 takes H.264 and H.265 with AAC, MP3, AC-3 or E-AC-3 (VP9 and AV1 in MP4 are valid but many players refuse them, and MP4 is chosen for those players); WebM takes VP8, VP9 and AV1 with Opus or Vorbis; MKV takes anything, so it always copies. Only a quality with no fitting stream is re-encoded, and each row says "No conversion" or "Converts" for the chosen format, with a note before the start. Audio re-encoding (AAC for MP4, Opus for WebM) is quick and always allowed.
3. Video is re-encoded to H.264 (MP4, MKV) or VP9 (WebM), at about the source's bit rate, raised when the source codec is more efficient (VP9 and H.265 by 1.4, AV1 by 1.8), or a usual rate for the height when the site gives none. Hardware encoders are tried first, in this order: NVIDIA NVENC, Intel Quick Sync, AMD AMF, then Media Foundation on Windows or VA-API on Linux. Each is tested once per ffmpeg by encoding a short generated clip, and the first that works is remembered while the app runs; one that fails on a real video is skipped from then on and the conversion goes on with the next. The media add-on's ffmpeg (BtbN's LGPL build on Windows and on Linux) has no libx264, so the software encoder is OpenH264 for H.264 and libvpx for VP9; an ffmpeg that has libx264 uses it instead of OpenH264.
4. Subtitles: the window lists the languages the video has, human-written ones first and auto-generated ones after, marked and never ticked unless asked for (machine translations into other languages are left out). MKV gets SubRip tracks, MP4 mov_text and WebM WebVTT, each named and labelled with its language; audio formats, and videos when the person asks, get `.srt` files next to the file. Subtitle files and the cover picture are downloaded by the engine under the same local network rule as the video, and checked to be the format they claim before ffmpeg reads them.
5. Chapters go into MP4, MKV, WebM and M4A through an ffmpeg metadata file; audio formats get title, artist and the video's picture where the format holds them (MP3, M4A, FLAC; tags only for Opus).
6. Every ffmpeg input, including subtitles, the metadata file and the picture, is a local file read only as its named format (`-protocol_whitelist file`, a format whitelist, one absolute `file:` path); text from the site goes into the metadata file, escaped, never into ffmpeg's options.
7. Conversion runs after the download, in the `.wcmedia` work folder, as its own "Converting" step with progress read from ffmpeg's `-progress` against the video's length; the file appears only when complete. Pause and Cancel kill ffmpeg, and a paused or failed conversion starts again from the downloaded parts without reading the page or downloading anything. When converting fails, the download is kept and the error offers Try again (converts again) and Keep the original, which saves the downloaded streams as they came.
8. The window starts from the last choices, kept separately for videos and for audio only (format, audio quality, subtitle languages and whether auto-generated ones are wanted, subtitle files, chapters), and since D50 on the saved resolution, which the core picks. They are in Settings, Media, and in the settings profile; older settings and profiles read as Original, so the profile format version is unchanged.

### D25. Installed for every user, never run as administrator
Decided by the maintainer on 2026-10-12, replacing D19's per-user Windows installer.
1. Windows installs per machine, in Program Files, like other desktop download managers. Installing takes one administrator prompt, and so does each update, since it replaces files there; starting, signing in and booting never do. Silent updates through an update service may come later.
2. The installer registers the browser bridge for every user of the computer: `wirecatch-bridge install --all-users` writes the manifests next to the bridge in Program Files (only administrators can change them) and the keys under `HKEY_LOCAL_MACHINE`. The uninstaller removes them. The app's own per-user registration on each start (D19) steps aside when that machine registration already covers its bridge, because an uninstall can only clean up the account that runs it; portable copies and Linux keep registering per user.
3. What belongs to a person stays per user: the download list, settings and cookies in each user's `%LOCALAPPDATA%`, and start at sign-in. One user's cookies are never readable by another.
4. Wirecatch never runs as administrator. A release build started that way says it does not need administrator rights and exits, because an elevated app could be driven by any program of the same user, and the unelevated browser extension could not reach it anyway. Only a start the person elevated ("Run as administrator") is refused: on an account that always has administrator rights, with user account control turned off or as the built-in Administrator, every program runs elevated, the browser included, so the app starts there. Whatever starts it, its endpoint is labelled at its own integrity level, so unelevated programs cannot open an elevated app's pipe. The installer starts the app after installing as the signed-in user, not elevated.
5. Linux is unchanged: `.deb` and `.rpm` already install system-wide, and the AppImage is per user by nature.
6. A Wirecatch the person closed stays closed until something needs it, as with other download managers. The browser extension starts it only for something the person did: a browser download it will take, the media button, or Open Wirecatch in its popup. Its checks on waking and its reconnects send `hello` with `start_app` off, so the bridge only reaches an app that is already running and otherwise answers `app_not_running`, and the extension then waits instead of retrying. This makes D5's "the bridge starts the app when needed" exact.

### D26. The published engine ships its library, and is tested in the workspace
Decided by the lead on 2026-10-12, during W14.
1. The engine's tests and examples share test servers with the other crates through `crates/test-support`, which is not published: one copy of each server instead of one per crate. So the engine's tests cannot be built from the published package.
2. The package therefore holds the library only (`include` in `crates/engine/Cargo.toml`): no `tests/`, no `examples/`. Its tests run in this repository, where CI runs them on Windows and Linux. A packager who wants to run them builds from the repository at the release tag. The in-source test modules (`src/ftp/tests.rs`, `src/http3/tests.rs`) stay in the package, since the library declares them, and also need the repository to build. The gate checks that the package holds no tests or examples, so a change that ships uncompilable files fails.
3. `wirecatch_engine::numeric` is public: `approx_f64` and `f64_to_u64`, the checked conversions every crate uses for byte counts, rates and floats read from outside the process (W14 decision 4), so they are written and reasoned about once. `saturating_cast` joins them for conversions between whole-number types where clamping to the nearest bound is the honest answer (a list's length in a protocol's `u32`, a byte count in SQLite's signed integers); both of its types are sealed to the built-in whole-number types, so the published API promises nothing about other types.
4. `wirecatch_engine::units` is public: `KIB`, `MIB` and `GIB` as byte counts (`u64`), and `KIB_USIZE` and `MIB_USIZE` as lengths in memory. The engine is the lowest crate that the crates measuring bytes already depend on (core, streams, the desktop app), so the units are defined once there rather than once per crate. Only the crates that do not depend on the engine spell sizes out: the protocol (which must not depend on it), the bridge, test-support (which the engine's own tests use) and the end-to-end tests.
5. `wirecatch_engine::url` is public with one function, `without_credentials`, which takes the user name and password out of a URL before it is passed on, logged or stored. The engine's fetcher and HTTP requests use it, and the core needs the same rule for the Mark of the Web; one function keeps the rule identical on both sides. Its neighbour `without_password`, which keeps the user name and serves the engine's error messages about links and its saved resume state, stays inside the engine.

### D27. No browser download is lost or duplicated in a handover
Decided during the extension's W14 review: a download the extension takes from the browser ends in exactly one place, the app or the browser. When that cannot be known, the browser keeps its copy, because two copies beat none, and the person is told what to check.
1. `capture/handover.ts`: each download is paused first, under a handover id the hub chose and saved beforehand. When the app has it, the browser copy is cancelled only if it still reads as paused or cannot be read, and erased only once it reads as interrupted after the cancel. A copy the person resumed or that finished before the cancel is left alone, and one whose state cannot be read after the cancel may have finished first; both get the two-copies warning. A copy read as paused that the browser would not cancel stays paused in its list, and the person is told they can remove it; one whose state could not be read and that would not cancel may be running, so it gets the two-copies warning.
2. On a timeout, a lost connection or an answer the extension cannot read, `withdraw_download` decides: `already_started` means the app has it; `withdrawn` or `not_found` means it does not; a withdraw that fails, or whose answer cannot be read, means the app may have it. Whenever the app does not have it or may have it, the browser copy is resumed. If resuming fails, a copy found running counts as resumed, one found paused is `stuck_paused`, one whose state cannot be read is `maybe_paused`, and one that finished, was interrupted or is no longer listed is gone.
3. `hub/notice-board.ts`: what the person is told about a kept download depends on its browser copy. A gone copy gets no notice. A `stuck_paused` or `maybe_paused` copy gets an urgent notice that it is paused, or may be paused, with how to resume it; when the app may have the download, the notice also says so and asks the person to check Wirecatch's list before resuming. A running copy the app may have gets an urgent warning that it may be downloading twice. A running copy the app does not have gets the reason it stayed in the browser, for the reasons worth telling; for an answer the extension could not read, that it could not be read and that updating the extension may help.
4. `hub/duplicates.ts` and `hub/notice-board.ts`: a copy the app may have is matched with the app's late answer to the same handover, whichever comes first, and what the person is told is decided from the copy's state when the answer arrives, since the person may have resumed or paused it since. A copy the browser lists as paused gets, for a sure confirmation, a notice that the app took it and the paused copy is left over in the browser's list; for an answer that cannot be read, it keeps the notice to resume it, which already asks the person to check Wirecatch's list, or gets the possible two-copies warning when it has no such notice (the person resumed it and paused it again). A copy that is interrupted or no longer listed gets nothing new. Any other copy, running, finished or one the browser will not describe, gets the two-copies warning: that the app took it after all for a sure confirmation, that the app may have it for an answer that cannot be read. A state read while the browser reported the download moving is read again, so what is said matches the copy as it is.
5. Notices form a short list in `storage.session`, newest first, at most one per browser download, each dismissable. A notice is urgent when it asks the person to act (resume a download, or check for two copies); when the list is full, the oldest non-urgent notices go first. A notice asking to resume a download clears when the browser reports the download running, finished, interrupted or erased (`downloads.onChanged` and `downloads.onErased`, in `capture/register.ts`), and on load when the browser says it is no longer paused. Every browser answer is in before stored notices are filtered, so one dismissed, replaced or resolved during the load does not come back.
6. `hub/hub.ts` and `hub/recovery.ts`: each handover is saved in `storage.session` with its id before pausing and stays saved until settled. After a restart, every handover whose browser copy is not interrupted or gone is settled by `withdraw_download` as after a timeout, even when the browser's state cannot be read, and the wait allows a full hello so the app can start. The same notices follow, with two differences: a copy resumed because the app does not have it (`browser_only`) gets no notice, where the live path says why the download stayed in the browser, for the reasons worth telling; and nothing is matched with late answers, since one could only come on the previous run's connections.
7. `native/client.ts`: `start()` connects only when there is no port and no retry pending, so a port with requests on it is never replaced. An answer that cannot be read fails its request at once as `unreadable`; a late one counts only as a possible confirmation, and an error answer that cannot be read drops the port and is never taken as one.
8. Tests: `tests/handover.test.ts` and `tests/native-client.test.ts` cover each case against the real hub, handover and client; `tests/hub-parts.test.ts`, `tests/register.test.ts` and `tests/popup.test.ts` cover the notice list.
9. Known limit: the app keeps handover ids in memory only. If it restarted after taking a download, `withdraw_download` answers `not_found`, so the browser resumes its copy while the app may restore its own: two copies with no warning. Saving handover ids in the app would close this.

### D30. The engine's durability, proxy reading, public errors and identity (W7)
Decided during W7 (engine audit), 2026-10-12.
1. Resume survives a power cut, not only a killed process. Each checkpoint reads the ranges that are done, flushes the part file to the disk (`sync_data`), then writes the resume file through a flushed temporary file and a rename; the finished file is flushed before its final rename. The resume file therefore never counts bytes the disk has not received (ENG-7). The cost is one flush per checkpoint interval and one at the end: on the local benchmark the uncapped 256 MiB runs, which end before the first checkpoint, went from about 0.2 s to about 0.6 s, which is the time the disk needs to receive the file; capped runs, which are what real downloads look like, did not change. A flush at the end is the price of a completed file that is really complete; narrowing the promise to "after the process is killed" was rejected.
2. Proxy settings are read in one place (`proxy.rs`) the way the HTTP client reads them, and `NO_PROXY` is matched by the client's own matcher (`hyper_util::client::proxy::matcher`, already built through reqwest), never by a second parser. A host that `NO_PROXY` exempts may use HTTP/3 and may be downloaded over FTP while a proxy is set, because the HTTP client reaches it directly too (ENG-15).
3. `Error::Io` names the action (`IoAction`) and the path, `Error` no longer converts from `io::Error`, `Error::State` is gone (an unreadable resume file is set aside and logged, never reported), `Error::Stalled` holds a `Duration`, and `Error::TargetRejected` holds a `PathRejected` (ENG-10, ENG-16). The `fetch` module is private and `naming::from_content_disposition` is crate-private; `header` is re-exported from the `http` crate (ENG-17). These are breaking changes for the next minor release of the pre-1.0 crate; the crate has no changelog, so the commits' `BREAKING CHANGE:` footers are the record.
4. A `PathResolver` refuses a file with `PathRejected`, a small public `#[non_exhaustive]` error carrying the caller's message (`PathRejected::new`, `message()`), which `Error::TargetRejected` holds. The message stays the caller's own words for a person, which the engine only carries; a typed error keeps `Result<_, String>` out of the public API without the `Box<dyn Error>` that ENGINEERING section 4 also rules out, or a type parameter on `DownloadRequest` for one callback.
5. The published engine names itself, never the app: its default `User-Agent` is `wirecatch-engine/<crate version>` and its messages do not say "Wirecatch" (XC-14). The engine depends on no product crate. The app sets its own agent, `<product name>/<app version>` from `wirecatch-product` (D29), in core's `headers::download_options`, which downloads, add-on downloads and media requests all start from (a browser's own agent replaces it when the browser sent one); core's tests check each path against the engine's default.
6. Superseded by item 7: `naming::unique_path` stayed public for a while because the streams crate used it; the name reservation of ENG-11 removed it.
7. A download takes its name by creating its part file and never replaces a file another program saved meanwhile (ENG-11, W4, 2026-10-13). `naming::unique_path` is gone: it picked the first name with no file, part file or resume file and the files were created later, so two downloads racing for one name both got it, and the finish's rename replaced whatever had appeared under the name while the download ran. Now a download into a folder creates the part file of the first free name with `create_new` (`O_EXCL` on Linux, `CREATE_NEW` on Windows), so downloads in this process or another each get their own name, and nothing appears under the final name until the data is complete and flushed. The finish moves the part file there in a step that fails when the name is taken: `MoveFileExW` without `MOVEFILE_REPLACE_EXISTING` (and with `MOVEFILE_WRITE_THROUGH`) on Windows, atomic on NTFS, ReFS and SMB; `renameat2` with `RENAME_NOREPLACE` through `syscall` on Linux, so no C library version is needed; local Linux file systems take that flag, FAT32 and exFAT included, since the kernel checks it itself; where the kernel or file system refuses it (`EINVAL` or `ENOSYS`: some FUSE, CIFS and older NFS; `EPERM` or `ENOSYS`: a sandbox that blocks the call) and on other Unix systems, a hard link to the new name then removing the old, whose `EEXIST` is atomic, undone when the old name cannot be removed so the file is never left under two names; and where hard links are missing too (an SMB mount without Unix extensions, some FUSE file systems) a check then a rename, the one case with a moment in which a file saved under the name is lost, documented. When another program took the name, the file moves to the next free name, so `Outcome::Completed::path` can differ from the `Progress::path` announced at the start, which is how Chromium finishes its `.crdownload` files. The public form is one function, `naming::move_to_free_name(from, dir, name)`, which the streams crate uses for a result whose extension changed the caller's name; the part-file reservation stays private. It refuses (`InvalidInput`) any name `naming::is_safe_name` refuses: one whose characters, start or end `sanitize` would change, or that is a Windows device, so a device (`NUL`, `COM1`), a stream inside another file (`f.zip:x`), a trailing dot or space that Windows drops, a folder part and the rest of what `sanitize` replaces are never "taken" without being a file of that name; one definition of a safe name, not a second weaker one. Length is the one rule `is_safe_name` does not share with `sanitize`: it takes any name whose part and resume files still fit the system's 255 bytes (247 bytes), while `sanitize` cuts to 200 so callers can add ` (1)` or another extension; core's media names (a title cut to 200 bytes, then `.mp4`, then ` (1)`) and a stream whose container changes its extension depend on that. `sanitize` itself checks for a device name after its cut (`CON` followed by 300 spaces was cut to `CON`), so whatever it returns it returns again unchanged and `is_safe_name` takes, which a property test holds it to. A free name for a name near the limit gives up the end of its stem to its number. The engine also gains the choice for a path of the caller's now, so the published API breaks once rather than again in W9: `DownloadRequest::if_exists`, an `ExistingFile` (`#[non_exhaustive]`, `Replace` by default, as before, or `Refuse`), and `Error::TargetTaken { path }`; with `Refuse` the finished data stays in the part file beside a resume file that says it is complete, so a later run only finishes it when it can resume (the server gave the size and takes ranges); otherwise that run downloads it again. Resuming is as before: a run of the same URL continues when its resume file matches and nothing is at the final name. Rejected: an empty placeholder file at the final name for the whole download, as Firefox does, tried first in this work. A person sees, opens and syncs a 0-byte file with the real name, it outlives every paused, failed or interrupted run, deleting it silently gave up the name, and on Windows the finish's replacing rename fails while any program holds it open without delete sharing, after all the data arrived. Release notes for the next release of `wirecatch-engine` (breaking, D30.3). Removed: `naming::unique_path`. Added: `naming::move_to_free_name` and `naming::is_safe_name`; `DownloadRequest::if_exists` and `ExistingFile`; `Error::TargetTaken`. Fixed: `sanitize` never returns a Windows device name, also when its cut to length leaves one. Changed: a download into a folder takes its name by creating its part file exclusively, so two downloads never share a name, and no longer replaces a file another program saves under its name while it runs: it finishes under the next free name, which `Outcome::Completed` reports and which can differ from `Progress::path`.

Decided by the lead on 2026-10-12 for AUDIT W8. ### D32. Both ends of a local connection agree on a protocol version, and a call one end lacks gets its own answer
Decided for the quality audit's W3 (IPB-4) on 2026-10-13. The extension comes from the browser stores and the app updates itself, so an old copy of one meets a new copy of the other for weeks after every release; an exact version match would cut every such pair off.
1. Protocol versions are whole numbers. A build speaks every version from `MIN_PROTOCOL_VERSION` to `PROTOCOL_VERSION`, both defined once in `crates/protocol/src/version.rs` and generated for TypeScript. Version 1 is the wire format before this decision; this decision is version 2, which also adds the error codes `limit_reached`, `wrong_state` and `update_check_failed`: a connection on version 1 gets `invalid_request` for each, as apps from version 1 sent.
2. The first `hello` settles the version. Its `protocol_version` names the oldest version the client speaks, because it is the only field apps from version 1 read and they accept only 1 there; `max_protocol_version` names the newest, and missing means the same as `protocol_version`, as clients from version 1 send it. The app answers `HelloReply.protocol_version` with the newest version both speak, and the connection uses it from then on (a later `hello` gets the same answer). A hello whose newest version is older than its oldest is refused with `invalid_request`; ranges that share no version are refused with `unsupported_version`, whose message names the side to update; either way the connection closes. The extension checks that the version the app chose is one it speaks, and otherwise shows a version mismatch naming the side to update.
3. On a connection each side sends only what the agreed version has. Every call, event and error code states the version that added it (`CallMethod::since`, `EventKind::since`, `ErrorCode::since`, in `version.rs`, each an exhaustive match), and a code added after the oldest version this build speaks names the older code a connection before it gets for the same failure. The app writes every message through `Message::as_of`, which leaves out events newer than the connection and turns newer codes into older ones. The tables are generated for TypeScript (`CALL_SINCE`, `EVENT_SINCE`, `ERROR_CODE_SINCE`, each typed as a record of every name the generated types have, so one left out fails the type check). The extension keeps the agreed version, refuses a call newer than it without sending it, with the same `unsupported_call` the app would answer, and offers `supports(method)` so a caller can hide what the app cannot do.
4. A request with a readable id whose method the app does not have, or whose call is newer than the connection, is answered `unsupported_call` for that id: nothing is done and the connection stays open for every other call. A method the app has, with parameters it cannot read, stays `invalid_request`. A connection on version 1 gets `invalid_request` instead, as apps from version 1 answered. The extension takes `unsupported_call` as the failure of that one request and keeps the connection.
5. An additive change raises `PROTOCOL_VERSION` by one (once per release: changes since the last release share the raised version), states that version in the new variant's arm, and leaves `MIN_PROTOCOL_VERSION`: older peers keep working at their own version. Additive are a new call, event or error code; a new reply or event field, which older clients pass over; and a new request field the app gives a default when it is missing (as `start_app` and `max_protocol_version` have) and that an older app may ignore without doing the wrong thing. A request field an older app must not ignore (a queue the download has to go to, say) is a new call instead, so an older app answers `unsupported_call` rather than doing something else. A change only one side can see, such as the wording of a message, raises nothing.
6. A new value of an enum inside a call, reply or event (`ClientKind`, `MediaKind`, `CaptureSource`, `AddAction`, `WithdrawOutcome`, and any added later) cannot be read by peers built before it: the generated validators and serde accept only the values they know, so the whole message would fail. It is a breaking change, unless the sender maps it, for connections older than the value, to an older value meaning the same, as `ErrorCode` does; a new `ClientKind` cannot be mapped, since the app reads it before any version is agreed. The test `the_values_of_enums_inside_messages_are_settled` fails on any change to these values until that choice is made.
7. A breaking change (removing or renaming anything, changing a field's type or meaning, making an optional field required, adding an enum value no older value can stand for) raises `PROTOCOL_VERSION` and raises `MIN_PROTOCOL_VERSION` past every version it breaks. Peers older than the new minimum are refused with `unsupported_version` and told to update, so it is a last resort: prefer an additive change that keeps the old shape readable until no supported version uses it. Its commit is marked with `!` and a `BREAKING CHANGE:` footer naming the versions it drops.
8. Each released version is frozen: the generated `Call`, `Event` and `ErrorCode` types of its release are kept byte for byte in `crates/protocol/released/v<version>/` (version 1's are main's before W3), `RELEASED` in `version.rs` names them, and a test fails when a version's tables no longer give exactly the names in its snapshot (so a new variant added to an old version's arm fails), when anything is newer than the last release but not in the version being built, or when `PROTOCOL_VERSION` is more than one past the last release. The `protocol` gate check fails when a snapshot main already has is changed or removed, so what a version holds is tied to what was released, not to a later branch's idea of it. Releasing a protocol version copies its generated types there and adds its entry; the release workflow will check that the version it ships is frozen (W6).
9. The desktop shell's fallback server, which answers every request with `app_unavailable` while the download list cannot open, reads only a request's id, so a call it cannot read never ends the connection. It agrees on no version, so it writes its answers through `Message::as_of` with the oldest version this build speaks.
10. The bridge passes frames through byte for byte and does not take part: it ships with the app, so the two are always the same build, and the codes it answers with itself (`app_unavailable`, `app_not_running`, `invalid_request`) are all in version 1. A new code the bridge answers with needs it to read the agreed version from the app's hello answer first. The CLI does not connect to the app (D13); when it does, it names its versions in `hello` as the extension does.

### D33. Builds spend disk and time only where they buy something
Decided on 2026-10-13, when the Linux CI job ran out of runner disk in the desktop crate's separate test build and no CI run had yet passed.
1. Debug and test builds keep line tables for the workspace's own crates and no debug info for dependencies (`[profile.dev]` in the root `Cargo.toml`; the `test` profile inherits it). It is set for every build, not only CI: local build folders shrink the same way (incremental builds are already off for disk, `.cargo/config.toml`), and CI and a developer's machine build the same thing. Backtraces and panics still name the file and line of our code. A debugger session sets `CARGO_PROFILE_DEV_DEBUG=full` for full debug info in our crates; dependencies stay without it.
2. The gate's `test` check runs every crate's tests, the desktop crate's included, in one `cargo test --workspace`, so every dependency is built once, in one feature resolution. The separate `test-desktop` check is gone. What it proved besides the tests, that the desktop crate and its tests compile with only the features it asks for, is now in `clippy` (`cargo clippy -p wirecatch-desktop --all-targets`, a check build, so no second codegen build or link). The desktop crate's tests themselves now run with the workspace's unified features. Its reason for existing, other crates' doctests failing to link when the desktop crate was in the same build, was Tauri's static Visual C++ runtime switch: it puts an empty `msvcrt.lib` in the desktop crate's build folder, and cargo hands every doctest the link paths of the whole build.
3. The switch is `build.windows.staticVCRuntime` in the Tauri configuration, its one home: off in `tauri.conf.json`, so plain cargo builds and tests in any profile link the runtime dynamically, and on in `tauri.bundle.conf.json`, which every packaging build (`bundle` and the debug `build:tauri`) merges in. So the app executable in every installer, debug ones included, links the runtime statically, as before. That covers the app executable only: the bridge the installer ships next to it is a plain cargo build and links the runtime dynamically (a W10 finding). The desktop build script removes a stub a static build left, so switching between packaging and a workspace test run in one build folder works.
4. CI installs cargo-deny and cargo-machete as prebuilt release binaries with `taiki-e/install-action` (pinned by commit, its `fallback: none`, so it never quietly builds from source), which checks each download against the checksum recorded in the action's own manifest. The versions stay in `TOOLS` in `scripts/gate/rust.mjs`; CI reads them with `node scripts/gate.mjs --tool-specs`, and a script test fails when a workflow names one of the tools anywhere but a comment or gives an installer any other `tool:` input. This trusts the tools' release binaries rather than a build from their lockfiles, for minutes saved on every supply-chain run and every weekly audit. `node scripts/gate.mjs --install-tools` still builds them from source for a developer machine.
5. Rust caches are saved on `main` only and also when a check fails; pull requests restore them and never write them, which keeps the caches inside the repository's 10 GB.
6. The `repo` group (text, exceptions, tauri-pairs, product, commits) runs in CI on Linux only: its inputs are the same bytes on every system (`.gitattributes` forces LF). The checks' own code is not: they start git and the product generator, so a change to them that breaks only on Windows is caught by `pnpm gate` on a Windows machine, not by CI. That trade saves about 90 seconds on the Windows JavaScript job; run the group on both systems again if such a break ever reaches main.

### D34. Every answer is checked against the first, the starting host gets no exception, and the address classifier is public (W4)
Decided during W4 (security hardening, engine findings), 2026-10-13.
1. Within one run, every answer after the first must be about the file the first answer described (ENG-6). Each partial answer, over HTTP/1.1, HTTP/2, HTTP/3 or from the `Fetcher`, goes through `http::check_partial`, and a whole answer that continues a transfer on a server without ranges, in a download or the `Fetcher`, through `http::check_whole`: the offset asked for, the same size where both are known, and validators that do not contradict the first answer's (point 2). Anything else ends the run with `Error::RemoteChanged`. Over FTP, which has no validator that comes with the data, the size (`SIZE`) and modification time (`MDTM`) are compared before every range, on a new control connection and on one kept from the last range; a file replaced while a range is being sent is still missed until the next range.
2. When both answers carry an `ETag`, it alone decides, compared weakly (`W/"x"` matches `"x"`): RFC 9110, section 13.2.2, gives the entity tag precedence. Otherwise a `Last-Modified` counts only when it is a strong validator on both answers, at least one second older than that answer's `Date` (section 8.8.2.2), compared as a time: a server that stamps each answer with the time it sends it (download scripts, some servlet containers) gives a new date every second that says nothing about the file, and failing on it would make such a server impossible to download from with more than one request. This deliberately departs from RFC 9110, section 15.3.7.3, which joins partial answers only when they share a strong validator matched by strong comparison: the engine refuses a contradiction and does not ask for proof of a match. Two answers with the same weak tag are joined as not contradicted, not as proven the same, and a validator that an answer leaves out proves nothing, because many servers send only weak tags (Node's `send` among them) and servers and caches drop validators from some answers; asking for proof would fail sound downloads from all of them. `Accept-Encoding: identity`, which every request sends, removes the usual reason for a tag to be weak. Resuming a paused download stays stricter (`ResumeState::can_resume`: a validator that appeared or vanished is a change), because there the cost of caution is a fresh start, while here it would be a failed download.
3. No `If-Range` is sent. A `206` must carry the `ETag` a `200` would have had (RFC 9110, section 15.3.7), so comparing headers sees what `If-Range` would. A failed `If-Range` comes back as a `200`, which the engine reports as `Error::RangeNotHonored`, a wrong message for a changed file, where the comparison gives the precise `RemoteChanged`. And a server or cache that answers every `If-Range` with the whole file would lose ranged downloads for good. What `If-Range` would still catch: an intermediary that strips validators from `206` answers, which the leniency of point 2 lets through.
4. The starting URL gets no exception for having been looked up first (found in the review of this work; it also corrects the fixes the audit proposed for ENG-9 and CORE-3). Under `PrivateNetwork::Block` the starting origin is exempt only when its host is written as an address, which the caller can classify; a starting host written as a name is checked before each request like any other, and every connection to it resolves through the filter, so a name that answered public to the caller and answers local when the engine connects (DNS rebinding) cannot reach the local network, its first request included. Before, the engine looked the starting host up once and, when every answer was local, kept those addresses for it in the filter: under `Block`, a website's name that answered local at that moment was let through. `PrivateNetwork::Auto` still decides from that one separate lookup whether the start is on the local network, because that is what it is for (a media server at home the user chose); its documentation now says a URL a website chose must not be started with it.
5. The engine's address classifier is public: `AddressKind`, re-exported at the crate root next to `PrivateNetwork`, with `AddressKind::of(IpAddr)` and `is_public()`, `#[non_exhaustive]` (ENG-9). Core uses it instead of its own weaker copy (CORE-2), so the app and the engine cannot disagree about what is local. An enum rather than a `bool` lets a caller say which range an address is in, in a message or a log line; `is_private` was rejected as a public name because the standard library's `Ipv4Addr::is_private` means the three RFC 1918 ranges only. No public helper resolves a host name: a separate lookup of a name a website chose decides nothing about the connection that follows (CORE-3). The product rule (decided by the lead for CORE-3, 2026-10-13): a URL the person typed or pasted keeps `Auto`, so a media server on the home network or an intranet, reached by host name, keeps working when the person enters it; every URL a website chose, captured streams and yt-dlp formats of a page on the internet included, uses `Block`. Whether a URL was typed or captured is known where the job is made, not from where it points. No setting for hosts the person trusts exists, and none is needed for now. Under `Block`, point 4 makes the rule hold for the starting host too. What W4 found when this was decided: three default entry points started with `Auto`, `Fetcher::new` (`crates/engine/src/fetch.rs`), `StreamRequest::new` (`private_network` defaulted to `Auto`, `crates/streams/src/model.rs`) and `wirecatch_streams::inspect` (through `Fetcher::new`, `crates/streams/src/lib.rs`). Core started captured URLs through two of them: `StreamRequest::new(job.url…)` for a stream job, whose URL may come from a page (`media_run.rs`), and `wirecatch_streams::inspect(&source.url, …)` when a captured stream is read (`media.rs`). Core's `network_rule` (`media_run.rs`), which picks the rule for yt-dlp formats, was the third place. D34.9 and D34.11 record what the code does now. The CORE-3 work changes the core call sites to pass `Block` for a captured URL, which needs `inspect` to take the rule; whether `Fetcher::new` and `StreamRequest::new` should default to `Block` is a behaviour change of two published APIs and gets its own decision. The `Fetcher` documentation and example now start a website's playlist with `Block`. Amended by D39: a link from a page on the person's network may reach it, and the person can list sites on their network.
6. The kinds follow every entry of the IANA IPv4 and IPv6 special-purpose address registries that is not reachable on the internet, plus multicast. Making the list public added documentation (`192.0.2.0/24`, `198.51.100.0/24`, `203.0.113.0/24`, `2001:db8::/32`, `3fff::/20`), IPv6 benchmarking `2001:2::/48`, the IETF protocol assignments `192.0.0.0/24` and `2001::/23` (except the ranges there that the registry marks reachable: Teredo, the PCP, TURN and DNS-SD anycast addresses, AMT, AS112, ORCHIDv2 and drone identifiers), the discard-only `100::/64`, the dummy prefix `100:0:0:1::/64` and SRv6 segment identifiers `5f00::/16` to what the guard refuses; none is ever a real download host. An IPv6 address that only carries an IPv4 one (mapped, compatible, NAT64 `64:ff9b::/96`, 6to4) is of that address's kind; Teredo and IPv4-translated (`::ffff:0:a.b.c.d`) addresses are not unwrapped, and local-use NAT64 `64:ff9b:1::/48` is a kind of its own, because only its gateway knows where it leads.
7. New kinds may be added, and an address that is `Public` now may be given one of them in a later minor version as the registries assign ranges; the type's documentation says so. Adding `AddressKind` is not a breaking change; the API diff is the enum, its two methods and the re-export.
8. Release notes for the next release of `wirecatch-engine` (the crate has no changelog, D30.3, so this is the text to publish with it). Added: `AddressKind`, the classifier `PrivateNetwork` uses, with `AddressKind::of` and `is_public`. Changed: a download or `Fetcher` request now ends with `Error::RemoteChanged` when an answer after the first carries another `ETag`, another strong `Last-Modified` where no `ETag` is shared, or another size (the `Fetcher` did not compare sizes before), including a whole answer that continues a transfer on a server without ranges; FTP compares the modification time as well as the size, before every range. Changed: with `PrivateNetwork::Block`, a starting URL whose host is a name that resolves to the local network is refused with `Error::PrivateNetwork`; before, it was allowed when every address it resolved to was local. Changed: the guard also refuses the documentation, benchmarking, IETF protocol assignment, discard, dummy and SRv6 ranges listed in point 6.
9. Core closes CORE-2 and CORE-3 (W4, 2026-10-13). Who chose a download's link is a typed value, `ChosenBy` (`crates/core/src/local_network.rs`): `Person` for a link added or refreshed in the app (`add_download`, `refresh_link`), and for everything the extension captures (a download, with or without the confirmation window, a stream and a video page) `LocalPage` or `Website` as D39 decides. It is set once, where the link arrives, kept with the download (the `chosen_by` column; a row stored before it existed reads as `Website`, the rule that fails closed, and so does a value the build does not know), and `ChosenBy::private_network` is the only place that turns it into a rule: `Auto` for the person's and a local page's, `Block` for a website's. Every start of a link takes the rule from it: a plain download (`engine_request`), a stream read (`inspect`) and downloaded (`run_stream`), and a page's formats (`network_rule`, through which the subtitles and pictures of a page go too). No call site picks a rule of its own, and core's request options cannot be made without one (`headers::download_options` and `media_options` take it). A captured plain download, which ran with the engine default `Allow` before, now runs under `Block`. A website's link that leads into the local network (its host a local address, or a name whose every address is local) is declined before core answers the capture, whatever the window or the queue would do next, so the browser keeps its own download: once core answers that it has the download, waiting for the person or queued, the extension lets go of the browser's copy. That check looks the name up only to refuse; a name that answers otherwise later is still refused by the engine.
10. A video page counts as on the local network (its formats may then go anywhere, `Allow`) when the person chose it and every address its name resolves to is local, as `Auto` decides for a link they typed, or when it is a `LocalPage` (D39). A website's page is never local, whatever its name answers: its owner controls that lookup (CORE-3). A website's link written as a local address, which the engine lets through as the start under `Block` (point 4) for its caller to classify, is refused by core, when it is captured and again before every start (D39). Core's own lookup of a format's host stays as an early refusal with a clear message and never lets anything through; the engine's `Block` decides at the connection, so a format name that answered public to that lookup and local at the connection is still refused. Core classifies with the engine's `AddressKind` (CORE-2): its own weaker copy is deleted.
11. `wirecatch_streams::inspect` and `StreamRequest::new` take the rule as an argument and have no default (W4 decided the question point 5 left open, for streams only). The crate is not published, so the change costs only its callers, and a caller that has to name the rule cannot forget it, which a default (`Auto` before) let every caller do. `Fetcher::new` keeps its `Auto` default only because it is a published API of the engine: core no longer calls it, since every fetch core makes names its rule (`Fetcher::with_private_network`; the media add-on's release addresses use `Block`, D38.5).

### D35. The extension's Public Suffix List comes from tldts and is current at every release
Decided for the quality audit's W4 (EXT-3) on 2026-10-13.
1. Which requests are same-site, and so which `SameSite=Strict` and `Lax` cookies the extension hands to the app, is decided from the Public Suffix List, both its ICANN and private sections, through `getDomain` from `tldts` (`registrableDomain` in `apps/extension/src/lib/cookies.ts`). The extension APIs do not expose the browser's own list, and a hand-kept approximation was the cause of EXT-3. `tldts` ships only in the background bundle and is pinned to an exact version in `apps/extension/package.json`, so the list changes only in a reviewed commit.
2. The bundled list ages, and the two kinds of drift fail in different directions. A suffix added to the list after the pinned release is unknown to the extension, so two customers of that host look like one site and the app gets cookies the browser withheld: this fails open, and is the EXT-3 attack again. A suffix removed from the list still separates two hosts the browser joins, so cookies are withheld and a logged-in download can fail: this fails closed. New top-level domains are safe either way, since the list's implicit `*` rule already treats an unknown last label as a suffix. Even the latest `tldts` trails the list, which changes almost every week: `tldts` gathers its changes into releases, about every 9 days over the last year (41 stable releases) but with gaps of up to 70 days (7.0.19 to 7.0.20, ending 2026-01-31). That lag is a limit of the source, accepted.
3. So `tldts` is security data, not an ordinary dependency, and D28's on-purpose cadence is not enough for it. The rule is that it is updated to its latest release before every release of the extension. The `suffix-list` check (`scripts/gate/suffix-list.mjs`) is a floor that catches a missed update, not the rule itself: it fails when the extension does not pin `tldts` exactly, when a newer stable release has been out for more than 60 days, when no stable release has come out for more than 180 days, or when the registry's release dates cannot be read. 60 days, about six `tldts` releases, keeps a release that is being prepared from failing on a version published the day before. Age alone does not fail it, since the newest release is the freshest list `tldts` offers; an upstream silent for more than 180 days does (about 2.5 times its longest gap), and then where the list comes from must be decided again: another library, or a snapshot generated from publicsuffix.org.
4. The check asks the registry and its result changes as the calendar moves, so it is never in the default run. It is in the `publish-extension` group, `publish` plus `suffix-list`, which the extension's release scripts (`pnpm build:store` and `pnpm sign:firefox`) run first. The desktop installers and the engine's crates.io release do not ship `tldts`, so they run `publish` alone and a stale list never holds them.
5. The app keeps its own list current while it runs (D44); this decision stays the floor at every release, for the extension's list and the one built into the app.

### D37. What the contract carries beyond types, and what stays with the app that uses it
Decided for the quality audit's W3 (EXT-8, EXT-9, EXT-14, XC-11, DUI-2, DUI-21) on 2026-10-13. D15 says every type crossing a process boundary is defined in `crates/protocol`; this settles the values, rules and lists around those types.
1. A value is part of the contract when two processes must agree on it, even when only one of them reads it: the bridge's start budget (`BRIDGE_START_BUDGET_MS`, from which the extension derives how long it waits for an app it may start), the largest frame, how many sites the list of sites to ignore holds and how long one may be (`MAX_IGNORED_SITES`, `MAX_SITE_CHARS`), which output formats suit videos, audio and lossless sound, the default queue and the extension's default settings. Each is defined once in `crates/protocol` and generated for TypeScript; the apps never restate it.
2. A rule both languages apply is written in Rust in `crates/protocol` and ported once into `@wirecatch/protocol`, next to the generated files: `normalize_site` (how an ignored site is kept, which core stores and both editors and the extension's matching use), `normalize_file_type` (how a file type is kept, which core stores and the extension's editor and matching use) and `ExtensionSettings::apply` (which the extension's popup shows before the app confirms, and the desktop's stand-in backend applies). The port is tested against cases the protocol's tests write into `generated/fixtures.json` from the Rust functions themselves, never against expectations copied by hand, so a change on one side fails the other's tests.
3. Ids are branded in TypeScript (`DownloadId`, `QueueId`, `QuestionId`), so one cannot pass for another. An id from the app is already typed; one read from the page, a drag or an address goes through its generated guard; the constructors `downloadId`, `queueId` and `questionId` are for numbers known to be that id, in the stand-in backend and in tests.
4. The extension's list of media page sites (`PAGE_SITES` in `apps/extension/src/lib/media/page-sites.ts`) does not cross a boundary and stays in the extension. It only decides where the extension offers to send the page itself; the app receives just the page's address (`MediaKind::Page`), decides with the media add-on whether the site is supported, and reads no copy of the list. If the app ever sends the add-on's site list so the offer tracks what is installed, that is a new field or call with the `since` of the version that adds it (D32), and the extension's list remains what it uses with an older app.
5. Values only one process uses are its own, even when they look like settings: the queue dialog's suggested schedule and speed limits (W3, DUI-11) and the extension's waits (`apps/extension/src/lib/native/timing.ts`). Of those, the wait for a connection, which may start the app, is derived from the bridge's start budget: `START_WAIT_MS` is the budget plus the time the app may take to answer `hello` once the bridge reached it (it accepts connections before its download list is open), the hello timeout is that wait, and a call that may start the app (a capture, the Open button) waits that long on top of its own answer's wait.

### D38. The add-on's parts are typed, run only from their checked files, and a new yt-dlp must be the release it claims (W4)
Decided during W4 (security hardening, add-on findings CMD-11, CMD-17 and CMD-18), 2026-10-13.
1. A part of the media add-on is a `ComponentId` (yt-dlp, ffmpeg, Deno), and its `as_str` is the only text that names a part's folder or its entry in `installed.json`, so no caller can name a folder outside the add-on's (CMD-11). A record naming any other part, or holding a checksum that is not 64 hex digits, is read as damaged: nothing it names is trusted or run. The public manifest types are parsed once: `Sha256Digest` (64 hex digits in either case, compared as bytes, written in lower case), `Fingerprint` (a full OpenPGP fingerprint, 40 or 64 hex digits, spaces and case ignored), `Url` for every address, `ReleaseFile` (its address, checksum and a size that is never 0, since the size caps what is downloaded), and `AddonComponent`, whose fields are private and whose constructor refuses a part with no file, a plain release with more than one, a target path that is not safe (point 3), two targets that are one file when case is ignored, an archive entry named twice, or a program that is not one of its files marked as a program. `for_release` gives the same part from another release, which is how an update check result and the tests make one. The app's own pins are put together directly and checked by a test against the same rules; parsing their addresses (`pinned_address`) is lint exception E12. This changes the public API of `wirecatch-core`, which is not published.
2. The programs are run only when each is one of its part's recorded files (CMD-17), and only when every recorded file is there with its recorded size (on every start of the app) and SHA-256 (on a repair and after a program could not be started). These checks find damage and half-finished installs. They do not stop another program running as the same person from changing a file between the check and the run, and need not: the add-on's programs run as that same person, at the same integrity level, so a program that can write the person's data folder already runs code as them and gains nothing by swapping yt-dlp (it could get the same persistence from a Run key). The app itself, installed per machine in Program Files (D25), is out of its reach; the add-on, in the person's own data folder, is not, and that is accepted. Keeping the files locked while the app runs was rejected because it would block the add-on's own update and removal.
3. A path a manifest names (`archive::is_safe_relative`) names a file inside its folder and the same file on every system: nothing absolute, no drive letter, `.` or `..`, no `:` (a drive or a Windows alternate data stream), no control character or other character Windows forbids (`<>"\|?*`), no part ending in a dot or a space (Windows drops them, so two names would meet in one file), no Windows device name (`CON`, `PRN`, `AUX`, `NUL`, `CONIN$`, `CONOUT$`, `CLOCK$`, and `COM` and `LPT` with one digit or superscript, with any extension), and nothing shaped like a Windows short name (a `~` followed by a digit, as in `FFMPEG~1.EXE`), which can be another file's second name. The same check guards the paths of a record read from disk.
4. yt-dlp's checksum list is signed, but it names files, not a version, so the signature ties the files to yt-dlp's key and not to a release. Someone who can publish on yt-dlp's GitHub page without that key, the attacker D21.1 is about, could publish an older release's files and its signed list again under a newer tag, and Wirecatch would install the old yt-dlp as the new one. So after the checks of D21.1, a yt-dlp the update check found is run once, unpacked in its staging folder, with the same isolation as every other run (`--ignore-config --no-plugin-dirs`, one list shared with every run, `ytdlp::version_args`) and `--version`, through the one runner of the add-on's programs (D31) with a one-minute limit, and installed only when it succeeds and prints exactly its tag and nothing else. Whether a part is checked this way is carried with it from where it was chosen (`Origin::Found`, against `Origin::Pinned`), never worked out by comparing it with the pin. A successful answer that is anything but its tag is the one sign of a replayed release, and refuses it as not what it claims: its download is deleted, it is not offered, downloaded or run again while the app runs, and the person is told in the add-on's note (not a second time as an install failure) even when the update was a quiet one. The note stays while the refusal still concerns the installed yt-dlp, beside the note of a newer release that waits, and goes once a newer yt-dlp is installed. A release that cannot be started, does not answer in time or ends with an error is an ordinary failure, tried again later from its download: an antivirus or a full temporary folder can cause that, and nothing is installed either way. Running it before it is installed is acceptable because its checksum already carries yt-dlp's signature. The yt-dlp the app pins is not run first: its checksum is written in the app. A release older than the installed one or the pin is never offered (D21.1).
5. Release files are downloaded following redirects to any host, since GitHub serves them from another one. What makes a file trusted is its checksum, written in the app or signed by yt-dlp's key, never where its bytes came from; the only addresses that are restricted are the ones a release list names, which must be exactly `<release folder><tag>/<file name>` (D21.1), the folder joined as an address so a base written without its last slash still matches. Every request for the add-on, release files and the release list alike, uses `PrivateNetwork::Block` (D34): a release host is never on the local network, so a name that answers with a local address (a poisoned name server, a hostile network) or a redirect there is refused rather than sent a request. Like any start written as an address, the tests' local server is let through (D34.4).
6. An archive is opened only after its checksum matched, and from the same open file (on Windows, a file nobody can write, replace or delete meanwhile). Entries are matched by name and never used as paths; links, hard links, folders and devices under an expected name are refused; each file is cut off past 1 GiB while it is written, so an entry that inflates past that is refused whatever its header says. What a tar entry the manifest does not name decompresses to is read through and not written; with a checksum that matched, a decompression bomb would need a hostile pinned release, so no total limit was added.
7. yt-dlp runs with `--cache-dir <add-on folder>/cache` (CMD-18), so it never reads or writes the cache another yt-dlp on the machine shares, and the cache is emptied whenever a new yt-dlp is put in place, since what another version cached is a known cause of failed reads. It goes with the add-on when the add-on is removed.

### D39. A website's link reaches the local network only from a page on it (amends D34.5)
Decided by the orchestrator for W4 (review of CORE-3), 2026-10-13. D34.5 said every link a website chose uses `Block` and that no setting for trusted hosts is needed; at home and in offices that refuses the downloads people start from their own NAS, router or intranet pages, and with the confirmation window on it lost them from the browser too.
1. A link the extension captures may lead to private or local addresses only when every page address the capture carries is on the person's network by its own address, never by a lookup core makes. The addresses are the tab's (`page_url`), the referrer, and the document the capture started in (`frame_url`: the frame a link or the media button is in, or for media the document that requested it, as the browser reports it), whichever are present, at least one. Every one must be, because a frame from another site on a local page chooses its own links. A capture that does not name its frame (an older extension, media whose requester the browser did not report) leaves the referrer as the only trace of it; when the referrer is missing too, as the browser drops it from an https frame to an http link, the frame is unknown and the capture is a website's, since only a browser download's page address is the initiating document's own (its referrer). `frame_url` is an optional field of `NewDownload`, which an app from before it ignores; by D32.5 it is additive, so it belongs to protocol version 2, the version being built, and raises nothing further. A page address is local in two tiers. Tier 1, its host is a local IP address (by `AddressKind`) or a name public DNS cannot serve, which is a single label that is not a top-level domain on the Public Suffix List (`nas`, but not `ai`, where public DNS has served records at the top level itself) or a name under `localhost`, `test`, `invalid`, `example` (RFC 6761), `local` (RFC 6762), `home.arpa` (RFC 8375), `service.arpa` (RFC 9665), `internal` (reserved by ICANN for private use, board resolution 2024.07.29.06), `home` or `corp` (which ICANN will not delegate, board resolution 2018.02.04.12), or `lan`, a product choice: home routers use it and nobody has reserved it, so it counts only while the Public Suffix List does not list it. The other host-naming entries of the IANA Special-Use Domain Names registry are left out: `onion` (RFC 7686) and `alt` (RFC 9476) name hosts on other networks, `ipv4only.arpa` (RFC 8880) resolves publicly and `resolver.arpa` (RFC 9462) names the resolver. The lists are data in one place, each entry with its source (`LOCAL_SUFFIXES` and `UNRESERVED_LOCAL_SUFFIXES`, `crates/core/src/local_network.rs`). Tier 2, its host is one of the person's sites on their network or under one (`local_sites` in `AppSettings`, below). Such a capture is `ChosenBy::LocalPage`, which runs under `Auto`; every other capture is `Website`, under `Block`.
2. Being the same site as the link is no reason: the site's owner controls its own names, so `dl.evil.example` answering `192.168.1.1` is as much the attacker's as `evil.example`. A page that looked local to a lookup is no reason either (CORE-3).
3. A `Website` link into the local network is declined before the capture is answered (D34.9): its host is a local address, or a name whose every address is local within three seconds. The browser keeps its download and the extension's notice says why. A `Website` link written as a local address is also refused before every start, for a row stored before this rule.
4. `AppSettings::local_sites`: host names, each also covering the names under it (`corp.example.com` covers `wiki.corp.example.com`), empty by default. Each entry must be one owner's: a registrable domain or a name under one by the Public Suffix List, both its ICANN and private sections, so `com`, `co.uk` and `github.io` are refused (each would make every site under it a local page) while `team.github.io` is accepted; an address is refused too, since a page at a local address needs no entry and suffix matching on an address means nothing (`2.3.4` would match `1.2.3.4`). An entry is read as a site to ignore is (`read_site`, D37.2), so a host name or a web address may be typed, and kept as its host the way the URL parser writes a page's (lower case, international names in ASCII form, dots trimmed). The list is read tolerantly (`#[serde(default)]`; a stored or imported list is cleaned on reading, and an entry that would be refused is dropped there) and checked on change (at most 256, a refused entry named in the message). Core reads the list through `crates/core/src/public_suffix.rs`, the list its manager holds, which the app keeps current while it runs (D44). It changes through the existing settings commands (`AppSettingsPatch::local_sites`, replacing the list). The field is optional on the wire, so the extension and older windows are unaffected. In the Settings page it is a list under Advanced, which takes what is typed down to its host as the list of sites to ignore does; its final place belongs to the UI revamp.
5. Accepted residual, as browsers accept it for private-to-private navigation: a local page that shows links others posted (an intranet wiki) gets `Auto` for them, so a posted link to a name that answers local is followed. The browser-observed address of the page was rejected as a signal: behind a proxy it is the proxy's address, often private, which would make every page look local.
6. The wording of a refusal follows who chose the link (`user_error::private_network`): for a website's link, that giving the download a new link in the main window and pasting the same one makes it the person's own (the row's fix, labelled "Get a fresh link" or "New link"); a new link given in the download's own window keeps the website's rule (D43.5), and that window still offers its own form for the fix, so the message names the main window. For the person's or a local page's link, it says that it was sent on from the internet into the local network, with no fix, since pasting it again changes nothing.

### D40. Every binary logs to a capped file through one crate, and no log line carries a secret
Decided for the quality audit's W5 (XC-15, DRS-3, CMD-14) on 2026-10-13, after a release build of the app on Windows, which has no console, was found to log nowhere.
1. `crates/logging` (`wirecatch-logging`, unpublished) is the one logging setup. It is a crate of its own because its users share no other home: the bridge and the command-line downloader do not depend on core, and core and streams need its redaction but not its setup. The setup is its default `setup` feature; core and streams turn default features off and build no subscriber. Every binary calls `wirecatch_logging::start(<binary>, <default filter>)` first thing in `main`, then `Logging::write_to` once it knows its log folder (lines logged before are held, up to 256 KiB, and written first): the app at once, in `logs/` of its channel's local data folder (or of the folder `WIRECATCH_DATA_DIR` names), so a start that fails before the data folder is settled is logged too (see 8); the bridge and the command-line downloader in the release app's folder, since they belong to no channel (D22); the headless example in its data folder.
2. Lines go to stderr and to `<binary>.log` in `logs/` of the data folder (`wirecatch-app.log`, `wirecatch-bridge.log`, `wirecatch.log`), one file per binary so no two kinds of process roll the same file. A file stops at 5 MiB and becomes `<binary>.1.log`; three old files are kept, so a binary's logs never pass 20 MiB while the files can be moved on (see 7 for when they cannot). Lines are written as they are logged, with no background thread: logging is rare enough, and a release build aborts on panic, so a buffered line would be lost exactly when it matters. That makes logging the one accepted exception to ENGINEERING section 4's rule against blocking calls on async tasks: a line costs a write, and a few file renames when the file moves on. A panic is reported as an error line in place of the standard report (see 9). `tracing-appender` was not used: it rolls by time only, so it cannot cap the folder's size.
3. `WIRECATCH_LOG` (`LOG_FILTER_VARIABLE`) chooses the lines in every binary, in `tracing`'s filter syntax; the desktop's `RUST_LOG` is gone. A value that is not a filter is reported and the binary's default is used: `info` for the app, the bridge and the headless example, `warn` for the command-line downloader. `WIRECATCH_LOG_DIR` (`LOG_FOLDER_VARIABLE`) moves the log files, which tests use so they never write into a person's folder. Both names are generated from the product slug into `wirecatch-product` (D29).
4. Every field is redacted as it is recorded, and every finished line again on its way out, whatever logged it and at any level (see 6): the password of a link (or its user name when it has no password), every query value and fragment of a link or of a request's path (a signed link carries its token there, and a log cannot tell which links are signed), the word after an authorization scheme, every JWT, and the value of every cookie, authorization header, password, token, secret, signature, key or session, however it is written. Lines carry no colors, since a color code between a name and its value would hide the pair. This is a net, not leave to log secrets: code still logs neither cookies nor headers nor a program's arguments. The display redaction core used for links shown to a person moved into the same module, which keeps the query of a person's own link.
5. What an add-on program wrote to standard error is kept as a `StderrTail` (`wirecatch_streams::process`): its last lines up to 8 KiB, each redacted as it is kept. A run that fails is logged as a warning with its exit status and the whole tail, and a run stopped for time or silence carries the tail in its `RunError` and is logged the same way. A person's message carries only the most telling line, cut to 300 characters (`MAX_REASON_CHARS`), or the exit status when the program said nothing; `Ran` keeps the `ExitStatus` instead of a `success` flag.
6. Changed after review, 2026-10-13: the redaction was blind to how `tracing` records values. It records every `&str` field with `Debug`, which escapes the quotes a name and value are recognised by, so `info!(body)` with a JSON password passed whole, and so did `Some("..")` values and `url::Url`'s `Debug`, which `reqwest` errors carry. The subscriber now writes fields through a formatter of `wirecatch-logging`'s own (`fields.rs`) that redacts each value before `Debug` escapes it, and hides the whole value of a field whose name marks a secret (`password = %typed`); the finished line is still redacted as a second net. `redact::text_for_log` was rewritten as four passes, each linear in the line's length (a long hostile line took seconds before): the user information of every link, links inside links included and passwords holding `/`, `?` or `#`; the query and fragment of every link and of every path written alone (`GET /v?st=..`); the word after `Bearer` (and after `Basic` or `Negotiate` when it looks like a credential), and every JWT; and the value of every secret name, quoted or escaped or URL-encoded, after `:`, `=`, `%3D`, in a `Debug` tuple or struct (looking through `Some(..)`), or after a command-line flag (`--password x`, `-p x`, `--add-header`, `-headers`). A quoted or wrapped value may sit on the next line, as pretty `Debug` (`{:#?}`) and JSON put it, and an escaped quote closes a value only with as many backslashes as opened it, so the `Debug` of a `Debug` is read too. Secret names are matched by parts and endings, so `author` and `tokens` keep their values, and a value after `:` or a cookie header's runs to the end of its field (a ` / ` or another `name=`), not of the line, so the diagnostics after it stay; an authorization header's runs to the end of the line, since `Digest` writes `name=value` pairs of its own. A command-line flag secret only as a cookie would be (`--cookies`, which takes a file, `--cookies-from-browser`, a browser's name) does not hide its value: yt-dlp prints both flags in the refusal a person reads. A secret flag's next word is its value even when it starts with `-` (`--password -x`), since yt-dlp's option parser takes it so. What a secret's name is moved into `crates/protocol` with the milestone review (see 10).
7. Changed after review: a reader holding the log without delete sharing (PowerShell's `Get-Content -Wait`, a .NET reader) made every move on fail, and the file was then emptied each time it filled. The file is now moved aside before the old files shift, a failed move is tried again after another sixteenth of the limit, the file is emptied only past twice the limit, and the line is always written. Several processes of one binary (a bridge per browser, command-line runs side by side) write one file: every sixteen lines, and on every line once the file is past half its limit, a writer checks that its file is still the one at the path, follows it when another writer moved it on, and counts the bytes the file holds rather than its own. A writer follows within sixteen lines, so a few of its lines may land in a file just moved on; they are lost only if that file is deleted first, which takes the other writers logging 15 MiB in between. Checking every line past half the limit costs two `stat` calls a line for half of each file's bytes, which halves those calls rather than cutting them sixteenfold; it keeps every writer's count exact as the file nears its limit. A file a move cut short left aside is shifted up with the old files at the next move, not overwritten; when two writers move one file on at once, the one shifted up may be the other's file in flight, so one more old file is dropped and `.1` is left empty, part of the two-writer race accepted here as rare and bounded.
8. Changed after review: the bridge (run by the installer as `wirecatch-bridge install`) and the command-line downloader made `%LOCALAPPDATA%\Wirecatch\logs` before an upgraded app first started, and the app's one-time move of its data folder out of the roaming profile ran only when the local folder did not exist, so the person got an empty download list. The move now decides by whether the local folder holds the download list, never by whether the folder exists: into a folder other programs made it moves entry by entry, keeping what is there, and puts the database in place last, copied with its journal, so a move cut short leaves the old folder whole and the next start finishes it. Anything may therefore live in the local folder first, and the app opens its log there before it starts. The log file and its folders are made only with the first line that passes the filter (so `--help` and a quiet run make nothing), on Unix with mode 0700; on Windows `%LOCALAPPDATA%` is already private to its user.
9. Changed after review: the panic hook called the standard one after logging, which printed the raw message to stderr, a sink like the file. The hook now replaces it, adding the backtrace when `RUST_BACKTRACE` asks (as the standard report reads it: none for `0` or unset, every frame for `full`, whatever `RUST_LIB_BACKTRACE` says, which is for errors that capture one), and writes the redacted report to the sink directly rather than through `tracing`, so no filter can silence it (`WIRECATCH_LOG=wirecatch_core=debug` leaves every other target out); a line the thread holding the log file logs meanwhile (a panic inside the sink) goes to stderr only instead of waiting on itself.
10. Changed after the milestone review, 2026-10-13: the log's redaction and the extension's (`apps/extension/src/lib/diag`) each decided on their own what a secret is, in two lists that had drifted apart (the log kept `PHPSESSID`, `csrf`, `otp` and camelCase names such as `userKey`; the extension kept `hdnts` and `private`, and lost the credential after `X-Auth-Token: Bearer`). What a secret is now lives once in `crates/protocol` (`secrets.rs`), since the cookies and sign-in headers it names are what crosses from the extension to the app (`NewDownload::cookies`, `Header`), and the generator there is the one way a fact reaches both languages (D37.2): the secret words and endings, the cookie and authorization headers, the scheme words and the service key prefixes are generated constants, and the rules that read them (`is_secret_name`: a name is a secret's when one of its segments, split at `-`, `_`, `.` and camelCase steps, is a secret word or ends in one; `names_a_password`; `looks_like_a_credential`; `is_service_key`) are written in Rust, which `wirecatch-logging` calls, and ported into `@wirecatch/protocol`. Every sample the rules and the two redactions are tested against lives in one data file both languages load, `crates/test-support/data/redaction.json`: each with the secrets that must not survive it, its exact output on each side where a test pins one, the sides that keep it as it is, and the side that skips it on purpose with why. It sits with the Rust loader (`wirecatch_test_support::redaction`, built into the crate with `include_str!`), and `@wirecatch/protocol/testing/redaction` reads the same file for TypeScript; no test of either language keeps a sample list of its own. A new form is added there. Both apply the same rules beyond the names: a cookie or authorization header line, and a password after `:`, runs to the end of its field and over the lines that continue it; any other secret's value after `:` runs to the end of its field on its line (the line's end, ` / `, or a space before another `name=` that does not follow `;` or `,`), and after `=` to the end of its word (an `&` no `name=` follows included); after `Bearer` as a header spells it any word is a credential, after the other schemes in any case only a word that looks like one, the credential may follow on the next line, and a scheme word right after `=` or `:` counts as one; a secret's value that starts with a scheme word takes the credential too; header objects are read name first and value first; a list or object value is hidden to its closing bracket. Changed after the milestone re-check: the log missed `X-Auth-Token=Bearer abc` and a credential on the line after the scheme, and the extension hid only the first word of `X-Auth-Token: Token abc`; both forms and their variants are in the shared cases. What differs is deliberate, and a case one side skips is marked `skipped_by` in the corpus rather than left out: the log reads Rust's `Debug` (`Some(..)`, tuples, `url::Url`, pretty output) and the command lines of the add-on's programs, which never reach the extension; the extension decodes percent-encoded text up to three rounds, while the log keeps text as it was written and reads only `%22`, `%3A` and `%3D` (every query value of a link is hidden anyway); the extension hides long opaque runs (hashes, padded base64, an AWS secret key), while the log keeps them, since checksums, segment and chunk names and ids are what places a download's failure (both hide JWTs and service keys); and the extension reduces every address to its site and hides file paths and e-mail addresses, while the log keeps hosts, paths and query names, since diagnosing a download needs them, and a diagnostics entry is a short error from a page a person was on, copied as it is into a support request. A sample shaped like a provider's credential (a Stripe or GitHub key, an AWS access key id, a JWT) is stored in pieces in the data file and joined by both loaders, since secret scanners refuse such a string in a push whatever it is for; the `text` gate check refuses one written whole anywhere in the repository. A hidden value reads `***` in the log and in the `Debug` of the protocol's types, and `[redacted]` in a diagnostics entry, which reads better in a sentence. The protocol's `Header` and `NewDownload` write a hand-made `Debug` that hides the cookies and the value of every header that may carry a sign-in (anything but `Referer`, `Accept` and `Accept-Language`, the rule core's `without_sign_in` keeps), so a `?capture` in a log line shows no secret before the redaction sees it.

### D41. Who may use the local endpoint, the shell as the app's parent, secrets that never print, and one manager per download list (W4)
Decided during W4 (security hardening, IPC and bridge findings), 2026-10-13, and revised after its review (`W4I-review`) the same day. Another process on the same computer and a hostile browser extension are the threats.
1. Both ends of a local connection check who is on the other side, on both systems (IPB-9). The Windows listener no longer relies on the pipe's descriptor alone: after a client connects it reads the client's token by impersonating it for one call on that thread and reverting before anything else runs there (a failed revert ends the process, since the thread would go on as the client). It serves only the current user at the listener's own integrity level or above, outside any sandbox (a restricted token or an AppContainer's, which keep the user's SID), and refuses a client that hides who it is. A refusal is `IpcError::PeerRefused` for that client only; the listener goes on, and the desktop accepts the next client without its error pause. The same check runs behind a descriptor that lets everyone in, which the tests use to stand in for a descriptor that regressed.
2. A client must open the pipe at the identification level, as `wirecatch_ipc::connect` does. One that opens it anonymously is refused as hiding who it is. One that opens it without naming a level (plain `CreateFile`, .NET's `NamedPipeClientStream` by default) hands the server its token only once it has written; serving it would mean reading from a client nobody has checked, so it is refused too, with a message that says to open the pipe at the identification level. Beyond that, a program of the same user at the same level is served: the bridge, later the CLI, and the user's own tools that open the pipe that way. The endpoint is no boundary against them (D14; the bridge's caller check is defense in depth, not a boundary, `crates/bridge/src/caller.rs`).
3. The bridge starts the app as a child of the desktop shell only when the shell is the bridge's own account (IPB-8): the same user, at no higher integrity level. A shell at a lower level than an elevated bridge stays allowed, since the app then starts unelevated, as D25.4 wants. It opens the shell's process, then asks for the shell's id again: the open handle keeps that id from going to another process, so a match proves the handle is the current shell and not a program that got the id after Explorer restarted. Otherwise it starts the app itself, as before. The accounts are read by `wirecatch_ipc::ProcessAccount` (a `Sid` and an integrity level from a process's token), the one place the token code lives (IPB-6 consolidates the Win32 helpers later).
4. The endpoint's name carries a per-user key (IPB-10): 128 bits from the system's random source as 32 lower-case hexadecimal digits, in the file `endpoint-key` in the channel's local data folder (`%LOCALAPPDATA%\Wirecatch`; on Linux `$XDG_DATA_HOME/wirecatch` or `~/.local/share/wirecatch`; `wirecatch_ipc::key_folder`), never the registry or a folder of its own. The pipe becomes `\\.\pipe\wirecatch-app-<SID>-<key>` and the Linux fallback `/tmp/wirecatch-<uid>-<key>`; a socket in `$XDG_RUNTIME_DIR` takes no key. Nothing Wirecatch writes shows the key: an `Endpoint` prints with it as D40's `***`, and so do the Linux errors that name its `/tmp` folder, since a log keeps long hexadecimal runs (D40.10) and may be attached to a support request. Only the listener writes the key (`Listener::bind_keyed`), and only while it holds `endpoint-key.lock` in the same folder, an exclusive system lock it keeps for as long as it listens. That lock is also the guard against a second copy of the app: a copy that cannot take it gets `AlreadyInUse`, whatever name it would listen at. Under the lock the key is written aside and renamed over the old one, so a reader sees the old key or the new one, never a part, and no hard links are needed. Clients only read the key and read it again at every attempt to connect (the bridge's start-and-retry loop does); no key is `IpcError::NoEndpointKey`, which the bridge treats as not running, so a client that sees other folders than the app (a browser from an app store, a snap or a flatpak) never makes a key the app does not read: it gets an error that names the folder it looked in. A key file that is damaged is refused by clients and replaced by the listener, which no other listener can be using while it holds the lock. One that is a link, not a plain file, another account's, or (Linux) readable by others is refused by both and never replaced, since someone else put it there. The listener writes the key with the user named as its owner and a protected access list that lets in the user alone, whatever the program's default owner: an elevated program, and every program of an administrator with UAC off (GitHub's Windows runners run that way), gives what it creates to Administrators unless it names an owner, and every later run then refused that key, the listener's own included. On Windows a key that Administrators or the system own is still the user's (a key an earlier elevated Wirecatch wrote is one). That opens nothing: Windows lets a program give a file only an owner its token holds as one, its user or a group it holds enabled with the owner right, so only an elevated administrator, the system, or a program with the restore privilege (administrators and Backup Operators hold it) can make such a file, and each of those can already read and write the user's files, the key included, and run code as the user. An unelevated program of the user holds Administrators only to deny, so it cannot, and does not need to: it can write the key as the user anyway (item 2). Another account without those rights can do neither. The pipe's owner check stays exact, since the listener always names the user as the pipe's owner. Linux takes no such exception: a key root wrote in the user's folder is root's alone to read, and running Wirecatch as root on the user's folders is not supported.
5. Switched on after W5 made the desktop's data migration decide by the data it finds rather than by whether the local data folder exists (2026-10-14). The app listens with `Listener::bind_keyed(CHANNEL, &Folders::of_user(CHANNEL)?)`, and `wirecatch_ipc::endpoint_for` (so `endpoint`, which the bridge uses) reads the key from the same folder; no name without a key is left, and the bridge treats every name as keyed. `Folders` names both places an endpoint is found from, the key folder and on Linux the runtime folder, and `Folders::of_user` alone reads them from the environment. Tests and tools pass folders of their own: the runtime folder used to be read inside the crate whatever key folder a caller named, so on Linux every keyed test listened at the session's one socket, the tests reset each other's connections, and a developer's tests reached their running Wirecatch Dev (W4 milestone review M1). The app takes its endpoint before it moves an earlier version's data folder, so the local folder may already hold the key and its held lock, as it may already hold logs (D40.8): the move goes into it entry by entry and leaves both where they are. Upgrading: a bridge started before the key exists finds none, which counts as not running, so it starts the app, which writes the key, and reads it again. An app from before the key that still runs after an update (a Linux package update leaves it running; on Windows the installer closes it first) never writes one, so a new bridge reports `NoEndpointKey`, whose advice is to close Wirecatch and open it again. A bridge from before the update looks only at the old name and says the app did not respond; it lasts only until the extension's next connection, which starts the new bridge. The app does not also listen at the old name for such bridges: that is the name any account can take first, so keeping it would keep the denial of service this decision removes. On Linux's `/tmp` fallback an app from before the key holds no lock the new one takes (neither the key's nor, before D41.8, the download list's), so only the single-instance plugin, which needs the session bus, keeps the two apart; nothing with the old name was released, so the app does not also look for the old socket's lock, which would be code kept for development builds alone.
6. The key stays fixed; it is renewed only when the name it gives is found taken by someone else, under the lock. A name stays secret only until someone sees it. On Windows any account can list `\\.\pipe\`; on Linux the `/tmp` fallback is worse, since `ls /tmp` shows every folder's name to everyone, and `/tmp` is emptied at reboot, so an account that saw the name once can create the folder first after every reboot. A listener that finds its keyed name held (the pipe by another account, or the `/tmp` folder not the user's own and private; no copy of ours can hold it while we hold the lock) writes a new key and listens with that, so taking the name costs the squatter a key it saw once and never keeps Wirecatch from starting, while the name stays the same across ordinary restarts. A client that reaches a squatter gets `WrongOwner` and sends nothing; the bridge then starts the app as it does when nothing listens, since that start is what renews the key, and reads the key again until the budget runs out (then it says another account holds the name). A new key at every start was rejected: without a lock it lets a second copy bind a new pipe and two managers open one list, and it changes the name at every restart for no gain against a squatter, who can only deny service.
7. A value that grants access does not print (IPB-11). `wirecatch_protocol::Secret` crosses the wire as the plain string (`#[serde(transparent)]`, TypeScript `string`), prints `"***"` under `Debug` (D40's `HIDDEN`, the one mark for a hidden value in what Rust writes), has no `Display`, and is read with `expose()`. It holds `NewDownload::cookies`, every `Header::value` and the headers yt-dlp reports for each format and subtitle (which carry the page's cookies). Every header value core builds for the engine is marked sensitive, so the engine's `DownloadOptions` prints none. `NewDownload`'s `Debug` shows its addresses without the user name and password they may carry, and so does `wirecatch_protocol::Link`, which holds the links the person gives the app (`AddRequest::url`, `refresh_link`'s `url`) and is `type Link = string` in TypeScript; text that is not an address with a host is shown only when it has no `@`, and an address whose sign-in could not be removed prints nothing of itself. The CLI names a refused `-H` header without its value and repeats a refused link only when it has no `@`. Not covered: a token in a link's query string (a signed link) prints with the link, and a malformed request's error answer still quotes what serde could not read, which goes back only to the client that sent it. These additions change no type on the wire, so D32 raises nothing.
8. One manager at a time opens a download list. Opening it first takes an exclusive system lock on `wirecatch.db.lock` beside the database, before anything touches the files, and the database thread holds it until its connection has closed. A list another manager keeps is refused with `CoreError::AlreadyOpen` after waiting two seconds in the system's own lock call, for a manager that is still closing. The endpoint used to be the only guard, and a copy that could not claim it for another reason (an unelevated copy beside an elevated one, whose high label refuses the probe, or a name another account holds) went on and opened the list: two managers then overwrite each other's rows, and the second one's start can set the first one's live file aside as damaged. The system releases the lock when a process ends, however it ends, and it holds across processes with different rights. On an NFS mount Linux emulates the lock with per-process locks, so there it does not refuse a second open within one process; the app never opens its list twice. A copy refused this way shows the same "already running" window as a copy refused at the endpoint, and closes; once the app listens with `bind_keyed`, the key lock refuses such a copy first, through the same window.

### D42. The JavaScript lint and format tools live at the root, and ESLint still runs once per package
Decided by the maintainer on 2026-10-14, to keep one copy of the lint and format setup instead of one per package. D34 to D41 are taken by work on other branches.
1. ESLint, Prettier and `prettier-plugin-svelte` are installed once, by the root `package.json`, at the versions in the catalog. A package lists one of them only when its own code loads it: `@wirecatch/eslint-config` runs ESLint's rule tester, and `@wirecatch/protocol`'s generator formats with Prettier, which loads the Svelte plugin the root `.prettierrc.json` names. Every other package lists `@wirecatch/eslint-config`, which its `eslint.config.js` imports.
2. `pnpm lint` and `pnpm format` are root scripts only. `lint` runs ESLint in every workspace package (`pnpm -r exec`, in the package's folder), then on the root's `scripts/`, then Prettier once over `apps`, `packages` and `scripts`. `js-policy` requires that script exactly, built from the folders in `pnpm-workspace.yaml`, so a new folder of packages cannot be left out, and fails on a package with a `lint` or `format` script.
3. Each package keeps its own `eslint.config.js`. The rules stay in `packages/eslint-config`; a package's file holds only what is its own: its globals, its build folders, and the boundaries between its layers (the desktop app's rules about who may call Tauri and the backend). Moving those to the root would make the root know every package's folders, and put a package's boundaries in a shared file its work package may not edit (PLAN).
4. Prettier run from the root reads only the root `.gitignore` and `.prettierignore`, so every ignore rule lives there, with the package folder in front; the packages' own `.gitignore` and `.prettierignore` files were folded in. `js-policy` fails on another one in a folder Prettier checks. Prettier checks the same 479 tracked files it did before. Unlike the layer boundaries in point 3, this puts something a package owns into shared files: a work package that adds a folder to ignore proposes the line in its report, as for any shared file (PLAN). That is accepted because ignore rules change rarely, the root `.gitignore` already held most of them, and the alternative, an ignore file in a package, is one Prettier would silently not read.
5. ESLint is not run once over the whole repository, though that was tried and would start one process instead of seven. In one process, once a file of one package has been linted, even a script linted without type information, `.svelte` files of another package lose the types of `$props()` and of their template's event handlers, and the type-checked rules report them: 134 false errors in the two apps (ESLint 10.12.0, typescript-eslint 8.71.1, svelte-eslint-parser 1.9.0). The configuration ESLint computes for those files is the same either way, and the state survives between ESLint instances, so it is held inside the parser libraries. The smallest case, from the root: `eslint scripts/gate.mjs apps/extension/src/components/SwitchRow.svelte` reports three errors that `eslint apps/extension/src/components/SwitchRow.svelte` does not. Revisit when that is fixed upstream.

### D43. A window's page is not trusted with what its commands can do (W4)
Decided during W4 (security hardening, desktop findings DRS-4 and DRS-5), 2026-10-14. The threat is a script that gets into a page: the download windows show file names, page titles and links that websites chose, and a bug in the interface or a dependency could one day let such text run. Whatever that script can call, the page can call, so the shell decides the dangerous parts itself. The main window shows the same names and links but stays trusted with every command it uses and any download: it is the person's view of the whole list and of settings, so a capability cannot narrow it without taking its job away. What protects it is that no site's text runs as code there (the content security policy allows only the app's own scripts, DRS-18) and, still to come, that its path commands take only a path the shell's own picker returned (item 4).
1. A downloaded program opens only once the person agreed to a warning the shell shows in a dialog of the system's own (DRS-5). `open_file` takes only the download; when `is_program` says the file can run code, the shell shows a warning over the calling window that names the file and its type as they are on disk (or says the file is marked as a program) and the site it came from (`site_of`, read with `url::Url`), with Open and Cancel, and opens the file only on Open. Cancel, Escape and closing the dialog open nothing and are not an error. The page used to show its own question and send `allow_program: true`, which any script could send without asking, and a one-time token from `is_program` would not help: the same script can ask for it. `is_program` is gone from the contract, since the page no longer needs to know. The sample backend asks with the browser's `confirm`, its equivalent of a dialog no page can answer. A script in the page can call `open_file` without a click and as often as it likes, so the warning can come up unprompted. While one warning is up for a download, `open_file` for it raises no second and opens nothing (`WarningsShown`), so a page cannot stack warnings. The dialog's default button is Open, accepted for a platform reason only: the system dialog makes the first button the default (rfd offers no other), and the dialog plugin reads a dismissed dialog as its second button, so putting Cancel first would open the file on Escape. A page that raises the warning while the person presses Enter could therefore have it answered Open; making Cancel the default needs a default-button option in the plugin or a dialog of the shell's own, and is carried in [AUDIT](AUDIT.md).
2. Each window calls only the commands its capability grants (DRS-4). The build script hands Tauri every command of the contract (`COMMAND_NAMES`, through a build dependency on `wirecatch-protocol`), so each one needs its own `allow-<command>` permission, and it removes the permission files of a command the contract dropped. `capabilities/default.json` grants the main window every command but the nine only a download window uses (its question, its download, and closing and fitting itself); `capabilities/download-windows.json` grants a download window the 26 it calls (item 6), and none of what adds downloads, lists or reorders them, edits queues, reads or writes a settings file, or manages add-ons beyond installing the media add-on. `tests/windows.rs` asks the app's real capabilities, command by command, from a main window, a question window and a progress window. A command added to the contract is refused everywhere until a capability names it, so a new command fails loudly in that test rather than opening to every window. The test lists what a download window may call and expects every other command on the main window only, so granting the download windows more means editing a list a review reads.
3. Within those commands a download window acts only on what it shows (DRS-4). A command that takes a download or question id refuses one that is not the question or download the window shows now, by the registry of download windows (`may_act_on`), and `remove` checks every id. `change_settings` from a download window may change only the two settings it shows: whether browser downloads start without asking, and whether progress windows open (`may_change`). The main window is not limited. The commands are generic over the runtime, so `tests/windows.rs` runs each of them from each kind of window on the mock runtime, and a command that loses its check fails a test. Commands without an id, acting on the window's own download, were the alternative; they would double the commands a download window calls, and the registry already knows what each window shows.
4. Not covered yet: the commands that take a path accept any path the page names, in every window. A download window names the folder for its own download (`set_download_folder`, and the folder in `confirm_capture`), so a script in its page could save or move the site's file into a folder that runs what it holds (a Startup folder). The main window's `export_settings` writes, and `preview_import` and `import_settings` read, any path, and its `set_download_folder` moves any download. The page got each path from the folder or file picker, but nothing checks that. The fix: a command that takes a path accepts only one the shell's own picker returned to that window (or a folder the settings already name), in every window. It is carried in [AUDIT](AUDIT.md).
5. Not covered yet: a download window reads every setting (`get_settings`, and the `settings_changed` event every window gets), and `refresh_link` fetches whatever link the page names for its own download, any but a finished one (queued, running, paused or failed). A script in that page could send the local site names (D39) and the folders, which hold the user name, to a host of its choosing. Settings hold no credentials. Narrowing it needs a projection of the settings for download windows, in the command and in the event; it is carried in [AUDIT](AUDIT.md) with item 4. Such a link no longer lifts D39's guard (W4 milestone review M3): `refresh_link` used to make every new link the person's, so a script in a website's download window could point its download at a router or a NAS and have it run under `Auto`. Now core takes where the link came from (`LinkFrom`): only the main window's is the person's (`Person`); a download window's keeps the rule of whoever chose the download's link (`SharedPage`), so a website's download stays under `Block` whatever link its page names. A download the person or a local page chose keeps `Auto`, so a script in its window could still point it at a host on the local network; the cure is the one item 4 needs, a value the shell itself asks the person for, and it is carried with item 4. `tests/windows.rs` gives a website's download a local link from its own window, which is refused before it starts, and from the main window, which runs.
6. Amended on 2026-10-14, merging the interface revamp (D36) into W4's rules. A download window also gets `system_appearance`, the system accent its page follows, and `core:window:allow-start-dragging`, so its frameless title bar drags it (Tauri's `data-tauri-drag-region`; Linux needs the permission, Windows also drags by the CSS app region). `core:window:allow-internal-toggle-maximize`, which Tauri's drag region sends on a double-click, stays the main window's: a download window cannot be maximized, and Tauri's window commands take any window's label, so it would let a download window's page maximize the main window. The same label argument lets that page start a drag of another window, which follows the pointer only while a mouse button is held; accepted. The main window also gets the revamp's commands: its caption buttons and frame (`control_window`, `window_frame`, `set_maximize_button`), `system_appearance`, `startup_notices`, `show_set_aside_list` and `take_captured`. `tests/windows.rs` holds both lists, the window permissions included.

### D44. The app keeps its own Public Suffix List current while it runs (W4)
Designed by the maintainer for W4 on 2026-10-13 and recorded with its implementation on 2026-10-14. D35 kept a list current only at each release; the list changes almost every week, and a suffix added since the release is unknown, which fails open (D35.2).
1. The app owns its list. A snapshot of publicsuffix.org's file, as published (`VERSION` and section markers included), is built into each release as `crates/core/data/public_suffix_list.dat` and read with the `publicsuffix` crate, the reader for lists loaded while a program runs by the author of `psl`, with the same lookups. `psl`, which core used before, compiles the list into code, so it can neither be replaced while the app runs nor be measured or dated against a newer copy. Every decision core makes about sites asks the list its manager holds (`SuffixList` in the manager's state, never a process-wide one): whether an entry of `local_sites` is one owner's (D39.4), whether a single label is a top-level domain (D39.1), and whether a listed site still counts, which it does only while the list in use says it is one owner's. A newer list that makes a listed site public drops it from the stored settings at once, as a start does (logged by its place in the list, and sent to the windows as a settings change), so the settings keep passing their own checks and every other setting can still change.
2. `AppSettings::update_suffix_list`, on by default (and read as on from older settings), turns the weekly check on. A profile written before the setting existed leaves the choice made here: turning the refresh off is a privacy choice, and an import must not undo it unasked. The check fetches `https://publicsuffix.org/list/public_suffix_list.dat` (`PUBLIC_SUFFIX_LIST_URL`) through the engine's fetcher with the app's user agent (`headers::download_options`), `PrivateNetwork::Block`, at most 2 MiB (`MAX_LIST_BYTES`; the file was about 330 KB in 2026) and two minutes for the whole request. It is due a week after the last check that ended with the newest list in use (a newer one taken, or none found), a day after one that did not, and, before any check, once the list in use is a week old; a check recorded after the clock's time ran while the clock was ahead and is due at once; the last check is kept in `public-suffix-check.json` in the data folder. It runs only while no download runs; the manager looks every hour, the first time an hour after it opens. Two checks never overlap, and whether the weekly one is due is decided once no other check runs, so one that waited for a Check now does not fetch again. A manager fetches nothing unless its configuration names a source (`ManagerConfig::with_official_suffix_list`, which the desktop app calls), so no test reaches the internet.
3. A downloaded list takes the place of the one in use only when it is at most 2 MiB, UTF-8, has its four section markers in order (the last one closes the file, so a transfer cut short is refused), says when it was published, every rule reads, holds at least nine tenths of the rules of the list in use and of its ICANN rules (so private rules cannot stand in for lost ICANN ones), at most twice its rules, says it was published no later than a day after the clock's time, and is newer than the list in use. A list far larger or dated ahead would otherwise stay in use for good, every real list after it looking much smaller or older, through updates of the app too. It is then written beside the kept one, flushed and renamed over it (`whole_file::replace`, which the add-on record uses too), and only then used. Anything else (no answer, a refused list, a list that could not be saved) keeps the list in use, is logged, and is told to a person who asked. At start the kept list goes through the same checks against the built-in one and the clock, and is used only when newer than the built-in one, which an update of the app may bring.
4. Settings, Advanced: "Keep the list of public domains up to date", with the day the list in use was published, when it was last checked, and Check now. Check now (`check_suffix_list`) checks whatever the setting says, since the person asked; with the setting off nothing else is fetched. Every check, the weekly one included and whether it worked or not, ends with `UiEvent::SuffixListChecked`, so an open settings page stays current; `SuffixListInfo::check_failed` makes the note say the last check failed. The setting's help is the privacy note: the request names Wirecatch and its version and carries nothing about the person's downloads or browsing, and publicsuffix.org sees the IP address.
5. D35 is the floor at release, here too: before a release, `crates/core/data/public_suffix_list.dat` is replaced with the file publicsuffix.org then serves, and the core tests read it whole. No check enforces that yet; a `publish` check of its `VERSION` date, like `suffix-list` for `tldts`, is the proposal.
6. Carried, not done: which cookies go with a captured download is still decided in the extension, from `tldts` (D35), since the extension alone sees each cookie's `SameSite` and the request's context, so the list kept current here does not yet reach that decision and the two lists can disagree. What it needs: the extension sends every cookie the browser holds for the download's address with its `SameSite`, and the request's context (the page's site, whether it is a top-level navigation, the method); that is a protocol addition, a new protocol version under D32 that an older app must still be served by; and core filters the cookies with the list its manager holds. It needs a unit that owns `apps/extension` and `crates/protocol`; it is carried to W13 (the extension), listed in [AUDIT](AUDIT.md) under the parts of W4 carried, and W4 lands without it. Until it lands, the extension's list is current at each release only (D35).

### D45. Every window is opaque, in its scheme's base colour from its first frame
Decided with the maintainer on 2026-10-21, as the first step of the interface redesign, after they saw each window appear white, then in the wrong style, then right. It replaces the system material of D36.2 and D36.10.
1. The cause: a window built transparent for Mica or Acrylic is empty when Windows first shows it, since Windows paints the material only once the window is on screen, and it drops the material to a flat colour whenever the window loses the focus and paints it again when it comes back. The search names the view it searches in its placeholder, with no chip, and while settings show it searches settings, in place of a second search field on that page.

The sidebar (amends D47.7) lists every status view at every count, so it never reflows; a queue's own actions are one "…" menu; Settings is a labelled item at its foot beside the palette and shortcuts icons; and the downloads waiting for an answer moved to the title bar, as a bell with their count in a slot that is always there, so nothing moves when it comes and goes.
6. The details (amends D47.5) keep the main action, Show in folder and Remove at their foot, with the download's own window, Copy link and Cancel download behind "…". Their facts are each said once: when it finished, its size while nothing of it is downloaded, its kind of file by extension ("ISO file"), and when it was added; where it waits in line is the line under its status. The speed graph keeps headroom above its peak, draws its baseline and says its peak and average.
7. Settings (amends D47.8) are the design system's setting rows. Media's settings sit under Videos and Audio only; the total speed limit, downloads at once and connections per download are together in Speed and limits; queues are a list with their hours and limits; every section says what it is in one line.
8. The queue editor turns each limit on with a switch that opens its fields, steps numbers, types times in the app's 24-hour form (Up and Down step a quarter hour), picks days as Every day, Weekdays, Weekends or single days, and asks before deleting with how many downloads move and where.
9. The download windows word their two options as Settings does ("Don’t ask again for files from the browser", "Keep the window open to show progress"), keep their buttons right-aligned at their own width, offer subtitles in a searchable list rather than a scrolling box (two that read alike told apart by their language code), and ask "Install the media add-on?" with the size on its button. The quality window is short whatever a video offers: Quality, Save as and Subtitles are one line each, the quality a searchable select whose options end with what sets them apart (Best, a conversion it needs, the size when known), the subtitles a searchable multi-select (`MultiSelect`; a page may offer dozens of languages); what a choice costs (an add-on to install, a conversion) is a one-line note, the source site goes with the title, and where the file goes folds into a line that says it (`Disclosure`); no download window grows past `DOWNLOAD_WINDOW_MAX_HEIGHT` (680px), beyond which its body scrolls; a window opens with its main button ready for Enter but no ring drawn until the keyboard moves. A quality names its format as Save as does ("2160p, WebM"), in the core and the app alike.

### D49. Release builds warn of placeholders; only publishing refuses them

Decided with the maintainer on 2026-10-22, who could not build an installer or a store package to try while the publisher's details are undecided. It amends D29.6.

1. Building is not publishing. The desktop `bundle` script (`prepare-bridge.mjs --release`) and the extension's `pnpm build:store` run the gate's `release-build` group (`release-build-extension` for the extension, which adds `suffix-list`, D35): `product` still fails when a generated file is out of date, and `product-placeholders-warn` prints which placeholders the build carries, says it is for testing only, and lets it go on.

### D50. A video can download with the saved choices, without asking

Decided with the maintainer on 2026-10-22, who saves a preference so a video simply downloads, and wants the quality window again only when the resolution they want is not there. It amends D23.3 and D24.4 and D24.8.

1. Settings, Media, Videos leads with "When a video is caught: Ask each time, or Use my choices" (`MediaDefaults::ask_each_time`), separate from "Show a window before each download", which keeps governing files. It applies to every video the core reads for a quality: browser captures, the extension's video button, and since D51 a video page added in the app.
2. The saved choices are the window's last choices (D24.8) plus a resolution (`VideoQuality`: Best available, a height, or Audio only) and what to do when a video lacks it (`QualityFallback`): the next lower (the default; the lowest when none is lower), the next higher (the best when none is higher), or Ask me, which opens the window on the next lower. A video that does not say its heights, or is audio alone, starts on its best option and never falls back.
3. Only the resolution can open the window. The format converts when a quality lacks it; each saved subtitle language takes its creator's subtitles, else its auto-generated ones, else none, never another language; chapters are added when the video has them. Leaving auto-generated subtitles unticked in the window no longer makes them unwanted, and they are wanted by default.
4. One rule decides where a video starts and whether it asks: `MediaDefaults::start` in the protocol crate. The core sends its answer with the choice (`MediaChoice::start`, and `missing_quality` when the saved resolution is not offered, which the window says), and downloads it without asking when it may. The desktop's sample backend uses a TypeScript port tested against cases written from the Rust (`fixtures.json`), so the window holds no copy of the rule.
5. Without asking, a video is read without a window (no `MediaAnalysing`), and its download is announced as a capture, as a file started without asking is (D36.7). The window still opens when the fallback is Ask me, when the media add-on must be installed first (installing needs the person's yes), and when the download cannot be added as chosen. A row picked by the fallback records the resolution it stands in for (`MediaSummary::instead_of`), and its details say "720p, from a video page. 1080p wasn’t offered."
6. The window's "Use these choices for every video" goes with its answer (`MediaSelection::every_video`): ticked, the next video does not ask; unticked, it does. Every pick from the window becomes the saved resolution, except from a video that lacked the saved one, and except picking the very quality the saved one chose, so Best available stays Best available.
7. Settings offers subtitle languages as a searchable list of every ISO 639-1 language, named by the system, instead of typed codes.

### D51. A video page added in the app is read for its video

Decided with the maintainer on 2026-10-22, who pasted a YouTube link into Add downloads and got the page's HTML. It amends D50.1.

1. A link added in the app (the Add dialog, a paste, links from the command line, which all go through the Add dialog) to a known video page is read for its qualities like a page from the browser (`Manager::add_video_page`): its window asks, or it downloads with the saved choices (D50), in the queue and folder chosen, paused when added paused.
2. The known video pages are one list for both apps, `VIDEO_SITES` with `videoSiteFor` in `packages/protocol/src/video-sites.ts`, which the extension's video button used to keep alone: each site's hosts, and the paths of its pages that show one video, so a home page or a search page is never taken. The person adds sites of their own in Settings, Media ("More video sites", `ExtensionSettings::video_sites`, any page but the home page), and both apps take them with the list.
3. Any other link starts as a plain download. When its server first answers with a web page while the media add-on is installed, the download gives way to reading that page (`Stop::ReadAsVideo`): a video found asks or downloads as above; none found, the page downloads as the page it is, without reading it again. This covers every site the media add-on reads, about 1,800, without a list of them, and costs a plain file nothing. Without the add-on, such a page downloads as before.
4. `video_sites` is optional in TypeScript, so an extension reads the settings of an app from before it, as `frame_url` was added (D32.5).

### D52. Each queue says when finished downloads are told, and one setting says how

Decided with the maintainer on 2026-10-22, who found a pop-up window out of nowhere too much and nothing at all too little, and wanted to be told once when a batch of downloads is done, not for every file. It amends D23 (a progress window closes by itself) and D43.2 and D43.3 (what a download window may call and change), and replaces `notify_on_complete`.

1. How is one setting for the whole app, "When a download finishes" (`AppSettings::finish_notice`, `FinishNotice`): a notification (the default), the download complete window, or nothing. The database's migration turns the old switch into the new setting (on became a notification, off nothing), and so does importing a profile written before it.
2. When is each queue's (`Queue::notify`, `QueueNotify`): each time one of its downloads finishes (the default, as before), or once the queue is done. Settings, General names the default queue's choice under the dropdown, with a link to change it, so a person who never makes a second queue still finds it. A choice for the whole app that queues may override was rejected: the same choice in two places, with rules for which wins, for a case per-queue choices already cover. "Done" for the whole app was rejected too: a queue scheduled overnight would hold back the news about three files downloaded now.
3. A failed download is told at once, whatever its queue's choice, once the engine's own retries are spent; a failure needs the person, and waiting for the queue would hide it. Downloads ending within three seconds of each other share one notice (`NOTIFY_BATCH`), and finished and failed ones never share one. A queue that tells once it is done counts its failures in that summary too, so a failure there is told twice, at once and with the rest; the summary is what the queue came to.
4. A queue is done when none of its downloads downloads or waits to start (`Queued`, `Connecting`, `Downloading`, `Processing`). A download the person paused does not hold its queue open; a paused queue, or one waiting for its schedule, is not done. The core keeps each queue's batch (`crates/core/src/batches.rs`) from the rows that change, so a progress tick costs nothing per download in the list; it sends `UiEvent::QueueFinished` with what finished and what failed since the queue last started working, cancelled and removed downloads left out, and nothing when nothing finished or failed. The batch is saved (`queue_batches` in the settings table), and shutdown records the rows the stopped ticker would have seen, so what finished before a restart still counts. A saved batch whose queue has nothing left at the next start is dropped: nobody listens yet to be told. A run of one download reads like that download's own notice. Only a change of status ends a download: one that already ended and is moved to another queue (by hand, or because its queue was deleted) starts no run there.
5. Notifications are the system's own, with buttons: Open and Show in folder for a finished file, Try again for a failure that trying again can fix, Show in folder (all in one folder) or Show in Wirecatch for several. Clicking the notification itself never opens a file, since people click a notification to dismiss it and the file may be a program; it shows the main window with those downloads selected, in their queue for a queue's summary (`REVEAL_EVENT`, or `take_reveal` for a page still loading). Open goes through the same program warning as the windows (D43.1). Windows shows toasts through the `windows` crate under the app's identifier, registered for the current user (`HKCU\Software\Classes\AppUserModelId`, with the name and an icon) so a debug build, which has no Start menu shortcut, shows them too, and the uninstaller removes it for the account running it; every text is escaped into the toast's XML, since file names come from websites. Tauri's notification plugin is gone: it could not show buttons or report a click on Windows. Linux sends them to the desktop's notification service with actions (`notify-rust`), off the async threads; a service without actions shows the text. Waiting for a click holds a thread until the notification closes, which a desktop that keeps notifications in its history may never do, so at most 16 wait at once (`MAX_WAITING`); past that a notification shows without buttons. Known limit: a click reaches the app through the toast's own handler, kept for the last 32 toasts while the app runs; a toast clicked in the notification centre after the app restarted does nothing. A COM activator would cover it and is not built.
6. The download complete window is one small window at the bottom right of the main screen, a download window by its label (`download-finished`), which opens without the keyboard focus and stays until the person closes it. What finishes or fails while it is open joins it, the newest first: downloads told one by one share a group, and a queue's summary is a group under its own heading. It keeps at most `MAX_FINISHED_GROUPS` groups of `MAX_FINISHED_LISTED` downloads; a queue's heading counts the rest. One download gets the room, with Open as the main button. "Use notifications instead" switches the setting in one click. A browser download whose progress window is open is not added: in this mode its progress window stays when the download finishes, and takes the complete window's place for it.
7. The complete window may call one command more than a progress window, `finished_list`, and acts only on the downloads it lists (`may_act_on`). Of the settings it changes only `finish_notice`, and only to a notification (`finished_window::may_change`): a script in a page showing a website's text must not be able to silence failures. The main window gets `take_reveal`, and takes a waiting selection only once its list is loaded.
8. Not built now: a sound of Wirecatch's own (the system's plays, and Do Not Disturb silences it), an action once every download is done (sleep, shut down or quit), which needs its own design, and a choice per download.

### D53. CI runs the tests in parallel: browser checks in their own job, Rust tests under cargo-nextest

Points 2 to 4 were reversed by D58.

Decided with the maintainer on 2026-10-23, when a CI run took 10 to 16 minutes against about 7 a week earlier. It amends D33.2 and D33.4.

1. The browser checks (`e2e-gallery`, `e2e-desktop`, `e2e-extension`) are the gate's `browser` group, apart from `js`, and CI runs that group in a Browser job of its own on both systems, alongside the others and without Rust. Their Playwright specs run fully parallel: each test has a browser context of its own and the desktop's mock backend lives in the page. On one worker they had made the JavaScript job three to four times longer.
2. The `test` and `test-http3` checks run the tests under cargo-nextest (`cargo nextest run`), still one build of every crate in one feature resolution, so each test runs in a process of its own and the test binaries run at once instead of one after another. cargo-nextest does not run doctests, so `cargo test --doc` follows it with the same crates and features.
3. Tests that must not overlap across processes are named in `.config/nextest.toml`: the protocol crate's TypeScript exports, which share files that ts-rs guards only within one process. Names a test makes for folders, pipes and files carry the process id, so they stay apart. Tests that start the bridge take the one the workspace test build made, with its test-only overrides (`crates/test-support/src/bridge.rs`, which the gate points at it): each e2e process building its own, as it did when one binary ran at a time, would relink the executable other processes are running. With `--no-fail-fast`, the doctests run even after a test fails. Nothing is retried. A test binary without the standard harness answers nextest's listing itself (`crates/logging/tests/panics.rs`).
4. cargo-nextest is in `TOOLS` in `scripts/gate/rust.mjs` with cargo-deny and cargo-machete, and the Rust jobs install it the way D33.4 installs those: a prebuilt release binary through `taiki-e/install-action`. `node scripts/gate.mjs --install-tools` builds it for a developer machine, and `pnpm gate` says so when it is missing.

### D54. Linux CI tests with the media add-on's own ffmpeg

Decided with the maintainer on 2026-10-23, when installing ffmpeg's hundred or so packages from Ubuntu's mirror took 49 minutes of one run (106 MB at 36 kB/s) and minutes of several others.

1. The Linux Rust job no longer installs ffmpeg with apt. It downloads the build the media add-on installs (`BtbN`'s LGPL shared build), from the add-on's pinned address, and checks it against the add-on's pinned SHA-256: `cargo run -p wirecatch-core --example ffmpeg_release` prints both from `crates/core/src/addons/manifest.rs`, so CI holds no second copy. The tests that need a real ffmpeg (`WIRECATCH_TEST_FFMPEG`, required in CI) now run the ffmpeg people get from the app, not Ubuntu's.
2. `actions/cache` keeps the unpacked build until `manifest.rs` changes, so a run downloads nothing and builds no example unless the pin may have moved. The download comes from GitHub's own release storage, not the Ubuntu mirror.
3. The WebKitGTK packages the desktop crate links against still come from apt, from the cache or the fastest mirror (D55).

### D55. Linux CI never waits long on an Ubuntu mirror

Decided with the maintainer on 2026-10-23, when the WebKitGTK packages alone, without ffmpeg (D54), took 20 minutes to install from Ubuntu's Azure mirror. It replaces D54.3. Every GitHub-hosted Linux runner without a fee pulls from that same mirror, so another runner would not help; larger and self-hosted runners cost what the project does not spend (no budget before the first release).

1. The packages are listed in `scripts/ci/linux-packages.txt` and installed by `scripts/ci/linux-packages.sh`. `actions/cache` keeps their .deb files per runner image (`ImageOS` and `ImageVersion`) and list, so a run on an image that installed them before installs them with dpkg and downloads nothing.
2. A run that misses must still never wait long, so a cache alone was not enough. Each official mirror in the script's list gets a parallel probe of 10 seconds on the first 10 MB of a large file every mirror carries. The mirrors are then tried fastest first, each with 120 seconds for its package lists and 120 for the packages, and a file that sends no data for 15 seconds counts as a failure. A mirror that runs out of time gives way to the next, and what it downloaded is kept. apt reads only the source list the script writes, so another repository on the runner cannot hold it up.
3. The wait is bounded: 10 seconds of probing, then at most four minutes for each mirror that fails before one delivers, a mirror that is slow from the start is tried last, and the step stops after 10 minutes whatever happens (D57). Any mirror is safe to use, because apt checks every file against Ubuntu's signed archive index.

### D56. Every build uses the latest stable Rust

Decided by the maintainer on 2026-10-23. `rust-toolchain.toml` names the `stable` channel instead of a fixed release, for local builds, release builds and CI alike.

1. CI installs the newest stable on every run (`rustup toolchain install` reads the file), and a developer brings theirs up to date with `rustup update`. The Docker script (`scripts/linux-test.sh`) starts from `rust:bookworm` and installs the same.
2. A new stable release can bring lints that fail `clippy` with no change of ours; the first run after a release shows them, and they are fixed in the next commit, as any other gate failure. The engine's promise to older compilers is unchanged: the `msrv` check builds it with the `rust-version` its manifest states.
3. A new release changes the Rust cache keys (the toolchain is part of rust-cache's environment hash), so the first run after one builds from an empty cache.

### D57. Every CI job has a time limit, and the Linux job clears no disk

Decided with the maintainer on 2026-10-23, after a run that spent most of an hour waiting on a mirror.

1. Each job's limit is well above its slowest healthy run, so a stall fails in minutes instead of holding a run for an hour: Rust 20 minutes (room for a build from an empty cache, which every new stable release brings, D56), JavaScript and Browser 15, supply chain 10. Installing the Linux system packages has a limit of its own, 10 minutes, on top of the deadlines inside it (D55).
2. The Linux Rust job no longer deletes the image's Android, .NET, Haskell and CodeQL folders, which took about two minutes of every run. The runner now starts with 86 GB free and the whole job uses about 10; the step dates from images with about 14 GB free (D33). The disk margin warning stays.

### D58. The Rust tests run under cargo test again

Decided by the maintainer on 2026-10-23. It reverses D53.2 to D53.4, which were adopted without measuring them on CI's runners or weighing other ways to shorten the Rust job.

1. On the four-core Windows runner, cargo-nextest shortened running the tests from 151 to 113 seconds, and the run as a whole was no shorter: building dominates that job. It cost a pinned tool in every Rust job, a configuration file, a listing reply in the `panics` test, and more load on the runner, under which a known flaky test (`resumes_after_pause_without_downloading_again`, W6) failed again.
2. The tests run in one `cargo test --workspace` as D33.2 describes. What D53.3 added for the bridge stays, because it holds without nextest too: the tests that start the bridge share one helper (`crates/test-support/src/bridge.rs`), and the gate points it at the bridge the workspace test build made, so they neither build nor relink a second one.
3. Other ways to shorten the Rust job (a faster linker on Windows, clippy in a job of its own, a Dev Drive) are measured on a branch and weighed against each other before any reaches main.

## Assumptions (not yet confirmed)

- A1. No cloud sync of settings in v1; export/import covers moving PCs.
- A2. Target user is the mainstream user who wants it to just work, with power features discoverable rather than hidden.
- A3. License identifier is `GPL-3.0-only` (not "or later"). Easy to change before the first outside contribution.
- A4. SFTP is not part of "FTP" for v1; it can be added later.
- A5. Firefox add-on id is `extension@wirecatch.app`. The Chromium id is `chdgnmpjoipbgfeldicipccjjghmagki` for every build, development and store alike (D22).
- A6. Saved site passwords are not exported in v1 (D6 encrypted export comes later).
- A7. HTTP/3 ships as an experimental option, off by default. For bulk downloads, several TCP connections already fill the link and QUIC costs more CPU; it turns on by default once the benchmark shows it winning. Decided by the lead.
- A8. The ffmpeg part of the media add-on is fetched from the builds the ffmpeg project links to (for example BtbN's GitHub releases for Windows and Linux), verified by checksum; yt-dlp from its official GitHub releases. Decided by the lead; the exact sources are recorded in the add-on manager.
