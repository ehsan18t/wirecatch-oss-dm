## How a finding gets fixed

1. A bug starts with a test that fails because of it. The failing test is the proof the finding is real; a finding that cannot be shown is closed as not reproduced.
2. The fix lands in its own commit with the gates from `CLAUDE.md` passing.
3. Someone other than the author of the fix reviews it before the workstream is marked done.

#### Flaky tests

Every flaky test seen in the audit run, in the order to fix them.

- Fixed (2026-10-22): every Rust test that bounded a measured duration from above or gave a wait that has to succeed a short fixed time, 29 places in the bridge, core, desktop, e2e, engine and streams crates. Each passed on an idle machine and failed on a busy CI runner whatever the change, which is why CI failed on pushes that local runs passed: `speed_limits_apply_to_streams` failed on Windows three times (the last on 97fdb502), and the others were the same race waiting for a slow enough runner. Each now waits for its event under `PATIENCE`, makes the slow path outlast `PATIENCE` (a held run, a long `Retry-After` or start budget, through the bridge's new `WIRECATCH_BRIDGE_TEST_START_BUDGET_MS` override), counts what was tried (QUIC attempts at the blocked port, back-offs of the store's writer), or keeps only the lower bound. The `test-timing` check refuses the pattern from now on.
- Fixed, to be confirmed by CI on Windows: `settle::a_part_file_left_by_a_crash_is_picked_up_again` (core, `crates/core/tests/manager/settle.rs:119`), `a_capture_starts_after_the_server_answers_and_completes` (e2e, `crates/e2e/tests/e2e.rs:46`) and `ask_before_download_waits_for_the_user` (e2e) each found a `.wcpart` after the row turned Completed, on Windows only. The cause was the product, not the tests: the ticker marks a running download's part file with the Mark of the Web, and when the engine renamed a fast download's part into place first, writing `<part>:Zone.Identifier` by name created a new, empty part file under the old name, left in the person's folder for good. The mark is now written through a handle to the file, opened without creating it (`crates/files/src/zone.rs`), with tests for a file already gone and one renamed while it is marked. If any of the three fails again, its cause is something else. `ask_before_download_waits_for_the_user` did fail again on Windows on 2026-10-21; 415e5c9a then stopped marking a part file from recreating it, and Windows CI has passed those tests since.
- Fixed, to be confirmed by CI on Windows: `a_dropped_download_never_writes_its_resume_file_again` (engine, `crates/engine/tests/download.rs`) failed on Windows CI (2026-10-22, 7349adda) with the resume file back after the test deleted it. The cause was the product as well as the test: a save checked for abandonment after flushing the part file but not after flushing its own temporary file, so a download dropped during that second flush still renamed it into place, and the test gave a save already running a fixed 300 ms, which a busy runner overran. A save now checks again before it replaces the resume file (`state::tests::a_download_dropped_while_its_resume_file_is_flushed_leaves_none`), and the test waits under `PATIENCE` for the temporary file to clear. The `test-timing` check missed the 300 ms sleep because it only reads waits that must succeed inside `timeout(..)`; the check proposed under "Fixed sleeps still in tests" (W14), on `tokio::time::sleep` in a test file outside a named helper, should cover the engine's tests too. Still open in the same file: its hand-written `PATIENCE` loops (and `pause_midway`'s unbounded one) want one shared wait in test support, and the test races its abort against the download finishing (4 MiB at 512 KiB/s) where it should hold the server.
- Fixed (2026-10-29): `a_resume_file_that_cannot_be_read_is_logged_with_the_reason` (engine, `crates/engine/src/target.rs`) failed once on a development machine. It compared the logged reason with the error of a second read of the same new folder, and another process (an antivirus scanning a folder just made in the temp folder) can open it between the two, so the two reads can fail differently; it did not fail in 60 local runs, so this is the likely cause rather than a seen one. The test now checks the logged event itself: its message, and an OS error in its `error` field. It fails when the engine logs the error without the system's reason. Ruled out: tracing's call-site cache, since tracing-core 0.1.36 lists a call site before working out its interest and rebuilds under the dispatcher lock.
- Fixed (2026-10-29): `socks::tests::a_proxy_that_is_not_there_is_a_proxy_failure` and `a_name_goes_to_the_proxy_unresolved` (engine) failed together once in 60 local runs of the engine's unit tests on 16 threads. The first bound a port, dropped the listener and connected to it, and in between the system gave the same port to the second test's proxy, which then saw a connection it did not expect. The first test now holds a socket bound but not listening, which refuses connections and keeps the port; 80 runs passed after.
- Fixed (2026-10-23): `resumes_after_pause_without_downloading_again` (engine, `crates/engine/tests/download.rs`) failed on Windows CI twice (2026-10-14, 3.7 MB fetched to fill 3.1 MB; 2026-10-23, 4.1 MB). It bounded every byte the server wrote during the second run, which counted what socket buffers took in before a connection was broken off, above all the probe from byte 0 that a resuming run breaks off once it has the headers, so the count grew with the runner's load. The server now holds the probe's body (`hold_bodies_from`), and the test checks the ranges the second run asks for: none may overlap the bytes the first run kept, as its resume file lists them. That is also stricter: the old slack of 512 KiB let a run fetch up to that much again unnoticed, and a run that asks for 64 KiB of kept bytes now fails. The six other tests that bounded bytes the server wrote were changed the same way (2026-10-23), with the helpers in `crates/test-support/src/resume.rs`: `an_exact_path_that_refuses_to_replace_keeps_the_data_for_later` and `a_paused_download_resumes_with_limited_requests` (engine) and core's restart test hold the probe and check the resumed run asks for no kept byte; core's schedule test checks no request arrives outside its window; `no_request_asks_for_more_than_the_limit_while_connections_split` keeps only its limit check; core's refresh-link test keeps only its range check; and core's retry test counts only the retry's own answers, at least the whole file from byte 0. Each still failed against a deliberately broken engine or core. Proposed check (W6): a total of the server's bytes sent (`bytes_sent`) in a test, which grows with the machine's load; the shared `resume` helpers or `Seen` per request instead.
- Fixed (2026-10-24): `extra_connections_told_to_wait_step_back_at_once` (engine, `crates/engine/tests/hardening.rs`) failed on Windows CI (run 40076517759, on a change to `deny.toml` alone) with "no part waited out Retry-After" after the whole `PATIENCE`. The cause was the product: a connection the server refused decided once, at the moment it handled the refusal, whether to step back, and stepped back only if another connection was receiving data just then. In this test the extra connections are refused about 4 ms in, while the first worker is about to read the first response and the one other connection allowed waits for its headers; on a busy runner neither had started receiving yet, so the refused connection kept its segment and waited out the 240 s `Retry-After`, longer than the test waits. A refused connection now steps back as soon as another starts receiving (D69), proven on tokio's paused clock by `worker::tests::a_refused_connection_steps_back_once_another_starts_receiving`, which fails against the old rule. In local runs the server's log shows the two allowed connections are never refused themselves; were every connection refused at once, none would be receiving and each would wait as the server asked, which is meant. No gate check fits: a decision taken on a snapshot of a shared count is for review to catch.
- Fixed (2026-10-24): `protocol::requests_beyond_the_limit_are_refused` (core, `crates/core/tests/manager/protocol.rs`) failed on Linux CI with no answer from the server. Core hands each request to its own task, and the test withdrew the capture once the first add reached the server, while some repeats of it had not run yet; a repeat that ran after the withdrawal found no handover, started the capture again and waited on the silent server longer than the client waits for an answer. The test's server now holds its answer until the request beyond the limit is refused, then answers, so every repeat shares the first one's outcome whenever it runs.
- Fixed (2026-10-29): `limits::progress_events_are_batched` (core, `crates/core/tests/manager/limits.rs`) failed on Windows CI (run 40829901361, on a change to the extension alone) with a speed of 45 KiB/s against a floor of 64. It read the smoothed speed one second after the first progress, but the speed is a three-second moving average that starts from the first 100 ms sample, connection setup included, so a slow first sample left it low; its floor of five batches in that second had the same weakness. It now waits under `PATIENCE` for five batches of progress from a 1 MiB download at 64 KiB/s a connection, checks the batches against the ticks that fit in the time it measured (`PROGRESS_TICK`, which a slow machine only loosens), and checks a speed reaches the row; the smoothing itself is `speed.rs`'s unit tests. It fails when the ticker runs every millisecond.
- Fixed (2026-10-29): `pausing_or_lifting_the_limit_never_waits_out_the_rate_limiter` (engine, `crates/engine/tests/download.rs`) failed on Windows CI (run 40845788910, on a change with no engine code) with "nothing arrived": it gave the first bytes 3 s, which connecting and the first chunk overran on a busy runner. Its limit is now 1 byte/s, so the first chunk puts the limiter hours in debt, and every wait is `PATIENCE`; it fails after `PATIENCE` when a pause waits for the limiter. The `test-timing` check missed it because the 3 s was a hand-written deadline loop, not a `timeout(..)`. `test-timing` now refuses a wait given a `Duration` constant under `PATIENCE`, and a deadline a short time away that a test asserts is not yet past (2026-10-29).
- Watch: the media tests in `apps/desktop/e2e/a11y.spec.ts` (90 s waiting for the sample download window, also on the base branch), and one desktop e2e page-draw timeout on a Windows CI run of the revamp branch that passed on rerun.
